# Demo Core / logistics implementation report

## Runtime contract

Core accepts demo behavior only for this exact environment triple:

```text
APP_STAGE=demo
DEMO_CONSOLE_ENABLED=true
EXTERNAL_INTEGRATIONS_MODE=mock
```

An incomplete or mixed demo configuration fails Core environment validation. Outside this triple the existing Hanjin gateway remains selected. Inside it, the carrier registry contains only the persistent demo implementation under the existing `HANJIN` carrier code, so existing waybill formatting and scanning continue to work without constructing or calling the Hanjin API client.

Authenticated routes are registered only in the safe demo environment and require `inventory.manage`:

- `GET /demo/catalog`
- `GET /demo/readiness`
- `GET /demo/shipments`
- `POST /demo/recompute` (delegates to the existing full replenishment recomputation)

`GET /demo/catalog` returns:

```ts
{
  fixtureVersion: 'demo-logistics-v1';
  items: Array<{
    variantId: string;
    masterId: string;
    versionId: string;
    skuId: string;
    sku: string;
    productName: string;
    unitPrice: number;
    availableQuantity: number;
  }>;
}
```

`GET /demo/shipments` returns the most recent 20 persisted mock-carrier records:

```ts
{
  items: Array<{
    reference: string;
    trackingNumber: string;
    status: 'allocated' | 'registered' | 'canceled';
    createdAt: string;
    updatedAt: string;
    registeredAt: string | null;
    canceledAt: string | null;
  }>;
}
```

`GET /demo/readiness` returns:

```ts
{
  enabled: true;
  fixtureVersion: 'demo-logistics-v1';
  ready: boolean;
  counts: {
    products: number;
    variants: number;
    skus: number;
    suppliers: number;
    warehouses: number;
    locations: number;
    demandDays: number;
    leadTimeObservations: number;
  };
  checks: Array<{ key: string; ready: boolean; actual: number; expected: number }>;
  recomputedAt: string | null;
}
```

The fixed IDs for item `NN` (`01` through `30`) are:

```text
masterId  = 019f1001-00NN-7000-a000-0000000000NN
versionId = 019f1002-00NN-7000-a000-0000000000NN
variantId = 019f1003-00NN-7000-a000-0000000000NN
skuId     = 019f1004-00NN-7000-a000-0000000000NN
sku       = DEMO-SKU-0NN
unitPrice = 10000 + (ordinal - 1) * 500
```

Channel ingestion uses item 30 for the happy path (quantity 1) and item 1 for the inventory-shortage path (quantity 10). Items 1–5 start with 2 units; items 6–30 start with 46–70 units.

## Seed entrypoint

Run reference data first, then the demo group for each deployment:

```bash
npm run db:seed:ref -- --stage demo --deployment lcnine-services --yes
npm run db:seed:demo -- --stage demo --deployment lcnine-services --group demo-logistics --yes
npm run db:seed:ref -- --stage demo --deployment lcnine-auth --yes
npm run db:seed:demo -- --stage demo --deployment lcnine-auth --group demo-logistics --yes
```

`demo-logistics` creates 30 mapped variants/SKUs and primary barcodes, a deterministic in-house delivery profile (`019f1009-0901-7000-a000-000000000901`), 3 suppliers, 2 warehouses, 8 workflow locations, balanced initial stock journals/events/ledgers, 365 days of synthetic demand for every SKU, and 5 completed purchase-to-receipt lead-time observations per supplier. Every fixture SKU references the delivery profile so channel-created fulfillment shipments can be planned and issued through the mock carrier. Domestic supply routes directly to the sellable demo warehouse; sea and air suppliers route from the overseas demo warehouse to the domestic destination. It then invokes the existing full replenishment job. Historical receipts are closed inputs with their full quantity marked put away, so they create neither fulfillment backlog nor stale protected inbound stock. Reapplying the fixture leaves current stock untouched because initial stock rows use durable idempotency keys and ledger conflicts do nothing.

Both check and apply reject any stage/resource identity other than exact `demo`. Reapplication converges an earlier baseline-plus-demo database to exactly one sellable warehouse, repairs supplier defaults and all 15 historical PO routes, and reruns recomputation whenever derived demand or supplier profiles are missing.

`db:seed:ref` excludes all `demo-*` groups. The auth-side `DemoLogisticsAuthSeedStep` is added only when `SST_STAGE=demo` and the selected registry contains `user-service`.

## Actual demo API acceptance — 2026-09-17

The deployed demo Core was exercised with the real admin-web OIDC session for management operations and a real
`warehouse-app` worker OIDC bearer for warehouse operations. The worker could read warehouses (`200`), was denied
the demo management endpoint (`403`), and successfully performed both outbound scan/dispatch operations.

- Purchasing and inbound: Core evaluated all 30 replenishment SKUs and returned 25 suggestions. Purchase order
  `75138a59-fdd0-432c-8cd1-96fe30a8f04f` was confirmed, received in two partial quantities of 2, put away by 2,
  moved by 1 between locations in the same warehouse, and received for the remaining 2. The final stock delta was
  `+4`, with zero outstanding purchase quantity.
- Happy outbound: Core sales order `64604b77-8d66-4adc-a3cb-8db774a26c48` produced shipment
  `fd09447d-1781-4012-8518-101f7097e134`. The persistent mock carrier registered waybill
  `72bdb284-e85b-46fc-97a2-b50a84e1c1b3` with tracking number `948819344728`; worker OIDC scan/dispatch attempt
  `0cd02373-5e56-4014-8f2b-551935b12292` completed the shipment.
- Inventory shortage and recovery: Core sales order `74ba7f75-a2f9-49b3-add6-c79ff7eca029` initially reserved 2 of
  10 units and rejected planning with `409 SHIPMENT_NOT_FULLY_RESERVED`. Purchase order
  `60661e57-3197-4b58-9417-a4d24bccde9b` received the missing 8 units. After putaway, the reservation retry reached
  `10/10`; fulfillment `9ba7e02f-18b1-4fbd-a9c4-189a8a8762ce` and shipment
  `bacedf46-cb98-4b8c-bfe7-3c204c774026` completed. The mock carrier registered waybill
  `cd6ec393-0e92-4052-a530-383dd89bbacc` with tracking number `943208804851`; worker OIDC dispatch attempt
  `8319e7a6-8453-4886-b6ec-0375bd5c59ee` completed the shipment.

A final read confirmed the shortage fulfillment and progress were `completed`, shipped quantity was 10, the SKU had
no pending putaway, and `GET /demo/shipments` contained both tracking numbers. Sanitized evidence is stored in:

- `.superpowers/sdd/2026-09-16-demo-stage/core-acceptance-purchasing.log`
- `.superpowers/sdd/2026-09-16-demo-stage/core-acceptance-outbound.log`
- `.superpowers/sdd/2026-09-16-demo-stage/core-acceptance-shortage.log`

Physical scanner hardware and physical label printing were not tested. Barcode scan behavior was exercised through
