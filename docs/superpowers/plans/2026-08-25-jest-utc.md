## 왜

라이브(ECS/Lambda)와 CI 러너(`ubuntu-latest`)는 **UTC** 인데 개발 머신은 `Asia/Seoul` 이다.
`date-fns-tz` 의 `toZonedTime` 은 **런타임 TZ 에 상대적**이라, 서울 머신에서는 이중 변환이
항등이 되어 버그가 통째로 사라진다. 항목 11(발견 ⑪)이 정확히 그 부류였다 — 라이브에서
KST 15:00~24:00 의 당일 입고 취소가 전부 400 이었는데, 로컬 스펙은 고치기 전 코드로도
초록이었다. 그 PR 은 "이 스펙의 방어력은 CI 에서 나온다"고 적고 넘어갔고, 그 자리에서
이 항목이 떨어져 나왔다.

TZ 를 로컬에서도 UTC 로 박으면 이 부류 전체가 **작성자 손에서** 보인다.

## 사전 실측 (설계를 정한 근거)

**① `globalSetup` 에서 `process.env.TZ` 를 할당하는 것은 유효하다.**

항목 11 계획서는 "jest 안에서 `process.env.TZ` 를 바꿔도 안 먹는다"고 기록했다. 그건
*스펙 파일 안*의 이야기이고, **워커 fork 전에 도는 `globalSetup`** 은 다르다. 스크래치
설정으로 세 실행 모드를 재 봤다:

| 실행 모드 | globalSetup 후 부모 | 스펙 안 |
|---|---|---|
| 기본 워커 | `UTC` / offset `0` | `UTC` / offset `0` |
| `--runInBand` | `UTC` / offset `0` | `UTC` / offset `0` |
| `--maxWorkers=2` | `UTC` / offset `0` | `UTC` / offset `0` |

(Node 22 는 `process.env.TZ` 할당 시 TZ 캐시를 갱신하므로 `--runInBand` 처럼 워커를 안
띄우는 모드에서도 먹는다. 워커 모드는 fork 시 env 를 상속해서 먹는다 — 경로가 둘 다 열려 있다.)

**② 폭발 반경은 사실상 0 이다.**

CI 러너가 이미 UTC 이고, 이 작업의 기준 커밋 `3bcb7cca3` 의 Verification gates 런이
**success** 다(run 32847128708). 즉 루트 jest 전 스위트가 UTC 에서 초록임은 이미 증명돼
있다. 남은 미지수는 **CI 에서 DB 가드로 skip 되는 통합 스펙**뿐이라 그건 로컬에서 직접
대조한다.

## 무엇을

### 1. `globalSetup` 파일 1개

`scripts/jest/global-setup.js` — `process.env.TZ = process.env.TZ || 'UTC'` 한 줄.

배선 대상:

| 설정 | 쓰는 명령 |
|---|---|
| 루트 `package.json` 의 `jest` 블록 | `npx jest` (게이트) · `npm test` · `test:admin-web` · `test:core:integration:local` |
| `apps/user-service/jest.config.js` | `npm run test:user-service` |
| `apps/core/test/jest-e2e.json` | `npm run test:e2e` |
| `apps/membership/jest-e2e.json` | `npm run test:membership` — **이미 `globalSetup` 이 있어** 그 파일에 한 줄 추가 |

**범위 밖**: `apps/medusa` — 별도 npm 프로젝트이고 자체 워크플로(`medusa-unit-tests.yml`)를
가진다. 루트 설정은 `modulePathIgnorePatterns` 로 이미 제외한다.

### 2. `|| 'UTC'` 인 이유 (하드 핀이 아니다)

항목 11 은 신규 스펙을 `TZ=UTC` · `Asia/Seoul` · `America/New_York` 셋으로 돌려 TZ 견고성을
증명했다. 그 escape hatch 를 죽이지 않는다. 셸에 `TZ` 가 없다는 건 확인했으므로
(`process.env.TZ === undefined`) 기본값은 UTC 로 떨어진다.

### 3. 가드 스펙

`scripts/jest/tz-is-utc.spec.ts` — `new Date().getTimezoneOffset() === 0`.
배선이 조용히 빠지면 빨개진다. 일부러 다른 TZ 로 띄웠을 때 이것 하나만 빨간 건 정상이며,
그 사실을 스펙 안에 적는다.

### 4. 낡아지는 주석 교정

이 변경이 들어가면 아래 두 헤더의 서술이 **거짓이 된다**. 안 고치면 다음 사람이 오독한다.

- `apps/core/src/modules/inventory/shared/services/time.util.spec.ts`
- `apps/core/src/modules/inventory/inbound/services/inbound.service.same-day-cancel.integration.spec.ts`

증명 못 한다"고 적혀 있다.

## 검증

TZ 변수만 순수하게 분리하기 위해, **저장소를 건드리기 전에** `npx jest` 와 `TZ=UTC npx jest`
를 각각 돌려 실패 항목명을 대조한다. 그다음 배선을 넣고 최종 확인 실행을 한다.

| 대조 | 명령 |
|---|---|
| 루트 스위트 | `npx jest --maxWorkers=2 --ci` |
| user-service | `npm run test:user-service` |
| admin-web | `npm run test:admin-web` |
| DB 통합 | `npm run test:core:integration:local` |

통합 스위트는 러너 패턴이 `integration` 이라 다른 서비스 스펙까지 딸려 와 **기준선부터 빨갛다**
(항목 11 이 기록한 기준선: 19 suite 실패 중 core 8 suite / 실패 항목명 13건). 숫자를 그냥 읽지
말고 **실패 항목명 문자열**을 diff 한다.

## 범위 경계

UTC 로 띄웠을 때 새로 빨개지는 것이 나오면:

- **스펙이 KST 를 가정한 것**이면 여기서 고친다.
- **프로덕션 버그**가 드러나면 고치지 않고 #724 에 항목으로 올린다.

이 작업이 TZ 버그 수정 작업으로 번지지 않게 한다. 항목 14(`audit_logs.timestamp` +9h)가
이미 그 부류로 분리돼 있다.

## 곁가지로 드러난 것 — 통합 러너가 매번 매달렸다

이 작업의 대조를 뜨다가 발견했다. **항목 13 범위 밖이었으나 사용자 판단으로 같이 넣었다.**

`scripts/local/test-core-integration-local.sh` 의 기본 패턴이 `integration` 이라
membership·channel-adapter·analytics 통합 스펙까지 끌어왔다. 이 러너의 `DATABASE_URL` 은
core 를 가리키므로 이들은 통과할 수 없다. 대가가 셋이었다:

1. **12 suite 가 늘 빨갛다** → 매번 "어느 게 내 탓인가"를 사람이 골라내야 했다.
   (항목 11 이 `git stash` 로 기준선을 다시 떠서 실패 항목명을 문자열 대조한 이유다.)
2. 붙을 수 없는 DB 를 기다리느라 **접속 타임아웃 5.3초**를 태웠다.
3. 그중 무언가가 열린 핸들을 남겨 **테스트가 끝난 뒤에도 jest 가 종료하지 못했다.**
   결과를 다 찍고 **48분**을 매달린 것을 실측했다(21:37:57 결과 출력 → 22:25:37 프로세스 생존).

세 앱을 하나씩 100초 상한으로 재 보니 **셋 다 매달린다** — 즉 옛 기본값은 확정적으로 매달렸다.

| 앱 | 판정 |
|---|---|
| membership | 매달림 |
| channel-adapter | 매달림 |
| analytics | 매달림 |

**처음 세운 "누수 스펙" 가설은 틀렸다.** postgres 클라이언트를 안 닫는 스펙을 찾았더니 9건이
나왔는데, `.end({ timeout: 0 })` 형태를 grep 이 놓친 **거짓 양성**이었다. 다시 재니 클라이언트를
안 닫는 스펙은 **0건**이고, `libs/events` outbox 통합 스펙도 2.1초에 정상 종료한다. 진짜 핸들이
무엇인지는 아직 모른다 — 이 항목에서 쫓지 않았다.

### 고친 방법

기본 패턴을 core DB 를 쓰는 트리로 한정했다:

```
(apps/core|libs/events|scripts/fulfillment-v2)/.*integration
```

빠지는 것들(`apps/search` · `scripts/local/seed-dev-core` · `apps/medusa` 등)은 전부 자기 전용
러너와 env 가드를 가진 트리다 — core DB 를 쓰는 스펙 중 누락은 없다(83개 = 실제 실행 83 suite).
옛 동작은 `npm run test:core:integration:local -- integration` 으로 재현된다.

**`--forceExit` 은 일부러 쓰지 않았다.** 그건 핸들 누수를 *숨긴다*. 대신 벽시계 상한
(`JEST_TIMEOUT_SECONDS`, 기본 300)을 걸어 누수가 생겨도 저녁을 통째로 먹지 않게 하고,
상한에 걸리면 `--detectOpenHandles` 진단법을 출력한다.

**효과**: 76초 + 무한 대기 → **66초 정상 종료**, 빨간 12 suite 의 노이즈 소멸.
