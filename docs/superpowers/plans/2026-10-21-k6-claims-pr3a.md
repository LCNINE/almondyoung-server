# K6 PR 3a — 청구(반품·교환) 수량을 한 공식 `claimable` 로 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 반품·교환의 자격·상한·환불 수량을 라인 수량 문의 SKU 층 청구 사실(`returnActive`·`returnConsumed`·`exchangeActive`·`claimable`)과 소포 단위 청구 자격 한 벌에서 읽게 하고, 반품·교환 생성 게이트 여섯 벌(스펙 §4.2 A~F)을 그 한 벌로 바꾼다.

**Architecture:** 청구 항목을 SKU 로 잇는 집계 조각(`claim-quantities.sql.ts`)을 두고, 2b 의 `lineSkuQuantitiesSql` 이 그걸 붙여 SKU 행마다 청구 칸과 `claimable` 을 낸다. 소포 단위 자격(`parcelClaimEligibilitySql`)은 배송완료 소포 × 그 SKU 행의 `claimable` 을 `least` 로 접는다. 반품·교환 생성은 한 트랜잭션에서 그래프·라인을 잠근 뒤 소포 자격을 읽어 검사하는 게이트 하나를 같이 쓴다. 판매 단위 환산(통째 세트 수)은 SQL 소비자가 없어 2b 의 `line-sales-units.ts` 에 TS 한 벌로 더한다.

**Tech Stack:** NestJS, Drizzle ORM(postgres.js, raw `sql` 조각), drizzle-kit 마이그레이션, Jest(유닛 + `describeIfDb` 통합), 소스 텍스트 가드 spec.

**Spec:** `docs/superpowers/specs/2026-10-20-k6-line-quantity-facts-design.md` (§6.1 청구 층·소포 단위 자격, §6.2 청구 행, §6.5 소비자, §6.6 가드, §7, §8 D2~D6, §5 F2·F3·F4·F7·F8·F14). ADR: `docs/adr/0047-line-quantity-facts-one-record-one-reader.md`. 앞선 계획: `docs/superpowers/plans/2026-10-21-k6-shipment-facts-pr2b.md`.

## 사용자 결정 (2026-10-21)

- **PR 3 을 3a·3b 로 나눈다.** 3a = 이 계획(Core 만). 3b = D7 관리자 입력 금액(마이그·상한·admin-web 입력)과 F9(`SalesOrderReturned` additive 필드 + ugc 소비).
- **D7 상한 규칙(3b 가 구현, 여기 기록만):** 요청 하나에 금액 하나. 요청에 세트 일부 줄이 하나라도 있으면 그 요청 전체 금액을 관리자가 입력한다. 상한 = 이 요청이 건드린 라인들의 배분액 합(지금 부분반품 공식: 라인 무게 × (결제총액 − 배송비) ÷ 라인 무게 합) − 그 라인들을 건드린 앞선 완료 반품의 환불액 전부. 수동 완료된 앞선 반품(금액 모름)이 그 라인을 건드렸으면 그 라인의 배분액은 0 으로 본다. 과환불은 막고 상한이 실제보다 낮게 나올 수 있다.

## 3a 가 정하는 것 (사용자 확인 필요)

- **N1. 소포 칸이 빈 청구 항목은 커널이 세지 않는다.** SKU 를 알 길이 없다(`shipment_line_id` 가 SKU 로 가는 유일한 길). 새 행은 언제나 소포를 적는다(Task 3·4 가 강제). 옛 행은 라이브 0 이 배포 게이트(D5)다. 기존 통합 테스트 `counts a completed nullable legacy item against the purchased sales-line cap` 은 이 결정을 고정하는 테스트로 바꾼다.
- **N2. 라인 단위 요청 펼치기(스펙 §6.5)는 «라인 구성이 SKU 하나, 1개당 수량 1, `claimable > 0` 인 소포 후보 하나»일 때만.** 스토어프론트는 판매 단위 수량을 보낸다(`exchange-client.tsx:158-180`). 1개당 수량이 2 이상이면 판매 단위와 SKU 단위가 갈려 같은 숫자가 두 뜻이 되므로 400 이다. 예외 필터는 메시지만 내보내므로(`http-exception.filter.ts:177`) 후보는 본문이 아니라 문구로 안내하고, 후보 목록은 기존 `return-eligibility` 응답이다.
- **N3. 라인 단위 `anyShipped`·`shippedComplete` 는 만들지 않는다.** 3a 에 소비자가 없다(ADR-0047 «소비자가 생기는 K7·PR 3 이 더한다» — PR 3 에도 안 생겼다).
- **N4. 구성 밖 SKU(`qtyPerUnit` null) 행의 `claimable` 은 0.** 출고 뒤 취소를 SKU 로 환산할 수 없다. 구성 밖 FOI 는 구성 대체가 qty 0 으로 남긴 것이라 배송완료 수량이 없다.
- **N5. 세트 일부 반품의 «완료»는 3b 전까지 자동 환불을 하지 않는다.** 검수 완료 → `refund_pending` 으로 넘기고 수동 환불 필요를 남긴다(지금 `walletIntentId` 없는 주문과 같은 갈래). 그 뒤는 기존 «수동 완료». 재시도는 400. 3b 가 관리자 입력 금액으로 대체한다.

## 이름 붙은 동작 변경 (스펙 G5 — 사용자 확인 필요)

라이브 영향 판단의 전제: 반품·교환은 라이브에서 시스템 밖(셀메이트)이고 `return_request_items`·`exchange_request_items` 는 0행(10-20 실측). 라이브 출고는 셀메이트(소포 없음), 직배는 사용 중(소포 없음). 그래서 소포가 있어야 열리는 청구는 warehouse-app 컷오버 전까지 라이브에서 열리지 않는다.

- **C1 (D2, F4). 교환 자격은 «소포가 배송완료»다.** SO `delivered`·FO `completed` 로 열던 `assertOrderDelivered` 를 지운다. 라이브: 교환은 지금도 FO `completed` 가 없어(직배 완료는 FO 를 `shipped` 로 둔다 — `direct-ship.service.ts:314`) 열리지 않는다. 잃는 것 없음.
- **C2 (D3, F3). 반품·교환이 한 공식을 쓴다.** 완료 반품은 교환에서도 소진, 진행 중 교환은 반품에서도 차감, 완료 교환은 어디서도 차감하지 않는다.
- **C3 (D4, D5). 청구 항목 수량은 SKU 단위이고 (SKU, 소포) 마다 한 줄이다.** 교환 항목도 소포(`shipment_line_id`·`dispatch_attempt_id`)를 적는다.
- **C4 (F7, F8). 생성 검사는 잠금 뒤 한 트랜잭션에서 한다.** 같은 소포·같은 (라인, SKU) 줄은 합산해 검사한다. 묶음 라인의 상한이 판매 단위가 아니라 SKU 단위다.
- **C5 (F14). 라인 단위 요청을 서버가 펼친다(N2).** 스토어프론트 반품이 단품·소포 하나인 라인에서 처음으로 동작한다. 라이브는 배송완료 소포가 없어 그대로 400.
- **C6 (D6, F2). 반품 환불 수량은 판매 라인별 합산이고, SKU 수량을 통째 세트 수로 환산한다.** 세트 일부면 N5.
- **C7. `SalesOrderReturned.returnedQuantity` = 그 라인의 완료 반품에서 통째로 돌아온 세트 수**(구성품별 `floor(returnConsumed ÷ qtyPerUnit)` 의 최솟값). 단품은 지금과 같다. 세트 일부만 돌아온 라인은 0 이라 페이로드에서 빠지고(스키마가 `positive`), 빠진 라인뿐이면 이벤트가 안 나간다 — 적립을 과하게 회수하지 않는다(스펙 §6.5). ugc 의 `demand` 비교(F9)는 3b.
- **C8. 고객 actions 의 반품·교환 버튼은 «`claimable > 0` 인 소포가 있다»로 연다**(`isReturnEligible` 삭제). **라이브 영향 있음:** 직배 완료 주문은 지금 버튼이 보이지만(`dropShipUnitPhase('completed') = 'delivered'`) 반품은 DTO 400(F14), 교환은 FO `completed` 없음 400 으로 언제나 실패한다 — 버튼이 사라진다. 인쇄가 안 끝난 혼합 주문은 창고 소포가 배송완료면 버튼이 열린다(라이브는 소포가 없어 해당 없음).
- **C9. 출고 뒤 취소(V1 사후취소)로 돈을 돌려준 수량은 다시 청구할 수 없다**(`claimable` 에서 `canceledAfterShipment × qtyPerUnit` 차감, 스펙 §6.1).

## Global Constraints

- 새 파일 위치: `apps/core/src/modules/sales-order/line-quantities/` (스펙 §6.3). 조각·문은 `wmsTables`·`returnExchangeTables` 만 읽고 호출자의 `trx` 를 받는다(ADR-0025). `DbService<MergedSchema>` 목록에 더하지 않는다. 새 `inTx` 헬퍼 금지.
- 정의는 SQL 한 벌. 수량 뺄셈(`delivered − 청구`, `least(...)`)은 조각 안에만 있다. TS 예외는 판매 단위 환산(`exactSetUnits`·`completedSetUnits`)뿐이고, 응답 DTO 의 `Math.max(0, …)` 표시 클램프는 표시라 허용한다.
- raw SQL 조각은 **모든 테이블에 별칭을 붙이고 칼럼을 별칭으로 한정한다**(2a 교훈). 합계는 `::int`. FOI `sales_order_line_id` 는 varchar 라 `= sol.id::text` 로 잇는다.
- 청구 상태 목록은 커널 한 곳(`line-quantities/claim-statuses.ts`)이 갖는다. 두 서비스의 복붙 상수(`store-return-exchange.service.ts:58-73`, `store-sales-orders.service.ts:74-89`)는 지운다.
  - 진행 중 반품 = `requested, approved, collection_pending, collected, inspected, refund_pending`; 소진 반품 = `completed`; 진행 중 교환 = 같은 여섯 값. `rejected`·`cancelled` 와 완료 교환은 아무것도 차감하지 않는다.
- 마이그레이션 하나(expand, additive): `exchange_request_items` 에 `shipment_line_id uuid null → shipment_lines(id) on delete restrict`, `dispatch_attempt_id uuid null → dispatch_attempts(id) on delete restrict`, 인덱스 둘(`idx_exchange_request_items_shipment_line`, `idx_exchange_request_items_dispatch_attempt`) — `return_request_items`(`inventory.schema.ts:5085-5107`)와 같은 모양. 생성은 `npm run db:generate:core -- --name add-exchange-item-parcel`. `schema.ts`·SQL·`drizzle/meta/` 를 한 커밋에. **배포 순서 `migrate → deploy`.**

## Review Focus

1. **같은 소포에 반품과 교환이 동시에 들어온다.** 둘 다 같은 그래프·라인을 잠그므로 하나만 성공한다. Task 4 `concurrent return and exchange on one parcel succeed only once` 가 고정한다.
2. **세트 라인에서 구성품 하나만 반품.** 생성은 된다(SKU 단위). 검수 완료는 자동 환불 없이 `refund_pending`(N5), 이벤트 없음(C7). Task 5 `set-partial return goes to manual refund`·`set-partial return publishes no returned event` 가 고정한다.
3. **배송완료 뒤 회수된 소포.** 추적 행이 남아도 반품·교환 둘 다 안 된다. Task 3 기존 `rejects a delivered tracking history after its exact attempt is recalled`(문구 갱신), Task 4 `exchange of a recalled parcel is refused` 가 고정한다.
4. **출고 뒤 취소가 있었던 라인의 반품.** 돈을 돌려준 수량만큼 `claimable` 이 준다(C9). Task 1 `after-shipment cancellation reduces claimable` 이 고정한다.
5. **같은 라인이 두 소포로 나뉘어 배송완료됐는데 스토어프론트가 라인 단위로 요청.** 400 과 «소포를 지정» 문구, 소포 하나면 펼쳐서 성공. Task 3 `line-level request with two parcels asks for a parcel`·`line-level request with one parcel is expanded` 가 고정한다.
