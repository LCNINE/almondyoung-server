#### 🔴 결정 1은 엔진과 충돌한다 — 우회가 필수다

**`computeActions` 가 `listActivePromotions_` 를 탄다**(`@medusajs/promotion/dist/services/promotion-module.js:374` → `:47-73`).
그 필터는 **캠페인 창이 지난 프로모션을 할인 계산 대상에서 아예 제외한다.** 즉 `campaign.ends_at` 을
채워 두면 「캠페인 종료 후에도 이미 발급된 쿠폰은 유효기간까지 사용 가능」이 **표현되지 않는다** —
발급 마지막 날 받은 「발급일+30일」 쿠폰이 캠페인 종료 즉시 죽는다.

**채택: 캠페인 창을 쓰지 않는다.** 발급 창은 `promotion_meta` 에 우리 필드로 두고 **발급 3경로에서
우리가 검사**한다. `campaign.ends_at` 은 비운다. 캠페인은 **예산(`budget`)이 필요할 때만** 남긴다.
A4/P10-B 에서 검증한 패턴 그대로다(엔진에 없는 개념 → `promotion_meta` + 우리 게이트).
**부수 효과: `1-3`(캠페인 탭 오염)이 함께 사라진다.**

**기각한 대안 — `campaign.ends_at` 을 「발급종료일 + 유효기간」으로 늘려 잡기.** 코드는 덜 드나
관리자가 보는 값과 실제 값이 갈리고, 유효기간을 바꿀 때마다 파생값 재계산이 필요하다.
두 값이 어긋나는 순간 **조용히** 틀린다.

**만료 강제는 캡보다 싸다.** 캡은 금액 조정이라 훅 4곳이 필요했지만 만료는 **거부**라 기존 배선을
그대로 쓴다 — `per-customer-limit.ts` 의 카트 3경로 + `complete-cart` 백스톱(`requiresIssuance` 검사 자리).

#### 🔴 결정 1이 P4 의 스키마를 바꾼다 — P4·P5 는 한 몸이다

「발급일 + delta」는 **발급 인스턴스마다 만료가 다르다**는 뜻이다 → 만료 실값은 프로모션이 아니라
**발급 링크 행의 속성**이고, 그건 정확히 P4 가 만드는 `extraColumns` 다.

→ **P4 의 `extraColumns` = `used_at` · `order_id` · `issued_via` + `expires_at`.**
따로 하면 마이그레이션을 두 번 치고 expand-contract 규율을 두 번 지켜야 한다.

→ **발급 시점에 계산해 박는다.** 정책에서 매번 도출하면 「+30일」을 「+7일」로 바꾸는 순간
이미 발급된 쿠폰이 **소급 만료**된다.

#### ✅ 진행 전 라이브 실측 3건 — **전부 통과 (2026-08-31 실측)**

```sql
-- ① 자동발급 규칙이 0건인가 (결정 3의 전제)
SELECT count(*) FROM promotion_meta
 WHERE auto_issue_trigger IS NOT NULL AND deleted_at IS NULL;   -- 기대: 0

-- ② birthday 행 (결정 2 — 있으면 어휘 제거 전에 정리)
SELECT count(*) FROM promotion_meta
 WHERE auto_issue_trigger = 'birthday' AND deleted_at IS NULL;  -- 기대: 0

-- ③ 메타 행 없는 활성 프로모션 (P10-A 닫힌 기본값의 전제 — 배포 전 필수)
SELECT p.id, p.code FROM promotion p
  LEFT JOIN promotion_meta m ON m.promotion_id = p.id AND m.deleted_at IS NULL
 WHERE p.deleted_at IS NULL AND p.status = 'active' AND m.id IS NULL;  -- 기대: 0행
```

**결과: ① 0 · ② 0 · ③ 0행.** 셋 다 기대치와 일치한다.

- **① = 0 → 결정 3의 전제 성립.** 플래그를 켜도 `getByAutoIssueTrigger` 가 빈 배열을 돌려주고
  라우트가 `{issued:[],skipped:[]}` 로 끝난다 — **누가 쿠폰에 트리거를 붙이기 전까지 아무 일도 안 일어난다.**
- **② = 0 → `birthday` 어휘 제거가 안전하다.** 정리해야 할 행이 없다.
- **③ = 0행 → P10-A 닫힌 기본값의 전제 성립. 0단계 배포가 안전하다.**
  ⚠️ 단 이 0은 **약한 증거**다 — active 프로모션 자체가 0개일 수 있고(ADR-0033, 2026-08-28 측정),
  그러면 「메타 없는 활성 쿠폰이 없다」가 공허하게 참이다. 배포 안전성에는 영향이 없다
  (어느 쪽이든 잠기는 쿠폰이 0건). 다만 **이 쿼리를 「메타 배선이 검증됐다」의 근거로 쓰면 안 된다.**

#### 그래서 작업 순서 (2026-08-31 확정)

```
0. 배포 (코드 0) ──→ 1. P4+P5 (마이그 1) ──→ 2. P7 ──→ 3. 리허설 2차 ──→ 4. A5 개통
   미배포 4건            링크 extraColumns       (fail-closed)
   + 실측 ③              + 유효기간 두 축
                    └─→ 2번 결정 반영(birthday 어휘 제거, 마이그)
   개통 후: P6 · 7-3 · P8 · P9
```

**`4-2` 는 버그가 아니었다 — 닫는다.** 「프리뷰는 per-promotion `expires_at`, 마이페이지는 캠페인 창」
이라는 진단은 **필드 이름이 만든 착시**였다. 프리뷰가 내려주는 `expires_at` 의 값이 곧
`promotion.campaign?.ends_at` 이다(`preview/route.ts:97`). 세 경로가 같은 값을 본다.
진짜 사실은 **`Promotion` 모델에 만료 필드가 없다**는 것이고(확인함 — `starts_at`/`ends_at` 는
`Campaign` 에만 있다), 그것이 결정 1을 부른 이유다.

### 새로 열린 결정 (2026-08-31)

**Medusa 네이티브 관리자 화면(`/app`)을 끌 것인가.** 「네이티브 대시보드는 쓰지 않는다」가 원칙인데

더 나쁜 건 그 위험을 잡는 유일한 검사(P1 Task 3 Step 5 ③ 「상세에서 두 한도가 다 보이는가」)를

### 그래서 P2·P4 플랜은 이렇게 쓴다

**P2 와 P4 는 정확히 같은 모양의 변경이다 — 둘 다 저장 위치를 옮긴다.**

1. **File Structure 표 옆에 «이 값을 읽는 소비자 목록»을 필수 항목으로 둔다.** 쓰기 경로와 읽기 경로를
   나눠 적고, 읽기 경로는 `grep` 결과를 근거로 붙인다.
2. **판정 로직은 `.ts` 로 뽑는다.** admin-web 의 jest transform 이 `^.+\.(t|j)s$` 라 `.tsx` 는 테스트가
   실행조차 되지 않는다. 표시·분기 로직이 `.tsx` 안에 있으면 그 태스크는 검증되지 않는다.
3. **하위 호환을 명시적 요구사항으로 적는다.** 옛 저장 위치의 데이터가 계속 읽혀야 한다면, 기존 분기를
   «대체»가 아니라 «추가»로 못 박고 그 케이스를 테스트로 덮는다.
4. **타입 게이트는 `cd apps/admin-web && npx tsc --noEmit`.** 루트 `npm run type-check` 는 admin-web 을
   제외한다.

## ~~미해결~~ 해결된 설계 질문 (2026-08-31) — P7 을 이 결론 위에 쓴다

> **결정: 3단 처방 그대로 간다. 근거 하나만 교체한다.**
> 두 전제를 로컬 스택에서 실측했고 둘 다 살아 있다 — (a) 엔진이 어드민에 노출하는 ORDER 스코프 룰은
> 여전히 다섯이고 고객 고유는 `customer.groups.id` 하나뿐(`GET /admin/promotions/rule-attribute-options/rules`
> 실측), (b) 우리 폼이 만드는 룰은 `subtotal` gte + `customer.groups.id` in 둘뿐
> (`build-create-promotion-payload.ts:77-84`, 유일한 작성자).
>
> **바꾸는 것은 ③ fail-closed 의 근거다.** 처음엔 「네이티브 대시보드가 나머지 넷을 만들 수 있다」를
> 근거로 삼았는데, **네이티브 대시보드를 쓰지 않는 것이 원칙**이므로 그 논거는 성립하지 않는다.
> 옳은 근거는 반대 방향이다 — **엔진이 지원하는 조건을 우리 화면이 안 만드는 것은 admin-web 의 기능
> 미비이고, 언젠가 채워진다.** 그날 발급 로직이 준비돼 있지 않으면 그 순간부터 조건을 무시한 발급이
> 조용히 시작된다. fail-closed 는 그 창을 막고, 새 조건을 화면에 추가한 사람이 발급 쪽도 함께 손봐야
> 한다는 것을 즉시 알게 한다.
>
> **분류표는 다섯 + `subtotal` 로 못 박는다.** `subtotal` 은 엔진이 어드민에 노출하지 않는데 우리 폼이
> 만드는 값이라 명시적으로 넣어야 한다. 목록을 닫아두면 Medusa 업그레이드가 6번째 속성을 추가했을 때
> 조용히 통과하지 않고 fail-closed 가지로 떨어진다.

아래는 그 결정에 이른 원래 분석이다.

**`1-5` 의 전제가 필드된 내용보다 약하다.** 플랜 작성 중 발견했다.

#488 은 «`meetsGroupRule` 이 그룹 룰만 봐서 `customer.email`, `customer.created_at` 등이 무시된다 →
범용 룰 평가기로 교체»라고 적었다. 그런데 엔진의 룰 평가(`areRulesValidForContext`)는
**컨텍스트 객체에서 `rule.attribute` 경로를 뽑아 비교**하는 방식이고, 발급 시점에는 **카트가 없다**.

Medusa 가 어드민에 노출하는 ORDER 스코프 룰 속성은 다섯이다
(`rule-attributes-map.js`): `customer.groups.id` · `region.id` · `shipping_address.country_code` ·
`sales_channel_id` · `currency_code`.

| 종류 | 속성 | 발급 시점 평가 |
|---|---|---|
| **고객 고유** | `customer.groups.id` | 가능하고 의미 있음 |
| **카트 문맥** | 나머지 4개 + `subtotal` | **불가능하고, 막아서도 안 된다** — 고객이 나중에 그 리전에서 살 수 있다 |

**즉 «모든 룰을 평가한다»는 처방은 그대로 쓰면 틀린다.** 고객 고유 속성은 오늘 `customer.groups.id`
하나뿐이고, 현재 구현은 **우연히 그것만 보고 있다.**

`validateRuleAttribute` 가 생성 경로에는 걸려 있지 않아(도우미 라우트에서만 호출) raw API 로
임의 속성을 넣을 수는 있으나, 우리 어드민이 만드는 것은 `subtotal` 과 `customer.groups.id` 뿐이다.

**따라서 P7 의 실제 과제는 «범용 평가기»가 아니라:**
1. 룰을 «고객 고유 / 카트 문맥» 두 부류로 분류하는 명시적 목록을 둔다
2. 카트 문맥 룰은 발급 시점에 **의도적으로 무시**하고, 그 사실을 주석·문서로 남긴다
3. **분류표에 없는 속성을 만나면 fail-closed** (발급 skip + 로그) — 지금은 fail-open 이다
