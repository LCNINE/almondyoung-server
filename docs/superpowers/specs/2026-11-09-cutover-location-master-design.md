# 셀메이트 선반 위치로 판매 창고 로케이션 마스터를 만든다 — 설계

- 이슈: #1235 (상위 지도 #1233 · 축 1 로케이션)
- 날짜: 2026-11-09
- 범위 밖: 재고를 실제 로케이션으로 옮기기(#1236), 실측 화면 위치 검색(#1237)

## 1. 왜

라이브 판매 창고에는 선반 로케이션이 없다. 로케이션 행은 전부 zone 이고, 재고는 입고기본존(`RECEIVING_DEFAULT`) 한 곳에 있다. 적치 목적지는 비시스템 로케이션이어야 하므로(`apps/core/src/modules/inventory/movement/` 의 `destinationIssue` 가 `SYSTEM` 을 거절한다), 로케이션이 없으면 **앱 입고가 적치 단계에서 막힌다.** 셀메이트를 끊으려면 꼭 있어야 한다.

셀메이트 선반 위치는 `sku_shelf_positions.position_code` 에 텍스트로만 있다(`scripts/sellmate/load-shelf-positions.ts` 가 적재, SKU 당 한 행). 현장에서 확인해 보니 그 위치에 실제로 상품이 있었다. 그래서 이 텍스트를 로케이션의 원천으로 쓴다.

## 2. 현장 사실 (사용자 확인)

- 선반 칸마다 **자석 라벨**이 붙어 있고, 코드 텍스트(`A-01-01`)와 **같은 값을 인코딩한 바코드**가 함께 있다. → **바코드 출력은 필요 없다.**
- 칸 번호는 99번까지 두 자리이고, 100번부터 세 자리다(`Z-01-05`, `Z-01-105`). 0을 앞에 채운 세 자리(`Z-01-005`)는 쓰지 않는다. 라이브 텍스트도 그렇다.
- **빈 칸에도 자석이 붙어 있다.** → 상품이 없는 칸도 로케이션으로 만든다.

## 3. 코드 사실 (2026-11-09 기준)

- 로케이션 모델은 열(`location_columns.column_name`) → 랙(`location_racks.rack_number`) → 칸(`locations`, `location_type='standard'`, `bin_identifier`) 이다. 코드 꼴은 `LocationService` 가 정한다: `${열}-${랙 두 자리 0채움}-${칸}`. 자동 생성 칸은 `padStart(2,'0')` 라서, 범위 1~180 이면 `01`…`99`, `100`…`180` 이 나온다. 현장 꼴과 같다.
- 랙 생성(`POST /inventory/locations/warehouses/:id/racks`)은 `standardBins.start..end` 를 **빠짐없이** 만든다. 커스텀 칸(`customBins`, `POST …/racks/custom-bins`)은 칸 이름을 자유 문자열로 받는다.
- **랙 수정(`PUT /racks/:rackId`)은 랙 행만 바꾼다.** `defaultBinEnd` 를 늘려도 칸이 생기지 않는다. 처음 의도는 "끝 번호를 늘리면 칸이 늘어난다"였으니, 지금 코드는 그 의도와 다르다. admin-web 랙 화면은 만들기만 있고 수정은 없다.
- 적치 화면(`native/warehouse-app/src/domains/inbound/PutawaySheet.tsx`)은 스캔 값과 `locations.code` 가 **글자까지 같아야** 목적지를 찾는다. 따로 발급하는 바코드 값은 없다. 코드가 곧 바코드다.
- 빈 로케이션은 출고 차감(`FifoLocationStrategy`, 원장 행 기준)에 영향이 없다. 셀메이트 `sync-stock` 은 기존 로케이션의 원장만 쓴다. → **컷오버 전 아무 때나 만들어도 운영에 영향이 없다.**
- `locations.id` 를 가리키는 외래키가 inventory 스키마에 23개 있다. 그중 상당수가 `ON DELETE SET NULL` 이다(`stock_events`·`inbound_receipts`·`inbound_work_logs`·`movement_*`·`skus.primary/secondary_location_id` 등). 나머지는 `RESTRICT` 또는 NO ACTION(`stock_ledgers`) 이다. **"지워 보고 막히면 남긴다"는 쓸 수 없다.** SET NULL 쪽은 막지 않고, 이력이 가리키던 위치를 조용히 지운다.

## 4. 목표 · 비목표 · 반목표

**목표**
- 판매 창고에 셀메이트 선반 코드와 **글자까지 같은 코드**의 standard 로케이션이 있고, 적치 화면에서 목적지로 스캔해 고를 수 있다.
- 형식에 안 맞는 텍스트를 어떻게 처리할지가 정해져 있다(자동으로 고쳐 읽기 / 사람이 정하기).
- 랙의 끝 번호를 API로 바꾸면 칸이 따라 늘거나 줄어든다.

**비목표**
- 재고 이동(#1236), 실측 화면 검색(#1237), 위치 바코드 출력, admin-web 랙 수정 화면.
- 랙별 실제 칸 수를 미리 조사하기. 데이터 기준으로 만들고, 모자라면 API로 늘린다.

**반목표 (돌아가도 실패인 것)**
- 자석 바코드와 다른 코드의 로케이션이 생긴다. 스캔해도 못 찾는 칸이 된다.
- 한 칸에 이름이 둘 생긴다(별칭, 또는 `CC-4-1` 과 `CC-04-01` 이 둘 다 로케이션이 되는 것).
- 칸을 줄이다가 재고·이력이 걸린 로케이션이 지워지거나, 이력의 위치가 NULL 이 된다.
- 스크립트가 운영 데이터(원장·이벤트·SKU 위치)를 건드린다.

## 5. 설계

### 5.1 고쳐 읽기 — 선반 텍스트 → 로케이션 코드 (순수 함수, 공유)

`sku-field-capture/position-code.ts` 처럼 **import 없는 순수 함수 파일** 하나로 둔다. 이 스크립트·#1236(SKU → 로케이션 연결)·판정 스크립트가 같은 함수를 써야 셋이 같은 답을 낸다. 입력은 `normalizePositionCode` 를 거친 값(공백 제거·대문자)이다.

결과는 넷 중 하나다.

| 결과 | 규칙 | 예 |
|---|---|---|
| `exact` | `^[A-Z]{1,2}-\d{2}-\d{2,3}$` 그대로 | `A-01-01`, `Z-01-105` |
| `fixed` | 0 빠짐: `^[A-Z]{1,2}-\d{1,2}-\d{1,2}$` → 랙·칸 두 자리로 채움 | `CC-4-1` → `CC-04-01` |
| `fixed` | 대시 자리: `^([A-Z]{1,2})(\d{2})-(\d{2,3})-$` → `X-NN-NN` | `O21-30-` → `O-21-30` |
| `custom-bin` | `^[A-Z]{1,2}-\d{2}-([가-힣]+)$` → 그 랙의 커스텀 칸 | `M-07-꼭대기` |
| `exception` | 위 어디에도 안 맞음 | 창고 이름, 랙 없는 `N-맨뒤`, `P-02--35`, `C-1F-F28` 등 |

- `fixed` 는 결과 코드와 함께 "어떤 규칙으로 고쳤는지"를 돌려준다. dry-run 이 그대로 보여 준다.
- 대시 자리 규칙은 **추정**이다(고친 코드가 칸이 많은 기존 랙에 들어가고, 겹치는 SKU 가 없다). 적용 전에 현장에서 한 칸만 확인한다.
- 커스텀 칸 이름은 원문 한글 그대로 쓴다(`M-07-꼭대기`). 자석에 무엇이 적혀 있는지는 아직 모른다. 다르면 예외로 돌린다(§7).

### 5.2 계획 도출

`sku_shelf_positions` 의 고유 코드를 5.1로 읽고, 열 → 랙 → 칸 계획을 만든다.

- 열: `exact`·`fixed`·`custom-bin` 에서 나온 열 문자 전부.
- 랙: **데이터에 나온 랙만** 만든다. **(Claude 판단)** 상품이 하나도 없는 랙은 칸 수를 알 길이 없다. 추측한 칸 수로 만들면 자석과 다른 행이 생길 수 있다. 그런 랙은 칸 수를 아는 사람이 기존 랙 생성 API로 만든다. 열 안의 랙 번호 구멍은 dry-run 보고에 "데이터에 없는 랙 번호"로 보여 준다.
- 칸: 숫자 칸이 하나라도 있는 랙은 **1번부터 그 랙의 가장 큰 숫자 칸까지** 자동 생성한다(`auto_generate_bins=true`, `default_bin_start=1`, `default_bin_end=최대`). 칸 번호가 2부터 보이는 랙도 1부터 만든다. 빈 칸에도 자석이 있다(§2).
- 커스텀 칸: `custom-bin` 결과를 그 랙에 커스텀 칸으로 더한다. 숫자 칸 없이 커스텀 칸만 있는 랙은 `auto_generate_bins=false`(`default_bin_start=default_bin_end=1`, 의미 없는 값)로 만들고 커스텀 칸만 단다. **(Claude 판단)**
- 같은 코드의 로케이션이 이미 있으면 다시 만들지 않는다. 그 행이 standard 가 아니거나 다른 랙에 붙어 있으면 건드리지 않고 "충돌"로 보고한다(apply 는 나머지를 계속한다). 2026-11-08 실측으로는 판매 창고의 기존 행이 `*_DEFAULT`·`zone-*` 이름의 zone 뿐이라 선반 꼴과 겹치지 않는다.
- `exception`: 만들지 않는다. 목록(원문 · 걸린 SKU 수)으로 보고한다. 그 SKU 들은 #1236 에서 입고존에 남는다.

### 5.3 적용 스크립트

- 위치: `scripts/sellmate/` 아래(셀메이트 원천을 읽는 일회성 도구라서). 이름은 빌더가 정한다.
- **dry-run 이 기본**이고 `--apply` 를 줘야 쓴다. 쓰기는 한 트랜잭션이다.
- 대상: core DB 하나. 실행 방식은 다른 셀메이트 스크립트와 같다(`DATABASE_URL`, 또는 `sst shell` 의 `Db` 리소스 + `CORE_DB_NAME`, 기본 `core`). 창고는 `is_sellable` 창고가 **정확히 하나일 때만** 자동으로 고르고, 아니면 `--warehouse-id` 를 요구한다. **(Claude 판단)**
- **멱등이고 늘리기만 한다.** 열·랙이 이미 있으면 다시 쓴다. 랙의 끝 번호가 계획보다 작으면 늘리고 빠진 칸을 만든다. 크면 그대로 둔다. 스크립트는 아무것도 지우지 않는다. T 전에 셀메이트 위치가 바뀌면 다시 돌리면 된다.
- 코드 꼴을 두 군데서 따로 만들지 않는다. `LocationService` 의 코드 생성(`${열}-${랙}-${칸}`)을 import 없는 순수 함수로 빼고, 서비스와 스크립트가 같이 쓴다. **(Claude 판단)** 스크립트는 다른 셀메이트 스크립트처럼 DB에 직접 쓴다(HTTP·토큰 없이).
- 쓰는 테이블은 `location_columns`·`location_racks`·`locations` 셋뿐이다.
- 보고(dry-run·apply 공통): 만들 열·랙·칸 수, 이미 있는 것, 끝 번호를 늘린 랙, `fixed` 목록(원문 → 코드 · 규칙), `custom-bin` 목록, `exception` 목록. 마지막에 "선반 텍스트의 몇 %가 로케이션으로 이어지는가"를 보여 준다.

### 5.4 core: 랙 끝 번호 바꾸기가 칸을 따라 바꾼다 (`PUT /racks/:rackId`)

랙을 수정한 뒤 `auto_generate_bins=true` 이면 **원하는 칸 집합 = 숫자 칸 `start..end`** 에 맞춘다.

- **늘리기:** 집합 안에서 아직 없는 칸 코드를 만든다(가운데 빠진 칸도 채운다). 이미 있으면 건너뛴다.
- **줄이기:** 집합 밖의 **숫자 칸**(`bin_identifier` 가 숫자뿐인 칸)마다 "사용 중"인지 본다. 사용 중이 아니면 지우고, 사용 중이면 남긴다. 커스텀 칸(숫자 아닌 이름)은 건드리지 않는다. 남긴 칸이 끝 번호보다 커도 정상으로 본다.
- **"사용 중"의 판정:** `locations.id` 를 가리키는 **모든 외래키 열**에 그 id 를 가진 행이 하나라도 있으면 사용 중이다. 지금 재고가 0이어도 이력이 있으면 사용 중이다. 외래키 목록은 손으로 적지 않는다. 판정 시점에 Postgres 카탈로그(`pg_constraint` 의 `confrelid = 'locations'::regclass`)에서 읽는다. 스키마에 새 참조가 생겨도 저절로 들어오고, SET NULL 외래키도 빠지지 않는다. 그다음 RESTRICT·NO ACTION 외래키가 있으니 DELETE 를 막는 건 DB 의 마지막 방어선일 뿐이다. 판정의 근거로 삼지 않는다.
- 한 트랜잭션 안에서 `dbService.run` 으로 돈다. 판정과 삭제 사이에 다른 트랜잭션이 그 칸을 쓰기 시작하는 경쟁은 지울 후보 칸 행을 `FOR UPDATE` 로 잠근 뒤 판정해서 막는다. **(Claude 판단, 빌더가 더 나은 방법을 골라도 된다)**
- `auto_generate_bins=false` 이면 지금처럼 랙 행만 바꾼다.
- 응답: 지금의 랙 필드는 그대로 두고, `binChanges: { created: string[]; deleted: string[]; keptInUse: string[] }` 를 더한다(추가만, 호환). admin-web `UpdateRackRequest` 쪽 타입은 응답 필드 추가만 반영한다.
- 레이어: 판정·생성·삭제는 Manager(또는 기존 서비스의 private 헬퍼) 에 두고, 에러는 `@app/shared` 도메인 예외로 낸다. 라우트 권한은 그대로 `inventory.master.write` 다.
- 스크립트(5.3)의 "늘리기"는 이 규칙의 늘리기 쪽과 같은 결과를 내야 한다. 같은 순수 함수(원하는 칸 집합 계산·코드 생성)를 공유한다.

### 5.5 판정 스크립트 맞추기

`scripts/ops/cutover-preflight/checks/location.ts` 의 "로케이션 3"은 지금 선반 텍스트 원문과 `locations.code` 를 그대로 비교한다. 이대로면 `fixed` 텍스트가 **영원히 ✗** 다. 5.1 함수로 고쳐 읽은 코드로 비교하게 바꾸고, `exception` 은 ✗ 가 아니라 "사람이 정할 목록 N개"로 따로 센다. "로케이션 1"(standard 로케이션 수 > 0)은 그대로 둔다.

## 6. 검증

- 5.1 순수 함수: 표의 각 줄, 세 자리 칸, 이미 바른 코드가 그대로 나오는지(멱등), 예외 꼴들.
- 5.2 계획: 랙 번호 구멍·칸 번호 구멍이 채워지는지, 커스텀 칸이 숫자 범위에 섞이지 않는지.
- 5.3 스크립트: 로컬 core DB에서 dry-run → apply → 다시 apply 했을 때 변화 0. 셀메이트 위치를 하나 더 넣고 다시 돌리면 그 랙만 늘어나는지.
- 5.4 API (통합 스펙, `describeIfDb`): 늘리기, 가운데 빠진 칸 채우기, 줄이기에서 ① 아무 참조 없는 칸은 지워짐 ② `stock_events` 만 가리키는 칸(SET NULL)은 남음 ③ `stock_ledgers` 행이 있는 칸은 남음 ④ 커스텀 칸은 안 건드림.
- 라이브: dry-run 출력을 사용자와 함께 본 뒤 apply 한다. 적용 뒤 판정 스크립트의 로케이션 1·3이 초록이 되고, 스테이션에서 자석 하나를 스캔해 적치 목적지로 잡히는지 확인한다.

## 7. 남은 것 · 빌더에게 맡긴 것

- **현장 확인 세 가지(적용 전):** ① `O21-30-` 꼴의 자리에 붙은 자석이 `O-21-30` 인가 ② `CC-4-1` 꼴의 자리에 붙은 자석이 `CC-04-01` 인가(같은 열에 `CC-04-01` 이 이미 정상 코드로 쓰이고 있어서 그럴 가능성이 높다) ③ `꼭대기`·`맨뒤`·`바닥` 칸의 자석에 무엇이 적혀 있나. ①·②가 아니면 그 규칙을 빼고 예외로 돌린다. ③이 원문과 다르면 커스텀 칸 규칙을 그 꼴에 맞춘다. 셋 다 규칙 하나를 켜고 끄는 일이라 구현을 미루지 않는다.
- 한 텍스트에 위치가 여럿 들어간 경우(구분자 결합)는 2026-11-09 실측에 없다. 위 표의 꼴이 전부다.
- **예외 목록의 결정**은 적용 뒤 사람이 하나씩 한다(만들지 않기 / 다른 코드로 묶기). 결정을 담는 방식(입력 파일 등)은 빌더가 정한다. 다만 이 레포는 공개 레포다. 창고·거래처 이름이 섞인 원문은 레포에 커밋하지 않는다.
- 스크립트 파일 이름, 보고 출력 모양, 순수 함수 파일의 위치·이름은 빌더가 정한다.
