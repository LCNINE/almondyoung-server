# 상품 일괄 등록/수정 — 수동 스모크 체크리스트

- 날짜: 2026-08-04
- 대상: `apps/core` catalog bulk-session 1~6단계 + `apps/admin-web` 화면 단계
- 전제: 배포 후 dev 또는 live 에서 사람이 실행한다
- 근거 문서: `docs/superpowers/specs/2026-07-31-product-bulk-session-design.md`(모체, §3·§8·§10·§11) · `docs/superpowers/specs/2026-08-04-product-bulk-session-admin-web-design.md`(화면 단계)

**왜 이 문서가 있는가**: core 2~6단계는 화면이 없어 수동 스모크를 한 번도 돌리지 않은 채 배포됐다. 이 브랜치가 화면을 붙이면서 그것이 처음으로 가능해졌다. 아래 항목은 그 다섯 단계 + 이번 화면 단계의 누적 미수행 스모크를 한 문서로 모은 것이다.

## 0. 배포 선행조건 (이것부터 — 여기서 막히면 나머지 전부가 403 이다)

- [ ] **MD 계정 `roles` 실측** — 실제로 스모크를 수행할 라이브(또는 dev) user DB 에서 그 계정의 `user_roles` 매핑을 조회한다. `BulkSessionController`·`FormExportController` 둘 다 `@UseGuards(RolesGuard('master', 'admin'))` 이고(`apps/core/src/modules/catalog/operations/bulk-session/bulk-session.controller.ts:66`, `form-export.controller.ts:14`), admin-web 의 두 라우트도 같은 롤로 `<RouteGuard requireRole={['admin','master']}>` 를 두른다(`app/(admin)/mall/bulk-sessions/page.tsx`, `[id]/page.tsx`). 계정에 `master` 또는 `admin` 이 없으면 화면 자체가 `/unauthorized` 로 리다이렉트되거나 API 가 전부 403 이라 이 문서를 한 줄도 진행할 수 없다.
      시드 롤은 `master`·`admin`·`membership`·`user`·`logistics_worker`·`logistics_manager` 여섯이다(`scripts/seeding/steps/user-service.seed-step.ts:94-109`). 실제 MD 계정이 이 중 어느 롤을 갖는지는 코드가 아니라 DB 실측으로만 안다.
- [ ] **배포 순서**: core → admin-web, 이 순서는 필수다. (core 는 대부분 이미 라이브 배포되어 있지만, 이 브랜치는 core 에 additive 변경 5건을 함께 싣고 있다 — 바로 아래 항목 참조. admin-web 을 core 보다 먼저 배포하면 그 5건이 옛 core 에서 조용히 무시된다: `conflict=undecided` 쿼리 파라미터가 드롭돼 `total` 이 전체 아이템 수가 되면서 모든 세션의 승인이 막히고, `publishStatus=failed` 가 드롭돼 발행 패널이 전체 행을 실패로 표시하며, 응답에 `bulkSessionId` 가 없어 세션 잠금 배너가 뜨지 않는다. core 를 먼저 배포해야 한다.)
- [ ] **배포 전 재확인**: 이 브랜치(`f313649d3`..HEAD)는 **마이그레이션 0건 · 시크릿 0건 · env 0건 · 이벤트 계약 0건**이다. `git diff --name-only origin/develop..HEAD -- 'apps/core/drizzle/*'` 가 비어야 하고, `apps/core/src/config/env.validation.ts`·`.env`·`sst.config.ts` 어느 것도 diff 에 없어야 한다.
      ⚠️ **모체 스펙 §3.1 헤더의 "core 소폭 변경 3건"은 이 브랜치 완료 시점 기준 낡은 숫자다.** 실제로는 리뷰 라운드를 거치며 **5건**으로 늘었다 — ① `GET /product-forms/blank` 빈 양식 엔드포인트, ② 버전 상세 응답의 `bulkSessionId` 노출, ③ `GET :id/items` 의 `conflict` 필터, ④ 검토 아이템에 `productName` 추가, ⑤ `GET :id/items` 의 `publishStatus` 서버 필터(발행 패널이 100행 상한에 걸려 실패 행이 유실되던 결함 수정). 다섯 다 additive 이고 마이그레이션은 여전히 0건이므로 이 절의 배포 판정 자체는 바뀌지 않는다 — 숫자만 정정한다.

## 1. 양식 (1단계 + 화면 — 이 절만 이번 브랜치 이전부터 있던 화면이다)

- [ ] 상품 목록에서 10건 선택 → 「양식 다운로드」 → 완료 후 다운로드 → **7시트**(상품·옵션·조합·카테고리·구매제약·이미지·카테고리 참조)가 열린다
- [ ] 「카테고리 참조」 시트에 현재 카테고리 트리가 경로 문자열로 들어 있다
- [ ] 선택 10건 중 복합 가격규칙 상품이 섞여 있으면 그 행의 판매가 셀이 정확히 `[복합 가격규칙]` 이다
- [ ] 완료 화면의 "작성을 마치면 **엑셀 일괄 등록/수정** 화면에서 올려 주세요" 링크가 `/mall/bulk-sessions` 로 이동한다 — 이하 모든 섹션이 이 화면에서 이어진다
- [ ] `/mall/bulk-sessions` → 「빈 양식 다운로드」 → 데이터 0행 + 헤더 + 카테고리 참조 시트(숨은 `_양식정보` 시트는 없다 — 만료 대상이 아니다)

## 2. 업로드·검증 (2단계 + 화면)

이 절부터 만드는 세션이 **연속성 세션**이다 — §3~§6 이 전부 같은 세션을 이어서 쓴다. 업로드는 아래에서 **딱 한 번** 한다 — 그 뒤로는 §7 전까지 새로 올릴 것이 없다. §3 의 충돌 시나리오도 여기서 함께 준비한다: 검증은 업로드 순간의 스냅샷을 기준으로 돌기 때문에, 라이브 편집은 반드시 업로드 **전에** 걸어 둬야 한다 — 업로드 뒤에 걸면 다음 세션에나 반영된다.

- [ ] 프리필 10건 중 서로 다른 두 상품을 §3 충돌 검증용으로 고른다(A·B 라 부른다). 상품 상세 화면에서 **A는 워크북에서 고칠 필드와 다른 필드**(예: 워크북에서 상품명을 고칠 계획이면 A는 판매가)를 고쳐 **발행**해 둔다. **B는 워크북에서 고칠 필드와 같은 필드**를, 워크북에 적을 값과는 다른 값으로 고쳐 발행해 둔다. 아래 업로드 전에 반드시 끝낸다
- [ ] 받은 프리필 워크북(10건)에서 A는 위에서 고른 다른 필드를, B는 같은 필드를(방금 라이브로 준 값과는 다른 값으로) 고친다. 「상품」 시트에는 **신규 행 5건**을 추가한다 — 4건은 상품키·상품명·판매가 등 필수 칸을 채워 완전히 유효하게 만들고(§5·§7 이 이 신규 행들로 "신규 행" 검증을 한다), 나머지 1건은 상품명 칸만 비워 바로 아래 "필수 칸을 비운 신규 행" 테스트 전용으로 남긴다. 유효한 4건 중 최소 1건은 「이미지」 시트에서 대표 이미지로 로컬 파일명을 참조하게 채운다(§4 가 이 값을 쓴다)
- [ ] 이 워크북(프리필 10건 + 신규 5건, A·B 필드 수정 포함)을 「양식 업로드」로 올린다 → 세션 상세로 이동, 상태 배지가 **「검증 중」** 으로 뜨다가 **「검토 대기」** 로 전진한다 — 이 업로드가 §3~§7 이 계속 참조하는 그 하나의 연속성 세션이다
- [ ] 위에서 상품명을 비워 둔 신규 행이 검토 화면 **「오류」** 탭에 뜨고, 펼치면 `상품명은 필수입니다.` 류의 한국어 사유가 보인다
- [ ] 프리필 10건 중 하나의 옵션값을 추가하거나 삭제한 수정 행이 「오류」 탭에 잡히고 `옵션값을 추가할 수 없습니다: …` 또는 `옵션값을 삭제할 수 없습니다: …` 가 뜬다(수정 행은 옵션 구조를 못 바꾼다)
- [ ] 프리필 10건 중 복합 가격규칙 행의 판매가 센티넬 `[복합 가격규칙]` 을 다른 숫자로 고친 행이 「오류」 탭에 잡히고 `복합 가격규칙 상품의 판매가은(는) 임포트로 수정할 수 없습니다: …` 가 뜬다
- [ ] 「상품」 시트에서 프리필 행 하나의 상품키를 다른 프리필 행과 똑같이 고치면(둘 다 무효가 된다) 그 두 행이 `상품키가 중복되었습니다: …` 로 「오류」 탭에 잡힌다
- [ ] **만료된 exportId 워크북 업로드가 거부되고 「양식이 만료되었습니다」가 뜬다.**
      이 항목은 **연속성 워크북과는 별개의 스로우어웨이 양식**으로 재현한다 — 위 프리필 워크북은 이미 업로드해 §3 부터 세션이 그것을 물고 이어지므로, 그 워크북의 `product_form_exports` 행을 지우면 §3 이후 전부가 조용히 끊긴다.
      **재현 방법**: 상품 목록에서 (연속성과 무관한) 상품 1~2건만 새로 골라 양식을 **따로** 받는다(업로드하지 않는다). `GET /product-forms/:exportId` 응답의 `exportId` 필드로 그 워크북의 `product_form_exports` 행을 특정해 DB 에서 직접 지운다. 그 스로우어웨이 워크북을 업로드하면 `POST /product-bulk-sessions` 가 즉시 400 을 내고 화면 토스트에 `양식이 만료되었습니다. 상품 목록에서 양식을 다시 받아 작성해 주세요.` 가 뜬다(세션 자체가 생기지 않는다 — 접수 전에 막힌다). 확인했으면 이 워크북은 버리고 위 연속성 세션으로 돌아간다
- [ ] §1 에서 받은 **빈 양식**에 신규 상품 행 몇 개만 채워 올리면(연속성과 무관한 또 다른 별도 세션), 「오류」·「충돌」 탭이 비고 전 행이 **「신규」** 로 분류된다(빈 양식은 알려진 상품키가 하나도 없어 전부 create 로 판정된다) — 이 세션도 확인만 하고 버린다, §3 이후로 이어가지 않는다

## 3. 충돌 (2단계 + 화면 — 이미 올라간 연속성 세션을 검토 화면에서 확인만 한다)

§2 에서 A·B 에 걸어 둔 라이브 편집과 워크북 편집이 그 하나의 업로드에 이미 함께 실려 있다. 여기서는 **새로 올릴 것이 없다** — 검토 화면에서 결과를 확인만 한다.

- [ ] A(다른 필드를 라이브로 고친 쪽) 행은 충돌이 아니다(자동 병합 — 「충돌」 탭에 안 뜬다)
- [ ] B(같은 필드를 라이브로 고친 쪽) 행이 「충돌」 탭에 뜨고, 화면 위쪽에 **「미결정 충돌 N건」** 배지가 뜬다
- [ ] 미결정이 남아 있는 동안 **「승인」** 버튼이 비활성이다(canApprove 는 `undecided === 0` 일 때만 켠다)
- [ ] B 행을 펼치면 그 필드에 라디오 두 개가 뜬다 — **「내 값 「…」」** / **「현재 값 「…」(남이 바꿈)」**. 충돌 필드가 한 행에 둘 이상이면 필드마다 다른 쪽을 골라 섞을 수 있다
- [ ] 오류 행이 있는 채 「승인」을 누르면 확인창이 정확히 `오류 {N}건은 제외하고 {M}건을 진행합니다.` 를 보여준다
- [ ] **승인 → draft 생성 → 발행 후, B 의 두 필드가 모두 살아 있다** — 자기 값을 고른 필드는 자기 값대로, 상대 값을 고른 필드는 상대 값대로 최종 상품에 반영돼 있는지 상품 상세에서 확인한다. 이 스펙 전체가 걸린 한 줄이다

## 4. 이미지 (3단계 + 화면 — 로컬 파일명을 참조한 행이 있는 워크북으로)

- [ ] 「이미지」 시트에서 로컬 파일명을 참조한 행이 있으면 승인 후 세션이 **「이미지 대기」** 로 간다
- [ ] 화면의 「폴더 선택」 버튼 또는 드래그로 폴더를 통째로 드롭하면, 안의 파일들이 이름으로 매칭돼 순차 업로드가 돈다(파일명 매칭은 대소문자를 무시한다 — `IMG.JPG` 로 요구했어도 `img.jpg` 가 붙는다)
- [ ] 요구 목록에 없는 파일을 섞어 올리면 **「요구 목록에 없어 건너뛴 파일 N건」** 블록에 그 파일명이 나열된다(브리프의 "「사용하지 않은 파일」" 문구는 실제 라벨과 다르다 — 위가 실제 문구다)
- [ ] 「이미지」 시트에서 같은 파일명을 대표(main)·본문(description)이 각각 요구하도록 만들면, 업로드가 그 파일을 두 번(각 용도로 한 번씩) 올린다
- [ ] 마지막 필수 이미지 하나가 채워지는 순간 진행률이 100%가 되며 자동으로 다음 화면(draft 생성 진행 → 검토 가능)으로 넘어간다(폴링이 phase 전환을 감지한다)
- [ ] 이미지 여러 장을 업로드하는 도중 브라우저를 새로고침한다 → 다시 연 화면에서 이미 올라간 요구는 목록에서 빠져 있고, 아직 안 올라간 것만 다시 요구한다

## 5. draft 생성·검토 (4단계 + 화면)

- [ ] §2 에서 추가한 **유효한 신규 행** 중 하나가 상품(master) + 임시(draft) 버전으로 새로 만들어진다(그 상품키로 상품 목록에서 검색해 확인)
- [ ] 프리필 수정 행 중 하나가 현재 active 버전에서 포크된 임시 버전으로 만들어진다(상품 상세의 버전 목록에서 확인)
- [ ] 「검토 가능」 패널의 행에서 **「임시 버전 열기」** 를 누르면 그 상품 상세(`/mall/products-list/{masterId}?versionId={draftVersionId}`)가 새 탭으로 열린다
- [ ] **그 상품 상세 화면에 「Version 발행」·「Draft 삭제」 버튼이 없고**, 대신 잠금 배너 `일괄 세션에 속한 임시 버전입니다. 발행·삭제는 세션에서 합니다.` 와 「세션 열기」 링크가 뜬다
- [ ] 그 화면에서 일반 필드 편집은 되고 저장된다(발행·삭제만 막혔다 — 편집 자체는 잠기지 않는다)
- [ ] 세션이 만든 draft 는 「작성중인 상품」(`/mall/my-drafts`) 목록에 **나타나지 않는다**(그 목록은 `bulkSessionId IS NULL` 인 draft 만 보여준다)
- [ ] draft 생성이 실패한 행이 있으면 「검토 가능」 패널에 **「draft 실패 N건」** 배지와 **「draft 실패 행 재시도」** 버튼이 뜨고, 버튼 옆에 `실패한 행만 다시 처리합니다. 신규 상품 행은 재시도할 때마다 내부 등록 기록이 한 번 더 쌓이므로, 원인을 확인한 뒤 눌러 주세요.` 경고가 함께 보인다

## 6. 발행·제외·재시도 (5단계 + 화면)

- [ ] 「검토 가능」 패널에서 **「일괄 발행」** → 세션이 「발행 중」으로 전환 → 진행률 표시 → **「발행 완료」**
- [ ] 발행된 상품이 목록에서 새 버전(active)으로 보인다
- [ ] 발행 전(「검토 가능」 상태)에 행 **「제외」** 를 누르면(확인창: `제외한 행은 다시 넣을 수 없습니다. 풀린 임시 버전은 작성중인 상품 목록에 나타납니다.`) 그 draft 가 「작성중인 상품」 목록에 다시 나타난다
- [ ] 제외한 행은 그 뒤 일괄 발행에서 처리되지 않는다(발행 대상에서 빠진다)
- [ ] 발행 실패 행이 있는 상태로 세션이 완료되면, **완료 문구("세션 발행이 완료됐습니다.")보다 위**에 `발행 실패 N건` 블록이 뜨고 각 행에 한국어 사유(`상품코드를 이미 사용 중인 다른 상품이 있습니다: …` 류)가 보인다
- [ ] **「실패 행 재발행」** 을 누르면 실패했던(또는 아직 발행되지 않은) 행만 다시 발행되고, 이미 「발행 완료」로 마감된 행은 두 번 발행되지 않는다(서버가 `publishStatus IN ('idle','failed')` 행만 골라 처리한다)
- [ ] **발행 시점 가드** — 「일괄 발행」을 누르기 직전, 세션 draft 와 무관한 별도 draft(같은 상품에서 세션과 별개로 새로 만든 draft)를 그 상품 상세 화면에서 따로 발행해 active 를 바꿔 둔다. 그 상태로 「일괄 발행」을 누르면 **그 행만** 실패로 떨어지고 사유가 정확히 `기준이 변경되었습니다. 이 상품은 양식을 다시 받아 작업해 주세요.` 다(다른 행은 정상 발행된다)

## 7. 취소·정리 (3~5단계 + 화면 — 연속성 세션과는 별개의 새 세션으로)

**연속성 세션(§1~§6)은 §6 에서 이미 발행까지 끝나 phase 가 `published` 다.** 취소는 `published`·`canceled` 두 phase 만 막으므로, 이미 발행 완료된 연속성 세션은 더 이상 취소 대상이 될 수 없다 — 아래는 전부 새로 만드는 세 번째 세션 하나에서 이어서 한다.

- [ ] 상품 목록에서 (연속성 세션과 겹치지 않는) 다른 상품 20~30건을 골라 양식을 새로 받고, 「상품」 시트에 신규 행을 2~3건 추가한다(§2 에서 신규 행을 추가한 것과 같은 방식으로 상품키·상품명·판매가를 채워 유효하게 만든다) → 이 워크북을 업로드해 새 세션을 만든다
- [ ] 검증(또는 draft 생성)이 진행되는 도중 상단 **「세션 취소」** 를 누른다(확인창: `취소하면 재개할 수 없습니다. 이미 만들어진 임시 버전은 남으며, 취소 후 이 화면에서 정리할 수 있습니다.`) → 진행 중이던 슬라이스가 그 시점에서 멈춘다(취소 이후 새로 claim 되는 행이 없다)
- [ ] **취소 커밋 이후에는 그 세션의 어떤 행도 더 발행되지 않는다** — 취소 전에 이미 draft 까지 만들어진 행이 있어도, 취소 후에는 화면에 발행 관련 액션이 없다(취소된 세션은 「임시 데이터 정리」 패널로만 간다)
- [ ] `failed` phase(예: 워커 예외로 실패한 세션)에서도 상단 「세션 취소」 버튼이 뜨고 취소가 된다(취소는 `published`·`canceled` 두 phase만 막는다)
- [ ] 취소된 세션에서 **「임시 데이터 정리」** 를 누르면 화면이 `remaining===0` 또는 `purged===0`(진전 없음)이 될 때까지 `POST :id/purge-drafts` 를 반복 호출해 끝까지 돈다(한 번에 최대 100행씩)
- [ ] 정리 후, 그 세션에서 **이미 발행된 적 있는 행**의 상품은 그대로 남아 있다(정리가 손대지 않는다) — 해당하는 행이 있다면 상품 목록에서 확인
- [ ] 정리 후, 위에서 추가한 **신규 행 중 하나**가 만든 상품(master)이 사라졌는지 그 상품키로 상품 목록을 검색해 확인한다(0건이어야 한다)
- [ ] 정리 후, 위 20~30건 중 **수정 행 하나**의 원래 active 버전이 손상 없이 그대로 남아 있는지 상품 상세에서 확인한다(만든 draft 만 지워진다)

## 8. 권한

- [ ] admin·master 롤이 없는 계정으로 로그인해 메뉴에서 「엑셀 일괄 등록/수정」을 눌러 보면, RouteGuard 가 서버 컴포넌트 단에서 토큰의 `roles` 를 검사해 `/unauthorized` 페이지(`접근 권한이 없습니다`)로 리다이렉트한다 — 화면이 빈 채로 뜨거나 그대로 열리지 않는다
- [ ] (edge case) 클라이언트 토큰은 admin·master 클레임을 갖고 있지만 서버 판정이 그와 어긋나 API 가 403 을 돌려주는 경우(배포 선행조건 §0 이 안 지켜졌을 때 재현 가능), 목록 화면이 빈 표 대신 `이 기능은 admin·master 권한이 필요합니다.` 문구를 보여준다
