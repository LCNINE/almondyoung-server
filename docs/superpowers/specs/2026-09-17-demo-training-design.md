# 직원용 발주·물류 가이드와 반복 실습 환경 설계 초안

상태: 사용자 승인 (2026-09-17). 구현·DB 반영·직원 배포 진행 상태는 구현 계획과 결과 보고서에 기록한다.
조사 기준: 2026-09-17, 저장소 HEAD `eb053df72` / PR #887.
이번 조사는 저장소의 구현과 이전 배포 보고서를 대상으로 했다. live/demo DB의 현재 건수와 실제 장비 동작은 새로 확인하지 않았다.

## 1. 목표와 산출물

리테일팀은 익숙한 실제 상품을 찾아 발주하고 입고 진행을 확인할 수 있어야 한다. 물류팀은 그 발주를 받아 입고·적치하고, 생성된 모의 주문을 피킹·검수·출고할 수 있어야 한다. 안내자는 데이터가 소진돼도 새로운 연습을 준비할 수 있어야 한다.

제안 산출물:

1. 리테일팀용 상세 HTML 가이드.
2. 물류팀용 상세 HTML 가이드. 사용자 확인에 따라 Windows PC + 바코드 스캐너·프린터를 기준으로 작성한다.
3. 두 팀이 같은 발주서·주문을 주고받는 합동 실습지.
4. 안내자용 demo 콘솔·데이터 보충 운영 안내.
5. 위 원본으로 만드는 가로 PDF. 직원 배포용 상세 문서와 별도 PPT 원본을 각각 수작업으로 유지하지 않는다.
6. live 상품 기준정보를 demo로 옮기는 도구, 실습 상태 준비 도구, 기존 콘솔의 여러 상품 주문 생성 확장.

## 3. 문서 형식 제안

| 방식 | 적합한 사용 | 한계 |
| --- | --- | --- |
| HTML 상세 가이드 | 업무 화면 옆에서 목차·검색·링크로 필요한 절차 찾기, 모바일 열람 | 오프라인 배포를 위해 이미지·스타일을 함께 묶어야 함 |
| 가로 프레젠테이션형 PDF | 집합 교육, 메신저 첨부, 정해진 순서로 실습 진행 | 긴 설명·문제 해결 항목이 많아지면 페이지가 늘고 개정본 관리가 필요 |
| **HTML 원본 + 가로 PDF 파생본** | 평소 참조와 교육·배포 모두 대응 | 처음에 인쇄용 페이지 구분과 이미지 가독성을 설계해야 함 |

세 번째 방식을 추천한다. HTML은 고정 목차, 업무별 직접 링크, 단계 번호, 주요 화면 확대 보기를 제공한다. PDF는 16:9 가로 페이지 기준으로 화면과 지시사항을 배치하되, 긴 절차를 작은 글자로 압축하지 않고 여러 페이지로 나눈다. PDF는 선택·검색 가능한 텍스트를 유지한다.

각 절차의 공통 틀은 `목적 → 준비 조건 → 어디로 이동하는지 → 클릭/스캔 순서 → 예시 입력 → 정상 결과 → 다음 담당자 → 막혔을 때`다. 화면마다 실제 메뉴명과 버튼명을 쓰고, 스크린샷에 번호를 표시한다. 표지에 기준 배포 버전·문서 날짜·demo 표시를 넣는다.

HTML/PDF는 같은 내용과 이미지를 사용한다. 변경 시 두 결과를 다시 생성하고 화면 및 인쇄 레이아웃을 검수한다. 배포되지 않은 콘솔 기능을 현재 사용법에 섞지 않는다.

## 4. 가이드 목차와 실습 구성

### 리테일팀

1. demo 접속, 계정 수령, 화면과 권한 확인. 비밀번호는 문서에 포함하지 않는다.
2. 상품명·SKU·바코드로 대상 찾기, 현재 재고·예약·입고 예정 수량 읽기.
3. `재고관리 → 보충 제안`에서 수요와 추천 수량 확인, 공급처·납기·보충 규칙 이해.
4. `발주관리`에서 발주서 생성, 요청 수량과 실발주 수량 구분.
5. 발주 상세의 품목별 `실행`, 단가·도착예정일 입력. 문서 생성만으로 발주가 실행된 것으로 안내하지 않는다.
6. `예정일 수정`, `불가`, `잔량 포기`, 발주 취소의 적용 조건과 결과.
7. 부분 입고 이후 `받음/남음`, 전량 입고 상태 확인. 입고 확정과 적치 완료의 차이.
8. 물류팀에 발주번호·입고 창고·품목·수량·예정일 전달, 완료 결과 확인.
9. 국내 발주 기본 실습 후 해외 발주의 출발/도착 창고·이동 흐름 심화 실습.

### 물류팀

1. Windows demo 앱 설치·로그인·창고 선택·작업 준비 상태 확인. 실제 바코드 스캐너의 입력/Enter 처리와 프린터·용지 설정을 안내한다.
2. `재고조회`로 SKU·바코드·로케이션별 수량 확인.
3. Windows 홈의 `입고`에서 발주 선택, 대상 품목과 실제 수령량 입력/스캔.
4. 개별 바코드와 박스 바코드의 포장단위 구분. 부분 입고 후 잔량 입고, 입고내역 확인.
5. `적치`에서 미적치 입고 선택, 도착 로케이션 확인·스캔, 수량 확정과 결과 대사.
6. `이동`에서 출발/도착 로케이션·SKU·수량 확인. 예약·가용 재고로 이동이 제한되는 경우 설명.
7. 관리 화면의 송장 발급/출고 준비 담당 단계와 앱의 `출고작업` 시작 단계를 연결.
8. 송장 조회/스캔, 단순/로케이션 출고에서 실제 나타나는 절차를 따라 상품·위치 확인, 검수·완료.
9. 통신 결과 미확정 시 화면의 재확인/복구 사용. 처리 중 중복 입력·새 작업 시작으로 우회하지 않도록 실제 표시와 함께 설명.
10. 실사·차이 확인은 심화 실습으로 분리한다.

### 합동 실습

| 실습 | 리테일팀/안내자 | 물류팀 | 성공 확인 |
| --- | --- | --- | --- |
| A. 기본 발주·입고 | 한 SKU 10개 발주, 품목 실행 | 4개 입고·적치 후 6개 입고·적치 | 발주 잔량 0, 미적치 0, 다른 작업이 없다면 시작 대비 재고 +10 |
| B. 정상 주문 출고 | 안내자가 준비된 상품으로 주문 생성, 담당자가 송장·출고 준비 | 출고작업 진행 | 주문/출고 완료와 실제 차감 수량, 모의 택배·채널 이력 |
| C. 부족 재고 보충 | 부족 주문 확인, 부족분 발주 | 입고·적치 후 출고 재준비·완료 | 미충족 예약 해소, 출고 완료, 품목별 수량 대사 |
| D. 여러 상품 주문 | 안내자가 여러 상품을 포함한 주문 묶음 생성 | 여러 위치/포장단위로 작업 | 주문 라인·구성 SKU 수량별 정확한 출고 |
| E. 예외·복구 | 예외 실습용 별도 발주/주문 준비 | 오스캔, 부분 수령, 미확정 결과 재확인 | 성공 이중 반영 없음, 다음 진행 방법 설명 가능 |

고정 숫자 실습은 시작 전 수량을 기록하고 동일 SKU에 다른 작업이 없는 범위에서 검증한다. 여러 사람이 동시에 쓰는 자유 실습은 주문·발주·작업별 원장 변화로 확인한다. 한 사람이 수량을 변경했다고 모든 직원의 가이드가 틀어지는 구성을 피한다.

## 5. live 전체 SKU와 업무 가능 상태 준비

### 5.1 기준정보 가져오기

첫 단계는 특정 시점의 live 상품 기준정보 스냅샷을 읽어 demo에 반영하는 방식으로 제안한다. 상시 자동 동기화는 초기 범위에 넣지 않는다. 이후 필요할 때 같은 도구로 추가/변경 항목을 반영한다.

가져오기 범위:

- SKU 식별자·코드·상품명·분류·옵션·물리 속성·바코드·포장단위.
- 발주에 필요한 공급처 관계·단위·납기·최소 주문수량 등 필요한 업무 속성.
- PIM 상품/버전/variant와 SKU 매칭, 세트 상품의 구성 SKU 및 수량.
- 상품 식별용 이미지. 파일 서비스 의존성과 권한을 검사하고 demo에서 접근 가능한 자산으로 연결한다.

원본 SKU ID와 demo ID의 대응을 보관한다. 충돌이 없으면 원본 ID를 유지하되 임의 덮어쓰기는 하지 않는다. live SKU와 기존 demo fixture를 구분해 전체 건수를 대사한다. 실습에 불필요한 메모·담당자 개인정보·외부 서비스 인증정보는 선택 목록에 포함하지 않는다.

`전체 SKU`는 soft-delete를 포함한 원본 행의 전체 건수와 비삭제 SKU 건수를 각각 보고한다. 삭제 상태는 보존하고 일반 주문 생성 후보에는 넣지 않는다. 주문 가능한 상품을 선별한다고 SKU 자체를 가져오기에서 누락시키지 않는다.

스냅샷 메타데이터에는 원본 환경, 추출 시점, schema 버전, 원본/반영 건수, 식별자 집합 대사, 내용 검증값을 남긴다. 가져오기 실패·매칭 누락·바코드 충돌은 행별 원인과 함께 보고하며, 전체 성공으로 표시하지 않는다. source는 읽기 전용 트랜잭션/권한을 사용하고 target은 demo 환경·DB 식별까지 검증한다.

### 5.2 실습용 업무 데이터

현재 운영 주문·고객·재고 원장을 복제하는 대신 demo 창고·로케이션·가상 고객·재고·발주·수요를 준비한다. 기준정보와 실습 이력의 갱신을 분리해 SKU 동기화가 직원 작업을 덮어쓰지 않게 한다.

SKU별로 다음 능력을 검사한다:

- 조회: 이름·코드·바코드 검색 가능.
- 발주: 공급처 관계와 필요한 입력값 존재.
- 입고/적치/이동: demo 창고·위치·바코드·포장단위 연결 가능.
- 주문/출고: 실제 판매 variant와 SKU 매칭·구성 수량·demo 배송 설정 존재.

판매상품이 연결되지 않은 물리 SKU에는 demo 전용 연습 상품 연결을 만들 수 있도록 설계한다. 연결 없이 생성 불가로 조용히 제외하지 않는다. 디지털·직배송 등 일반 창고 출고 대상이 아닌 SKU는 해당 특성과 가능한 업무를 표시한다. 외부 배송 설정은 demo 모의 프로필로 연결하고 그 변환을 기록한다.

준비 모드는 `기본 교육 세트`, `선택한 상품으로 연습`, `자유 실습 재고 보충`으로 나눈다. 모든 SKU를 담는 것과 모든 SKU에 무거운 365일 이력을 만드는 것은 구분한다. 초기에는 고정 교육 상품에 수요·납기 이력을 준비하고, 직원이 선택한 상품에도 재현 가능한 수요 패턴을 추가한 뒤 기존 재계산을 실행한다. 전체 SKU 일괄 이력은 실제 건수·처리량을 측정한 뒤 배치 실행할 수 있게 한다.

재고는 원장·예약·집계의 일관성을 보존하는 기존 업무 경로로 준비한다. 충전은 새 입고/보충 작업을 만들며 미완료 주문·발주를 삭제하거나 현재 수량을 무조건 초기값으로 되돌리지 않는다. 재실행은 같은 준비 작업을 중복 반영하지 않아야 한다.

## 6. 기존 demo 콘솔 확장

별도 앱을 추가하지 않고 기존 `/demo`를 확장한다.

### 데이터 준비 상태

기존 fixture 준비 상태와 live 상품 반영 상태를 구분해 보여준다. 마지막 반영 시점, 전체/비삭제 SKU 수, 발주·출고 가능 SKU 수, 미준비 사유, 수요 준비 상태를 표시한다. 전체 상품은 서버 검색·페이지 단위로 조회한다.

### 주문 생성

- 생성 방식: 지정 상품 / 무작위 여러 상품.
- 주문 수: 기존 1~50건 상한 유지.
- 주문당 서로 다른 상품 수와 품목별 수량 범위: 초기 제안 1~5종, 각 1~3개. 기존 지정 상품 방식과 호환.
- 후보 범위: 전체 주문 가능 상품, 선택 SKU/상품, 선택 공급처 등 필요한 필터.
- 시나리오: 정상 출고 / 재고 부족. 정상은 전체 생성 묶음의 누적 수량과 세트 구성 수량까지 고려한다. 부족은 현재 가용 수량을 기준으로 부족할 수량을 계산한다.
- 부족한 정상 주문 후보가 없으면 생성 가능 수량과 보충 방법을 표시한다. 동시 작업으로 달라진 재고는 실제 예약 결과에서 다시 확인한다.
- 실행 결과에 주문별 상품·수량·외부 주문번호와 기존 주문 화면 링크를 제공한다.

무작위 추출은 요청마다 한 번 수행하고 품목·수량·당시 상품 정보를 저장한 뒤 기존 주문 수신 경로로 보낸다. 같은 요청을 재확인하면 저장한 결과를 사용한다. 실패 항목 재시도에서 다른 상품을 뽑거나 완료 주문을 다시 만들지 않는다. 기존 단일 variant 이력도 조회·재시도가 가능해야 한다.

화면은 `생성 요청/이벤트 접수`와 `주문 반영/출고 준비`를 구분한다. 기존 비동기 흐름을 유지하고 실제 업무 상태를 확인할 수 있게 연결한다. 처음부터 시간 예약 자동 생성까지 추가하지 않고 수동 주문 묶음 생성으로 반복 실습을 제공한다.

### 실습 보충

안내자가 SKU를 선택해 새 실습 상태를 준비하고 결과를 확인한다. 준비 결과에는 관련 발주·입고·위치·상품 바코드와 시작 수량을 제공한다. 전체 DB 초기화 기능은 초기 범위에서 제외한다.

## 7. 작업 순서와 완료 기준

1. **데이터 조사:** live/demo의 SKU·variant·매칭·바코드·공급처 건수와 결손을 읽기 전용으로 확인. 원본 범위와 누락 보고서 확정.
2. **기준정보·실습 준비:** 스냅샷 가져오기와 선택 SKU 실습 준비 구현, demo에서 반영 건수·관계·재실행 검증.
3. **콘솔 확장:** 데이터 기반 후보 조회와 여러 상품 주문, 저장된 요청 재시도, 실제 업무 상태 확인.
4. **실제 화면 실습:** 두 팀 계정/역할로 기본·부족·여러 상품 흐름 수행. Windows demo 설치 파일, 로그인 후 앱 복귀, HID 스캔·포커스·Enter 처리, 프린터·용지·송장 바코드 출력과 재스캔을 검증.
5. **문서 완성:** 그때 확인한 실제 화면을 캡처해 HTML과 PDF 제작. 각 절차를 문서만 보고 따라가며 검수.

완료 기준:

- 추출 시점 기준 live SKU 식별자 누락 0. 비삭제/삭제/실습 제외 사유별 건수 합계 일치.
- 선택한 정상 물리 SKU로 발주·입고·적치·출고 가능. 필요한 demo 보완 관계와 제한 사유가 기록됨.
- 지정/무작위 여러 상품 주문이 기존 처리 경로를 거쳐 출고 작업에 나타남.
- 동일 요청·실패 재시도·재고 보충 재실행에서 중복 주문/이중 재고 반영 없음.
- 부족 재고 시나리오를 보충 후 완료하고 예약·재고 원장을 대사함.
- 데이터 갱신·보충 뒤 기존 직원 작업이 보존됨.
- 관리자·작업자 권한과 demo 전용 실행 경계 검증.
- HTML의 목차·링크·이미지와 PDF 전 페이지의 잘림·글자 크기·검색 가능 텍스트 확인.
- 해당 장비의 실물 검증 여부를 명시. API 성공만으로 스캐너·프린터 검증 완료라고 표시하지 않음.

## 8. 사용자 확인이 필요한 결정

- 추천 형식인 HTML 원본 + 가로 PDF 파생본으로 진행할지.

확정된 장비: **Windows PC + 바코드 스캐너·프린터**. PDA 가이드는 초기 산출물에 포함하지 않는다. 스캐너·프린터 모델과 라벨 규격은 실물 인수 단계에서 확인하고, 검증 전까지 특정 드라이버·용지 설정값을 단정하지 않는다.

상품 반영은 일회 스냅샷 + 필요 시 수동 갱신, 반복 실습은 기존 콘솔 확장과 선택 상품 보충을 초기 범위로 제안한다. 상시 live 동기화·시간 예약 주문 생성·전체 DB 초기화는 초기 완료 조건에 포함하지 않는다.
