# 선적 입고 ③ — 스테이션 상자 입고 화면 (#1239) + 선적 상세 상자 열기 (#1341)

> 상위 설계: `docs/superpowers/specs/2026-11-16-inbound-shipment-boxes-design.md`(이하 «모델 설계»)의 §8·§10·§12 ③.
> 선적이 무엇인가는 `2026-11-16-inbound-shipment-upload-screen-design.md`(이하 «② 설계») §3.
> core 라우트·DTO 의 정본은 `apps/core/src/modules/inventory/inbound-shipment/` 의 컨트롤러·DTO 다(특히
> `dto/receive.dto.ts`, `controllers/inbound-shipment-box.controller.ts`) — 이 문서는 바꾸는 것만 적는다.
> ①(core, PR #1337)·②(admin-web, PR #1340)는 develop 에 머지됐고 둘 다 배포 전이다.

## 1. 왜

컷오버(#1233) 첫날부터 중국 선적을 받아야 한다. ①·② 로 선적을 올리고 확정할 수는 있지만, 현장이 **상자 하나를 열어
줄마다 센 수량을 넣고 확정하는 화면**이 없으면 재고가 들어오지 않는다. 물류팀은 틈날 때 상자 하나를 들고 와 리스트를 보며
처리한다(모델 설계 §1) — 상자를 스테이션 앞에 가져와 처리하는 작업이다.

같은 릴리스에 기존 입고 화면이 새 source(`inbound_shipment`)를 알아야 하고(모델 설계 §12 ③), admin-web 에서 «이 상자에서
무엇을 몇 개 셌나»를 볼 수 있어야 한다(#1341).

## 2. 이번에 정한 것 (사용자 결정, 2026-11-16)

이미 정해져 있던 것(요청에 적힌 것):

- 상자 확정·확정 취소·리스트에 없던 상자의 권한은 `inventory.stock.operate`. 세 라우트 모두 창고 작업 계약 v2 만 받는다.
- `counts` 는 그 상자를 덮는 줄 전부를 정확히 한 번씩 담는다(0 포함) — «안 셌다»와 «0개»의 구별.
- 같은 이름 상자가 열린 선적 둘 이상에 있으면 고르게 한다(선적 이름·도착 예정일·첫 품목 2~3개, 기본 선택 없음). 연 상자
  화면 맨 위에 선적 이름을 늘 보인다.
- 전달용 상자는 열면 비고만 보이고 확정 버튼이 없다.

이번 대화에서 정한 것:

- **세는 것이 원칙이다. 믿고 넘길지는 물류팀이 판단한다.** 현장은 실제로 셀 때도 있고 리스트를 믿을 때도 있다. 그래서
  화면은 **빈칸으로 시작**하고(빈칸이 남으면 확정이 안 된다), «리스트대로»는 **줄마다 작업자가 직접 누르는 행동**으로 둔다.
- **«센 것»과 «리스트대로»를 기록에서 구별한다.** 집계 행마다 표시가 남고 admin-web 에서도 보인다. 나중에 재고가 모자랄 때
  그 수량이 센 것인지 믿은 것인지가 원인을 찾는 단서다. core 마이그 하나가 늘어난다(§7.1).
- **스테이션이 우선이다. 폰은 지금 설계하지 않는다.** 그래서 접근 A — 스테이션 전용 화면(§4).
- **저절로 끝난 선적에도 리스트에 없는 상자를 더할 수 있다.** 더하면 선적이 «입고 중»으로 돌아간다(§5.7·§7.6). 간편입고로 돌리면
  그 물건이 어느 선적에서 왔는지가 사라지고, 관리자 다시 열기로 돌리면 현장이 멈춘다.

## 3. 목표 · 비목표 · 반목표

**목표**

- 스테이션에서 상자 이름을 치거나 스캔하면 그 상자가 열리고, 줄마다 센 수량을 넣어 확정하면 그 상자만큼 RECEIVE 된다.
- 리스트에 없던 물건을 스캔해 더할 수 있고, 리스트에 없던 상자도 받을 수 있다.
- 확정한 상자를 당일 그 화면에서 취소할 수 있다.
- 앱이 꺼지거나 응답이 끊겨도 같은 상자가 두 번 들어가지 않고, 넣던 수량이 남는다.
- 입고내역·적치 대기가 선적 입고 줄을 보여 주고 올바른 곳으로 보낸다.
- admin-web 선적 상세의 상자 탭에서 상자를 열어 줄별 센 수량과 «센 것/리스트대로»를 본다(#1341).

**비목표**

- 폰(핸드헬드) 화면. 폰에서 이 경로로 들어오면 «스테이션에서 하는 작업이에요»만 보인다(반품 F7 선례).
- F3 입고 탭 전체의 스테이션 개편(발주 입고·간편입고는 지금 화면 그대로).
- 상자 이름 바코드 라벨 만들기. 상자 이름은 손으로 적혀 오므로 입력이 기본이고, 스캐너 입력도 같은 칸이 받을 뿐이다.
- 선적 끝내기·다시 열기·취소(② 의 admin-web 몫, `inventory.inbound_shipment.write`).
- 확정 뒤 센 수량 고치기. 고치려면 당일 확정 취소 뒤 다시 확정한다.

**반목표 (돌아가도 실패인 것)**

- 빈칸과 0 이 화면에서 같아 보인다. 빈칸이 남았는데 확정된다.
- 상자 전체를 한 번에 «리스트대로» 채우는 길이 생긴다 — 원칙(센다)을 버튼 하나로 무력화한다.
- 범위 줄(상자 여럿을 덮는 줄)에 «리스트대로»가 있다 — 리스트에는 합계뿐이라 이 상자 몫은 지어낸 숫자다.
- 응답이 끊긴 뒤 재시도가 새 멱등 키로 나가 상자가 두 번 확정된다(서버가 409 로 막지만, 작업자는 실패로 본다).
- 작업자가 고른 선적이 아닌 다른 선적의 상자가 열린 채 확정된다(화면 맨 위 선적 이름이 늘 보여야 한다).
- 입고내역 화면이 선적 입고 한 건 때문에 통째로 안 뜬다(지금 실제로 그렇다 — §8.1).

## 5. 화면 (스테이션)

### 5.1 입구와 경로

- **경로** `/inbound/boxes` (F3 탭 소속 — `tabs.ts` 의 F3 `owns: ['/inbound']` 가 이미 덮는다). 라우트는
  `isStationDevice()` 면 스테이션 화면, 아니면 `PlaceholderScreen`(«스테이션에서 하는 작업이에요»). 선례
  `src/app/routes/CustomerReturnsRoute.tsx`.
- **입구**: 기존 입고 화면(`ExpectedArrivalListScreen`) 위쪽, «간편입고»·«입고내역 · 취소» 링크 옆에 **«선적 상자 입고»**
  링크. 스테이션에서만 그린다. **(Claude 판단)** 대화에서는 «입고 화면 맨 위에 상자 이름 칸»을 제안했지만, 그 화면은 폰과
  같이 쓰는 옛 화면이라 거기에 스테이션 입력 규칙(타이핑하면 입력칸이 열림·스캔 버퍼)을 심지 않고, 상자 이름 입력은
  스테이션 화면의 «대기» 상태가 받는다.
- 화면 하나가 상태 기계다(출고 검수 `InspectionScreen` 과 같은 결): **대기 → (고르기) → 상자 작업 → 확정 확인 → 끝 →
  대기**. 끝난 뒤 바로 다음 상자 이름을 받는다.

### 5.2 대기 — 상자 찾기

```
┌ F3 입고 ─ 선적 상자 ────────────────────────────┐
│                                                │
│   상자 이름을 입력하거나 스캔하세요   [ L7     ]   │
│                                                │
│   열린 선적                                      │
│    11월 2차 배편 · 11-20 도착 · 상자 40           │
│    11월 1차 배편 · 11-12 도착 · 상자 32           │
└────────────────────────────────────────────────┘
 F12 리스트에 없는 상자로 받기
```

- 사람이 치기 시작하면 입력칸이 열린다(스테이션 스펙 §5.6). 스캐너 입력도 같은 칸으로 들어온다. Enter 로 찾는다.
- 찾기는 `GET /inventory/inbound-shipment-boxes?warehouseId=&label=`(기기 창고). 정규화(공백 제거·대문자)는 **서버가
  한다** — 화면은 친 그대로 보낸다. 범위 표기(`L5-L9`)는 서버 400 문구를 그대로 띄운다.
- 결과:
  - **0개** → «이 이름의 상자가 열린 선적에 없어요» + F12 «리스트에 없는 상자로 받기»(§5.7).
  - **1개** → 바로 연다.
  - **2개 이상** → 고르기(§5.3).
- «열린 선적» 목록은 `GET /inventory/inbound-shipments?warehouseId=&status=expected,receiving`. 이름·도착 예정일·상자 수만
  보인다. 목록은 안내일 뿐 누르지 않아도 된다. **(Claude 판단)** 선적별 진행(12/40)은 목록 응답에 없어서 보이지 않는다 —
  필요해지면 목록 요약에 추가형 필드를 더한다.

### 5.3 고르기 — 같은 이름이 둘 이상

```
 L7 이 두 선적에 있어요. 고르세요.
  1  11월 2차 배편 · 11-20 도착   수강가방 미디엄, 수강가방 라지, 헤어끈
  2  11월 1차 배편 · 11-12 도착   박스테이프, 용기 50ml
```

- 숫자(또는 숫자 명령 바코드)·↑↓+Enter 로 고른다. **기본 선택 없음** — 커서가 처음엔 어느 줄에도 없고 Enter 만 쳐서는 안 열린다.
- 후보마다 `BoxCandidateViewDto` 의 `shipmentName`·`expectedArrival`·`previewItems` 를 보인다.
- Esc 는 대기로.

### 5.4 상자 작업 — 열린 재고 상자

`GET /inventory/inbound-shipments/:id/boxes/:boxId` 로 연다.

```
┌ 11월 2차 배편 · 상자 L7 ─────────────────────── 11-20 도착 ┐
│ 제품명 · 옵션              우리 상품           리스트   센 수량 │
│ 수강가방 미디엄 · 블랙      SKU-1023 수강가방M     40    [ 38 ] │  ← 센 것
│ 수강가방 라지 · 블랙        SKU-1024 수강가방L     20    [ 20 ≡] │  ← 리스트대로(표시가 다름)
│▶헤어끈 · 랜덤              SKU-2001 헤어끈     L5~L9 합계 1,076 │
│                                       다른 상자 612  [    ] │  ← 빈칸(색이 다름)
│ 박스테이프 (자유 줄)         —                  2    [    ] │
│ + 리스트에 없던 물건: 손거울 SKU-3300               [  3 ] │
└──────────────────────────────────────────────────────────┘
 F8 리스트대로   F9 리스트에 없던 물건   F10 확정 (빈칸 2)
```

- **맨 위 줄은 늘 «선적 이름 · 상자 이름 · 도착 예정일»** 이다.
- **줄** = 응답 `lines[]`(행 번호 순, 서버 정렬 그대로) + 이 상자에서 더한 «리스트에 없던 물건» 줄.
  - 제품명·옵션은 엑셀 원문. `kind = 'sku'` 줄은 우리 SKU 코드·이름을 옆에 보인다(§7.2 에서 응답에 더한다).
  - 리스트 수량: 이 상자 하나만 덮는 줄은 `expectedQty`. **범위 줄**(`coversBoxLabels` 가 2개 이상)은
    «L5~L9 합계 N · 다른 상자 M»(`alreadyCountedInOtherBoxes`) — 이 상자 몫은 보이지 않는다(모른다).
  - `kind = 'free'` 줄은 «자유 줄»로 표시하고 스캔 대상이 아니다.
  - 열린 재고 상자에는 `unresolved` 줄이 없다(선적 확정 조건, 모델 설계 §6.2). 만약 오면 그 상자는 확정을 막고 «관리자 화면에서
    줄을 정해야 해요»를 띄운다(방어).
- **센 수량 칸은 세 상태**를 칸 모양으로 구별한다: **빈칸**(아직 안 넣음) / **센 것**(숫자) / **리스트대로**(숫자 + 표시).
  0 은 «센 것»의 0 이며 빈칸과 다르게 보인다.
- **입력 (입력 그리드)**: 숫자 = 지금 줄 덮어쓰기 · Enter 다음 줄 · ↑↓ 줄 이동 · Esc 그 칸 되돌림. 숫자 명령 바코드도 숫자로
  받는다. 상한은 서버와 같은 `MAX_LINE_QTY`(1,000,000).
  - **(실행 중 결정)** Backspace 로 한 자리 숫자를 지우면 0 이 아니라 빈칸으로 돌아간다(지움 = 안 센 것, 0 은 «센 것»). 줄이 바뀌면(서버가 줄을 고친 뒤 다시 읽었을 때) 바뀐 줄은 센 수량을 지켰더라도 «N줄 다시 확인»에 들어간다(§6).
- **상품 바코드 스캔**: `GET /inventory/skus?barcode=`(기존 `useSkuByBarcode`)로 SKU 와 그 바코드의 입수(`packingUnit`)를 얻는다.
  - 이 상자의 `sku` 줄 중 그 SKU 인 줄이 있으면 그 줄에 **+입수**(빈칸이면 입수부터). 같은 SKU 줄이 여럿이면 **지금 줄이 그
    SKU 면 지금 줄, 아니면 행 순서상 첫 줄**로 가고 커서를 그 줄로 옮긴다.
  - 없으면 «리스트에 없던 물건» 줄로 더한다(이미 있으면 +입수). 소리·테두리는 «주의»(정상 스캔과 구별)로 낸다.
  - 못 찾은 바코드는 오류음 + «등록되지 않은 바코드예요».
  - 스캔이나 숫자로 고친 «리스트대로» 칸은 «센 것»이 된다.
- **F8 «리스트대로»**: 지금 줄만, 그 줄의 `expectedQty` 로 채우고 «리스트대로» 표시. 범위 줄·리스트에 없던 물건 줄에서는 꺼져
  있다(기능키 바에 안 그린다, U2). **상자 전체를 한 번에 채우는 키는 없다**(반목표).
- **F9 «리스트에 없던 물건»**: 바코드가 훼손된 물건용 SKU 검색(기존 SKU 검색 부품). 고르면 줄이 하나 생기고 수량을 친다.
  리스트에 없던 물건 줄을 0 으로 만들면 그 줄은 지운다(서버는 `quantity >= 1` 만 받는다).
- **F10 확정**: 빈칸이 있으면 막고(«빈칸 N줄» 오류음, 커서를 첫 빈칸으로), 없으면 확정 확인(§5.5)으로 간다.
  - **(실행 중 결정)** 확정을 막는 사유가 둘 더 있다 — `stale_list`(«리스트대로» 칸인데 줄이 바뀌어 더는 단일 상자·예정 수량이 아님)와 `unplanned_on_list`(리스트에 없던 물건으로 넣은 SKU 가 그새 리스트 줄에도 생김 — 서버는 이중 집계를 받아주므로 앱이 막고 줄로 옮기게 한다).
- **Esc**: 넣은 수량은 기기에 남아 있으므로(§6) 대기로 돌아가도 잃지 않는다. 같은 상자를 다시 열면 이어서 한다.

### 5.5 확정 확인

```
 L7 확정 — 리스트와 다른 줄
  수강가방 미디엄     리스트 40 → 38
  헤어끈 (범위 줄)    이 상자 400 (합계 1,076 · 다른 상자 612)
  손거울 (리스트에 없던 물건)  3
                                     F10 한 번 더 = 확정 · Esc 돌아가기
```

- 보이는 것: 이 상자만 덮는 줄 중 센 수량이 리스트와 다른 줄, 범위 줄 전부(이 상자 몫은 비교할 수 없으니 넣은 값을 다시
  보인다), 리스트에 없던 물건 전부. 다 맞으면 «리스트와 같아요» 한 줄.
- **F10 을 한 번 더 누르면 보낸다**(반품 화면의 두 번 누르기와 같은 결).
  - **(실행 중 결정)** 확정이 성공하면 같은 상자를 한 번 다시 읽어 서버 기준으로 확인하고, 읽은 줄이 낡은 리스트로 확정된 것이면 «리스트가 바뀌었어요» 안내를 띄운다. 응답 유실 뒤 재전송은 같은 키를 바로 다시 쓴다(서버 멱등).
- 본문: `{ contractVersion: 2, idempotencyKey, counts: [{ lineId, countedQty, method }], unplanned: [{ skuId, quantity }] }`.
  `counts` 는 `lines[]` 전부, 행 순서. `method` 는 §7.1.

### 5.6 끝 · 확정된 상자 · 확정 취소

- 성공하면 완료음·초록 테두리, «L7 확정 — 적치 대기로 갔어요»를 띄우고 대기로 돌아간다. 선적이 이걸로 끝났으면(`shipmentStatus
  = 'closed'`) «이 선적의 상자를 다 받았어요»를 더한다.
- **확정된 상자**를 열면(찾기 결과의 `status = 'received'`) 읽기 전용으로 줄별 센 수량·«센 것/리스트대로»·리스트에 없던 물건을
  보인다. 기능키는 **F11 «확정 취소»** 하나, 두 번 눌러 보낸다. 당일·전량·적치 시작 전 같은 규칙은 **서버가 판정**하고(모델 설계
  §8.3) 거절 문구를 그대로 띄운다.
  - **(실행 중 결정)** 확정 취소 400 은 서버 문구가 아니라 **앱의 한국어 문구**를 보인다 — 작업 러너가 `serverMessage` 를 버리고 커널 메시지는 영어라서. 서버 문구 그대로 보이려면 러너 변경이 필요해 이번에 하지 않았다. 409(동시 확정)는 상자를 다시 읽고, 그 상자가 이미 확정이면 넣던 수량을 버린다.
- 취소가 되면 상자가 다시 열린 상태가 되고 **빈칸에서 다시 시작한다** **(Claude 판단)** — 확정 때 넣었던 수량을 미리 채우지
  않는다. 다시 확정하는 이유가 대개 «잘못 셌다»이기 때문이다.
- «끝» 상태에서도 방금 확정한 상자에 F11 «확정 취소»를 둔다 — 다음 상자 이름을 치기 전까지. **(Claude 판단, 리뷰 반영)**
- **선적이 저절로 끝난 뒤에도 당일 취소가 되어야 한다.** 찾기(`findBoxes`)는 열린 선적만 보므로, 마지막 상자를 확정해 선적이
  `closed` 가 되면 그 상자를 이름으로 다시 찾을 수 없다. 그래서 찾기가 **닫힌 선적의 상자 중 오늘(KST) 확정된 상자**도 돌려준다
  (§7.5). 닫힌 선적 전부를 넣지 않는 이유: 선적마다 `L1` 부터 다시 시작하므로 옛 선적이 쌓일수록 매번 고르기가 뜬다.

### 5.7 리스트에 없는 상자로 받기

- 대기에서 찾기 결과가 0개일 때만 F12 가 켜진다. 선적을 고른다(§5.3 과 같은 고르기, 기본 선택 없음). 선적이 하나뿐이어도
  한 번 고르게 한다 — 이름이 틀렸을 가능성이 크므로 «리스트에 없는 상자»를 만드는 건 작업자의 명시적 행동이어야 한다.
- **고를 수 있는 선적 (사용자 결정 2026-11-16)**: 열린 선적(`expected`·`receiving`)과 **저절로 끝난 선적**(`closed` 이고 사람이
  닫지 않음). 리스트 상자를 다 받아 선적이 저절로 끝난 뒤에 리스트에서 빠진 상자가 나오는 경우를 받기 위해서다. 저절로 끝난
  선적은 **끝난 지 30일 안**만 보인다 **(Claude 판단 — 옛 선적이 끝없이 쌓이지 않게)**. 저절로 끝난 선적에는 «끝남» 표시를 붙인다.
  사람이 닫은 선적은 고를 수 없다 — admin-web 에서 «다시 열기» 뒤에 받는다(사람이 일부러 닫은 결정을 현장이 뒤집지 않는다).
- `POST /inventory/inbound-shipments/:id/boxes { contractVersion: 2, idempotencyKey, label }` → 받은 `boxId` 로 상자 작업을 연다.
  저절로 끝난 선적에 더하면 서버가 선적을 `receiving` 으로 되돌리고(§7.6), 그 상자를 확정하면 다시 저절로 끝난다.
- 줄이 0개라 리스트에 없던 물건만 넣고 확정한다. 리스트에 없던 물건이 하나도 없으면 확정을 막는다 **(Claude 판단 — 빈 상자를
  «받았다»로 남기면 차이 화면에 뜻 없는 상자가 생긴다)**.

### 5.8 전달용 상자

`disposition = 'forward'` 면 `BigPanel` 에 «전달용 상자 — 재고로 받지 않아요»와 비고 원문(`forwardNote`)만 보인다. 기능키 없음.
Esc 로 대기.

### 5.9 동시에 두 곳에서

두 스테이션이 같은 상자를 열 수 있다. 서버가 확정을 상자 행 잠금으로 직렬화하므로, 늦은 쪽은 409 를 받는다. 화면은 «다른 곳에서
이미 확정했어요»를 띄우고 상자를 다시 읽어 확정된 상자 화면으로 바꾼다. 늦은 쪽이 넣던 수량은 버린다.

## 6. 기기 저장 · 재시도

기존 기반을 그대로 쓴다 — 새로 만들지 않는다.

- 쓰기는 `operationRunner`(IndexedDB `almondwms-work-v2`)를 거친다. 그곳이 `contractVersion: 2`·멱등 키를 본문에 붙이고, 응답이
  끊긴 작업을 `uncertain` 으로 남긴다. **단 러너는 `ledgerPath` 허용 목록에 든 경로만 감싼다**(`operationRunner.ts:6-7`) — 선적
  쓰기 세 경로(상자 확정·확정 취소·상자 더하기)를 그 목록에 넣고, 같은 파일의 `resource()` 에 «선적 상자» 갈래(예:
  `inbound-shipment-box:<boxId>`, 상자 더하기는 `inbound-shipment:<shipmentId>`)를 더한다.
- 넣던 수량은 `useWorkDraft` 에 **상자 id 를 키로** 저장한다. 내용: 줄별 `{ qty, method }`, 리스트에 없던 물건, 그리고 **확정용 멱등
  키**. 키는 상자 작업 초안을 처음 만들 때 한 번 만들고, 확정 재시도는 언제나 그 키를 쓴다(발주 입고의 `draft.value.key` 와 같다).
- 확정을 한 번 보낸 뒤 결과가 `uncertain` 이면 **수량을 잠근다** — 같은 키로 다른 본문이 나가지 않게. 상자를 다시 읽어
  `received` 면 끝으로, `open` 이면 같은 키·같은 본문으로 다시 보낸다(발주 입고 `useReceiptReconciliation` 과 같은 결).
- `confirmed`·`rejected` 가 되면 그 상자의 초안을 지운다. 거절(4xx)이면 수량은 화면에 남긴 채 다시 고칠 수 있게 **새 키**를 만든다.
- 확정 취소 키는 **그 확정이 만든 집계 행 id 묶음**(예: 첫 `countId`)을 키로 한 초안에 둔다. 회차 id 는 쓰지 않는다 — 0·자유 줄만
  있는 상자는 회차가 없어(`receiptId = null`) 확정→취소→재확정→취소에서 두 번째 취소가 첫 취소와 같은 키로 나가고, 서버 멱등이
  옛 응답을 돌려줘 **취소가 안 됐는데 앱은 성공으로 본다**. 리스트에 없는 상자 키는 «선적 id + 친 이름»을 키로 한 초안에 둔다.
- **초안과 서버 줄이 어긋날 때 (Claude 판단, 리뷰 반영)**: 상자가 열려 있는 동안 관리자가 줄의 종류·SKU·예정 수량을 고칠 수 있다
  (모델 설계 §6.4). 그래서 상자를 열 때마다 초안을 새로 읽은 줄과 맞춘다 — 없어진 줄의 값은 버리고, 종류·SKU 가 바뀐 줄은
  빈칸으로, 예정 수량이 바뀐 줄의 «리스트대로»는 빈칸으로 되돌린다(센 숫자는 남긴다). 하나라도 바뀌면 «관리자가 리스트를 고쳤어요
  — N줄 다시 확인»을 띄우고 커서를 첫 줄로. 확정 직전(F10 두 번째)에도 한 번 더 읽어 맞춘다.
- 정확한 훅 배치·키 이름은 빌더 몫.

## 7. core 변경 (전부 추가형)

①이 배포 전이므로 같은 배포에 싣는다. 마이그는 **새 파일 하나**(①의 `20261115172410_add-inbound-shipments.sql` 은 고치지
않는다 — 로컬·dev 에 이미 적용됐을 수 있다).

### 7.1 집계에 «센 것 / 리스트대로»

- `inbound_shipment_box_counts.count_method` — 새 enum `inbound_shipment_count_method` (`counted` | `list`), NOT NULL,
  기본 `counted`.
- CHECK: `line_id IS NOT NULL OR count_method = 'counted'`(리스트에 없던 물건은 늘 센 것).
- `ReceiveBoxCountDto.method: 'counted' | 'list'` — **필수**(아직 부르는 클라이언트가 없다).
- 서버 규칙(`inbound-shipment-receiving.manager.ts`): `method = 'list'` 는 **그 줄이 이 상자 하나만 덮고, `countedQty ===
  expectedQty`** 일 때만 받는다. 아니면 400. (화면이 막지만 서버가 최종 판정이다 — 범위 줄의 «리스트대로»는 지어낸 숫자다.)
- `ALTER TYPE … ADD VALUE` 가 아니라 새 enum 이므로 같은 마이그 안에서 써도 된다.

### 7.2 상자 열기 응답

`BoxViewDto` 에 더한다:

- `lines[].sku: { code, name } | null` — `kind = 'sku'` 일 때만.
- `counts[].method`.
- `receivedAt` — 확정한 때(열린 상자는 null). 확정된 상자 화면과 admin-web 서랍이 보인다.
- `counts[]` 의 리스트에 없던 물건(`lineId = null`)에 `skuCode`·`skuName`(admin-web 서랍과 확정된 상자 화면이 이름을 보인다).

### 7.3 입고내역 줄의 선적 상자

`InboundReceiptHistoryLineDto` 에 `inboundShipmentBox: { shipmentId, shipmentName, boxId, boxLabel } | null` — `source =
'inbound_shipment'` 일 때만 채운다(`inbound_shipment_box_counts.receipt_line_id` 로 잇는다). 입고내역이 선적 입고 줄을 그 상자로
보내는 데 쓴다(§8.1). 커널 쪽 조회에 문서 모듈을 끌어들이지 않도록 붙이는 위치는 빌더가 `inbound-kernel-boundary.arch.spec.ts`
에 맞춰 정한다.

### 7.4 work-context 에 상자 입고 권한

`GET` work-context 응답의 `permissions` 에 `inboundShipmentOperate`(`inventory.stock.operate` 를 가졌는지)를 더하고, 앱
`OperationContext.tsx` 타입에도 더한다. 지금 앱은 `stockAdjust`·`forceDispatch`·`stationForceDispatch`·`shortPick` 만 안다
(`warehouse-work-context.controller.ts:30-38`). 옛 앱은 모르는 필드를 무시한다.

### 7.5 찾기가 오늘 확정된 상자도 돌려준다

`findBoxes`(`inbound-shipment.reader.ts`)의 조건을 «선적이 `expected`·`receiving`» **또는** «선적이 `closed` 이고 상자가 오늘(KST)
`received`» 로 넓힌다. 응답 `BoxCandidateViewDto` 에 `shipmentStatus` 를 더해 화면이 닫힌 선적임을 표시한다. 닫힌 선적의 열린
상자(사람이 닫은 선적에 남은 상자)는 여전히 안 돌려준다 — 받을 수 없는 상자다. «오늘»의 경계는 기존 당일 취소 규칙과 같은
기준을 쓴다(빌더가 커널의 당일 판정을 재사용).

**(실행 중 결정)** 사람이 닫은 선적의 오늘 확정된 상자도 돌려준다 — 모델 설계 §8.4 가 닫힌 선적(수동 포함)의 당일 취소를 허용하고, «사람이 닫은 선적은 상자를 더할 수 없다»는 제약은 `addBox` 에만 걸린다.

### 7.6 저절로 끝난 선적에 리스트에 없는 상자 더하기 (사용자 결정 2026-11-16)

- 상자 더하기(`addBox`)의 조건을 «선적이 `expected`·`receiving`» **또는** «선적이 `closed` 이고 사람이 닫지 않음(`closed_reason
  IS NULL`)» 으로 넓힌다. 후자면 같은 트랜잭션에서 선적을 `receiving` 으로 되돌리고 `closed_at`·`closed_by` 를 지운다.
- 사람이 닫은 선적은 지금처럼 409(«다시 열기 뒤에 받으세요»). `reopen` 규칙(사람이 닫은 선적만)은 바꾸지 않는다.
- 목록 요약(`InboundShipmentSummaryDto`)에 `closedAt`·`closedManually`(boolean)를 더한다 — 앱이 «저절로 끝난 지 30일 안»을 고른다.
- 같은 키 재시도는 같은 상자를 돌려준다(이미 계약 v2 멱등).

### 7.7 core 변경을 싣는 곳

§7.1~§7.6 은 ③ 의 core PR 하나로 묶는다(앱·admin-web 보다 먼저 배포).

## 8. 기존 화면이 새 source 를 안다 (같은 릴리스)

### 8.1 warehouse-app 입고내역

- **지금 결함**: `receiptHistory.ts:128` 의 응답 검사가 줄 source 를 `direct`·`purchase_order` 로만 받아, 선적 입고 줄이 하나라도
  있으면 **응답 전체를 거부**한다 — 409 가 아니라 화면이 안 뜬다.
- 고침: 검사·타입(`receiptHistory.ts`·`receiptState.ts`·`useReceiptReconciliation.ts`)이 `inbound_shipment` 를 받는다. 선적 입고
  줄에는 줄 단위 취소를 그리지 않고 «선적명 · 상자 L7» 을 보인다. 스테이션에서는 그 줄에서 상자 화면(§5.6)으로 간다. 폰에서는
  «스테이션에서 취소해요». 직접 입고 취소 경로로 보내지 않는다(그쪽은 서버가 409).

### 8.2 warehouse-app 적치 대기

`types.ts` 의 `PutawayPendingItem.source`·`PutawayTarget.source`·`isActionablePutaway` 가 `inbound_shipment` 를 받는다. 적치는 회차
라인 단위라 커널이 같으므로 시트는 그대로 연다. 시트가 다시 읽는 상세(`receiptState`)도 같이.

### 8.3 admin-web

## 9. #1341 — admin-web 선적 상세 상자 탭

- 상자 탭(② 의 확정 뒤 상세)에서 상자 행을 누르면 **옆 서랍**이 열린다(② 의 줄 서랍과 같은 모양). 데이터는 `GET
  /inventory/inbound-shipments/:id/boxes/:boxId`(§7.2 로 넓힌 `BoxViewDto`) — 새 라우트 없음.
- 보일 것: 맨 위 «선적 이름 · 상자 이름 · 상태(열림/확정·확정 시각)». 줄마다 제품명·옵션·우리 SKU·리스트 수량(범위 줄은 «L5~L9
  합계 N»)·이 상자에서 센 수량·**«센 것 / 리스트대로»**. 리스트에 없던 물건(이름·수량). 전달용이면 비고만.
- 열린 상자는 «아직 확정 전» 한 줄과 줄 목록(센 수량 칸 없음).
- 서랍에는 쓰기 동작이 없다(확정·취소는 현장 앱 몫).
- 표시 규칙은 순수 함수(예: `boxDrawerRows(BoxView)`) + 스펙. admin-web 은 컴포넌트 테스트를 못 한다.
- 권한·게이트: 선적 상세 화면의 기존 `screen-access` 권한(`inventory.stock.read`) 안이다. Medusa 호출 없음, 개인정보 없음.

## 10. 권한

- 화면을 열고 상자를 찾는 데 `inventory.stock.read`, 확정·확정 취소·리스트에 없는 상자에 `inventory.stock.operate`. 작업자 역할은
  둘 다 이미 가진다.
- `operate` 가 없으면 F8~F12 를 기능키 바에 그리지 않는다(U2). 앱은 이 권한을 `work-context` 로 안다(§7.4). 서버 403 은 기존 403 안내(권한 이름 표시)를 그대로 쓴다.

## 11. 배포

- 같은 배치: ①(core) · ②(admin-web) · ③. 마이그는 ① 것과 §7.1 것 둘, 전부 추가형 → **expand: migrate → deploy**.
- 순서: core(migrate → deploy) → admin-web → warehouse-app 릴리스. 화면이 없으면 새 라우트는 휴면이다.
- 배포 전에 `npm run deploy:preflight -- --stage live`.
- warehouse-app 은 스토어 배포가 아니라 앱 업데이트(`UpdatePrompt`)다 — 옛 앱은 새 라우트를 모를 뿐 깨지지 않는다. 다만 옛 앱의
  입고내역은 §8.1 결함 때문에 **첫 선적 상자가 확정되는 순간부터 안 뜬다** → 새 앱 배포를 core 직후에 하고, 첫 상자 확정 전에
  스테이션이 새 앱인지 확인한다.
