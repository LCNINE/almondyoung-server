# 셀메이트 컷오버 1단계 — 자사몰은 core, 마켓은 셀메이트, 재고 정본은 core

> 상위: #1233(셀메이트 컷오버 지도). 이 문서가 그 지도의 «빅뱅» 결정을 고친다.
> 코드·데이터에서 도출되는 숫자는 적지 않는다 — 판정 스크립트(`scripts/ops/cutover-preflight`)로 본다.

## 왜 바꾸나

컷오버 날짜가 계속 밀렸다. 원인은 **두 목표를 한 날에 묶은 것**으로 본다:

1. core 가 물류(입고·피킹·출고·로케이션)를 독자적으로 처리한다.
2. 네이버·쿠팡 주문을 core 로 통합한다(수집·송장 전달·품절 반영·취소 정지).

2번이 남은 일의 큰 몫이고(API 키 발급, 연동 앱 이전, 옵션 단위 식별, shadow 점검, 재고 push 배선), 1번과 얽혀 날짜를 붙잡았다. **1번을 먼저 끝내고 2번은 다음 단계로 뗀다.**

## 목표 · 비목표 · 반목표

**목표(1단계가 끝난 모습)**
- 자사몰(Medusa) 주문은 전부 warehouse-app(Windows 스테이션)으로 피킹·검수·출고되고, `stock_events` 에 SHIP 이 찍힌다.
- 입고(국내 발주 입고와 중국 상자 입고 모두)는 앱에서 받는다.
- **core 가 재고 정본이다.** `sync-stock` 은 T 이후 다시 돌지 않는다.
- 셀메이트는 마켓 주문의 출고·반품·교환만 한다. 셀메이트의 재고는 매일 저녁 core 값으로 맞춰진다.
- 로케이션 라벨·SKU 바코드 라벨을 앱에서 뽑는다(#1281).

**비목표(2단계로 미룸)** — 마켓 주문 수집(#1244 네이버 나머지·#1245 쿠팡), 마켓 재고·품절 반영(#1246), 택배사 코드(#1136), 마켓 취소요청 출고 정지의 실가동(#1283 은 머지돼 휴면), 셀메이트 해지.

**반목표(동작해도 실패로 본다)**
- 저녁 맞추기가 어떤 품목을 **조용히 건너뛴다** — 그 품목은 core 가 마켓 판매를 영영 모르고 과판매된다.
- 맞추기가 같은 변화를 두 번 반영하거나 놓친다(재실행·작업 시간 겹침).
- `sync-stock` 이 T 이후 한 번이라도 돈다 — 절대값이라 core 원장(입고·출고)을 되돌린다.

## 정해진 것 (사용자 결정, 2026-11-11)

- **B안: core 가 재고 정본, 셀메이트는 마켓 출고 도구.** (A안 «셀메이트 정본, core 는 자사몰 출고 도구»는 정본 전환의 빅뱅을 2단계로 미룰 뿐이라 기각.)
- **같은 선반·같은 작업자가 도구 둘을 번갈아 쓴다** — 마켓 주문은 셀메이트 송장으로, 자사몰 주문은 스테이션 앱으로. 불편은 감수.
- **입고는 앱에서 받는다.** 중국 상자 입고(#1238 입고리스트 업로드·#1239 상자 단위 검수)는 첫날 필수 — 간편입고로 버틸 수 없다.
- **셀메이트에는 입고예정을 더 넣지 않는다.** 스토어프론트 입고예정일은 앱 선적(#1240)에서 나온다. 실무자에게 양해를 구한다.
- **하루 안의 과판매(같은 날 자사몰과 마켓이 마지막 재고를 같이 파는 일)는 과도기 동안 감수한다.** 없애는 것은 2단계(채널까지 core)의 몫이다. 지금도 가끔 있고, 이 프로젝트의 동기 중 하나다.
- 셀메이트 → core 로 들어가는 재고 변화는 마켓 출고·반품 입고·교환(반품 입고 + 재출고) 셋이다. 반품·교환은 셀메이트가 이미 알고 있고 물류팀이 셀메이트에서 반품 입고 처리한다.
- 신상품은 우리 시스템(PIM)에 등록한다. **1단계부터 셀메이트 등록은 마켓에서 파는 상품만** 필요하다.
- 셀메이트 «재고조사» 화면에서 엑셀 일괄 업로드가 가능해 보인다(사용자 확인, 세부 동작은 아래 «확인할 것»).

## 역할 나누기

| 일 | 1단계 | 2단계 |
|----|-------|-------|
| 자사몰 주문 출고 | 앱 | 앱 |
| 마켓 주문 수집·출고·송장·클레임 | 셀메이트 | 앱 |
| 입고·입고예정·재고 조정·실사 | 앱(core) | 앱(core) |
| 재고 정본 | core | core |
| 마켓 재고 반영 | 셀메이트(저녁에 core 값을 받아서) | core(#1246) |
| 라벨 출력 | 앱(#1281) | 앱 |

`collect-cellmate`(자사몰 주문을 셀메이트로 넘김)는 T 에 멈춘다. `load-shelf-positions`·`clear-reservations`·`sync-stock` 도 T 의 마지막 실행 뒤 멈춘다.

## 저녁 맞추기 (새 도구)

### 규칙

셀메이트 품목마다 **셀메이트 가용 = `현재재고 − 미발송주문수`** 를 기준으로 잰다. (`현재재고` 로 재면 틀린다 — 마지막 `sync-stock` 이 이미 미발송을 빼고 core 에 넣었으므로, T 이전 주문이 셀메이트에서 나갈 때 두 번 빠진다.)

1. **받기.** 셀메이트 재고 CSV(옵션정보일련번호·현재재고·미발송주문수)를 받는다.
2. **차이 반영.** 품목마다 `차이 = 지금 셀메이트 가용 − 기준값`. 기준값은 직전 맞추기 때 올린 core 가용(첫 회는 T 의 마지막 `sync-stock` 이 넣은 값). 차이를 core 원장에 ADJUST_UP/DOWN 으로 반영한다(사유는 맞추기임을 알 수 있게).
   - 이렇게 재면 마켓 주문은 **주문이 들어온 순간** core 에서 빠지고(미발송 증가), 마켓 취소·반품은 다시 더해진다. 드레인 중 T 이전 주문 출고는 현재재고와 미발송이 같이 줄어 차이 0 이다.
3. **올리기.** 품목마다 `core 가용 = ON_HAND − confirmed 예약`(자사몰 미출고분이 빠진 값)을 계산하고 — **단 T 이전에 만든 판매주문의 예약은 빼지 않는다**(그 수량은 셀메이트 `미발송` 에 이미 들어 있고 마지막 `sync-stock` 도 뺐다. 빼면 드레인 내내 두 번 빠진다) **(Claude 판단)** — 셀메이트 재고조사로 **`현재재고 = core 가용 + 지금 미발송`** 을 올린다. 그러면 셀메이트 가용 = core 가용. 이 core 가용을 다음 회 기준값으로 저장한다.
4. **닫기 확인.** 올린 뒤 셀메이트 재고를 다시 받아 품목마다 `셀메이트 가용 = core 가용` 인지 본다. 다르면 품목을 띄운다.
5. 차이를 반영한 SKU 는 sellable 을 재계산해 스토어프론트(Medusa)에 반영한다.

**모자람은 이월한다. (Claude 판단)** 마켓 주문이 core 에 남은 재고보다 많으면(또는 T 에 이미 `현재재고 − 미발송 < 0` 인 품목) ADJUST_DOWN 은 0 에서 멈추고, 모자란 수량을 품목별로 **이월 모자람**으로 저장한다. 이후 core 에 재고가 들어오면(입고·반품) 맞추기가 먼저 이월분을 갚고(그만큼 ADJUST_DOWN), 남는 것만 가용으로 올린다. 이월분이 있는 품목은 매 회 결과에 띄운다. 자사몰 확정 예약은 깎지 않는다 — 마켓 과판매가 자사몰 결품으로 번지지 않게. 이월 없이 0 으로 자르면 밀린 마켓 주문이 나중에 입고분으로 나갈 때 차이가 0 이라 core 가 실물보다 영구히 많이 본다(반목표 «놓친다»).

**첫 맞추기는 T 당일 저녁에 무조건 돈다. (Claude 판단)** 드레인(T 이전 주문 출고)이 며칠 걸려도 기다리지 않는다 — 위 예약 제외 규칙 덕에 드레인 중에도 계산이 맞다.

**돌리는 사람은 개발자다(사용자 결정).** 그래서 형태는 기존 `scripts/sellmate/*` 와 같은 스크립트(러너 `run.sh`, 터널·SST 셸 전제)다. admin-web 화면은 1단계 범위가 아니다.

### 지켜야 할 것

- **조용한 시간에 돈다.** 받기와 올리기 사이에 셀메이트에서 출고·반품 입고가 일어나면 그 변화가 덮어쓰기로 사라지거나 다음 회에 잘못 더해진다. 반품 입고는 4번 확인에도 안 잡힌다(조용한 유실). 그래서 «맞추기 동안 셀메이트 출고·반품 입고 정지»는 운영 규칙이다. (새 마켓 주문은 미발송만 바꾸므로 다음 회에 바르게 잡힌다.)
- **닫기 확인이 어긋나면 자동으로 다시 올리지 않는다. (Claude 판단)** 어긋난 품목과 양쪽 숫자를 띄우고 사람이 판단한다 — 올린 뒤 들어온 정상 마켓 주문까지 지울 수 있어서. 재고조사가 차이 업로드를 받는다면(«확인할 것») 경합이 구조적으로 없어지므로 그 방식을 우선한다.
- **멱등.** 같은 입력으로 두 번 돌려도 두 번 반영하지 않는다. 기본은 하루 한 번(물류팀 작업이 끝난 뒤), 바쁜 날 점심에 한 번 더 돌릴 수 있게 한다 — 그때는 몇 분간 셀메이트 작업을 멈춘다. **(Claude 판단)**
- **짝 못 지은 품목은 크게 띄우고 0 이 아니면 실패로 끝낸다.** 셀메이트에서 들여온 SKU 는 `skus.code = 옵션정보일련번호` 로 맞는다. core 에서 먼저 만든 SKU 를 나중에 셀메이트에 등록한 경우는 바코드로 짝짓는다. **(Claude 판단)**
- **동기화 금지 목록(`scripts/sellmate/excluded.ts`)의 품목은 양방향 모두 건드리지 않는다.** **(Claude 판단)** — 그 상품들은 셀메이트 재고 ≠ 판매 가능 재고라서.
- **dry-run 이 기본**이고, 반영 전에 품목별 차이와 올릴 값을 보여 준다(기존 셀메이트 스크립트들과 같은 관례).
- **반품·교환 처리 위치. (Claude 판단)** 마켓 주문과 T 이전 자사몰 주문(셀메이트가 내보낸 것)의 반품·교환은 셀메이트에서 처리한다 — 차이로 core 에 들어온다. T 이후 자사몰 주문의 반품은 앱의 고객 반품 경로(K8, `customer-return-receiving.manager.ts` 가 RETURNED → ON_HAND 를 원장에 쓴다)로 받는다. T 이전 자사몰 주문은 core 에 소포 사실이 없어 앱 반품 경로가 열리지 않으므로 셀메이트가 맞다. 한 주문을 두 곳에서 받으면 두 번 더해진다.
- 셀메이트에서 손으로 고친 재고도 차이로 core 에 들어온다. 동작은 하지만 **재고 조정·실사는 core 에서 한다**는 운영 규칙으로 막는다.

### 알고 감수하는 것

- core `ON_HAND` 는 «실물 − 아직 안 나간 마켓 주문»이 된다. 앱 피킹은 실물보다 적게 본다 — 과판매 쪽이 아니라 안전한 쪽이다.
- core 원장에는 «마켓 출고 N개»가 아니라 «셀메이트 맞추기 −N»으로 남는다. 보충 제안의 수요 통계가 이 기간 마켓 판매를 못 본다. 필요하면 셀메이트 주문 내역을 `import-demand-history.ts` 로 넣어 메운다.
- 하루 안의 과판매(위 결정).

## 컷오버 당일 (1단계)

0. 전날까지 판정 스크립트 초록(1단계 항목만). #1247 배포.
1. **시각 T** — 셀메이트에서 재고 CSV·상품목록·주문이력을 받아 둔다.
2. `clear-reservations` → `sync-stock` → `load-shelf-positions` 를 **마지막으로** 돌리고 멈춘다. 이때 셀메이트 가용을 맞추기의 첫 기준값으로 저장한다(음수 품목은 0 + 이월 모자람). 그 **직후** 위치가 하나인 SKU 재고를 입고기본존에서 실제 로케이션으로 옮긴다(#1236) — `sync-stock` 이 증가분을 입고기본존에 넣으므로 전날 옮기면 다시 갈린다.
3. `collect-cellmate` 를 멈춘다. T 이후 자사몰 주문은 앱으로 간다(출고 준비 → 배치 → 앱 출고). **1건 먼저** SHIP 이 찍히고 Medusa 에 반영되는 것을 본 뒤 나머지를 연다.
4. **드레인:** T 이전 자사몰 주문은 셀메이트가 끝까지 내보낸다. 다 나가면 `mark-shipped-from-csv`·`mark-core-shipped`·`mark-medusa-shipped`·`close-shipped-shipments` 를 마지막으로 한 번 돌리고 멈춘다.
5. 첫 저녁 맞추기. 닫기 확인까지 초록인지 본다.

마켓 주문은 T 와 무관하게 셀메이트에 계속 들어온다 — 마켓 쪽 드레인은 2단계의 일이다.

## 확인할 것 (사람)

- [ ] 셀메이트 재고조사 업로드가 **정확히 어떤 값을 덮어쓰는지**(현재재고 절대값인지, 차이인지), 양식(키 열이 옵션정보일련번호인지 바코드인지), 한 번에 올릴 수 있는 행 수.

- 맞추기의 ADJUST_DOWN·UP 을 **어느 로케이션**에서 빼고 넣을지(재고가 있는 실제 로케이션 우선, 모자라면 띄우기 등). 음수 원장은 만들지 않는다.
- 기준값을 어디에 저장할지(테이블·파일), 맞추기 실행 이력을 어떻게 남길지.
- 재고조사 업로드 엑셀의 생성 방식(확인 결과에 맞춰).
