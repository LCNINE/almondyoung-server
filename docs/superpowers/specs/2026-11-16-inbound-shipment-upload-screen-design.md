# 선적 입고 ② — 입고리스트 올리기·정리·선적 상세 화면 (#1238)

> 상위 설계: `docs/superpowers/specs/2026-11-16-inbound-shipment-boxes-design.md`(이하 «모델 설계»). 이 문서는 그
> §12 의 작업 순서 ② 를 정한다. core API(①)는 PR #1337 로 develop 에 머지됐고 배포 전이다. core 라우트·DTO 의 정본은
> `apps/core/src/modules/inventory/inbound-shipment/` 의 컨트롤러·DTO 다 — 이 문서는 그것을 다시 적지 않는다.

## 1. 왜

중국 직원은 선적할 때마다 입고리스트 엑셀을 메신저로 보낸다. 셀메이트를 끊으면(#1233) 이 물량을 받을 길이 core
선적 입고뿐이고, core 에는 화면이 없어 휴면이다. ② 가 끝나면 중국 직원이 리스트를 올리고, 바코드로 못 찾은 줄을
정해 확정하고, 한국 쪽은 입고가 진행되는 동안 상자별 진행과 예정·실제 차이를 보고 선적을 끝낸다. 현장의 상자 확정은
③(warehouse-app)이다.

## 2. 이번에 정한 것 (사용자 결정, 2026-11-16)

- **AI 는 ② 에서 뺀다.** 샘플(251줄)의 미확인 17줄 중 약 8줄은 포장 자재·전달 물건이라 SKU 후보가 쓸모없고, 나머지는
  제품명으로 검색하면 사람이 바로 고를 수 있다. 대신 **미확인 줄을 열면 제품명이 채워진 SKU 검색이 바로 뜬다**. 라이브에서
  «바코드 꼴인데 DB 에 없는 줄»이 많고 검색으로도 안 잡히면 그때 AI 를 붙인다. 모델 설계 §7 은 보류다.
  core 의 `PUT …/lines/:lineId/ai-candidates` 라우트와 `ai_candidates` 열은 **지우지 않고 휴면**으로 둔다(Claude 판단 —
  지우면 마이그만 늘고, 나중에 붙일 자리다). 화면은 `aiCandidates` 가 있으면 후보로 보여 주되 지금은 늘 비어 있다.
- **화면 범위는 선적의 일생 전부다.** 올리기·초안 정리·확정에 더해 확정 뒤 상자 진행·차이·끝내기·다시 열기·취소까지.
  끝내기·다시 열기는 `inventory.inbound_shipment.write` 라 현장 앱(③, `inventory.stock.operate`)의 몫이 아니다 — 여기서
  안 만들면 상자를 잃은 선적을 끝낼 길이 API 직접 호출뿐이다.
- **초안 정리 화면은 «표 + 옆 서랍»** 이다(작업 카드를 한 줄씩 넘기는 모양은 버렸다 — 미확인이 20줄 안팎이라 대기열이
  필요 없고, «수강가방 미디엄/라지»처럼 옆 줄을 같이 봐야 정해지는 경우가 있다).
- **전달용 상자는 사람이 확인해야 확정된다**(서버가 막는다, §7.6). 처음엔 확인 단계를 뺐다가 되돌렸다 — «발송» 글자 하나로
  상자가 아무 확인 없이 재고 입고에서 빠지기 때문이다.
- **SKU 이름 검색은 단어 AND 로 바꾼다**(core, §7.5).
- **용어**: 한 번에 온 물량은 «선적», 그 엑셀은 «입고리스트». 현장이 이미 그렇게 부른다(지금은 배편으로 온다).

## 3. 선적이 무엇인가 (모델 설계 보충)

선적은 입고도 창고간이동도 아니다. **받는 쪽이 «무엇이 어떤 상자로 오는지» 미리 적어 둔 도착 예고 문서**(업계의 ASN)
이고 재고를 움직이지 않는다. 재고가 바뀌는 건 상자 확정 때의 RECEIVE 하나다. 발주와 나란히 입고 커널에 일을 넘기는
문서다.

입고냐 이동이냐는 «출발지가 우리 원장 안에 있느냐»로 갈린다. 지금은 중국 창고가 우리 밖이라(2026-11-08 결정) 도착만
입고로 받는다. 나중에 중국 창고를 원장에 올려 창고간이동으로 다루고 싶어지면, 선적은 버리지 않고 이동 지시서의 «도착
부분»이 된다. 바뀌는 곳은 둘이다.

1. 선적에 출발 쪽 연결(`transfer_order_id` 같은 nullable 열) — 추가 마이그라 expand.
2. 상자 확정이 커널을 부르는 한 곳(`inbound-shipment-receiving.manager.ts` 의 `recordArrival`)이 «입고»에서 «이동 도착»
   으로.

상자·리스트 줄·집계·이 문서의 화면·③ 의 앱 화면은 그대로다. 선적 모듈에는 중국을 전제한 코드가 없다(2026-11-16 grep).
남는 공백: 중국 창고에 도착했지만 아직 선적되지 않은 물량은 어디에도 안 보인다(`CONTEXT.md` «발주·입고예정·이동
지시서» 항목). 선적이 올라온 뒤부터 #1240 이 «오는 중»으로 보여 준다.

## 4. 목표 · 비목표 · 반목표

**목표**

- 중국 직원이 admin-web 에서 입고리스트를 올리면 초안 선적이 생기고, 미확인 줄을 전부 정해 확정할 수 있다.
- 원본 엑셀이 보관되고, 선적 화면에서 한국 쪽 직원도 내려받을 수 있다.
- 확정 뒤 같은 화면에서 상자 확정 수·모자람·남음·안 옴·리스트에 없던 물건·전달용 상자를 보고, 끝내기·다시 열기·취소를 한다.

**비목표**

- AI 후보(§2). 상자 확정·확정 취소·리스트에 없던 상자(③, 현장 앱).
- 기존 입고 화면이 새 `source = 'inbound_shipment'` 를 아는 것 — 모델 설계 §12 ③ 대로 ③ 과 같은 릴리스.
- 테넌트 셸에 이 화면을 여는 것(아래 §8). 확정 뒤 «고친 리스트 다시 올리기».

**반목표**

- 화면이 판정을 한다 — 열 이름 맞추기·바코드 정규화·확정 가능 여부를 브라우저가 «결정»하면 core 스펙으로 고정한
  규칙과 갈린다. 브라우저는 읽고 보여 줄 뿐이고, 확정 가능 여부의 최종 판정은 서버 409 다.
- 엑셀 원문이 화면에서 사라진다(사람이 «파일에서 몇 행»을 찾아갈 수 없게).
- 원본 파일을 올린 사람만 열 수 있다.

## 5. 브라우저가 엑셀을 읽는 규칙 (core 계약)

순수 함수 하나(`readInboundShipmentWorkbook(ArrayBuffer) → { header, rows }`, 이름은 빌더 몫)로 두고 스펙으로 고정한다.
admin-web 은 컴포넌트 테스트를 못 하므로 판정 로직은 전부 순수 함수에 둔다.

- 라이브러리는 이미 쓰는 SheetJS `xlsx`. 샘플(20MB, 사진 포함)을 0.2초에 읽었다. 사진은 읽지 않는다.
- **내용이 있는 첫 시트**를 읽는다(샘플은 `Sheet2` 가 비어 있다).
- **병합 셀은 왼쪽 위 칸의 값으로 범위 전체를 채운다**(`!merges`). 상자 이름(A)·총수량(H) 열이 병합돼 있다.
- **머리글 = 첫 번째 비어 있지 않은 행**, 나머지가 데이터 행이다(Claude 판단). 열 이름 맞추기는 core 가 하고, 맞는 열이
  없으면 core 400 문구를 그대로 띄운다. 머리글 행을 찾으려고 «박스번호»를 뒤지지 않는다 — 판정이 브라우저로 새어 나온다.
- 칸마다 `{ text, value, formula? }`: `text` = 표시 문자열(`w`, 없으면 `String(v)`), `value` = 원값, `formula` = 수식(`f`).
  **날짜 칸의 `value` 는 `Date.toISOString()` 문자열로 보낸다** — core 는 `/^\d{4}-\d{2}-\d{2}T/` 로 «날짜로 바뀐 옵션»을
  알아본다(`inbound-shipment-list.parser.ts` 의 `ISO_DATE`). 숫자 칸은 숫자 그대로(core 가 바코드 정수화를 한다).
- `rowNumber` 는 **엑셀의 실제 행 번호**(1부터). 빈 행도 번호를 건너뛰지 않는다 — 사람이 파일에서 그 행을 찾는다.
- **끝의 빈 행·빈 열은 잘라서 보낸다.** 서식 때문에 사용 범위(`!ref`)가 넓게 잡힌 파일이 흔하고(샘플은 `A1:I1002` 인데
  데이터는 251줄), DTO 한도가 빈 행 포함 5,000행·64열이라(`upload.dto.ts`) 자르지 않으면 사람이 못 읽는 400 이 난다. 중간의
  빈 행은 그대로 보낸다(core 가 뺀다). 파서 상한은 빈 줄 제외 2,000, 업로드 라우트 본문 한도 4 MiB.
  브라우저는 데이터 행 수만 «251줄 읽음»으로 보여 주고 상한 판정은 core 에 맡긴다.

## 6. 원본 파일 보관 (file-service)

- `apps/file-service/src/database/default-file-contexts.ts` 에 컨텍스트 하나: `inbound-shipment-list`(이름 빌더 몫), 비공개,
  `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, 상한 50MB. 선례는 같은 파일의 `product-bulk-form`.
- **`apps/file-service/src/access/file-access.ts` 의 `STAFF_CONTEXT_PERMISSIONS` 에 `inbound-shipment-list →
  inventory.stock.read` 한 줄.** 없으면 비공개 파일은 올린 사람(중국 직원)만 연다. 이 표는 테넌트 일치일 때만 연다(기존 규칙).
- admin-web 은 `uploadFileToFileService(file, { contextId, isPublic: false, compress: false })`(presign → S3 직접 PUT).
  **순서는 원본 업로드 → core 초안 만들기**다(Claude 판단 — core 에는 `sourceFileId` 를 나중에 붙이는 라우트가 없고, 20MB
  직접 PUT 은 몇 초라 기다려도 된다). 원본 보관이 실패하면 **조용히 넘어가지 않고 묻는다**: «원본을 보관하지 못했습니다
  (사유). 원본 없이 올릴까요?» — 예면 `sourceFileId` 없이 초안을 만들고 초안 화면에 «원본 없음» 한 줄(Claude 판단 —
  ① 과 ② 가 한 배포에 실리면 `db:seed:ref` 전까지 컨텍스트가 없어 404 가 나는데, 그때 원본 없는 초안이 소리 없이 쌓이면 안 된다).
- 내려받기는 기존 `getFileSignedUrlFromFileService`/다운로드 프록시.
- **file_contexts 는 시드다** — 배포 뒤 `db:seed:ref` 가 돌아야 업로드가 404 를 안 낸다.

## 7. 화면

경로(Claude 판단): 목록 `/inventory/inbound-shipments`, 상세 `/inventory/inbound-shipments/[id]`. 메뉴는 «재고» 아래 «입고 관리»
다음에 «선적 입고». 코드는 `src/features/inventory/inbound-shipments/`, API 는 `src/lib/api/domains/inventory/inbound-shipments.client.ts`,
쿼리·뮤테이션은 기존 `src/lib/services/inventory/` 꼴.

### 7.1 목록

탭(진행 중 = `draft·expected·receiving` / 끝남 = `closed` / 취소)과 «입고리스트 올리기» 버튼. 줄마다 이름·상태·상자 수·줄 수·도착
예정일. 창고 필터는 창고가 둘 이상일 때만.

### 7.2 올리기 대화상자

파일 고르기 → 브라우저가 읽어 «251줄 읽음» → 창고(해외가 아닌 창고가 하나뿐이면 미리 고름, Claude 판단) · 이름(기본값 =
확장자 뺀 파일 이름) · 도착 예정일(선택) → «올리기» → 초안 상세로 이동. 읽기 실패(xlsx 아님·빈 시트)는 대화상자 안에서 알린다.

### 7.3 초안 상세 (`draft`)

- 머리: 이름·도착 예정일·메모(고치기), 원본 파일 ⬇, «미확인 N», «확정», «취소».
- **전달용 상자 띠**: core 는 비고에 «발송»이 든 줄이 덮는 상자를 **전부** 처음부터 `forward` 로 만든다. 전달용 상자에만 얹힌
  줄은 SKU 로 정해져 있어도 확정을 막지 않고 입고되지도 않는다(`inbound-shipment.rules.ts`). 그래서 띠는 상자마다 비고 원문과
  **«이 상자 안의 SKU 줄 N개는 재고로 안 들어옵니다»**를 보여 준다. 상자마다 **«전달용 맞음»** 체크와 «재고로 받기»(→ `stock`)
  가 있고, **전달용 상자를 전부 체크해야 확정이 켜진다.** 서버도 같은 것을 본다(§7.6). 상자 탭에서 상자를 전달용으로 돌리면
  체크 안 된 채 띠에 나타난다. 체크는 화면 상태일 뿐 저장하지 않는다 — 새로 고치면 다시 체크한다.
- **상자 탭(초안에도 있다)**: 상자마다 이름·처분·덮는 줄 수. 처분은 **양방향**(비고에 «발송»이 없어 놓친 상자를 전달용으로)
  이고, 초안이면 이름도 고친다(Claude 판단 — `editBox` 가 둘 다 지원한다).
- **표**: 행 번호·상자(범위는 `L5~L9`)·제품명·옵션·바코드 원문·수량·종류·사유(이슈 코드를 사람 말로). 기본 필터
  **«확인 필요»** = 미확인 줄 + **경고 이슈가 남은 자동 확정 줄**(Claude 판단). 바코드가 하나로 맞으면 상자 이름을 추측했거나
  (`box_label_guess`) 수량이 수식이어도(`qty_formula`) 자동으로 `sku` 가 되므로(`inbound-shipment-draft.manager.ts`) «미확인만»
  으로 두면 틀린 상자 추측이 보이지 않은 채 확정된다. 표시만 하는 이슈(`contact_hint`·`forward_hint`)는 경고로 치지 않는다 —
  어느 코드가 경고인지는 빌더가 이슈 목록을 보고 정해 스펙으로 고정한다.
- **서랍**(줄을 누르면):
  - 원문 칸(`raw` — core 가 별칭으로 맞춘 8개 열만 남긴다. 이미지·모르는 열은 없다), 이슈 설명.
  - **SKU 검색**: 입력칸에 **제품명**을 미리 채워 바로 검색한다(옵션은 SKU 이름에 없을 수 있어 채우지 않는다 — Claude 판단).
    사람이 단어를 지워 가며 좁힌다. 바코드 후보(`barcodeCandidates`)가 있으면 맨 위. 입력이 숫자 8자리 이상이면 `?barcode=` 와
    `?code=` 를 둘 다 부른다(셀메이트 코드는 `skus.code` 에 있을 수 있다). 아니면 이름 검색 `?name=`. 전부 `GET /inventory/skus`,
    `inventory.stock.read` — 새 라우트·새 권한 없음. 이름 검색은 §7.5 의 core 변경을 전제한다.

### 7.5 core 변경 — SKU 이름 검색을 단어 AND 로 (사용자 결정 2026-11-16)

`GET /inventory/skus?name=` 은 지금 입력 전체를 한 덩어리 `ILIKE '%…%'` 로 찾는다(`sku-catalog.reader.ts`). 그래서 «니트릴 장갑
S*100개/박스» 를 그대로 넣으면 SKU 이름에 그 글자열이 통째로 있어야만 걸린다. **공백으로 나눈 단어마다 `ILIKE` 를 AND 로**
바꾼다. 지금 걸리는 결과는 바뀐 뒤에도 전부 걸린다(한 덩어리가 들어 있으면 그 단어들도 다 들어 있다) — 이 검색을 부르는
다른 화면(admin-web·warehouse-app 약 49곳)에서 결과가 사라지지 않는다. `%`·`_` 이스케이프, 빈 단어 제거, 단어 수 상한은
빌더 몫. `?barcode=` 의 정규화(`="…"` 옛 행)는 바꾸지 않는다 — 미확인 줄은 이미 매처가 정규화로 못 찾은 줄이다.
`sku-catalog.reader` 스펙에 «두 단어가 떨어져 있어도 찾는다 / 한 덩어리로 찾던 것은 그대로 찾는다» 를 고정한다.
  - «이 SKU 로» / «자유 줄로», 수량(비었거나 이상할 때), 덮는 상자(초안만, 범위 표기 가능).
- 확정: 화면은 «재고 상자를 덮는 미확인 줄 수»로 버튼 옆에 안내만 하고, 판정은 서버다. 409 면 서버 문구를 그대로 보여 준다.
  확정 응답의 `labelOverlaps` 가 있으면 «같은 창고의 열린 선적과 상자 이름이 겹칩니다: L1, L2 …» 경고(막지 않음).

### 7.4 확정 뒤 상세 (`expected·receiving·closed·canceled`)

- 머리: 상태 배지·창고·도착 예정일 ✎·원본 ⬇, 사람이 끝냈으면 사유·시각. 버튼: «끝내기…»(사유 필수, `expected·receiving`) ·
  «다시 열기»(사람이 끝낸 `closed` 만 — 서버가 저절로 닫힌 선적에 409) · «취소»(`expected` 이고 받은 상자 0, 또는 초안).
- 요약 카드: 상자 확정 수/입고용 상자 수, 모자람 줄, 남음 줄, 안 옴 줄, 리스트에 없던 물건, 전달용 상자, 리스트에 없던 상자.
- 탭: **줄**(기본 필터 «차이 있는 줄만», 차이 = `difference.state`: 진행 중 (n/m 상자) · 맞음 · 모자람 · 남음 · 안 옴) ·
  **상자**(이름·처분·상태·센 수량·확정 시각, 리스트에 없던 상자 표시) · **리스트에 없던 물건**(상자별).
- 줄 서랍: 원문·센 수량 합계·덮는 상자마다 상태(받음/열림). 줄×상자로 쪼갠 센 수량은 상세 응답에 없으므로 서랍에는 두지
  않는다(Claude 판단 — 범위 줄은 상자가 50개까지라 상자마다 `openBox` 를 부르면 무겁고, core 를 바꾸지 않는다. 상자별 내용은
  상자 탭에서 그 상자를 열어 본다).
- 고치기 규칙(서버가 409 로 막는 것을 버튼 비활성 + 사유로 미리 보여 준다): 줄의 종류·SKU·수량은 **선적이 `expected`·`receiving`
  이고** 그 줄이 덮는 상자 중 받은 것이 없을 때만(`inbound-shipment.rules.ts`). 상자 처분은 **선적이 `closed`·`canceled` 가
  아니고** 그 상자가 열려 있을 때만. 사람이 끝낸 `closed` 선적은 다시 열어야 고친다.

### 7.6 core 변경 — 확정은 사람이 확인한 전달용 상자 목록을 싣는다 (사용자 결정 2026-11-16)

모델 설계 §6.3 은 «발송»이 든 상자를 **후보**로 두고 사람이 정한다고 했는데, ① 의 구현은 «발송» 글자만 보이면 그 줄이 덮는
상자를 전부 바로 `forward` 로 만든다. «발송 완료»처럼 지시가 아닌 말이 들어가도 그렇다. 현장 작업자는 전달용 상자를 확정할 수
없고 처분을 되돌릴 권한(`inventory.inbound_shipment.write`)도 없어서, 잘못 잡힌 상자가 그 자리에서 입고되지 못한다.

- `POST /inventory/inbound-shipments/:id/confirm` 에 본문 `{ acknowledgedForwardBoxIds: string[] }`(필수, 전달용 상자가 없으면 빈
  배열, uuid 각각).
- 서버는 선적 행을 잠근 채(기존 확정 트랜잭션 안) 그 목록이 **지금 `disposition = 'forward'` 인 상자 id 전부와 집합으로 정확히
  같을 때만** 확정한다. 다르면 409 «전달용 상자 확인이 화면과 다릅니다 — 새로 고쳐 다시 확인하세요». 빠진 것·남는 것을 구별하지
  않는다(화면이 낡았다는 뜻은 같다). 확정 차단 사유(`confirmBlockers`)와 함께 판정하고, 판정 순서는 빌더 몫.
- 규칙은 `inbound-shipment.rules.ts` 의 순수 함수로 두고 스펙으로 고정한다. 확정 통합 스펙(`describeIfDb`)도 새 본문을 싣는다.
- 확정을 부르는 곳은 이 화면뿐이고 ① 은 배포 전이라 호환성 문제가 없다. 확정 뒤(`expected`·`receiving`)의 처분 바꾸기는 사람이
  상자를 골라서 하는 일이라 확인을 따로 받지 않는다.
- 모델 설계 §6.2 확정 조건에 이 줄을 «(실행 중 결정)»으로 더한다.

## 8. 권한·게이트 배선

- `screen-access.ts`: `'/inventory/inbound-shipments'` 와 `'/inventory/inbound-shipments/[id]'` 를 `any('inventory.stock.read')`.
  쓰기 버튼은 뮤테이션 훅이 판정한다.
- 뮤테이션 훅마다 `useX.permission = ['inventory.inbound_shipment.write']`(올리기·머리 고치기·줄 고치기·상자 고치기·확정·취소·
  끝내기·다시 열기). 버튼은 `run={useX}`(`mutation-guard.gate.spec.ts`).
- **개인정보**: 고객 개인정보는 없다. 다만 원문 비고에 직원·거래처 이름이 들어 있다(«○○님께 연락바람») — 고객 PII 가 아니다.
  `pii-screens.ts` 의 `PII_SCREEN_NOT_SHOWN` 에 두 화면을 사유와 함께 적는다.
- **테넌트 셸**: `TENANT_SHELL_SCREENS` 에 넣지 않는다(Claude 판단 — 중국 선적은 테넌트 1 업무다. 필요해지면 그때 한 줄).
- 권한 카탈로그는 그대로(`inventory.inbound_shipment.write` 는 ① 에서 생겼다). AI 를 뺐으므로 `ai.assistant.use` 를 중국 직원에게
  줄 필요도 없다.

## 9. 배포

- ① 이 아직 배포 전이라 ② 는 대개 같은 `sst deploy` 에 실린다(배치 배포). 한 스택이라 앱 사이 순서는 없고, 남는 순서는
  **① 의 마이그 → 배포 → `db:seed:ref`** 다. 시드 전까지 원본 업로드는 404 이고, 그 동안은 §6 의 «원본 없이 올릴까요?»가 막는다.
  ② 자체에는 마이그가 없다(file_contexts 는 시드). core 변경은 §7.5 검색과 §7.6 확정 본문 둘이고, 화면보다 먼저 떠야 하지만
  한 배포라 순서 문제가 없다.
- 배포 뒤 중국 직원 역할에 `inventory.inbound_shipment.write` · `inventory.stock.read` 부여(모델 설계 §11).
- 첫 라이브 초안을 올려 «바코드 꼴인데 못 찾은 줄» 수를 본다 — AI 를 붙일지 정하는 숫자다(§2).
