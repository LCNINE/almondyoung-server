# 제조 완료 후 재고를 반영하는 진입점 — 설계

- 이슈: #1254 (상위 지도 #1233)
- 날짜: 2026-11-12
- 시안: [`2026-11-12-manufacture-completion-entry-mockup.html`](./2026-11-12-manufacture-completion-entry-mockup.html) (브라우저로 열어 위쪽 단계 버튼으로 넘겨 본다)
- 범위 밖: 핸드헬드(휴대폰·PDA) 진입점(#1171), 제조 전용 권한, 앱 안의 재고 이력 화면

## 1. 왜

자체 제조·주문제작 상품도 미리 재고를 쌓아 두지 않으면 창고 출고가 실제 가용재고를 기다린다. #1233 논의에서 이 동작은 의도라고 정해졌다. 디지털 상품과 달리 제조한 상품은 제조 사실과 수량이 기록돼야 하므로, **제조가 끝나면 수량을 세서 재고조정으로 올리는 흐름**을 유지한다. 주문제작도 지금은 같은 방식에 태운다.

지금 그 흐름은 재고 조회 → 상품 상세 → 재고 조정 → 위치·증감량·사유 입력으로 3단계를 거치고, 사유 선택지에 제조가 없어 `기타`에 직접 적는다. 반복 작업의 경로를 줄이는 것이 이 설계의 목적이다.

## 2. 코드 사실 (2026-11-12 기준)

- 앱 사유 목록은 `ADJUST_REASONS = ['파손','분실','발견','오출고 정정','기타']` 다(`native/warehouse-app/src/domains/inventory/useAdjustStock.ts`).
- 서버 `AdjustStockDto.reason` 은 자유 문자열이다(`apps/core/src/modules/inventory/core/dto/inventory/adjust-stock.dto.ts`). → **core 는 고칠 게 없다.** 사유는 `stock_events.reason` 에 그대로 남는다.
- `POST /inventory/stocks/adjust` 는 `inventory.stock.adjust`(관리자·물류 관리자, DANGEROUS) 권한이다. 작업자는 403 이다.
- `AdjustStockScreen` 에 멱등키 회전(성공 후에만 새 키, payload 가 바뀌면 새 키)과 권한 사전 확인(`permissions.data?.stockAdjust === false`)이 이미 있다.
- 스테이션에는 홈이 없다. F1~F7 탭 바가 홈이고(`native/warehouse-app/src/station/tabs.ts`), F6 이 재고 조회(`/inventory`)다. 탭은 하위 탭(`sections`)을 가질 수 있다.
- 상품 선택은 `SkuPicker`(바코드 스캔·검색)를 입고·간편입고·실사가 이미 쓴다.
- 앱 상품 상세에는 재고 이력이 없다. 이력은 `GET /inventory/stocks/history`(`inventory.stock.read`)가 `stock_events` 원본 행을 돌려주고, admin-web 재고 현황의 이력 drawer 가 그걸 보여 준다.
- SKU 기준으로 예약을 못 잡은 대기 출고를 세는 API 는 없다. 앱이 받는 재고 값은 위치별 `quantity`·`reservedQuantity`·`availableQuantity` 뿐이다.
- 컷오버 전 라이브 재고는 전부 시스템 구역 입고기본존 한 곳에 있다(#1233 축 1). 선반 로케이션은 #1235·#1236 이 만든다.
- 조정으로 원장이 오르면 대기 출고 예약 재시도가 이미 돈다. 이슈 첫 코멘트에서 `기타` +4 조정 뒤 예약 68/72 → 72/72·준비 완료를 로컬로 확인했다.

## 3. 정한 것

| 질문 | 결정 | 이유 |
|---|---|---|
| 누가 등록하나 | 지금 권한 그대로, `inventory.stock.adjust` 가 있는 관리자만 | #1233 이 조정은 admin 이 맡는다고 정했다. 제조는 확인·기록이 목적이다. 현장에서 너무 불편하면 그때 늘리기만 하는 좁은 권한을 검토한다 |
| 진입점 | 스테이션 F6 재고 조회 안의 하위 탭 `제조 완료` | 스테이션엔 홈이 없고 탭 바가 홈이다 |
| 화면 | 기존 `AdjustStockScreen` 을 제조 모드로 재사용 | 멱등 로직을 복제하지 않는다 |
| 사유 | 제조 모드는 `제조` 고정. 일반 조정 사유 목록에도 `제조` 추가 | 다른 경로로 들어와도 `기타`에 적지 않게 |
| 수량 | 제조 모드는 양수만 | 줄이는 일은 일반 재고 조정의 몫이다 |
| 위치 | 그 SKU 재고가 있는 위치가 한 곳이면 자동 선택, 둘 이상이거나 없으면 직접 선택. 입고기본존도 후보 | 컷오버 전에도 바로 쓰여야 한다(그땐 늘 입고기본존이 골라진다). 컷오버 뒤 선반 재고가 생기면 위치가 둘이 되어 자연히 직접 고르게 된다 |
| 가상 구역 표시 | 달지 않는다 | 위치 이름이 이미 입고기본존이다. 표시하려면 core 응답에 필드가 더 필요하다 |
| 결과 확인 | 등록 직후 결과 화면(상품·위치·수량 전 → 후·사유). 지난 기록은 admin-web 재고 현황 이력 | 완료 조건을 이걸로 채운다. 등록하는 사람(관리자)과 볼 곳이 맞다 |
| 오늘 등록 목록·앱 이력 | 두지 않는다 | 이력 화면은 별개 기능이다. 현장에서 필요하다고 나오면 따로 이슈를 연다 |
| 대기 출고·예약 변화 표시 | 두지 않는다 | SKU 기준 API 가 없다. 모자란 수량을 띄우면 센 수량 대신 그 숫자를 넣게 만들 위험이 있다 |
| 핸드헬드 | 이번엔 안 한다. 사유 목록의 `제조` 만 받는다 | 첫날 기기는 스테이션만이다(#1233). #1171 때 같이 한다 |

## 4. 화면 흐름

1. **상품 고르기** — F6 → `제조 완료`. `SkuPicker` 로 바코드를 스캔하거나 검색해 고른다. 권한이 없으면 이 단계에서 관리자 작업이라는 안내를 띄우고 진행을 막는다(수량을 넣고 나서 거절돼 미전송으로 남는 일이 없게, #1261).
2. **위치·수량** — 상품 카드, 보관 위치(규칙대로 자동 선택 또는 직접 선택), 숫자 패드(양수만), 사유 `제조` 고정 표시, `제조 완료 등록` 버튼.
3. **확인** — 상품·위치·수량(전 → 후)·사유를 보여 주고 `등록`.
4. **결과** — 등록했다는 안내, 위치 수량 전 → 후, `다음 상품 등록`. 바코드를 바로 스캔해도 다음 상품으로 넘어간다. 일반 조정처럼 상품 상세로 이동하지 않고 이 화면에 머문다.

경로는 `/inventory/manufacture`(상품 고르기) → `/inventory/$sku/adjust?mode=manufacture` 를 생각하고 있다. `/inventory/$sku` 와 겹치지 않는지는 구현 때 라우터에서 확인한다.

## 5. 완료 조건

- [ ] F6 재고 조회에 `제조 완료` 하위 탭이 있고, 상품 선택 → 위치·수량 → 확인 → 결과까지 위 규칙대로 동작한다.
- [ ] 일반 재고 조정 사유 목록에 `제조` 가 있다.
- [ ] 재고 조정 권한이 없는 계정은 수량을 넣기 전에 관리자 작업이라는 안내를 본다.
- [ ] 재고 부족만으로 수량을 자동으로 올리지 않는다(화면이 부족 수량을 미리 채우지 않는다).
- [ ] 로컬 E2E 에서 관리자 계정으로 제조 등록 → 원장 반영 → 대기 출고 예약 재시도(준비 완료)까지 확인하고 결과를 PR 에 적는다.
- [ ] 배포 뒤 담당자가 라이브에서 실제 제조분으로 한 번 등록해 아래 완료 절차를 마치고, 현장에서 불편했던 점을 이슈에 남긴다.

## 6. 완료 절차 (배포 뒤 담당자가 한다)

⚠️ 라이브에서는 **실제로 만든 수량만** 넣는다. 확인용으로 가짜 수량을 넣지 않는다. 원장에 그대로 남고 스토어프론트 재고가 늘어난다.

1. **실제 제조가 끝난 날을 고른다.** 만든 상품과 개수를 직접 센다.
2. **작업자 계정으로 먼저 확인한다(입력 없이).** 스테이션 앱 F6 → `제조 완료` 로 들어가 수량을 넣기 전에 관리자 작업이라는 안내가 뜨는지 본다. 아무것도 등록하지 않고 나온다.
3. **관리자 계정으로 등록한다.** F6 → `제조 완료` → 상품 바코드 스캔 → 자동으로 골라진 위치 확인(컷오버 전이면 입고기본존) → 센 수량 입력 → 확인 창의 상품·위치·수량·사유가 맞는지 보고 `등록`.
4. **결과 화면을 확인한다.** 수량이 전 → 후로 센 만큼 늘었고 사유가 `제조` 인지 본다.
5. **원장 기록을 확인한다.** admin-web 재고 현황에서 그 상품의 이력을 열어 방금 등록한 줄의 사유가 `제조` 로 남았는지 본다.
6. **대기 출고가 있었다면 풀렸는지 본다.** 그 상품 때문에 예약을 못 잡던 출고가 있었다면, 출고 화면에서 예약이 다 차고 준비 완료로 바뀌었는지 본다. 대기 출고가 없었다면 건너뛰고 그렇다고 적는다.
7. **이슈에 코멘트를 남긴다.** 등록한 날, 확인한 단계, 현장에서 불편했던 점(없으면 없다고). 불편이 크면 #1233 쪽 논의로 넘긴다.
8. 완료 조건을 모두 체크하고 이슈를 닫는다.
