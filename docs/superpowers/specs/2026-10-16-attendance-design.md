# 아몬드영 출결 시스템 설계

상태: 구현 착수 승인. 2026-10-16 사용자가 공유 캘린더까지 확정하고 브랜치를 생성해 구현하도록 명시적으로 지시했다. 구현 중 세부 선택은 계획과 작업 기록에 남긴다.

빌더 검토: 초기 초안 검토 이후 추가된 개인 캘린더, 경리나라 승인 유지, 반차 시간표, 입력 검증을 반영한 갱신본을 새 소프트웨어 엔지니어 검토자가 확인했다. 2026-10-16 검토 결과는 ‘nothing important left’였으며 구현 계획을 막는 추가 질문은 없었다. 이 검토 이후 관리자 공통 근무 현황 및 공유 캘린더로 범위를 갱신했고 사용자가 구현 착수를 지시했다.

## 목적과 범위

직원이 개인 휴대폰으로 회사 근처에서 출퇴근을 기록하고, PC 어드민에서 같은 기록을 조회한다. 위치 확인 실패·누락·오입력은 정정/예외 요청으로 처리한다. 요청의 1차 검토는 AI가 보조하며 최종 승인은 마스터 권한 보유자가 한다.

사용자가 확정한 사항:

- 현재 미리보기의 디자인, 기존 shadcn/ui·Tailwind 구성 유지. 당근·토스는 시각·인터랙션 참고다.
- PC 홈 우측 독립 근무 카드. 개인 휴대폰에서 실제 출퇴근 기록.
- 확인 모달 없이 버튼 클릭 → 위치 확인 → 기록 중 → 완료 표시/소리 → 상태 갱신.
- 위치는 출퇴근 시점에만 확인한다. 근무 중 지속 추적하지 않는다. 재택은 범위 밖이다.
- 안내는 `?`로 제공한다. 첨부 영역에는 AI 가상 인물 사진을 사용한 촬영 예시가 있다.
- 정정/예외 상세 사유의 줄바꿈은 입력·저장·직원 내역·담당자 화면에서 유지한다.
- 이미지 첨부는 선택. 사진·오류 스크린샷을 받을 수 있고, 얼굴 사진을 필수로 요구하지 않는다.
- 정정/예외 요청의 최종 승인 권한은 마스터에게만 있다.
- 마스터는 본인의 정정/예외 요청도 직접 승인할 수 있다. 자기 승인도 동일한 감사 이력을 남긴다.
- 하루 출퇴근 한 쌍을 기본으로 하고 당일 재출근 기능은 1차 범위에서 제외한다. 실수 기록은 정정 요청으로 처리한다.
- 모바일 제공 방식은 홈 화면에 추가해 실행하는 PWA로 확정했다. 별도 설치형 웹뷰 앱은 만들지 않는다.
- 직원마다 근무 시간이 다르며, 개인이 출근·퇴근 리마인더를 각각 켜고 끄고 시각을 설정한다.
- 개인 리마인더 시각은 알림용이며 지각·조퇴 판정의 기준이 아니다.
- 1차 내부 캘린더에는 출결·휴가·오전/오후 반차를 둔다. 회의·행사는 당분간 타임트리를 유지하고 장기적으로 내부 캘린더로 이전한다. 이번에 회의·행사 관리까지 구현하지는 않는다.
- 휴가 승인은 경리나라에서 유지한다. 직원이 승인받은 휴가를 본인 캘린더에 직접 등록·수정하며 내부 재승인을 받지 않는다.
- 공유 캘린더는 모든 관리자(admin·master)가 직원 전체의 휴가·반차를 조회한다. 본인 일정만 등록·수정·삭제한다.
- 별도로 ‘직원 근무 현황’ 페이지를 제공한다. 업무 조율을 위해 모든 관리자(admin·master)가 직원들의 현재 출퇴근 기록 상태와 해당 날짜의 종일 휴가·오전/오후 반차를 조회한다. 공유 캘린더와 별개이며 승인 권한을 확대하지 않는다.
- 오전 반차의 퇴근 예정은 평소 퇴근 시각을 유지한다. 평소 09~18시는 13~18시, 평소 10~19시는 14~19시가 기본값이다. 출근 예정에 4시간 30분을 더하는 계산은 폐기한다.
- 휴가 등록의 날짜별 제외·다시 추가, 잘못된 시간 순서 차단, 모달이 열려 있는 동안 배경 스크롤 방지를 적용한다. ‘계산 기준’ 영역과 그 아래 설명은 삭제한다.


이번 범위: 출결 기록, 회사 위치 확인, 개인 기록, 정정/예외, 선택 첨부, AI 검토 보조, 마스터 검토, 관리자 공통 직원 근무 현황, 내부 출결·휴가·반차 캘린더, 홈 화면 웹앱, 푸시 및 개인 리마인더.

제외: 급여·수당 계산, 법정 근로시간 판정, 지각/조퇴 자동 판정, 재택, 백그라운드 위치 추적, 얼굴 인식/신원 매칭, 사진 진위·출석 사실의 AI 확정, 회의·행사·일반 일정 관리 및 타임트리 자동 동기화. 연차 발생·잔여일수·정산 장부는 초기 범위에서 제외하는 설계자 제안이며 필요하면 별도 설계한다. 단순 위치 실패나 AI 실패를 자동 결근/반려로 취급하지 않는다.

## 기존 구조 조사와 배치 제안

### 모듈 내부 파일 구조 (사용자 확정)

core와 같이 기능별 모듈을 두고 그 내부를 책임별 디렉터리로 나눈다. 예를 들어 `attendance/attendance.module.ts` 아래에 `controllers/`, `services/`, `guards/`, `dto/`, `repositories/`를 둔다. 모든 파일을 모듈 루트에 평평하게 나열하지 않는다. 복잡도가 커지면 서비스에서 조회 책임을 Reader, 상태 변경·업무 규칙·트랜잭션 책임을 Manager로 분리한다. Reader/Manager는 단순 통과 계층을 늘리기 위해 만들지 않고 복잡한 조회·변경 책임이 생겼을 때 도입한다. 실제 배치는 인접 core 모듈의 관례를 따른다.

### 문장·코드 줄바꿈과 가독성 (사용자 확정)

프런트엔드와 백엔드 모두 사람이 읽기 편하게 작성한다.
설명 문서는 문장 단위로 줄바꿈한다.
코드의 여러 명령문·조건 처리·메서드 본문을 한 줄에 몰아넣지 않는다.
함수 안에서도 값 계산, 검증/분기, DB/API 호출, 반환 사이를 빈 줄로 분리한다.
서로 다른 책임의 선언·메서드·블록 사이에도 빈 줄을 둔다.
긴 인자·쿼리 조건·DTO 데코레이터·JSX 속성은 읽기 쉬운 여러 줄로 정리한다.
Prettier 실행만으로 이 요구를 충족했다고 보지 않으며, 작성자가 의미 단위 줄바꿈을 직접 확인하고 리뷰어도 검토한다.

다음은 코드 조사에 근거한 설계자의 선택이며 기존 구현이 이미 출결을 지원한다는 뜻은 아니다.

| 소유 영역 | 책임 |
| --- | --- |
| `apps/admin-web` | 홈 근무 카드, 출결 전용 모바일 페이지, 내 기록/요청, 출결·휴가 캘린더, 마스터 검토, 개인 설정, 웹앱 manifest·service worker |
| `apps/user-service` | 출결·휴가 도메인·DB, 위치 판정, 정정/예외와 승인 트랜잭션, 캘린더 조회·알림 발생 조건 |
| `apps/file-service` | 비공개 이미지 업로드·열람·삭제. 요청과 fileId의 연결은 출결 도메인이 보유 |
| `apps/ai` | 비동기 출결 요청 요약·증빙 내용 추출·확인할 사항 제시. 출결 상태를 변경할 권한 없음 |
| `apps/notification` | 웹 푸시 구독 관리·발송·실패 처리. 기존 알림 전송 구조와 연결 |

현재 `MainTemplate`의 오늘 할 일 → 매출 목표 → 현황판 → 주요 서비스 순서를 유지하며 우측 카드 열을 추가한다. 개인 기록은 기존 회사/조직 메뉴의 출퇴근 자리, 마스터 검토는 경영지원의 휴가/근태 자리를 활용한다.

기존 `/mobile`은 물류용 하단 메뉴와 역할 가드를 공유한다. 출결 전용 페이지는 예를 들어 `/attendance` 아래 독립 레이아웃을 사용하고, `MainLayout`에서도 해당 경로에 PC 헤더·사이드바를 적용하지 않는다. 경로의 정확한 파일 구성은 계획 단계에서 결정한다.

OIDC 로그인 및 HttpOnly 세션을 재사용한다. 미로그인 진입은 로그인 후 요청한 출결 경로로 복귀한다. 제공 방식은 홈 화면 웹앱(PWA)으로 확정했다. iPhone은 iOS 16.4 이상 홈 화면 웹앱에서 알림 허용이 필요하며, Android는 지원 브라우저의 알림 허용이 필요하다. 아이콘만 추가한다고 푸시가 구현되는 것은 아니며 구독·서비스 워커·서버 발송을 구현하고 실기기에서 검증한다. 네이티브 패키징은 이번 범위에서 제외한다.

## 역할과 접근 권한

- 일반 직원은 직원 역할(admin/master 등 현재 직원 영역의 허용 역할)에 해당하는 계정이며, 출결 대상 여부는 서버에서 확인한다. 일반 고객 계정에 API를 열지 않는다.
- 직원은 본인 상세 기록·요청·첨부·알림 설정만 조회하고 수정할 수 있다. userId는 인증 주체에서 가져온다. 관리자는 별도 근무 현황 API로 다른 직원의 업무 조율용 최소 상태와 당일 휴가 종류를 조회할 수 있다.
- 마스터는 전체 기록/요청을 조회하고 승인·반려·추가 확인을 요청하며 근무지 설정을 관리한다.
- 마스터는 본인 요청도 직접 승인할 수 있다(사용자 확정). 요청자와 승인자가 동일한 경우도 감사 이력에 명시하며 일반 직원에게 승인 권한이 생기지는 않는다.
- UI 숨김 외에 API 역할·소유권 검사를 적용한다. 마스터는 기존 권한 서비스와 가드 규칙을 따르며 프런트가 보내는 역할을 믿지 않는다.
- `file-service`의 현재 비공개 파일은 소유자/마스터 열람을 지원한다. 출결 컨텍스트를 일반 직원 전체 열람 목록에 추가하지 않는다. 출결 도메인도 요청과 파일의 소유권·관계를 검증한다.
- 승인 전 첨부를 소유자가 삭제해 증빙이 사라지지 않도록 제출 후 파일 변경/삭제 정책도 요청 상태와 함께 검사한다. 일반 파일 삭제 API로도 우회할 수 없어야 한다. 이를 위한 컨텍스트별 제한과 도메인 경유 삭제를 계획에 포함한다.

## 출퇴근 처리와 위치 검증

1. 화면에서 본인 이름·근무지·기록 상태를 확인한다. 모바일 전용 화면에서 출퇴근 버튼을 누른다.
2. 클릭 시 소리 재생 컨텍스트를 준비하고 최근 위치를 요청한다. 최초 사용에는 OS/브라우저 권한 요청이 표시될 수 있다.
3. 좌표·정확도·측정 시각과 클라이언트의 요청 식별자를 서버로 전송한다. 기록 시각의 권위는 서버 수신 시각이다.
4. 서버는 활성 직원, 현재 출결 상태, 측정값 형식/범위, 위치 신선도·정확도, 활성 근무지와 거리를 검증한다.
5. 성공 트랜잭션 후에만 성공 표시·완료음과 출결 상태를 갱신한다. 중복 클릭·재시도는 같은 결과를 반환한다.
6. 실패는 원래 상태를 유지하며 권한 거부/시간 초과/정확도 부족/범위 밖/연결 오류를 구분한다. 재시도와 정정/예외 요청을 제공한다.

출근 시 열린 근무 세션을 생성하고 퇴근은 그 세션을 닫는다. 날짜가 바뀌어도 열린 세션을 임의로 자동 퇴근시키지 않는다. 날짜는 Asia/Seoul 기준으로 표시하고 시각은 UTC instant로 저장한다. 열린 세션은 직원별 최대 1개이며 DB 제약으로 동시 출근을 막는다.

확정: 같은 날 퇴근 후 재출근(분할근무)은 1차 범위에서 제외하고, 야간 근무의 자정 이후 퇴근은 허용한다. 일별 기록은 출근일에 귀속한다. 퇴근 완료 상태는 출근일 당일에는 유지하며, 다음 날 새 출근을 허용한다. 자정이 지나도 열려 있는 세션은 자동 퇴근/초기화하지 않는다. 실제 추가 근무로 한 쌍을 벗어나는 경우도 자동 합치지 않고 마스터 확인이 필요한 예외로 취급한다.

근무지에는 이름, 좌표, 허용 반경, 허용 정확도, 활성 상태, 적용 버전을 둔다. 초기 반경은 현장 측정 후 정한다. 경계에서 위치 오차가 큰 값을 무조건 회사 안으로 승인하지 않고 재측정/예외로 넘긴다. 구체적인 보수적 거리 판정식과 신선도 제한은 계획에서 정의하고 테스트한다.

모바일 UA·화면 너비만으로 개인 휴대폰임을 보증하지 않는다. 서버 인증과 위치 검증이 기본이며 좌표 변조·기기 대여를 완전히 막는다고 안내하지 않는다. 더 강한 기기 등록/네이티브 검증이 필요하면 별도 범위로 결정한다.

## 정정과 예외 요청

정정은 누락/시각 오류, 예외는 위치 확인 오류/정확도 부족/근무지 범위 오류/외근 등이다. 실제 방문 위치나 재택을 자동으로 승인하는 수단이 아니다.

입력: 대상 근무일, 대상 세션 또는 미기록 항목, 출근/퇴근 구분, 실제 시각(날짜 포함), 사유 코드, 상세 사유, 첨부 fileId 목록. 야간 퇴근은 다음 날짜를 명시할 수 있게 해 현재 시안의 날짜+시각 입력을 보완한다. 상세 사유는 공백만 허용하지 않으며 줄바꿈을 보존하고 HTML로 해석하지 않는다.

상태:

`pending → approved | rejected | needs_information`

`needs_information → pending` (직원이 보완 제출)

검토 대기 중 직원 취소는 허용하는 설계자 제안이다. 취소된 요청은 반영되지 않는다. 검토 중 본문/첨부는 바로 수정하지 않고 보완 요청 또는 취소·재요청으로 처리한다. 재제출마다 버전을 올리고 예전 AI 결과와 결정은 덮어쓰지 않는다.

마스터 화면은 원래 기록, 요청 날짜·시각, 상세 사유, 첨부, AI 의견, 과거 처리 이력을 함께 보여준다. 승인/반려/추가 확인 시 담당자와 시각을 기록하고, 반려·추가 확인 사유는 필수로 한다. 직원에게는 담당자가 확정한 답변만 표시하고 AI 내부 의견은 노출하지 않는 설계 제안이다.

승인 시 같은 트랜잭션에서 요청의 현재 버전·상태와 대상 기록 버전을 검사하고 출결의 유효 기록을 반영하며 감사 이력을 추가한다. 두 마스터의 동시 결정은 하나만 성공한다. 검토 중 원래 기록이 달라졌다면 자동 덮어쓰기 대신 다시 확인하도록 한다. 승인 후 바꾸려면 새 정정 요청을 생성한다.

요청만으로 출결을 수정하지 않는다. 원본 이벤트와 실제 적용된 수정 이력을 함께 남긴다. 특정 요청에서 출근·퇴근을 모두 바꿔야 하면 별도 항목 2개를 한 요청에서 다루는지, 각각 요청하는지는 빌더가 UI 복잡도와 트랜잭션 경계를 고려해 결정할 수 있다.

## 첨부와 AI

첨부 목록은 없음일 때 `[]`로 정규화한다. 최대 3장·장당 10MB·JPG/PNG/WEBP를 초기 제안으로 한다. MIME·실제 파일 형식·크기를 서버에서 검증하고 기존 presign → 직접 업로드 → confirm 흐름을 재사용한다. HEIC는 지원 여부를 감지해 안내하고 잘못된 형식이 요청 본문 제출까지 막지 않도록 개별 첨부 오류로 표시한다.

`attendance-request-image` 같은 비공개 전용 컨텍스트를 등록한다. 본문에 외부 이미지 URL을 직접 저장하지 않고 fileId만 연결한다. 비공개 열람 URL은 짧은 수명으로 발급하고 브라우저 캐시·로그에 원본 이미지나 좌표가 불필요하게 남지 않게 한다. 파일 참조와 삭제 책임은 ADR-0009대로 출결 도메인에 둔다. 첨부 보관/파기 기간은 운영 결정 후 적용한다.

얼굴과 배경 촬영 예시는 참고 안내이며 필수 인증이나 얼굴 인식으로 사용하지 않는다. 생성 이미지는 가상 인물 예시라는 표시를 유지한다. 업로드에 타인·고객 정보가 담기지 않도록 안내한다.

AI는 제출 버전 기준 비동기 작업으로 실행한다. 사유·기존 기록·요청 시각·허용된 첨부만 전달하고 비밀번호·원시 위치 좌표·다른 직원 정보는 전달하지 않는다. 이미지의 외모·민감 속성·얼굴 동일인 여부를 평가하지 않는다. 문서나 이미지 속 지시는 데이터로 취급하고 도구 실행이나 정책 변경의 지시로 따르지 않는다.

출력은 구조화된 요청 요약, 확인 가능한 내용, 불일치/부족 정보, 추가 질문, `reviewable / needs_information / undetermined` 의견이다. 범죄·허위·부정출근 확정이나 자동 승인·반려를 수행하지 않는다. 근거 없는 출근 시각·위치 추정도 하지 않는다.

AI 작업에는 queued/running/succeeded/failed 상태, 시도 횟수, 입력 버전/해시, 모델·프롬프트 버전, 결과, 생성 시각을 둔다. 결과가 도착하기 전에 요청이 변경/처리됐다면 기존 결정과 기록을 변경하지 않는다. AI 실패 시에도 마스터는 수동 검토할 수 있다. 첨부가 없으면 사유·기록만으로 요약하며 미첨부 자체를 불이익 근거로 쓰지 않는다. 실제 모델/제공자 및 승인된 이미지 처리 설정은 계획 단계에서 기존 AI 어댑터를 조사해 선택하고 운영 설정으로 관리한다.

## 내부 출결·휴가 캘린더

1차는 관리자 공통 공유 근태 캘린더다. 월별 날짜 선택과 선택 날짜의 전체 직원 휴가·반차 목록, 본인 휴가/반차 등록으로 구성한다. 모든 관리자(admin·master)가 직원 이름과 휴가 유형·날짜·예정 시각을 조회하되 등록·수정·삭제는 본인 일정만 할 수 있다. 상세 출퇴근 원장은 본인/마스터만 조회한다. 타임트리의 회의·행사·댓글·채팅 기능은 만들지 않는다.

경리나라가 휴가 승인 절차를 담당한다.
어드민에서는 직원이 본인 승인 휴가를 직접 등록·수정·삭제하고 작성자·변경 이력을 남긴다.
내부 신청·승인 상태나 마스터 재승인 절차를 추가하지 않는다.
경리나라 승인 사실을 API로 자동 검증·동기화하지 않는다.
등록창에는 ‘경리나라 승인 후 등록’ 안내를 표시한다.
공유 캘린더 하단의 승인·본인 일정 수정 및 삭제 안내 문구는 표시하지 않는다.
월간 캘린더는 타임트리를 참고해 날짜 칸을 연결한 격자와 이름·휴가 유형이 있는 색상 막대로 표시한다.
종일 휴가·오전 반차·오후 반차는 초록·노랑·파랑으로 구분하되 유형 문구도 함께 제공한다.
PC에서는 오른쪽에 선택 날짜의 상세 목록을 표시하고 모바일에서는 달력 아래에 표시한다.
한 날짜에 세 명까지 표시하고 초과 인원은 더 보기 문구로 안내하며 날짜 선택 시 전체 목록을 표시한다.
독립 출결 페이지의 PC 캘린더는 넓은 화면을 활용하도록 최대 너비를 늘린다.

입력은 본인 이름(인증 계정으로 고정), 시작일·종료일, 날짜별 종일/오전 반차/오후 반차, 반차인 날 출근·퇴근 예정이다. 같은 기간 안에 종류를 섞을 수 있다. 날짜별 제외 버튼과 제외 날짜 다시 추가를 제공한다. 전체 제외 시 등록을 비활성화한다. 등록 일수는 종일 1일, 반차 0.5일로 합산한다. 사용자 예시의 ‘정중식 1.5’, ‘정중식 2’는 이름과 등록 휴가 일수이며 시각이 아니다. 연차 잔여 차감 장부로 사용하지 않는다.

개인별 평소 근무 시간표를 예정값 계산의 기준으로 둔다. 초기 UI는 평소 출근 시각을 직원이 설정하고 기본 퇴근은 9시간 뒤로 채우는 방식을 설계자의 선택으로 제안한다. 이는 개인 리마인더 시각과 구분해 저장하며 알림 설정 변경으로 평소 시간표가 바뀌지 않게 한다. 기존에 권위 있는 직원 시간표가 있다면 중복 설정 없이 그 소스를 재사용하는 것은 빌더에게 위임한다.

오전 반차는 평소 출근 시각 +4시간을 출근 예정 기본값으로, 평소 퇴근 시각을 퇴근 예정 기본값으로 채운다. 확정된 예: 09~18시 → 13~18시, 10~19시 → 14~19시. 출근 예정을 수정해도 퇴근 예정은 평소 퇴근 시각을 유지한다. 직접 수정한 퇴근 예정은 덮어쓰지 않고 ‘자동 계산으로’ 복원을 제공한다. 실제 출근이 빨라지거나 늦어졌다는 이유로 퇴근 알림을 자동 이동시키지 않는다. 앞서 제안한 실제 출근+4시간30분 방식은 확정 정책에서 제외한다.

오후 반차는 평소 출근 시각을 출근 예정 기본값으로 채우고 퇴근 예정은 직원이 직접 지정하도록 둔다(추가 자동 계산 규칙이 확정되기 전 최소 동작으로 설계자가 선택). 오전/오후 명칭은 쉬는 시간을 뜻한다. 오전 반차는 오후 근무, 오후 반차는 오전 근무다. 사용자의 예시 발언에 용어 혼동이 있어 잘못된 반대 차단 규칙은 확정하지 않는다.

현재 확정한 검증은 필수값·유효 날짜·시각·종료일≥시작일·하나 이상 날짜·동일 직원/날짜 휴가 중복 금지·퇴근 예정>출근 예정이다. 잘못된 값은 서버와 폼에서 차단하며 입력란 바로 아래에 원인과 수정 방법을 표시하고 첫 오류로 포커스를 옮긴다. 입력 도중 바로 등록 오류 모달을 띄우지 않는다. 13시 고정/이후 허용 여부 및 반차별 허용 시각 구간은 사용자가 보류하기로 했으므로 임의로 정해 차단하지 않는다. 이 한계는 구현 계획에도 명시한다. 당일 반차 예정 시각은 같은 날짜 안에서 입력하며 실제 야간 출퇴근 및 정정은 별도로 날짜를 명시해 지원한다.

종일 휴가는 예정 시각 입력을 숨기고 해당 날짜 출퇴근 리마인더를 생략한다. 반차는 저장된 당일 예정 시각을 알림에 사용한다. 예정 시각은 출근 버튼을 막거나 실제 출결을 자동 생성·수정하지 않는다. 휴가일에 실제 근무한 기록이 있어도 삭제하지 않는다. 급여·법정 근로 및 휴게 충족 판정은 이 계산의 역할이 아니다.

기록이 충분히 쌓인 뒤 개인·반차 유형별 과거 ‘예정 시각’의 일관된 경향을 추천한다. 실제 지각 기록으로 기본값을 조용히 바꾸지 않는다. 최소 표본 수·산포 제한·중앙값 등은 빌더가 테스트 가능한 기준으로 정하며, 추천은 직원이 눌러 적용한 뒤 수정할 수 있다. 오전 반차의 퇴근 추천도 확정된 평소 퇴근 유지 원칙을 따르고 과거의 잘못된 퇴근 예정으로 덮어쓰지 않는다.

날짜별 종류 선택은 모바일에서 화면 밖으로 펼쳐지는 네이티브 셀렉트 대신 세 개의 인라인 선택 버튼으로 둔다. 등록창 헤더·하단 등록 버튼을 고정하고 본문만 스크롤한다. 중첩 모달이 열려 있으면 배경 스크롤을 계속 잠그며 마지막 창이 닫힐 때 원래 위치로 복원한다. ‘계산 기준’ 펼침 영역과 중복 안내 문구는 제거한다.

저장 모델은 출결 원장과 직원 등록 휴가를 구분한다. 캘린더는 이를 합쳐 보여주는 조회 화면이며 출결 이벤트를 범용 일정으로 복제하지 않는다. 미래의 일반 일정 기능을 위해 현재 범위에 초대·반복 엔진을 만들지 않는다. 일정 변경·삭제 시 미래 알림을 다시 평가하고 발송 직전 최신 버전을 확인한다. 이미 지난 알림은 소급 발송하지 않는다.

## 직원 근무 현황 (추가 범위·상세 흐름 설계 전)

사용자 확정: 업무 조율을 위해 현재 업무 중인 사람, 퇴근한 사람, 휴가·반차인 사람을 볼 수 있는 별도 페이지를 제공하며 모든 관리자(admin·master)가 조회한다. 캘린더도 관리자 공통 공유 화면이며, 현황 화면은 현재 상태를 빠르게 확인하는 용도로 구분한다. 마스터의 전체 상세 기록·정정 승인 화면과도 별개다.

이하 UI와 조회 방식은 설계자의 제안이며 아직 화면 승인을 받지 않았다. 기본은 오늘 현황이며 이름·소속 검색, 근무 중/출근 전/퇴근/휴가·반차 필터, 요약 인원수를 둔다. 기존 기록에 근거한 ‘근무 중’(열린 출근 세션), ‘퇴근’(종료된 세션), ‘출근 전’(당일 기록 없음)을 표시하고, 당일 일정의 ‘종일 휴가/오전 반차/오후 반차’는 별도 배지로 함께 표시한다. 오전 반차 뒤 출근한 사람은 ‘근무 중 · 오전 반차’처럼 보이게 한다. 휴가와 실제 기록이 함께 있으면 어느 하나를 숨기지 않는다. 기록 없음만으로 결근·지각을 판정하지 않는다. 지속 위치 추적을 추가하지 않는다.

관리자 공통 응답에는 직원 식별/이름/소속, 출퇴근 상태, 당일 휴가 종류, 필요한 예정 시각, 마지막 갱신 시각 등 최소 정보를 둔다. 상세 사유·첨부·위치·AI 의견·과거 출퇴근 원장은 이 응답에 넣지 않는다. 원본 출퇴근 시각 자체를 일반 관리자 목록에 표시할지는 상세 UI에서 확인하고, 현재는 현황 조회 권한을 근거로 과거 원장 전체를 개방하지 않는다. 수정·승인 권한도 함께 부여하지 않는다.

초기 구현은 조회 주기와 포커스 복귀 시 재조회로 갱신하는 것을 설계자 제안으로 둔다. 화면에 마지막 갱신 시각과 새로고침을 제공한다. 실제 갱신 주기·다중 세션 및 날짜 경계 표시·직원 목록 포함 기준·배치 위치는 다음 전체 흐름/코드 설계에서 구체화한다. 상태 집계와 휴가 결합은 서버가 처리하고 클라이언트가 직원별 상세 API를 순회하지 않는다.

## 알림과 리마인더

개인 설정: 출근 알림 on/off·시각, 퇴근 알림 on/off·시각, 알림 요일, 시간대(초기 Asia/Seoul), 완료음 on/off. 초기 리마인더는 꺼짐으로 제안하며 직원이 선택한 뒤 알림 권한을 요청한다. 푸시 권한은 브라우저/OS가 관리하고 서버 설정과 별도로 표시한다.

리마인더는 서버 스케줄러가 발생시킨다. 웹페이지를 열어둔 타이머에 의존하지 않는다. 같은 직원·날짜·알림 종류에 대해 중복 발송하지 않고, 발송 직전 출결·승인된 휴가 일정·최신 개인 설정을 다시 확인한다. 이미 출근/퇴근했거나 요일에서 제외되면 생략한다. 설정 변경 후 지난 시각의 알림을 소급 발송하지 않는다.

종일 근무는 개인이 설정한 평소 알림 시각을 사용하며, 반차가 등록된 날은 저장된 당일 출근·퇴근 예정을 우선한다. 당일 알림만 끄기는 다음 날 평소 설정으로 복귀한다. 출근 후 경과시간 모드는 이번 확정 범위에 추가하지 않는다. 오전 반차의 알림도 실제 출근+4시간30분으로 이동하지 않는다. 설정 화면에는 평소 시각과 오늘 적용 시각을 구분해 표시한다.

휴가 승인은 경리나라, 본인 출결·휴가 일정은 내부 캘린더로 둔다. 회의·행사는 당분간 타임트리를 사용한다. TimeTree의 종료된 Connect API나 공식적으로 지원되지 않는 외부 자동 반영을 전제로 동기화 기능을 설계하지 않는다.

알림용 하루는 설정된 요일과 현지 시각 기준이다. 자정 전후 출퇴근 알림의 짝은 리마인더 설정에서 다음날 퇴근을 명시하거나 열린 세션을 기준으로 해석하도록 UI·서버 계약을 정한다. 리마인더가 실제 근무 일정의 권위가 되지 않게 한다.

직원 알림: 승인·반려·추가 확인. 마스터 알림: 새 요청. 결과는 페이지 내 상태에도 남겨 푸시 미수신이 결과 누락으로 이어지지 않게 한다. 잠금화면 문구에는 상세 사유·얼굴 사진·좌표를 넣지 않고 요청 상세 링크만 제공한다.

구독은 인증 주체+기기별로 등록하며 타인의 userId로 등록할 수 없다. 만료/폐기 구독은 정리한다. 로그아웃·계정 전환 시 기존 수신 대상과 구독의 연결을 해제하고 재로그인 후 현재 계정으로 다시 바인딩한다. 알림 클릭 시 서버가 현재 사용자 접근 권한을 재검증한다. 푸시 지연과 OS 알림 설정에 따라 정확한 수신 시각은 보장하지 않는다.

## 데이터와 API 경계

개념 모델(정확한 스키마 명칭은 빌더에게 위임):

- 근무지 및 판정 정책 버전.
- 근무 세션: 직원, 시작/종료 instant, 출근일, 현재 유효 기록, 버전.
- 변경 불가 출결 이벤트: 원본 서버 기록, 위치 검증 결과와 정책 버전, 요청 식별자.
- 정정/예외 요청과 버전, 상세 사유, 대상 기록 버전, 상태.
- 요청-첨부 연결: 제출 버전별 fileId.
- 검토 결정/변경 이력: 요청 버전, 담당자, 결정, 사유, 수정 전/후 값.
- AI 작업과 결과.
- 직원 등록 휴가/반차 일정과 날짜별 예정 시각·버전·변경 이력, 개인 평소 시간표. 캘린더 조회는 출결 세션과 휴가의 합성 결과다.
- 개인 리마인더·완료음 설정, 알림 발생/중복 방지 키.
- notification 서비스의 웹 푸시 구독/발송 결과.

자기 조회 API와 관리 API를 나눈다. 자기 API는 상태/기록/출퇴근/요청/보완/취소/설정, 관리 API는 전체 목록/상세/결정/근무지 설정이다. 푸시 구독 등록·해제는 notification API에 둔다. 사용자 원시 좌표와 첨부는 일반 직원 전체 조회 API에 포함하지 않는다.

검토 결정, 출퇴근 기록, 알림 이벤트는 outbox와 도메인 트랜잭션을 묶고 기존 이벤트 계약 등록 규칙을 따른다. 소비자는 멱등성을 갖춘다. 구체적 REST 경로·DTO·인덱스·이벤트 이름은 구현 계획에서 작성한다. 공개 사용자 역할을 확대하거나 기존 API 동작을 바꾸지 않는다.

## 검증과 출시

핵심 검증: 위치 경계/정확도/오래된 측정값, 중복 클릭·동시 출근, 자정 이후 퇴근, 계정별 소유권, 일반 직원의 승인 차단, 마스터 동시 승인 충돌, 원본 버전 충돌, 파일 삭제/열람 우회, 미첨부·업로드 실패, 줄바꿈 보존, AI 지연/실패/오래된 결과, 알림 중복·설정 변경·로그아웃/계정 전환.

프런트는 현재 시안의 PC/모바일 레이아웃, 본문 스크롤·고정 헤더/푸터, 키보드/포커스, 위치 권한 거부, 소리 비활성화를 확인한다. iPhone 홈 화면 웹앱과 Android 실기기에서 위치·설치·푸시·배너 클릭 복귀를 확인한다. 서버 Jest는 저장소 지침에 따라 `--runInBand`로 순차 실행한다.

출시 순서 제안: DB·설정/API → 개인 기록/모바일 위치 → 정정·첨부·마스터 검토 → 내부 캘린더·휴가/반차 → AI 보조 → 웹 푸시·일정 기반 리마인더 → 실기기 파일럿. 이는 출시를 잘게 나누기 위한 제안이며 본 요청의 최종 범위에서 AI나 알림을 제외한다는 뜻이 아니다.

## 보류한 세부 규칙과 배포 전 설정

- 반차 출근 시각을 정확히 고정할지, 일정 구간 안에서 변경을 허용할지는 사용자 결정 보류다. 현재는 시간 순서 검증까지 적용하고 엄격한 반차 구간 차단은 넣지 않는다.
- 오후 반차의 퇴근 자동 계산은 미확정이다. 기본 출근+직접 퇴근 예정 입력으로 계획해 오전 반차 정책을 잘못 확장하지 않는다.
- 개인 평소 시간표 입력 방식, 추천 표본 수, 미제출 요청 취소, 파일 제한은 위에서 설계자의 선택/제안으로 표시했다.
- 원시 위치·첨부의 보관/파기 기간과 실제 근무지 좌표·반경·정확도는 배포 전 운영자가 입력해야 하는 설정이다. 값을 추정해 운영에 배포하지 않는다. 구체 기간 없이도 구현 계획은 작성할 수 있다.

최신 미리보기는 `.superpowers/brainstorm/19405-1792122713/content/attendance-halfday-clean-v22.html`이다. 시안은 디자인 참고용이며 본 문서의 확정 규칙이 우선한다. 시안에 남아 있는 오후 반차 자동 계산 등 미확정 동작을 제품 코드로 그대로 옮기지 않는다.
