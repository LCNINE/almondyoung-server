A와 B가 초기 스테이션 입고·이동·실사의 운영 범위다. C는 앞선 점검에서 확인된 출고 위치 위험을 해결하는 별도 변경이다. 각 PR의 통과와 전면 운영 합격을 구분한다. 문서는 구현 계획이며 제품 수정·테스트 통과 기록이 아니다.

## 사용자 흐름

### 홈

Windows 홈에 `재고조회 / 입고 / 적치 / 이동 / 실사 / 출고작업 / 입고내역 / 설정`을 제공한다. 입고내역은 B에서 추가한다. OS에 따른 화면 선택은 유지하며, 프로필 전환 기능은 추가하지 않는다. 기존 핸드헬드 기능을 유지한다. 미구현 `/shipments`의 출고조회 타일은 초기 스테이션 홈에서 노출하지 않는다. 기존 경로의 제거·이름 변경은 하지 않는다.

### 입고

- 발주입고: 발주 선택 → 품목 선택 → 실제 받은 낱개 수량 입력 → 등록. 현재 발주 수령 API로 발주 잔량과 실입고를 함께 반영한다.
- 간편입고: 상품명·코드 검색 또는 스캔 → 실제 받은 낱개 수량 입력 → 등록. 발주가 없는 직접 입고다. 발주 물건을 이 경로로 대신 입력하도록 안내하지 않는다.
- 검색 선택은 1개를 초기 제안한다. 같은 상품 재선택으로 수량을 몰래 증가시키지 않고 해당 행을 편집한다. 바코드 스캔은 기존 포장 단위와 접수 순서를 유지한다.
- 간편입고와 발주입고는 기존 입고기본존 등록 후 적치 모델을 유지한다. 입고는 끝내고 적치는 나중에 처리할 수 있다. 입고등록과 적치를 하나의 트랜잭션처럼 표시하지 않는다.
- 입고/검수 명칭을 스테이션 진입에서 `입고`로 표현하고, 전수 검수 없이 실제 받은 수량을 기록한다는 설명을 붙인다.

### 적치·이동

실제 보관 위치의 코드/이름을 검색해 선택하고 낱개 수량을 입력한다. 스테이션을 선반으로 들고 갈 필요 없이 현장에서 확인한 위치를 PC에서 기록할 수 있다. 출발과 도착 위치, 수량이 확정 화면에 명확히 나타나야 한다. 이동은 기존 동일 창고·ON_HAND 재고 범위다. 불량재고나 창고 간 이동으로 확대하지 않는다.

### 실사

실사 생성 → 위치 검색 또는 코드 입력 → 기존 품목별 실물 총수량 입력 → 목록에 없는 SKU는 상품 검색으로 추가 → 차이 검토 → 확정. 0은 실제 0개, 미입력은 미실사로 유지한다. 추가 SKU에는 바코드 등록을 요구하지 않는다. 동일 SKU/위치가 이미 추가되어 있으면 최신 행을 다시 읽어 편집한다. 과거 조회를 바탕으로 기존 카운트를 덮어쓰지 않는다.

### 기록과 취소

입고내역은 선택 창고·서울 날짜·상품·입고 방식으로 조회하고 취소된 입고도 확인할 수 있어야 한다. 입고 행의 직접/발주 출처에 맞는 기존 취소 API를 사용한다. 같은 날, 전량, 미적치·미회송 등의 서버 제약을 유지한다. 취소가 안 되는 상태에서 재고조정으로 자동 대체하지 않는다. 등록 수량을 바로 수정하는 기능은 만들지 않는다. 취소 성공을 확인한 뒤 정정 입고를 새 작업으로 등록한다.

### 출고 위치

배정 출발 위치를 작업자에게 보여주고 실제 집은 위치를 선택/스캔해야 한다. 같은 SKU라도 지정 위치의 잔량만 피킹한다. 다른 위치로 자동 분배하지 않는다. 잘못된 창고·위치·초과 수량은 재고 변경 없이 거절한다. 스캔 생략 시에도 위치별 실물 확인은 생략하지 않는다.

## Global Constraints

- 초기 운영 대상은 Windows 스테이션이며 핸드헬드 사용을 전제하지 않는다.
- 모든 수량은 낱개 정수다. 입고·적치·이동은 1 이상, 실사 총수량은 0 이상이다.
- 발주입고와 간편입고의 출처 및 발주 잔량 처리를 유지한다.
- 입고는 기존 입고기본존 등록 후 적치 모델을 유지한다.
- 재고 변경은 기존 영속 작업 실행기, 원래 요청 본문과 키, 계정/API 범위, 서버 권한 검증을 사용한다.
- 저장 실패·결과 미확인 중 새 확정·편집·의미가 바뀌는 화면 이동을 차단한다.
- 검색은 재고를 변경하지 않는다. 이전 검색의 결과를 새 선택에 사용하지 않는다.
- 일반 화면에는 필요한 행동 안내만 표시한다. 요청·응답·키 등 기술 정보는 권한이 있는 개발자 모드에만 표시한다.
- 기존 출고·입고·실사 미확인 작업의 경로·본문·키를 새 계약으로 바꾸어 재전송하지 않는다.
- 서버의 기존 API 기본 동작을 호환 유지하고 새 계약은 서버부터 배포한다.
- 테스트 데이터 변경은 별도의 로컬 DB에서만 수행한다. 운영 데이터와 기존 테스트 DB를 초기화하지 않는다.
- 실제 Windows 설치·로그인·HID 스캔·장애 복구 검증을 모의 테스트 통과로 대체하지 않는다.

## 입력 장치와 중복 방지

PC 키보드 입력과 HID 스캐너가 같은 keydown 이벤트를 사용한다. 검색창·숫자 입력에서 Enter를 눌렀을 때 전역 스캔과 폼 제출이 동시에 재고 입력을 만들면 안 된다. 업무 폼 내부의 텍스트 편집은 명시적 제출만 사용하고 전역 스캔 처리를 억제한다. 스캐너 입력은 검색/스캔용 필드 또는 일반 작업 화면에서 기존 경로로 처리한다. 등록 버튼은 Enter를 자동 확정으로 받지 않는다. 스캐너와 수량 입력의 포커스 전환을 시험한다.

## 검증 시나리오

1. Windows에서 메뉴만 사용해 모든 목표 화면에 진입한다.
2. 스캐너 없이 2종 상품을 각각 10·3개 직접 입고 → 기본존 증가 → 일부 적치 → 잔여량 확인.
3. 발주 10개 중 4개 수령 → 발주 잔량 6개. 같은 요청 재확인에도 4개만 입고.
4. A에서 B로 3개 이동 → A −3/B +3, 창고 총수량 불변.
5. 실사 기존 SKU 0개·신규 발견 SKU 2개 → 완료 전 재고 불변 → 차이 검토 후 정확히 한 번 반영.
6. 같은 요청 응답 유실 후 재개, 저장 실패 후 복구, 다른 계정 로그인에서 중복/잘못된 전송 없음.
7. 당일 미적치 입고 전량 취소 → 원장 역분개 1회 → 취소된 입고가 이력에 남음.
8. 같은 SKU가 A/B에 있을 때 B 선택 출고가 A 수량을 건드리지 않음. A 전용 배정이면 B 선택 거절.
9. 두 작업자의 동일 실사 행·출고 박스 충돌을 검출하고 최신 내역을 다시 확인하도록 안내.

## 범위 제외 및 운영 조건

발주 생성, 신규 SKU/바코드 마스터 등록, 송장 발급·인쇄, 반품·회송 프로세스 확대, CSV 일괄 업로드, 자동 업데이트는 이번 구현에 추가하지 않는다. 이 준비 작업은 기존 관리자 도구/운영 절차를 사용한다. 출고 이력 전체 화면은 별도 기능이며 미구현 링크를 초기 홈에 노출하지 않는다.

A/B만 완료했을 때는 입고·적치·이동·실사 시험 운영의 소프트웨어 조건을 충족한 것으로 판단한다. 출고를 포함한 전체 운영 판정은 C와 실제 장비·실물 대사까지 확인한다.
