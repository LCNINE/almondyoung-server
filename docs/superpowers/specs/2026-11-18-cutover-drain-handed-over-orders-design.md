# 드레인 중 셀메이트에 넘긴 주문을 앱 출고 경로에서 뗀다 (#1412)

상위: #1233 (컷오버 1단계) · 축 3 출고 · 컷오버 당일

## 왜

시각 T 에 셀메이트가 들고 있던 자사몰 미발송 주문은 셀메이트가 끝까지 내보낸다(드레인). 그동안 그 주문들의 core 상자는
`draft`·`planned` 로 열려 있다. #1243 은 드레인이 끝난 뒤 판매주문 상태를 보고 이 상자들을 닫는다.

출고 준비 리더(`apps/core/src/modules/fulfillment/outbound-preparation/outbound-preparation.reader.ts`)는 창고의
`draft`·`planned` 상자를 전부 오래된 순으로 보여 준다. 화면(`OutboundPreparationTemplate.tsx` 의 `selectedIds`)은 아무것도 체크하지 않으면
그 분류에서 **앞쪽 100건**을 잡는다. 그래서 드레인 중에는 버튼 한 번에 셀메이트 주문이 먼저 잡혀 **이중 출고**가 난다.
런북만으로는 막을 수 없다.

## 목표 · 비목표

- 목표: 드레인 동안 셀메이트가 맡은 주문 줄이 앱 출고 경로(출고 준비 목록·합포장 후보·계획 확정)로 나가지 않는다.
- 비목표: 넘긴 주문을 앱이 넘겨받는 길은 만들지 않는다. 사용자 판단으로는 드레인이 일주일 안에 끝난다(고객이 몇 주를 기다리지 않는다).
  그래서 셀메이트가 끝까지 내보낸다(아래 «결정» A).
- 비목표: admin-web 은 고치지 않고 화면 문구도 더하지 않는다.
- 반목표: 교환품처럼 앱이 맡아야 할 출고가 드레인 끝까지 묶이면, 동작은 해도 실패다.

## 경계 — 이미 정한 것

**«셀메이트에 넘긴 주문» 집합으로 가르고, 시각으로 자르지 않는다**(사용자 결정 2026-11-17, `2026-11-17-sellmate-evening-reconcile-design.md`).
이 집합은 T 에 `evening-reconcile init` 이 `sellmate_handed_over_orders(sales_order_id …)` 에 한 번 저장한다. 시각으로 자르면
마지막 수집과 T 사이에 들어온 주문이 어느 쪽에도 없게 된다. 이 표는 #1354 마이그레이션으로 라이브에 이미 있다.

## 결정

- **드레인 끝에 오래 남는 주문: A — 셀메이트가 끝까지 내보낸다**(사용자, 2026-11-18). 드레인은 일주일 안에 끝난다.
  만들지 않은 B 는 «며칠 뒤 앱이 넘겨받기»다. 그러려면 셀메이트 취소, 집합에서 빼기, core 재고 되돌리기가 필요하고 #1304 설계도 고쳐야 한다.

## 방식 (Approaches)

| 방식 | 판정 |
|---|---|
| 런북만 (화면에 표시하고 사람이 고르지 않는다) | ✗ 기본 선택이 앞쪽 100건이라 버튼 한 번에 셀메이트 주문이 잡힌다 |
| 계획 확정만 거절 | ✗ 기본 선택 100건이 전부 거절돼 버튼을 못 쓴다 |
| 목록에서만 뺀다 | ✗ 계획 API(`shipment-planning.controller.ts`)로 확정하는 길이 남는다 |
| **목록·합포장 후보에서 빼고 + 계획 확정에서 거절** | ✓ 선택 (사용자 승인 2026-11-18) |

`draft → planned` 로 가는 길은 `ShipmentPlanningService.plan()` 하나뿐이다(`shipment-transitions.ts` 의 전이, `to: 'planned'` 를
쓰는 곳은 거기 하나). 출고 준비 화면도 계획 API 도 이 함수를 부른다. 그래서 거절은 여기 한 군데에 둔다.

## 설계

**«셀메이트 줄»:** 상자 라인 → FOI → `sales_order_lines` 로 거슬러 갔을 때 판매주문이 `sellmate_handed_over_orders` 에 있고
`exchange_return_line_id IS NULL` 인 줄.
- 교환품 줄은 같은 판매주문에 붙는다. 판매주문 단위로 막으면 드레인 동안 생긴 교환품이 묶인다. 그래서 줄 단위로 막는다.
  #1243 이 교환품을 app-work 로 보는 것과 같은 판단이다.
- 입점사 상자(`supplier_id IS NOT NULL`)는 출고 준비 목록에 원래 없으므로 건드리지 않는다.
- 셀메이트 줄이 하나라도 든 상자를 «셀메이트 상자»라고 부른다.

**바꿀 곳 (core 만):**
1. 출고 준비 리더 `summarize` — 셀메이트 상자를 분류 전에 뺀다. 개수에도 넣지 않는다.
2. 합포장 후보(`ConsolidationBoardReader.findBoard`) — 셀메이트 상자를 후보에서 뺀다. 안 빼면 같은 고객의 T 뒤 주문과 «합칠 수 있어요»로 뜬다.
   출고 준비 리더도 이 함수로 `mergeable` 을 가른다.
3. `ShipmentPlanningService.plan()` — 셀메이트 상자면 `ConflictError('SHIPMENT_HANDED_OVER_TO_SELLMATE: <id>')` 로 거절한다(409).
   잠근 뒤, 상태를 바꾸기 전에 판정한다.
4. 배치 합류 판정(`OutboundBatchOrchestrator.assertJoinableBox`) — 같은 코드로 거절한다(최종 리뷰에서 더함). T 에 이미 `planned` 인
   셀메이트 상자가 배치 후보·추가·합류로 나가는 길을 막는다. 배치 후보 목록은 이 거절을 조용히 건너뛰므로 목록에서도 빠진다.

판정 쿼리는 한 곳에 두고 셋이 같이 쓴다. 상자 id 목록을 받아 셀메이트 상자 집합을 돌려준다. 표가 비어 있으면(init 전·다른 테넌트) 빈 집합이다.

**범위·배포:** 마이그레이션 없음, core 만. T 전에 배포 한 번. 다른 테넌트에는 표가 비어 있으니 동작이 바뀌지 않는다.

**수명:** 드레인이 끝나 #1243 이 그 상자들을 닫으면 셀메이트 상자는 0건이 되고, 장치는 할 일이 없어진다. 코드는 2단계 정리 때 뺀다.

## 런북 #1251 에 더할 것

- 출고 준비 화면은 `evening-reconcile init --apply` 가 끝난 뒤에 연다. init 전에는 표가 비어 있어 아무것도 가려지지 않는다.
- init 직후 «이미 `planned` 이거나 배치 작업에 든 셀메이트 상자»가 0건인지 센다. 0이 아니면 그 상자를 배치에서 빼고 사람이 본다
  (새 배치 추가·합류는 막지만, 이미 배치 작업에 든 상자는 막지 않는다). 이 SQL 은 교환 상자까지 세어 넉넉히 센다.
  셀메이트 줄과 다른 줄이 섞인 상자 수도 함께 센다 — 그 상자의 앱 주문은 드레인 끝까지 묶인다.

## 빌더에게 남긴 것

- 판정 쿼리를 어디에 둘지(fulfillment 서비스 쪽 reader 하나). DB 접근 규칙은 inventory 규칙(`select().from().innerJoin()`)을 따른다.
- ~~합포장 실행에 거절을 더할지~~ → **더한다**(계획 쓰면서 정함, Claude 판단). 합포장 후보는 보드 말고도
  `consolidation-candidates`·`consolidation-options` 두 경로(상자 상세 화면)가 더 있다. 그래서 세 후보 목록을 다 고치는 대신
  `ConsolidationService.consolidate()` 한 곳에서 같은 코드로 거절한다. 안 막으면 T 뒤 주문과 섞인 상자가 생기고, `plan()` 이 그 상자를 거절해
  T 뒤 주문까지 묶인다. 상세 화면의 후보 목록에는 셀메이트 상자가 뜰 수 있지만, 합치기를 누르면 거절된다.
- 테스트: 리더 통합 스펙(셀메이트 상자 빠짐, 교환품 줄 상자는 남음), `plan()` 거절, 합포장 후보 제외.
