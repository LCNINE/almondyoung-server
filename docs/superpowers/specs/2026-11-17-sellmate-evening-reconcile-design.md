# 셀메이트 저녁 맞추기 (#1304) — 설계

> 상위: #1233(컷오버 지도) · 이슈 #1304.
> 규칙의 정본은 [`2026-11-11-cutover-phase1-core-stock-owner-design.md`](https://github.com/LCNINE/almondyoung-server/blob/docs/cutover-phase1-core-stock-owner/docs/superpowers/specs/2026-11-11-cutover-phase1-core-stock-owner-design.md)
> «저녁 맞추기» 절이다(아래 «정본»). 이 문서는 그 규칙을 **어떻게 만드는지**만 정한다. 정본과 어긋나는 곳은 «정본과 다른 점»에 모았다.
> 코드·데이터에서 도출되는 숫자는 적지 않는다.

## 왜

1단계에서는 core 가 재고 정본이고, 셀메이트는 마켓 주문의 출고·반품·교환만 한다. 두 시스템이 같은 선반에서 따로 재고를 줄인다.
그래서 매일 저녁 두 가지를 한다. 셀메이트 쪽 변화(마켓 주문·취소·반품)는 core 원장으로 가져온다. core 가용은 셀메이트로 돌려보낸다.
셀메이트가 자기 재고 숫자로 마켓에 품절을 보내기 때문이다(#1246). `sync-stock` 은 절대값이라 core 원장을 되돌리므로 T 이후에는 쓰지 않는다.

## 목표 · 비목표 · 반목표

**목표**
- T 당일 저녁 첫 맞추기가 닫기 확인까지 초록이다.
- 같은 입력으로 다시 돌려도 core 원장이 바뀌지 않는다.
- 컷오버 판정(`scripts/ops/cutover-preflight`)이 세 가지를 본다: 기준값이 있는지, 이월 모자람, 짝 못 지은 품목.

**비목표**
- admin-web 화면. 돌리는 사람은 개발자다(사용자 결정).
- 셀메이트 업로드 자동화. 업로드는 사람이 셀메이트 관리자 화면에서 한다.
- 셀메이트 입출고 목록(입력일시)으로 맞추는 동안의 변화를 판별하는 일. 지금은 운영 규칙(맞추는 동안 셀메이트 출고·반품 입고 정지)으로 막고, 필요하면 다음 판에서 한다.
- 위탁(3PL) 화주 옮기기(#1334). 맞추기는 화주와 상관없이 SKU 단위로 맞춘다.

**반목표** (정본과 같다)
- 품목을 **조용히** 건너뛴다.
- 같은 변화를 두 번 반영하거나 놓친다.
- `sync-stock` 이 T 이후 한 번이라도 돈다.

## 정해진 것

### 명령 (`scripts/sellmate/evening-reconcile.ts`, 러너 `run.sh`)

모든 하위 명령은 **dry-run 이 기본**이고, `--apply` 일 때만 쓴다. 표와 요약은 dry-run 과 apply 가 똑같이 찍는다.

| 하위 명령 | 입력 | 쓰는 곳 | 언제 |
|-----------|------|---------|------|
| `pair` | 셀메이트 재고 현황 CSV | 짝 표만(원장 안 건드림) | T 전부터 언제든. 판정의 «짝 못 지은 품목»이 이 결과를 본다 |
| `init --cutover-at=<T> --sellmate-orders=<파일>` | 마지막 `sync-stock` 에 쓴 바로 그 CSV + T 의 셀메이트 미발송 주문 목록 | 짝 표 · 기준값 · 이월 · 넘긴 주문 집합 | T 에 한 번. 두 번째는 거절 |
| `apply` | 지금 받은 CSV | 짝 표 · 원장 · 기준값 후보 · 회차 · 업로드 CSV 파일 | 저녁(바쁜 날은 점심에 한 번 더) |
| `close` | 업로드 뒤 다시 받은 CSV | 회차 · 기준값 확정 | `apply` 뒤 사람이 업로드를 마치면 |
| `status` | 없음 | 없음(읽기 전용) | 열린 회차·이월·짝 못 지은 품목 보기 |

CSV 는 기존 `parse.ts`(`readRows`·`detectColumns`)로 읽는다. 스냅샷 시각은 파일 이름에서 읽는다(`clear-reservations.ts` 의 `parseCutoff` 와 같은 규칙). 시각을 못 읽으면 거절한다.

### 짝 짓기

- 대상은 CSV 의 품목(옵션정보일련번호)이다. `excluded.ts` 에 걸린 품목은 **양방향 모두** 건너뛰고, 짝 못 지은 품목으로 세지 않는다. 대신 사유별 건수는 찍는다.
- 1순위는 `skus.code = 옵션정보일련번호`, 2순위는 셀메이트 바코드로 `sku_barcodes` 에서 찾는다(core 에서 먼저 만든 SKU).
- 바코드는 `formula-barcodes-plan.ts` 의 `unwrapFormula` 로 `="…"` 를 벗긴다.
- **짝 못 지은 품목** — 하나라도 있으면 `apply`·`init` 은 반영 없이 1 로 끝난다.
  - core SKU 를 못 찾았다.
  - 셀메이트 바코드가 비었다(업로드 키가 없다).
  - 같은 바코드가 셀메이트 옵션 둘 이상에 걸렸다.
  - code 로 찾은 SKU 와 바코드로 찾은 SKU 가 다르다.
  - 셀메이트 옵션 둘 이상이 같은 SKU 로 짝지어졌다.
- 업로드 CSV 의 키는 **셀메이트 쪽 바코드**(그 CSV 의 바코드 열)다. 받기 쪽 키는 옵션정보일련번호다.

### 계산 (품목마다, 부천 창고 grain)

기호:
- `S` = 셀메이트 가용 = `현재재고 − 미발송주문수`. 음수도 그대로 쓴다.
- `B` = 기준값 = 직전에 셀메이트에 올린 가용.
- `C` = 이월 모자람(≥ 0).
- `A` = core 가용 = 부천 ON_HAND 합 − confirmed 예약 합. **단 «셀메이트에 넘긴 주문» 집합의 판매주문에 걸린 예약은 빼지 않는다**(정본의 «T 이전 판매주문»을 이 집합으로 정한다 — 아래). 예약 → 상자 라인 → 상자 → 출고주문 → 판매주문으로 거슬러 간다.
- `R` = 뺄 수 있는 여유 = `max(0, 부천 ON_HAND − confirmed 예약 전부)`. T 이전 예약까지 다 뺀 값이라 늘 `A` 이하다. 앱의 예약 불변식(`warehouse-availability.ts` `violatesAvailability`)을 원장 밖에서 깨지 않기 위해서다. 드레인 중에 T 이전 예약 때문에 못 뺀 양은 이월로 가고, 그 예약이 풀리면 갚는다.

`apply`:
1. `net = (S − B) − C`
2. `net ≥ 0` 이면 ADJUST_UP `net`, `C := 0`
3. `net < 0` 이면 `down = min(−net, R)` 만큼 ADJUST_DOWN 하고 `C := −net − down`
4. 반영 뒤 `A'` 를 다시 계산하고, 올릴 가용은 `U = max(0, A' − C)`, 올릴 현재재고는 `U + 미발송주문수(받은 CSV)`
5. `U` 를 이 회차의 **기준값 후보**로 저장한다. `B` 는 `close` 에서 확정된다.

`init` 은 원장을 쓰지 않는다. 마지막 sync 가 이미 넣었기 때문이다. `B := S`(**음수도 그대로**), `C := max(0, −S)`, T 를 저장한다.
- `B` 의 뜻은 «core 가 이미 반영한 셀메이트 가용»이다. 보통은 올린 값과 같고, init 때만 음수일 수 있다.
- `B := max(0, S)` 로 두면 안 된다. 셀메이트는 여전히 `S < 0` 을 보이므로, 변화가 없어도 다음 회에 `S − B` 가 또 `S` 가 되어 이월이 두 배가 된다(빌더 점검에서 찾음).
- **init 은 회차를 닫힌 상태로 만든다.** 셀메이트에 아무것도 올리지 않는다. 첫 `apply` 가 올린다.
- **init 은 한 번뿐이라 입력을 확인한다**(빌더 점검 2차): 짝 지은 품목마다 부천 ON_HAND 가 `max(0, S)`(마지막 sync 가 넣은 값)와 다르면, 그리고 넘긴 자사몰 주문이 0건이면(판매처 이름이 틀린 것과 구별되지 않는다) 목록을 띄우고 거절한다. 확인했으면 `--accept-onhand-mismatch`·`--no-handed-over-orders` 로 넘긴다.

**init 뒤 짝 표가 바뀐 품목 (내 판단)**
- **새로 짝지어진 품목**(T 뒤 셀메이트에 새로 등록, 제외 목록에서 빠짐 등)은 `B := S`, `C := 미발송주문수` 로 시작해 **같은 회에** 위 `apply` 1~5 를 탄다. 그래서 core 가 그 미발송을 여유 `R` 안에서 바로 빼고(남은 것은 이월), 업로드도 그 결과를 올린다. 출력에 «새 품목»으로 띄운다. 왜: 그 품목의 core 재고는 셀메이트 미발송 마켓 주문과 한 번도 상계된 적이 없고, 그 주문이 나갈 때 셀메이트는 현재·미발송이 같이 줄어 `S` 가 그대로라 다음 회 차이로도 영영 안 잡힌다. init 은 마지막 sync 가 이미 상계했으므로 `C := max(0, −S)` 그대로다(빌더 점검 2차에서 고침 — 처음엔 init 처럼 `C := max(0, −S)` 로 두고 원장을 안 썼다).
- **CSV 에서 사라진 품목**(기준값이 있는데 이번 CSV 에 없다)은 짝 못 지은 품목과 같이 다룬다. `apply` 는 반영 없이 1 로 끝난다.
- **다른 SKU 로 다시 짝지어진 품목**도 같다. 사람이 짝 표를 고칠 때까지 막는다. 품목 상태의 키는 sku_id 이고, 짝 표가 옵션정보일련번호 ↔ sku_id 를 1:1 로 지킨다.
- **`excluded.ts` 에 새로 들어간 품목**은 상태를 그대로 얼린다. 나중에 빠지면 새 품목으로 다시 시작한다.

**«셀메이트에 넘긴 주문» 집합 (사용자 결정, 2026-11-17 — 시각으로 자르지 않는다)**
- 왜: `collect-cellmate` 는 시각이 아니라 display_id 와 입금 대기 목록으로 넘긴다. 시각으로 자르면 세 가지 주문이 틀린다. T 에 입금 대기였다가 T 뒤에 입금돼 앱으로 간 주문, 마지막 수집과 T 사이 주문, core 에 늦게 들어온 주문이다. 그 수량만큼 core 가용이 크게 잡혀 셀메이트에 올라가고, 마켓에서 과판매된다.
- 입력: T 에 받은 **셀메이트 미발송 주문 목록**. 당일 순서 1번 «주문이력을 받아 둔다»와 같은 때에 받는다. 자사몰 판매처 행의 주문번호 `YYYYMMDD-display_id` 에서 display_id 를 뽑는다.
- 짝: display_id → Medusa `order.id` → core `sales_orders.channel_order_id`. `mark-core-shipped.js` 와 같은 경로다. Medusa DB 가 하나 더 필요하다. `run.sh` 는 DB 하나만 넣으므로 `MEDUSA_DATABASE_URL` 같은 두 번째 접속을 받는다.
- 하나라도 core 판매주문으로 못 찾으면 `init` 은 반영 없이 1 로 끝난다. 조용히 빠진 주문은 그만큼 두 번 빠진다.
- 집합은 init 때 한 번 저장하고 바꾸지 않는다. 드레인이 끝나 그 주문들의 예약이 풀리면 자연히 효과가 사라진다.

이월은 «재고가 들어오면 먼저 갚는다»(정본)를 위 1~3 이 일반형으로 처리한다. 입고·반품뿐 아니라 예약이 풀려 `R` 이 커질 때도 갚는다.

### 원장 쓰기

- `stock-delta.ts` 의 `applyStockDelta` 를 쓴다. `source = 'sellmate-reconcile'`.
- 잠금은 sync-stock·handover 와 같은 advisory lock 키 `sellmate-stock-sync` 를 쓴다. 한 `apply` 는 한 트랜잭션이다.
- **로케이션 (내 판단):**
  - ADJUST_DOWN 은 지금처럼 수량이 많은 로케이션부터 뺀다.
  - ADJUST_UP 은 그 SKU 의 ON_HAND 가 입고기본존이 아닌 로케이션 **한 곳에만** 있으면 그곳에 넣는다. 아니면 입고기본존에 넣는다.
  - 근거: #1236 뒤 반품을 입고기본존에 넣으면 피킹 안내가 실물과 갈린다.
  - `applyStockDelta` 에 증가 로케이션 인자를 더한다. 기본값은 지금과 같아서 sync·handover 동작은 그대로다.
- 반영 뒤(커밋 후) 원장이 바뀐 SKU 의 sellable 을 다시 계산한다. `recalc-sellable.ts` 와 같은 서비스(`ProductSellableQuantityService`)를 쓴다. `recalc-sellable.ts` 의 reason 필터에도 `sellmate-reconcile` 을 더한다(실패 시 손으로 다시 돌리는 길).

### 회차 · 멱등

- 열린 회차(`awaiting_close`)가 있으면 `apply` 는 거절한다. 닫히지 않은 업로드 위에 차이를 더 쌓으면 기준값이 틀린다.
- 거절하는 경우:
  - 입력 파일 sha256 이 이미 반영한 회차와 같다. 그 회차의 업로드 CSV 경로를 다시 찍고 0 으로 끝난다.
  - 스냅샷 시각이 직전 회차의 **닫기 입력**(init 이면 init 입력)보다 이르다. apply 입력과 비교하면 업로드 전에 받은 CSV 가 통과해 `S − B` 가 틀린다.
- 업로드 CSV 는 `apps/core/tmp/sellmate-reconcile-<회차>-upload.csv` 로 쓴다. 열은 `바코드번호,재고수량` 이고, UTF-8 BOM 여부는 셀메이트 확인에 맞춘다. 값이 지금 `현재재고` 와 같은 품목도 넣는다 — 셀메이트가 같은 값은 적용하지 않는다(이슈 확인 결과).
- `init` 이 있으면 `sync-stock.ts` 는 시작하자마자 거절한다(반목표). 탈출구는 두지 않는다.
- `handover-stock-addback.ts` 도 `init` 이 있으면 거절한다. 그 스크립트는 «마지막 sync 직후 마켓 키 전환»을 전제로 하는데, 두 단계로 나눈 뒤에는 그 사이에 맞추기가 돈다. 쿠팡 주문이 미발송에서 빠지는 순간 맞추기가 `+n` 을 이미 더하므로, 되더하면 두 번 들어간다.
- 반대로 `sellmate-handover` 이벤트가 있으면 맞추기가 거절한다. 2단계에서 마켓이 core 로 넘어갈 때 맞추기를 끝내거나 마켓별로 좁히는 규칙은 #1306 의 몫이다. 이 작업은 두 경로가 섞이지 않게만 막는다.

### 닫기 확인 (`close`) — 정본과 다른 점

정본은 «`셀메이트 가용 = core 가용` 인지 본다»고 한다. 그대로 하면 업로드 뒤 들어온 **정상 마켓 주문**도 어긋남으로 뜬다. 그래서 업로드가 실제로 먹었는지를 `현재재고` 로 보고, 미발송 변화로 원인을 가른다.

품목마다 `Δc = 지금 현재재고 − 올린 현재재고`, `Δu = 지금 미발송 − 받을 때 미발송`.

| 모양 | 뜻 | 판정 |
|------|-----|------|
| `Δc = 0, Δu ≥ 0` | 업로드 반영, 새 마켓 주문이 있었다 | 정상 — 다음 회 차이로 들어간다 |
| `Δc = Δu < 0` | 업로드 뒤 출고 | 정상 |
| `Δc > 0, Δu = 0` | 업로드 뒤 반품 입고 | 정상 — 다음 회 차이로 들어간다 |
| `Δc = 0, Δu < 0` | **업로드 전에 출고**됐다. 덮어쓰기로 셀메이트가 실물보다 많이 본다 | ✗ — 고친 업로드 CSV(`현재재고 = 올린 값 + Δu`)를 만들어 준다 |
| 그 밖 | 업로드가 안 먹었거나 섞였다 | ✗ — 양쪽 숫자를 띄운다 |
| CSV 에서 품목이 사라졌다 | — | ✗ |

- ✗ 가 있으면 닫지 않고 1 로 끝난다. 사람이 고친 CSV 를 올리고 다시 받아 `close` 를 다시 돌린다.
- `Δc = 0, Δu < 0` 은 **apply 때 미발송이던 주문이 업로드 전에 마켓에서 취소된 경우**와 숫자가 같다(빌더 점검 2차). 사람이 셀메이트 주문 목록으로 가른다 — 출고였으면 고친 CSV 를 올리고 다시 받아 닫고, 취소였으면 고친 CSV 를 올리지 않고 `--accept-landed` 로 닫는다(`B := U`, 취소분은 다음 `apply` 가 core 에 더한다).
- **고친 CSV 를 만들 때 그 품목의 비교 기준을 바꿔 저장한다.** `올린 현재재고 := 고친 값`, `기준 미발송 := 이번 닫기 CSV 의 미발송`. 그래야 다시 닫을 때 같은 ✗ 가 되풀이되지 않는다. 회차 품목에 두 값을 칸으로 둔다.
- 자동으로 다시 올리지는 않는다(정본).
- 원인을 알고 그대로 닫을 때는 품목을 지목하되, **업로드가 먹었는지를 사람이 갈라 지목한다.** 그에 따라 `B` 가 다르다.

| 지목 | 사람의 판단 | `B` |
|------|-------------|-----|
| `--accept-landed=<옵션정보일련번호,…>` | 업로드는 먹었고 다른 변화가 섞였다 | `U` |
| `--accept-not-landed=<…>` | 업로드가 안 먹었다 | 이번 apply 의 `S`. core 는 거기까지만 반영했다. 다음 apply 가 다시 올린다 |

- 업로드가 안 먹은 품목에 `B := U` 를 두면, core 쪽 변화(입고·자사몰 예약)의 반대 부호가 다음 회 `S − B` 에 섞여 원장에 다시 들어간다(빌더 점검에서 찾음).
- 정상 품목과 `--accept-landed` 품목은 `B := U` 다. 고친 CSV 를 올린 품목은 고친 값에서 받을 때 미발송을 뺀 값이다.
- 업로드 **전** 반품 입고는 덮어쓰기로 사라지고 위 표로도 안 잡힌다. 이 구멍은 운영 규칙이 막는다(정본 «지켜야 할 것»).

### 저장 (core 마이그 — `inventory.schema.ts`)

이름과 정확한 칸은 구현자 몫이다. 담아야 할 것:

- **짝 표** — 옵션정보일련번호(PK), 상품일련번호, 이름, 셀메이트 바코드, sku_id(nullable), 짝 지은 방법(code/barcode), 짝 못 지은 사유, 갱신 시각.
- **품목 상태** — sku_id(PK) 또는 옵션정보일련번호, 기준값 `B`, 이월 `C`, 마지막 회차.
- **넘긴 주문** — init 회차, display_id, Medusa order id, core sales_order_id.
- **회차** — 종류(init/apply), 상태(awaiting_close/closed), 입력 파일 sha256·스냅샷 시각, T(init 행), 업로드 CSV 경로, 닫기 입력 해시, accept 목록, 만든·닫은 시각.
- **회차 품목** — 회차별 `S`·`B`·`C` 전후·반영한 delta·`U`·올린 현재재고·닫기 판정. 감사 기록이고, «왜 이 숫자였나»에 답한다.

이 테이블은 추가만 하는 변경이고, 앱 코드는 읽지 않는다. **T 전에 live `db:migrate` 가 필요하다**(배포는 아님 — 다음 묶음 배포에 schema 가 실려도 무해). 테넌트마다 생기지만 쓰는 건 테넌트 1 core DB 뿐이다.

### 판정 검사 (`scripts/ops/cutover-preflight/checks/reconcile.ts`)

| 검사 | 컷오버 전 | 컷오버 뒤(`--after-cutover`) |
|------|-----------|------------------------------|
| 기준값(init) 있는지 | 없으면 ◆ 당일 처리 | 없으면 ✗. **열린 회차가 하루 넘게 안 닫혔으면 ✗.** init 의 T 가 `channel_adapter.reservation_projection_settings.cutover_at`(#1247)과 다르면 ✗ — T 의 원천이 둘로 갈리지 않게 |
| 짝 못 지은 품목 | `pair` 가 한 번도 안 돌았거나 1건 이상이면 ✗ | 같음 |
| 이월 모자람 | 품목 표(정보, 실패 아님) | 같음 |

- ✗ 마다 고치는 명령을 적는다(`bash scripts/sellmate/run.sh live evening-reconcile pair --apply <csv>` 등).
- 테이블이 아직 없으면(마이그 전) ✗ 이고, 고치는 명령은 `db:migrate` 다.

## 지켜야 할 것

- 스펙 없는 계산은 없다. 계산(`net`·`R`·`U`·닫기 판정 표)과 짝 짓기는 DB 없는 순수 함수로 두고 유닛 스펙을 붙인다. 정본의 각 시나리오를 스펙 한 개씩으로 둔다:
  - 드레인 중 T 이전 주문 출고는 차이 0
  - 마켓 주문 → 다음 회 −n
  - 취소·반품 → +n
  - 이월 생기고 입고로 갚기
  - 같은 파일 재실행
- DB 를 쓰는 부분은 기존 관례처럼 `describeIfDb` 가드가 있는 통합 스펙으로 둔다(`build-location-master.integration.spec.ts` 가 본).
- 스펙 안에서 `dotenv.config()` 를 부르지 않는다.
- 공개 레포다. 실제 품목명·바코드를 픽스처에 쓰지 않는다.

## 첫 live `--apply` 전에 사람이 확인할 것

- [ ] 재고 수정 업로드가 **바코드번호 1~3·글로벌바코드 중 어느 것**과 맞추는지. 시험 상품 1개의 값을 바꿔 올리고 되돌려 본다. 결과에 따라 짝 짓기·업로드가 읽을 CSV 바코드 열을 정한다(열 이름은 환경변수로 덮을 수 있게 둔다).
- [ ] 마켓에 보내는 숫자에 **안정재고**가 끼는지. 끼면 `U` 의 정의를 고친다.
- [ ] 셀메이트 미발송 주문 목록 export 에 **판매처와 주문번호** 열이 있는지, 자사몰 주문번호가 `YYYYMMDD-display_id` 꼴로 남는지(`collect-cellmate.js` 가 그렇게 넣는다).
- [ ] 재고 현황 CSV 양식에 바코드 열이 있는지. 없으면 «개발팀 데이터 내보내기용» 양식에 더한다.
