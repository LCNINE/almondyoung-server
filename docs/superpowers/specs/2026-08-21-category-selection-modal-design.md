# 상품 카테고리 선택기 개선 설계

- 이슈: [#686](https://github.com/LCNINE/almondyoung-server/issues/686)
- 날짜: 2026-08-21
- 범위: `apps/admin-web` 전용. 백엔드 변경 0건, 마이그레이션 0건

## 1. 문제

`apps/admin-web/src/features/mall/products-detail/components/general/category-selection-modal.tsx`
가 카테고리 트리를 **평탄한 1차원 목록**으로 그린다. 접기/펼치기가 없어 수백 개
카테고리가 한 화면에 쏟아지고, 들여쓰기(`paddingLeft: depth * 16`)만으로 계층을
가늠해야 한다. 비활성 카테고리가 섞여 목록을 부풀리고, 선택 해제와 대표 지정이
왼쪽 목록에서만 되며, 검색은 단순 부분일치뿐이고 키보드로 쓸 수 없다.

모달 크기도 `max-w-4xl`(896px)에 목록 높이가 `h-[430px]` **고정**이다.

### 이슈 본문의 정정 사항

이슈는 "검색 추가"가 아니다. 검색은 2026-06-08 `bb82ddf11`(resolve #389)로 이미
들어가 있다. 이 작업은 **모달 자체의 개선**이다.

### 이슈에 없던 발견

`src/features/mall/categories/`(카테고리 관리 페이지)에 이슈가 요구하는 트리가
**이미 구현돼 살아 있다**:

- `hooks/use-tree-expansion.ts` — 접기/펼치기 + 검색 시 매치 노드 조상 자동 펼침
- `components/tree/tree-node.tsx` — 재귀 노드, 매치 하이라이트, `role="tree"` ARIA
- `tree-state.ts` — 평탄화·트리 재구성·후손 탐색 순수 함수

따라서 이 작업의 성격은 "트리를 새로 만든다"가 아니라 **"있는 트리를 선택기가
쓸 수 있게 떼어낸다"** 이다. 단, 그대로는 못 쓴다 — `CategoryNode` 가
`hasPendingMove`/`hasPendingReorder` 같은 관리 페이지 전용 필드를 들고 있고,
`TreeNode` 는 `dragProps`/`dragState`(드래그앤드롭)를 필수 prop 으로 받는다.

그리고 `src/features/mall/categories/` 아래에는 **스펙이 0건**이다. 트리 로직이
현재 전혀 검증돼 있지 않다.

## 2. 확정된 결정

| 항목 | 결정 | 기각한 대안 |
|---|---|---|
| 모달 크기 | 전체화면 시트 `96vw × 92vh` | 1152px 확대 / 폭 제한 |
| 탐색 형태 | 들여쓴 단일 트리 | 컬럼(Miller) 브라우저 |
| 남는 가로폭 | 행 오른쪽에 `slug · 뱃지 · 대표 버튼` | 2단 조판 / 여백으로 방치 |
| 공유 범위 | **순수 로직만** 공유, 뷰는 각자 | 트리 컴포넌트까지 공용화 / 자급자족 |
| 검색 | 공백 무시 + 경로 토큰 매칭 | 초성 검색(제외) |
| 키보드 | 포함 | — |
| 선택 항목 상단 고정 | 제외 | — |

### 왜 "순수 로직만 공유"인가

**admin-web 은 컴포넌트 테스트가 불가능하다.** `test:admin-web` 의 transform 이
`.ts`/`.js` 만 처리하고 `.tsx` 는 밖에 있다. 뷰를 공유해도 그 공유분은 영원히
검증되지 않는다. 공유해서 실익이 있는 건 테스트 가능한 순수 로직뿐이다.

**관리 페이지에 스펙이 0건이다.** 뷰까지 공용화하면 살아 있는 관리 페이지를
안전망 없이 리팩터링하는 셈이고, 드래그앤드롭 회귀를 사람 눈으로만 잡아야 한다.

**두 뷰의 요구가 실제로 다르다.** 관리 트리는 `dragProps`·`dragState`·
`hasPendingMove`·`onAddChild` 를, 선택기 트리는 체크박스·대표 버튼·slug 열·
`selectedIds` 를 받는다. 합집합은 얕고 넓은 모듈이 된다.

**덤:** 추출하면서 스펙을 붙이면 관리 페이지의 트리 펼침 로직이 처음으로
테스트를 갖는다.

## 3. 모듈 경계

### 공용 순수 모듈 — `src/lib/utils/category-tree.ts` (+ spec)

두 기능이 모두 만족하는 **최소 노드 형태** 하나만 요구한다:

```ts
type CategoryTreeNodeLike = {
  id: string;
  name: string;
  slug?: string;
  description?: string;

```

관리 페이지의 `CategoryNode` 도, 선택기가 받는 `CategoryDto` 도 이 형태를 이미
만족한다. 어느 쪽도 자기 타입을 바꾸지 않는다.

| 함수 | 역할 |

| `normalizeSearchTerm` | 소문자화 + 공백 제거 |

| `pruneTree` | 술어 기반 가지치기 (§5) |

## 4. 검색 매칭 규칙

검색어를 공백으로 쪼개 토큰 목록을 만들고, **마지막 토큰은 "찾는 대상", 앞
토큰들은 "위치 한정"** 으로 읽는다.

```
매치 =  마지막토큰 ⊂ (이름 | slug | 설명)
     && 앞토큰들이 전부 ⊂ 전체경로문자열
```

비교는 전부 소문자화 + 공백 제거 후에 한다.

**"전체경로문자열"은 조상뿐 아니라 자기 이름까지 포함한다** (`화장품/스킨케어`).
자기 이름을 빼면 `스킨 케어` 가 불매치가 된다 — `스킨` 이 조상 `화장품` 에 없기
때문이다. 이 한 글자 차이가 세 번째·두 번째 예시의 결과를 뒤집는다.

| 입력 | 결과 | 이유 |
|---|---|---|
| `토너` | `…/스킨케어/토너` | 단일 토큰 → 이름 매치 |
| `스킨 케어` | `…/스킨케어` | `케어` 가 이름에, `스킨` 이 경로에 |
| `바디 크림` | `…/바디케어/크림` | `크림` 이 이름에, `바디` 가 조상 경로에 |
| `화장품` | `화장품` **하나만** | 자손은 이름에 `화장품` 이 없다 |
| `크림 바디` | 0건 | 순서는 넓은 것 → 좁은 것 |

**네 번째 줄이 핵심 방어선이다.** 경로 전체를 그냥 부분일치시키면 `화장품` 을
쳤을 때 그 아래 수백 개가 전부 매치돼 트리가 통째로 펼쳐진다. 마지막 토큰을
이름에 묶어두면 그 폭발이 막힌다.

### 관리 페이지 회귀 없음

**단일 토큰 검색은 기존과 100% 동일하다.** 앞 토큰이 없으면 두 번째 조건이
공집합에 대한 `every` 라 항상 참이 되어, 예전의 이름·slug·설명 부분일치 그대로다.
달라지는 건 공백이 들어간 검색뿐인데 그건 지금 `name.includes("바디 크림")` 이라
사실상 항상 0건이었다.

## 5. 가시성 — 하나의 규칙

검색 필터와 비활성 필터를 따로 적용하면 사고가 난다. `화장품(비활성) /
스킨케어(활성)` 에서 비활성을 숨기면 부모가 사라지며 **활성 자식까지 증발한다.**

```
노드가 보인다 = 본인이 술어를 통과  OR  자손 중 통과하는 게 있다
```

`pruneTree(tree, predicate)` 하나가 검색과 비활성을 둘 다 처리한다. 술어는
`검색 매치 ∧ 비활성 정책` 의 합성이다. 통과 못 했지만 자손 때문에 남은 노드는
**구조 유지용**이므로 흐리게 그리고 체크박스를 비활성화한다.

이것이 이슈 1번의 "검색 시에만 평탄화"보다 나은 형태다. 현재 관리 페이지는
검색해도 트리를 통째로 그리고 매치만 하이라이트해 **목록이 안 줄어든다.**
가지치기를 넣으면 검색이 실제로 좁혀준다.

**비활성 정책:** 기본 숨김. 단 **이미 선택된 비활성 카테고리는 토글과 무관하게
항상 통과**시킨다 — 아니면 잘못 붙은 것을 뗄 방법이 사라진다.

## 6. 펼침·선택·키보드

### 펼침 상태 (두 겹)

- `userExpanded` — 사용자가 토글한 것. **모달을 열 때 이미 선택된 카테고리들의
  조상으로 초기화**한다 (아니면 열자마자 뭘 골라놨는지 트리에서 안 보인다)
- `searchExpanded` — 검색 매치 노드의 조상. 파생값이라 검색어를 지우면 사라진다
- 실제 펼침 = 둘의 합집합

이렇게 나누면 "모두 접기"가 `userExpanded` 만 비우면 되고 검색 자동 펼침과 싸우지
않는다. 관리 페이지가 이미 쓰는 구조라 이관도 자연스럽다.

**모달은 `categories/hooks/use-tree-expansion.ts` 를 import 하지 않는다.** 그 훅은
관리 페이지 소유로 남고(초기값 빈 집합), 모달은 같은 두 겹 모델을 자기 상태로
따로 갖는다(초기값 = 선택된 것들의 조상). 두 훅이 공유하는 건 §3의 순수 함수뿐이다.
초기값이 서로 다르다는 것이 훅을 공유하지 않는 이유다.

### 선택과 대표

- 선택 순서를 무시하고 **트리 전위 순회(pre-order DFS) 순서로 정렬**해 저장
  (현 `sortCategoryIds` 와 같은 의미)
- 대표가 없는데 뭔가 선택되면 → 첫 번째가 대표
- 대표를 선택 해제하면 → 남은 것 중 첫 번째로 승계
- 전부 해제하면 → 대표 `null`
- 대표 지정 버튼은 **트리 행과 선택됨 패널 양쪽**에

### 키보드

```
resolveKeyboardMove(보이는노드순서, 현재인덱스, 키, 펼침집합)
  → { nextIndex? , toggleExpandId? , selectId? }
```

훅은 이 함수를 부르고 상태만 반영한다. 키보드 규칙 전체가 렌더러 없이 검증된다.

이 함수는 **트리에 포커스가 있을 때의 키만** 다룬다. `Esc` 는 Radix Dialog 가
자체 처리하므로 함수 반환값에 없고, "검색창에서 `↓`" 는 검색 입력의 핸들러가
포커스를 트리 0번으로 옮기는 별도 경로다.

| 키 | 동작 |
|---|---|
| `↑` `↓` | 보이는 순서대로 이동 (접힌 노드의 자식은 건너뜀) |
| `→` | 접혀 있으면 펼치기, 이미 펼쳐졌으면 첫 자식으로 |
| `←` | 펼쳐져 있으면 접기, 이미 접혔으면 부모로 |
| `Space` / `Enter` | 선택 토글 |
| `Esc` | 모달 닫기 |
| 검색창에서 `↓` | 트리 첫 항목으로 진입 |

## 7. 뷰

**크기.** `DialogContent` 를 `!max-w-[96vw] sm:!max-w-[96vw] h-[92vh]` 로 바꾸고,
목록의 `h-[430px]` 고정을 걷어내 `flex-1 min-h-0` 사슬로 잇는다. 높이가 화면을
따라가야 전체화면을 고른 의미가 산다.

**행 구성.** 왼쪽에 `펼침 화살표 · 체크박스 · 이름`(들여쓰기 `depth * 16`),
오른쪽 끝에 `slug · 예외 뱃지 · 대표 버튼`. 평소엔 조용하게:

- `slug` — 항상
- 뱃지 — 비활성 / 멤버십 전용일 때만
- 대표 버튼 — 선택된 행에만

**배선 변경.** `index.tsx` 가 모달에 평탄 배열 대신 **트리를 그대로** 넘긴다.

**가상화는 넣지 않는다.** 현재는 수백 행을 항상 그리지만 트리는 기본이 접힘이라
초기엔 루트 몇 개만 그린다. 화면이 커지는데 렌더는 오히려 가벼워진다.

신규 spec 은 40케이스 안팎:

- 키보드 6종 × 경계(첫/끝 항목, 자식 없음, 루트에서 `←`)
- 대표 승계 4종

### 수동 스모크 (필수 — 컴포넌트 테스트가 불가능하다)

1. 카테고리 여러 개 선택 → 적용 → 서랍 요약 줄 반영 → 저장
2. 재진입 시 선택된 것들의 조상이 펼쳐져 있는지
3. `바디 크림` 처럼 공백 검색 → 매치가 좁혀지는지
4. `화장품` 처럼 루트 이름 검색 → 트리가 폭발하지 않는지
5. 비활성 토글 껐을 때 비활성 부모 아래 활성 자식이 보이는지
6. 이미 선택된 비활성 카테고리를 뗄 수 있는지
7. 선택됨 패널의 `×` 와 `★`
8. 키보드만으로 검색 → 이동 → 선택 → 적용 (`Esc` 포함)
9. **관리 페이지 회귀** — 드래그앤드롭 이동, 검색, 저장
10. 상품 목록 카테고리 필터가 그대로 동작하는지

## 9. 영향과 위험

**배포 영향:** admin-web 전용. 마이그레이션 0건, 백엔드 변경 0건, 배포 순서 제약
없음.

**위험:**

- **관리 페이지 회귀** — 훅 내부를 갈아끼운다. 순수 로직에는 처음으로 스펙이
  붙지만 드래그앤드롭 뷰는 눈으로만 확인된다 → 스모크 9
- **서랍 위 다이얼로그의 포커스 트랩** — 모달은 오른쪽 `기본 정보 수정` Drawer
  위에 뜬다. 키보드 내비게이션을 넣으며 처음 문제가 드러날 수 있는 지점 → 스모크 8
- **`CategoryDto` 에 상품 수 필드가 없다** — 행에 "이 카테고리 상품 N개"는 못
  띄운다. 넣으려면 백엔드 작업이고 이번 범위 밖

## 10. 범위 밖

- 초성 검색 (`ㅅㅋㅇ` → 스킨케어)
- 선택 항목 트리 상단 고정
- 카테고리별 상품 수 표시 (백엔드 필요)
- 상품 신규 등록 경로 별도 대응 — `/mall/product-registration` 은 빈 draft 만
  만들고 편집 페이지로 보내므로 **같은 모달을 탄다.** 한 곳만 고치면 등록/수정
  양쪽이 해결된다
