# 출고 준비 일괄 처리 설계

작성일: 2026-11-05

## 1. 왜 하는가

지금은 주문, 합배송, 3PL 상관없이 상자 하나마다 네 단계를 손으로 밟는다.

1. 출고주문 상세에서 배송 계획 확정 (`POST /shipments/:id/plan`, 상자 1개 단위)
2. 운송장 발급 화면에서 체크 후 일괄 발급 (`POST /waybills:batch`, 최대 100건)
3. 출고 배치 화면에서 배치 생성 (`POST /outbound-batches/v2`)
4. 배치 상세에서 상자마다 추가 (`POST /outbound-batches/:batchId/shipments/:shipmentId`, 상자 1개 단위)

35건이면 클릭이 약 75번이고 화면 3개를 오간다. 운영 단계에서 감당하기 어렵다.

셀메이트는 같은 일을 분류 단위로 한다. 재고할당 한 번에 미발송 주문이 완전출고, 부분출고, 출고불가, 미할당(미매칭)으로 나뉜다. 송장 출력 화면에서는 분류 한 줄(예: 완전출고 35장, 단일 7 / 합포 28)에 있는 송장 연동, 피킹리스트 버튼이 그 묶음 전체를 처리한다. 부분출고 줄에는 부분출고합포나누기 버튼이 있다. 정리하면 셀메이트에서는 분류가 곧 작업 단위다.

목표는 이렇다. 어드민 웹 한 화면에서 완전출고 묶음을 고르고 버튼 한 번을 누르면 계획 확정, 송장 발급, 배치 생성, 상자 담기가 끝나서 피킹을 시작할 수 있어야 한다. 사람은 판단이 필요한 건만 본다. 부분출고를 나눌지, 어느 주문을 합칠지, 출고불가와 미매칭 건이 그것이다.

## 2. 결정 사항 요약

| 항목 | 결정 |
|---|---|
| 버튼 한 번의 범위 | 계획 확정 → 송장 발급 → 배치 생성 → 상자 담기까지 |
| 작업 위치 | 어드민 웹 |
| 배치 구성 | 고른 상자 전부를 배치 1개로 묶는다. 피킹 방식은 화면 위에서 창고와 함께 고르고(창고가 지원하는 방식이 하나면 저절로 고른다), 확인 창은 고른 방식을 보여 준다 |
| 일부 실패 | 성공한 상자만 진행한다. 실패한 상자는 사유와 [다시 시도]를 남긴다 |
| 일시 오류 | 진행 창이 자동으로 재시도하고(최대 3회), 그래도 안 되면 [다시 시도]로 남긴다 |
| 합칠 수 있는 상자 | 일괄 대상에서 빼고 "합칠 주문 있음"으로 표시한다. 합치기는 기존 기능으로 한다. 지금 함께 보낼 수 있는 짝(전량 예약된 draft)이 있을 때만 이 분류다 — §4.4 |
| 부분출고 | 체크한 건만 일괄로 나눈다. 재고 있는 부분은 먼저 보낸다 |
| 구현 방식 | 단계별 일괄 API + 어드민 화면이 순서대로 호출 |
| 화면 모양 | 셀메이트 송장 출력처럼 분류별 줄에 건수와 버튼을 둔다 |

## 3. 화면

### 3.1 위치

지금의 운송장 발급 화면(`/order/waybill-issue`)을 출고 준비 화면으로 넓힌다. 창고 선택, 체크박스 목록, 100건 상한, 합배송 경고(`merge-warning.tsx`)가 이미 있으므로 새 페이지를 만들지 않는다.

### 3.2 분류표

창고 하나를 기준으로 셀메이트 송장 출력 화면과 같은 표를 보여 준다.

| 구분 | 표시 | 기능 |
|---|---|---|
| 완전출고 | 상자 수 (단일 / 합포) | [출고 준비], [내역보기] |
| 부분출고 | 상자 수 | [있는 것만 먼저 보내기], [내역보기] |
| 출고불가 | 상자 수 | [내역보기] |
| 미매칭 | 주문 수 (전 창고) | [매칭하러 가기] |
| 합칠 주문 있음 | 상자 수 | [내역보기], 줄마다 [합치기] |
| 이어서 처리 | 상자 수 | [출고 준비] (남은 단계만 진행) |
| 정보 부족 | 상자 수와 사유 | [내역보기], 상자 상세 링크 |

[내역보기]를 누르면 상자 목록이 열린다. 처음엔 전부 체크된 상태다. 체크를 푼 상자는 이번 처리에서 빠진다.

### 3.3 흐름

1. 운영자가 완전출고 줄의 [출고 준비]를 누른다.
2. 확인 창이 뜬다. 문구는 "완전출고 N건을 출고 준비할까요?"이고, 화면 위에서 고른 피킹 방식과 [시작] 버튼이 있다. 방식을 확인 창이 아니라 화면 위에서 고르는 것은 분류마다 확인 창을 열 때마다 같은 선택을 반복하지 않기 위해서다.
3. 진행 창이 단계별로 진행 상황을 보여 준다.
   - 계획 확정 35 / 35
   - 송장 발급 34 / 35
   - 배치 "11/05 토탈피킹 14:03:27" 생성, 34건 담음. 이름은 만들기 직전 시각을 초까지 쓴다 — 순번(#1)은 서버에 세는 곳이 없어 두 탭이 같은 이름을 만들 수 있다
4. 실패한 상자는 주문번호, 한국어 사유, [다시 시도]와 함께 남는다. 다시 해도 안 되는 실패에는 [상자 보기]도 함께 둔다. 다시 시도해서 성공하면 같은 배치에 담는다(배치가 아직 시작 전일 때).
5. [배치로 가기]를 누르면 배치 화면으로 간다. 작업 시작, 라벨 출력, 피킹은 지금과 같다.

한 번에 처리하는 상한은 지금처럼 100건이다. 목록은 분류마다 200건씩 돌려주고, 나머지는 [더 보기]가 `bucket`·`offset` 으로 더 부른다.

## 4. 서버

### 4.1 원칙

상자 하나하나의 검증은 기존 코드를 그대로 거친다. 기존 검증에는 전량 confirmed 예약, 같은 창고, 배송 프로필 일치, 수령인 정보, dispatchable 송장, 활성 work item 중복 금지가 있다. 새로 만드는 것은 여러 건을 받아 건별로 돌리고 결과를 모아 주는 층뿐이다. 상자마다 트랜잭션을 따로 쓴다. 그래서 한 건이 실패해도 나머지는 진행된다.

### 4.2 API

| # | API | 새로 만드나 | 권한 | 하는 일 |
|---|---|---|---|---|
| 1 | `GET /outbound-preparation?warehouseId=` | 새로 | `fulfillment.shipment.read` | 분류별 건수와 목록 |
| 2 | `POST /outbound-preparation/plans` | 새로 | `fulfillment.warehouse.operate` | 상자마다 `ShipmentPlanningService.plan` |
| 3 | `POST /outbound-preparation/waybills` | 새로 | `fulfillment.warehouse.operate` | 상자마다 송장 발급 또는 이어 가기 (§5.2) |
| 4 | `POST /outbound-batches/v2` | 기존 | `fulfillment.warehouse.operate` | 배치 생성 |
| 5 | `POST /outbound-preparation/batches/:batchId/shipments` | 새로 | `fulfillment.warehouse.operate` | 상자마다 기존 배치 추가 |
| 6 | `POST /outbound-preparation/unreserved-splits` | 새로 | `fulfillment.warehouse.operate` | 상자마다 기존 `split-unreserved` |

새 라우트 다섯은 컨트롤러 하나(`outbound-preparation.controller.ts`)에 모은다. POST 는 `Idempotency-Key` 헤더를 받고, 상자별 키는 `<헤더 키>:<shipmentId>` 로 만든다(`waybills:batch` 와 같은 규칙).

새 일괄 API(2, 5, 6)는 응답 모양이 같다.

```ts
{
  succeeded: string[];                                          // shipmentId
  failed: { shipmentId: string; code: string; message: string; transient: boolean }[];
}
```

`transient`는 다시 부르면 성공할 수 있는 실패인지를 나타낸다. 진행 창은 이 값으로 자동 재시도 여부를 정한다.

송장(3)만 응답 모양이 다르다. 기존 `waybills:batch` 의 항목(`shipmentId`·`status`·`trackingNo`·`reason`·`nextAttemptAt`)에 실패일 때 `transient`·`code` 를 더한 배열이다. 송장은 «성공/실패» 둘이 아니라 `allocated`·`pending` 처럼 «아직»이 있어서 진행 창이 상태를 직접 봐야 한다. `waybills:batch` 를 그대로 쓰지 않는 이유는 이미 `registered` 인 상자를 넘기고, 멈춘 송장을 키와 상관없이 이어 가야 하기 때문이다(§5.2).

### 4.3 계획 확정 일괄의 입력

단건 `plan`은 `shippingProfileId`, `expectedManifestVersion`, `expectedReservationVersion`을 받는다. 일괄 API는 상자 id만 받고 나머지는 서버가 정한다.

- **배송 프로필**: `assertPlanProfile`이 이미 상자의 모든 SKU가 프로필 하나를 공유해야 한다고 요구한다. 그래서 상자의 SKU `deliveryProfileId`에서 프로필이 하나로 정해진다. 하나로 정해지지 않는 상자는 `SHIPMENT_PROFILE_INCOMPATIBLE`로 실패하고, 현황 화면에서는 애초에 정보 부족으로 분류된다.
- **버전 값**: 서버가 처리 직전의 현재 값을 읽어 넘긴다. 단건 화면에서는 이 값이 운영자가 본 화면과 서버 상태의 차이를 잡는 장치다. 일괄에서는 운영자가 상자 하나하나를 보지 않으므로 이 대조가 의미가 없다. 그 대신 `plan` 안의 전량 예약 검사와 상태 검사가 처리 시점 기준으로 다시 돈다.

### 4.4 분류 규칙

모든 분류는 DB 상태에서 계산한다. 분류를 저장하는 새 컬럼은 없다. 대상은 해당 창고의 창고 상자(`supplierId` 없음)다.

| 분류 | 조건 |
|---|---|
| 완전출고 | `draft` + 모든 라인 confirmed 예약 수량 = `qty` + 프로필 하나로 정해짐 + 수령인 완전 + 합칠 후보 아님 |
| 부분출고 | `draft` + 예약된 라인과 모자란 라인이 섞임 |
| 출고불가 | `draft` + confirmed 예약 0 |
| 미매칭 | FO 생성 backlog `awaiting_matching` (상자도 창고도 아직 없어 창고와 무관하게 전체 주문 수로 센다) |
| 합칠 주문 있음 | 완전출고 조건 + 합배송 후보 그룹(`findBoard`)에 «지금 함께 보낼 수 있는 짝»이 있음 — 짝도 `draft`·전량 예약·활성 work item 없음 |
| 이어서 처리 | `planned` + 활성 work item 없음 (송장 유무 무관) |
| 정보 부족 | `draft` + 전량 예약 + 프로필이 갈리거나 비었거나 수령인 정보 누락 |

짝이 부분출고·출고불가라 지금 함께 못 보내면 이 상자는 완전출고로 따로 나간다. 짝을 기다리게 하면 바로 보낼 수 있는 상자까지 짝의 재고가 들어올 때까지 묶인다. 고객은 상자 두 개를 받을 수 있다. 라인이 0개인 draft 상자는 보낼 것이 없으므로 출고불가로 센다.

단일 / 합포 구분은 상자의 라인 수(1개 / 2개 이상)로 정한다. 셀메이트 화면과 같은 정보를 주기 위한 표시용이다.

목록 항목은 상자 id, 주문번호, 품목 요약, 수량, 사유만 싣고 수령인은 싣지 않는다. 지금의 `GET /shipments/planned` 와 같은 수준이라 개인정보 응답이 아니다(`@PiiResponse` 불필요). 화면의 `PII_SCREENS` 표시는 합치기 시트가 수령인을 열 수 있으므로 그대로 둔다.

### 4.5 동시 작업

두 운영자가 같은 상자로 동시에 눌러도 이중 처리되지 않는다. 상자마다 기존 상태 검사(`draft`가 아니면 계획 거절, 상자당 활성 송장 1개, 상자당 활성 work item 1개)가 있기 때문이다. 늦은 쪽은 그 상자가 실패 목록에 이미 처리됨 사유로 나온다.

## 5. 실패와 재시도

### 5.1 자동 재시도와 [다시 시도]

| 실패 종류 | 예 | 처리 |
|---|---|---|
| 일시 오류 | 네트워크 끊김, 서버 5xx, 한진 일시 거절(ERROR-05/06), 결과를 모름(unknown_outcome), 45초 예산 초과로 남은 건 | 진행 창이 자동으로 다시 부른다. 간격은 2초, 5초, 10초로 최대 3회다. 그동안 "재시도 중"으로 보여 준다 |
| 확정 오류 | 주소 확인 불가, 예약 부족, 이미 다른 배치에 있음, 상태가 바뀜 | 재시도하지 않고 바로 사유와 [다시 시도]를 남긴다 |
| 자동 재시도 3회 초과 | | [다시 시도]로 남긴다 |

송장 쪽 재시도 장치는 이미 있다. 일시 거절은 `TRANSIENT_ATTEMPTS_CAP: 3`, 결과를 모르는 경우는 `PENDING_ATTEMPTS_CAP: 5`이고 `nextAttemptAt`으로 간격을 둔다. 다만 혼자 도는 폴러가 없어서 누군가 다시 불러야 진행된다. 진행 창의 자동 재시도가 그 역할을 한다.

### 5.2 다시 불러도 안전한 이유

- 계획 확정: `draft`가 아닌 상자는 거절된다. 응답을 못 받았지만 실제로 성공한 상자를 다시 부르면 "이미 planned"로 나온다. 진행 창은 이 상자를 실패가 아니라 이미 됨으로 보고 다음 단계로 넘긴다.
- 송장 발급: 상자당 활성 송장은 1개(`uq_waybills_shipment_active`)이고, 발급은 멱등 커맨드로 시작한다. 상자에 멈춘 활성 송장(`pending`·`allocated`)이 있으면 새로 발급하지 않고 그 행을 이어 간다(`WaybillService.resumeActive`). 같은 키로 replay 한 것과 같은 일이라, 키를 브라우저에 붙들지 않아도 다른 PC·새로고침 뒤에 같은 결과가 된다. 그 행이 지금 상자 내용(manifestVersion·수하인)과 다르면 이어 가는 순간 옛 주소로 등록되므로 `WAYBILL_NEEDS_REVIEW`(확정 오류)로 멈추고, 운영자가 상자에서 송장을 abandon 한 뒤 다시 시도한다(abandon 라우트는 있고, admin-web 화면은 #1241). 내용이 같으면 멈춘 송장은 `PENDING_ATTEMPTS_CAP` 뒤 저절로 `abandoned` 가 되거나 `registered` 로 끝나므로 운영자가 볼 일이 없다.
- 배치 담기: 상자당 활성 work item은 1개다.

### 5.3 중간에 브라우저를 닫으면

진행 중이던 상자는 `planned` 상태로 남는다. 출고 준비 화면의 이어서 처리 줄에 나타나므로, 거기서 [출고 준비]를 누르면 남은 단계(송장, 배치)만 진행한다. 남는 배치(상자가 하나도 안 담긴 배치)는 기존 배치 화면에서 취소할 수 있다.

## 6. 이번에 만들지 않는 것과 이유

| 만들지 않는 것 | 이유 | 다시 볼 때 |
|---|---|---|
| 단일 / 합포를 서로 다른 배치로 나누기 | 지금 피킹 방식을 하나(토탈피킹)로 정했고, 단일과 합포를 다른 방식으로 피킹하는 운영이 아직 없다. 표에는 단일 / 합포 건수를 보여 주므로 나중에 나눌 기준은 이미 보인다 | 단일은 토탈피킹, 합포는 멀티오더처럼 나눠 피킹하기 시작할 때 |
| 택배사, 3PL, 배송 프로필 기준 자동 배치 분리 | 실제로 연동된 택배사는 한진 하나다. 배치에도 택배사 컬럼이 없고, 3PL은 배송 프로필의 지원 모드 검사만 다르다. 나눌 기준이 실제로 갈리지 않는다 | 두 번째 택배사가 연동되거나 3PL 물량이 따로 피킹될 때 |
| 서버 백그라운드 작업(잡 테이블 + 워커) | 하루 물량이 수십에서 백여 건이다(셀메이트 기준 인쇄대기 167장). 60초 요청 제한은 기존 `waybills:batch`의 45초 예산과 남은 건 재호출로 충분히 넘긴다. 잡 테이블, 워커, 테넌트별 `forEachDatabase` 크론까지 만드는 비용이 이득보다 크다. 화면이 단계별 API를 부르는 구조라 나중에 옮겨도 화면은 거의 그대로 쓴다 | 한 번에 수백 건 이상을 처리해야 하거나, 브라우저를 닫아도 끝까지 진행돼야 할 때 |
| 창고 앱에서 출고 준비하기 | 출고 준비는 사무실에서 어드민으로 한다고 정했다. 앱은 배치 시작과 피킹을 맡는다 | 현장에서 출고 준비까지 해야 하는 운영이 생길 때 |
| 100건 상한 늘리기 | 한진 호출이 상자당 2회이고 서버 동시성은 8이다. 100건은 45초 예산 안팎에서 끝나는 크기라 기존 상한을 유지한다 | 상한 때문에 버튼을 여러 번 누르는 일이 잦아질 때 |
| 출고불가, 미매칭 건을 이 화면에서 처리 | 출고불가는 재고가 들어와야 풀리고 기존 재시도 워커가 채운다. 미매칭은 기존 매칭 화면이 있다. 이 화면은 건수와 링크만 준다 | 운영자가 이 화면에서 바로 처리하기를 원할 때 |
| 합칠 수 있는 상자 자동 합치기 | 고객이 따로 보내 달라고 한 주문까지 합쳐질 수 있다. 계획 확정 뒤에 합치려면 송장을 취소해야 해서 잘못 합친 것을 되돌리기 어렵다. 그래서 표시만 하고 사람이 합친다 | 합치기 규칙이 분명해지고 예외가 거의 없을 때 |
| 부분출고 묶음 전체 자동 나누기 | 일부러 다 모아서 보낼 주문을 빼 둘 수 있게 체크한 건만 나눈다 | 매번 전부 체크해서 나누는 게 습관이 될 때 |

## 7. 테스트

### 7.1 서버

- 분류 규칙마다 해당 상자가 맞는 줄에 들어가는지 확인한다. 실 DB가 필요하므로 `describeIfDb` 가드를 쓴다.
- 일괄 API 2, 5, 6에서 확인할 것
  - 일부가 실패해도 나머지는 성공한다.
  - 같은 상자로 두 번 불러도 한 번만 처리된다.
  - 실패 항목의 `transient` 값이 맞다.
- 계획 확정 일괄이 SKU에서 프로필을 정하는지, 프로필이 갈리는 상자를 실패로 돌려주는지 확인한다.

### 7.2 어드민 웹

- 진행 창이 계획 → 송장 → 배치 생성 → 담기 순서로 부르는지 확인한다.
- 일시 오류는 자동 재시도하고, 확정 오류는 바로 [다시 시도]가 뜨는지 확인한다. 부분출고 나누기도 같은 규칙으로 자동 재시도한다.
- 원래 키 없이 다시 불러도 멈춘 송장을 이어 가고, 내용이 바뀐 송장은 «확인 필요»로 멈추는지 확인한다.
- 송장 단계가 `pending/time-budget-exceeded`로 돌려준 남은 건을 이어서 부르는지 확인한다.
- 이미 planned인 상자를 실패가 아니라 이미 됨으로 보고 넘기는지 확인한다.

### 7.3 가드 스펙
