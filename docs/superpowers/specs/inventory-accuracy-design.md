## 권장 구조

### 1. 입력 처리: 접수한 스캔을 정확히 한 번 반영

공통 스캔 처리기를 두되 전 업무를 하나의 전역 순서로 묶지 않는다. 입고 초안·출고 박스·실사 위치 등 업무 단위로 순서를 보장한다. 한 이벤트에는 eventId, 업무 ID, 사용자, 창고, 위치/송장, 바코드, 접수 시각을 고정한다. 동일 바코드도 두 번 접수했으면 두 개의 별도 이벤트다.

입고 상품 조회는 읽기 요청이므로 실패 시 재조회할 수 있다. 조회 결과를 카트에 적용할 때 eventId를 함께 저장해 재시작·응답 중복에도 한 번만 더한다. 조회 중인 스캔이 남아 있으면 입고 확정은 대기한다. 확정 버튼을 누른 순간의 초안을 동결하고 다음 스캔을 그 제출에 섞지 않는다.

발주 입고는 목록 버튼으로 열면 잔여수량을 제안할 수 있다. 스캔으로 수량을 세는 모드라면 첫 스캔부터 포장단위만큼 센다. 현행 전량 프리필과 실카운트가 섞이는 동작은 명시적으로 분리한다. 이는 A1과 별개인 입력 의미 개선이며 기존 기대 테스트를 함께 바꾼다.

모달·등록·위치 전환 중 받을 수 없는 입력은 성공음 없이 짧게 이유를 안내한다. 이미 접수한 입력을 조용히 버리지 않는다. 실사 위치 변경과 수량 직접 정정은 기존 대기열을 모두 확정한 후 수행한다. 대기열이 결과 불명 상태라면 후속 정정도 잠근다.

### 2. 재고 변경: 영속 작업 기록과 불변 요청

업무 상태는 `draft → queued → sending → confirmed | rejected | uncertain`으로 관리한다.

- 전송 전에 IndexedDB 트랜잭션으로 작업 ID, 사용자/서버/창고, 업무 ID, 최초 payload와 키를 저장한다. 저장 실패 시 전송하거나 접수 완료로 표시하지 않는다.
- sending/uncertain 상태에서는 payload를 바꾸거나 새 키로 대체하지 않는다. 실패한 요청의 성공 여부부터 해결한다.
- confirmed는 작업 결과를 저장한 뒤 해당 eventId를 한 번만 반영한다. 표시용 재조회가 실패해도 확정 작업을 다시 실행하지 않는다.
- rejected는 서버가 미반영을 보장한 도메인 오류일 때만 사용한다. 수정은 그 뒤 별도 작업으로 만든다.
- 네트워크 오류·타임아웃·형식을 알 수 없는 응답은 uncertain이다. 연결이 돌아오면 같은 키와 바이트 단위로 고정한 본문을 재전송한다. 권한이 바뀌어 거절되면 원래 사용자/관리자의 확인 경로로 넘긴다.
- 최초 전송 시도 후 재시도는 1·2·4초 간격, 최대 3회. 이후 작업을 남기고 업무 안내와 결과 확인 버튼을 제공한다. 409는 일괄 재시도하지 않고 도메인 코드로 분류한다.
- uncertain은 취소 버튼이나 로그아웃으로 지워지지 않는다. 계정·API 서버가 달라지면 자동 전송하지 않는다. 원래 사용자로 돌아와야 재개한다.
- 앱 재시작에서 sending은 uncertain으로 복원한다. 업무 단위 실행권을 저장소 트랜잭션으로 확보해 StrictMode/중복 마운트가 다른 작업들을 동시에 전송하지 않게 한다. 동일 작업 재전송 자체는 서버의 중복 방지가 최종 방어다.
- 서버의 inventory idempotency 기록은 현재 30일 후 삭제된다. 29일 이상 미확인 작업은 자동 재전송을 금지하고 관리자 확인 대상으로 남긴다. 해당 기간 안이라도 서버 기록 유실을 발견하면 자동 재실행하지 않는다.
- 오프라인 전체 작업 기능은 추가하지 않는다. 연결이 끊긴 것을 알면 새로운 재고 변경 접수를 중단하고, 이미 접수한 항목과 초안만 보존한다.

IndexedDB는 WebView 재시작 보존을 위한 선택이다. 실제 Android/Windows 저장 실패·강제 종료 실험을 통과해야 한다. OS 수준 데이터 삭제나 전원 장애까지 무조건 보존한다고 주장하지 않는다.

### 3. 서버 계약: 저장 응답 재생과 검증 순서

기존 InventoryIdempotencyService와 FulfillmentCommandService를 유지한다. 조정 API에는 작업 키+본문 해시 검증을 API 경계에 추가한다. 낮은 단계의 adjustUp/Down의 키만 보고 성공하는 경로를 앱의 재시도 계약으로 쓰지 않는다. 실사 증가/정정/완료도 동일 요청을 다시 적용하지 않도록 트랜잭션에 감싼다.

인증과 권한 검사는 항상 먼저 한다. 이미 처리한 동일 작업의 재생 검사는 현재 세션 완료 여부·재고 부족 검사보다 먼저 해야 한다. 완료 후 응답이 유실된 작업이 재시도에서 “이미 완료됨”으로 실패하지 않게 하기 위함이다. 다른 본문에 같은 키를 쓰면 명확한 409 코드로 거절한다.

이동·간편입고 등 작업자 ID는 인증된 사용자로 서버가 주입한다. 클라이언트가 임의 actorId를 선택하는 방식을 허용하지 않는다. 사용자 ID는 작업 fingerprint에도 포함한다. 기존 저장 키의 본문 해시를 변경하는 경우 호환성 검증이 필요하므로 API 계약 버전을 분리한다.

서버 선배포 후 새 앱을 배포한다. 기존 admin-web과 네이티브 호출자를 함께 조사해 새 키/버전/미리보기 토큰을 적용한다. 중복 방지·버전 검증이 빠진 구형 요청은 최종 전환 후 조용히 수용하지 않는다. 구형 앱에는 업데이트 필요 문구를 보낸다.

### 4. 실사: 카운트 시점과 적용 시점을 연결

실사 라인에 revision과 countBaselineVersion을 추가한다. 카운트를 시작할 때 해당 위치·SKU ON_HAND 원장의 version을 기록한다(원장 행이 없으면 0). 수량이 다시 원래 값으로 돌아왔더라도 version 변경은 감지한다.

실사 스캔·직접 정정은 세션/라인 잠금과 같은 재고 가용성 잠금 순서를 공유한다. 스캔은 키 기반 증가, 직접 정정은 expectedRevision 조건부 변경이다. 새 위치나 수량을 고르는 행동으로 결과 불명 작업을 우회할 수 없다.

카운트 도중 또는 카운트 후 재고 version이 달라지면 기존 카운트로 완료하지 않는다. 해당 라인의 “다시 세기”는 별도의 명시적 작업이며 새 기준 version을 잡고, 카운트를 새로 시작한다. 단순 증분 스캔이 기준 version을 몰래 갱신해서는 안 된다. 다른 위치의 재고 변경 때문에 전체 창고 작업을 막지는 않는다.

미리보기는 sessionRevision, 라인 revision, 기준/현재 원장 version, 카운트, 적용 delta 전체를 묶은 previewToken을 서버가 돌려준다. 완료는 이 토큰과 작업 키를 받고 같은 잠금 아래 다시 계산한 fingerprint와 비교한다. 불일치하면 원장 쓰기 0건으로 거절한다. 토큰은 권한을 대신하지 않는다.

완료 대상은 variance!=0 라인만이 아니라 세션 범위의 모든 카운트 라인이다. 미카운트 라인이 있으면 완료를 막으며, 아직 방문하지 않은 위치까지 실사됐다는 뜻으로 취급하지 않는다. 전체 창고 실사는 별도 범위 등록이 필요하다. 현재 위치별 작업에서는 방문/등록된 위치를 완료 범위로 명시한다.

원장 버전은 기존 StockEventStore 경로에서 증가함을 확인했다. 다른 원장 쓰기·행 삭제/재생성 경로도 테스트해야 하며, 그 조건을 만족하지 못하면 version 비교만으로 안전하다고 결론 내리지 않는다.

### 5. 표시와 진단

원장 변경 종류별 캐시 무효화를 공통 함수로 모은다. 결과 불명에서도 기존 수량을 확정 잔량으로 표시하지 않으며, 재조회 성공만으로 특정 작업의 성공을 추정하지 않는다. 작업 성공 여부는 작업 키의 결과로 확인한다.

권한 있는 사용자만 개발자 모드에 들어간다. 기존 inventory.manage를 서버에서 검사하는 진단 접근 확인 API를 이용하고, 기본 모드는 꺼둔다. 이는 새 권한 부여 작업을 뜻하지 않는다. 일반 logistics_worker에게는 개발자 모드 진입점이 나타나지 않는다. 권한 확인 실패 시 표시하지 않는다.

기록은 최근 24시간·최대 1,000건의 정제된 진단만 유지한다. 미확인 작업 원장은 진단 로그와 별도로 보존한다. 화면 문구에는 요청 키·HTTP 코드·서버 stack trace를 포함하지 않는다.

## 출시 합격 기준

1. 연속 스캔 100건에서 누락·중복 반영 0건.
2. 서버 커밋 직후 응답을 끊고 재시도/앱 재시작을 반복해도 원장 변경 1회.
3. 결과 불명 중 수량 편집·새 제출·계정/창고 변경으로 다른 작업이 전송되지 않음.
4. 이동 전후 출발 감소=도착 증가, 창고 합계 불변. 입고/출고/조정 delta가 의도한 값과 정확히 일치.
5. 실사 동일 키 스캔은 1회, 다른 키 두 스캔은 2회. 오래된 정정/미리보기/원장 기준은 적용 0건.
6. 작업자 화면에 기술 정보 없이 필요한 안내만 표시되고, 확정 전 완료음/완료 상태가 없음.
7. 기존 테스트와 새 회귀 테스트, 실제 테스트 DB 통합, 네이티브 장비 검증 모두 통과. DB 조건 미충족 skip은 통과로 계산하지 않음.
