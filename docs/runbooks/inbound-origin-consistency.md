# 입고 원위치 불일치 감사와 전환 절차

이 감사는 입고 누계와 원위치 재고, 배치 관리 수량, 과거 반출 근거를 읽어 **실물 대사가 필요한 후보**를 남긴다. 재고 정본은 `stock_ledgers`, 입고 처리 정본은 입고 라인과 업무 기록이다. 현재 잔량으로 입고 회차를 역산하거나 어느 입고가 먼저 반출됐는지 지정하지 않는다.

## 실행

Node 22와 저장소 의존성이 설치된 환경에서 저장소 루트에서 실행한다. 접속 대상은 운영자가 명시적으로 설정한 `DATABASE_URL`만 사용한다. `.env`는 읽지 않는다. 비밀번호가 포함된 URL을 명령 기록·보고서·메신저에 붙여 넣지 말고 승인된 비밀 관리 방식으로 환경에 주입한다.

```bash
corepack yarn tsx scripts/inventory/audit-inbound-origin-consistency.ts \
  --warehouse-id '<대상 창고 UUID>' \
  --output '/absolute/audit-directory/inbound-origin-first.json'
```

대상 창고는 DB에 존재해야 한다. 출력 상위 디렉터리는 미리 준비한다. 파일은 새로 생성하며 권한은 `0600`이다. 기존 파일과 심볼릭 링크를 덮어쓰지 않는다. 재검사는 새 파일명으로 실행한다. 실패한 출력은 완전한 보고서로 취급하지 않는다.

| 종료 코드 | 의미                               | 다음 행동                                                                            |
| --------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| `0`       | 조회 성공, 후보 없음               | 실물 대사와 전환 검증을 계속한다. 전체 이력의 무결성을 보증하는 코드는 아니다.       |
| `2`       | 조회 성공, 확인이 필요한 후보 있음 | 보고서를 보존하고 담당자와 대사한다. 미해결 창고는 시험 운영에서 제외한다.           |
| `1`       | 입력·조회·출력 실패                | 창고/접속 설정/새 출력 경로를 확인하고 다시 실행한다. 후보 없음으로 처리하지 않는다. |

DB가 `REPEATABLE READ READ ONLY` 트랜잭션으로 읽기 전용 스냅샷을 강제한다. 감사에는 재고 변경, 입고 누계 변경, 업무 로그 추가 기능이 없다. 실패 진단은 단계만 출력하며 URL·접속 자격증명·원시 DB 오류를 출력하지 않는다.

## 보고서 읽기

보고서 `version`은 `1`이다. `warehouseId`와 DB 스냅샷 시각 `checkedAt`을 먼저 확인한다. `candidates`는 SKU와 원위치별 후보다.

- `onHandQty`: 해당 창고·SKU·원위치의 `ON_HAND` 원장 합계. 원장이 없으면 `0`이다.
- `pendingQty`: posted 입고 중 같은 창고의 시스템 원위치에 대해 `quantity - putawayFromOriginQty - returnedQty - canceledQty`를 합산한다. 이상 누계를 0으로 보정하지 않는다. 정상 일반 선반 직접입고는 대기 보호 대상이 아니다.
- `batchControlledQty`: 같은 원위치의 `active`/`recovery_required` 배치 세션 중 `SETTLED`를 제외한 관리 수량 합계.
- `generallyAvailableQty`: `max(0, onHandQty - pendingQty - batchControlledQty)`. 후보의 이 수치를 출고 허용이나 보정 근거로 사용하지 않는다.
- `lineIds`, `lines`: 모든 해당 입고 라인 ID, 회차 ID, 입고 출처, 개별 누계와 원시 잔량, 입고 시각과 라인 생성/갱신 시각. `originLocationId: null`은 원위치 정보가 실제로 없다는 뜻이며 임의 위치로 치환하지 않는다. 다른 창고의 원위치도 원래 ID를 보존하며 잘못된 입고로 표시한다.
- `eventIds`: 아래 기간에 같은 SKU·원위치에서 `ON_HAND`를 줄인 이벤트 후보 ID. MOVE·감소 조정·출고 등 실제 감소 방향으로 판정한다. 이벤트가 어떤 입고 라인에 귀속되는지 확정하지 않는다.

| 사유                  | 해석                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------- |
| `INSUFFICIENT_ORIGIN` | 원위치 원장이 입고 대기 + 배치 관리 수량보다 적다.                                                |
| `POSSIBLE_BYPASS`     | 입고가 미처리였을 가능성이 있는 기간에 일반 반출 이력이 있다. 후속 보충으로 수량이 맞아도 남는다. |
| `INVALID_RECEIPT`     | 0 이하 입고, 음수 누계, 수량을 초과한 누계, 원위치 누락 또는 창고 불일치다.                       |

### 이력 근거의 범위와 한계

- 현재 잔량이 양수이면 입고 시각부터 감사 스냅샷까지를 후보 기간으로 사용한다(`completionBasis: OPEN`, `possiblePendingUntil: null`). 잔량이 0이어도 과거 후보는 유지한다.
- 완전히 처리된 라인은 실제 이벤트와 라인·회차·SKU·창고·출발지·수량·작업 방향이 일치하는 PUTAWAY/RETURN/CANCEL 업무 로그를 확인한다. 현재 POSTED인 이벤트의 처리량 합계가 입고량과 같으면 마지막 처리 이벤트 시각을 종료로 사용한다(`WORK_LOGS`). 취소는 원입고 이벤트의 역분개 연결도 일치해야 한다.
- 완료를 증명할 로그가 없는 과거 라인은 라인의 `updatedAt`을 임시 종료 시각으로 사용한다(`UPDATED_AT`). 이것은 후보 탐색 범위일 뿐 완료 증명이 아니다. 과거 갱신 시각이 유지되지 않았거나 이벤트가 소실된 경우를 이 도구로 완전히 복원할 수 없다. 수동 이력/실물 대사가 필요하며 오탐 후보도 보존한다.
- 정상 입고 작업과 정확히 연결된 이벤트는 VOIDED가 되었어도 일반 반출 후보에서 제외한다. 이름이나 reason 문자열만으로 제외하지 않는다. 미확정 `PENDING` 이벤트는 제외하며, 반출 뒤 역분개된 `VOIDED` 이벤트는 과거 확인 근거로 남길 수 있다.
- 현재 `posted` 회차가 대상이다. `voided` 회차 자체는 후보를 만들지 않는다. 정상 일반 선반 입고와 대기 기간 밖 이벤트, 다른 창고 데이터도 후보 대상이 아니다. 원위치가 없으면 임의 이벤트를 연결하지 않고 잘못된 입고 사실만 남긴다.
- 시간상 겹치는 여러 입고가 있어도 FIFO나 임의의 라인을 골라 귀속시키지 않는다. 후보 없음은 누락·삭제·잘못된 시각을 포함한 모든 과거 문제의 부재를 보장하지 않는다.

## 운영 순서

1. **대상 창고의 신규 재고 변경을 중지한다.** 입고·적치·일반 이동·출고·조정의 작업 중지 시간과 담당자를 기록한다. 기존 요청의 결과가 불명확하면 새 작업으로 다시 보내지 않는다.
2. **감사를 실행하고 원본 보고서를 보존한다.** 코드 `1`은 실패이므로 재실행한다. 코드 `2`이면 창고·SKU·원위치별 후보와 모든 line/event ID를 대사 목록으로 옮긴다.
3. **실물과 입고/이동/출고 이력을 대사한다.** 회차별 누계, 원위치 실제 재고, 후속 보충과 배치 관리 재고를 함께 확인한다. 증빙과 담당자의 판단을 남긴다. 미해결 후보가 있는 창고는 새 시험 운영에 넣지 않는다. 데이터 보정 실행은 별도 승인된 운영 절차의 범위이며 이 문서는 자동 FIFO 또는 누계 보정 SQL을 제공하지 않는다.
4. **모든 기기의 미확인 작업을 보존한다.** v2 작업 키, 원래 요청 본문, 사용자/API 범위와 확정 결과 재생 정보를 그대로 유지한다. 앱 저장소를 지우거나 새 키로 바꾸지 않는다. 상태 조회에 실패하면 작업 성공이나 취소 완료로 표시하지 않는다.
5. **Core와 앱을 전환한다.** 앱/admin-web을 배포 가능한 상태로 준비한 후 중지 시간대에 Core 가드·조회 계약, 앱 순서로 전환한다. 창고 권한과 범위 검증을 유지한다. capability 확인, 과거 키로 결과 확인, 입고 → 적치 → 선반 간 이동 → 출고, 취소 → 재개를 점검한다.
6. **새 보고서와 당일 실물을 재검사한 후 제한적으로 운영한다.** 첫 보고서는 덮어쓰지 않는다. 새 오류나 미해결 후보가 있으면 신규 변경을 멈추고 미확인 기록을 보존한다. 보호 가드를 제거하는 롤백으로 정상 운영을 대신하지 않는다.

## 개발 검증

통합 테스트는 이미 마이그레이션된 전용 DB `inbound_workflow_consistency_test`만 허용한다. 테스트는 개별 창고 fixture의 과거 상태를 SQL로 준비하고 지운다. 보호를 우회하는 제품 API를 추가하지 않는다.

```bash
# DATABASE_URL을 전용 테스트 DB로 명시적으로 주입한 뒤 실행한다.
corepack yarn test --runInBand --runTestsByPath \
  scripts/inventory/audit-inbound-origin-consistency.integration.spec.ts
```
