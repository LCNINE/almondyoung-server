# Medusa CPU 포화 — 사이트 전반이 느려질 때

**증상**: 카테고리 필터·상품 목록이 몇 초씩 걸린다. 특정 기능이 아니라 **전부** 느리다. 502 가 간헐적으로 난다.

**즉효약: 재배포(= 재시작)한다.** 원인 분석은 그 다음이다.

```bash
cd deployments/lcnine/services
nvm use 20.20.1 && export BUILDX_BUILDER=sst-builder
npx sst deploy --stage live --target Medusa
```

코드를 안 고쳐도 된다 — 효과를 내는 건 **태스크 교체**다. 옛 컨테이너가 죽으면서 그 안에 쌓인 대기 요청·메모리 상태가 통째로 사라지고, 새 컨테이너가 빈 손으로 시작한다.

## 왜 재시작으로 낫나 — 자기지속(self-sustaining) 포화

Medusa 는 **태스크 1개**로만 돈다 (valkey 사이드카 때문에 스케일아웃 불가). 이 1 vCPU 가 밀리기 시작하면:

```
요청이 느려짐 → 처리 중 요청이 내부에 쌓임 → 동시성이 올라가 더 느려짐 → …
```

**원인이 사라져도 상태가 안 돌아온다.** 2026-07-29 사례에서 유입 큐가 45건→8건으로 줄어든 뒤에도 CPU 는 50분간 100% 를 유지했다. 재배포하자 즉시 40% 로 떨어졌다.

## 진단 순서 — 어디가 원인인지 가르기

재시작 전에 5분만 쓰면 원인을 남길 수 있다. 순서대로 보면 후보가 하나씩 지워진다.

| 확인 | 정상이면 | 명령 |
|------|---------|------|
| **DB 활동** | active 소수, 느린 쿼리 0 → **DB 는 무죄, Node 내부 연산** | `pg_stat_activity` (아래) |
| **ALB 트래픽** | 급증 없음 → **유입 증가가 아님** | CloudWatch `RequestCount` |
| **메모리** | 평소 30~60% 변동. **한 값에 고정되면 이상** | CloudWatch `MemoryUtilization` |
| **SLOW 로그** | 특정 엔드포인트만 느린지, 전부 느린지 | CloudWatch Logs (아래) |

**전부 느리다 + 트래픽 그대로 = 자기지속 포화.** 특정 엔드포인트만 느리면 그건 쿼리/코드 문제라 재시작해도 안 낫는다.

```sql
-- medusa DB: 지금 뭘 하고 있나
SELECT state, count(*), max(now()-query_start) AS 최장
FROM pg_stat_activity WHERE datname='medusa' GROUP BY 1;
```

```bash
# SLOW 로그를 엔드포인트별로 집계 (포화 전 구간과 비교하는 게 핵심)
G=/sst/cluster/lcnine-services-live-ClusterCluster-zbwvckhv/lcnine-services-live-Medusa-cekfbtdh/main
aws logs filter-log-events --region ap-northeast-2 --log-group-name "$G" \
  --start-time <ms> --end-time <ms> --filter-pattern SLOW --limit 2000 \
  --query 'events[].message' --output json
```

## 예방

**1. 대량 작업은 새벽 4~7시에.** 최근 30일 주문 1,354건의 시간대 분포:

```
15시  150건 (피크)   13~16시에 30% 집중
12시   99건
 5시    1건 ← 30일간 1건
 4시    6건 / 6시 7건 / 7시 11건
```

02~03시는 심야 주문이 남아 있어 **04시 이후**가 안전하다.

**2. 배포 직후에 대량 작업을 붙이지 말 것.** 콜드 태스크가 큐를 떠안으면 회복이 안 된다. 배포와 최소 수십 분은 띄운다.

**3. 작업별 위험도** (2026-07-29 실측):

| 작업 | 이벤트 | CPU 영향 | 낮에 해도 되나 |
|------|--------|---------|---------------|
| 일일 재고 동기화 | 수백 건 | +8~10%p | ✅ (새벽이 더 안전) |
| 상품 대량 수정/게시중단 | 상품 수만큼 | 포화 위험 | ❌ 새벽 필수 |
| 대량 SKU 매칭·정책 일괄변경 | 1.8만 건 | 시간 단위 | ❌ 새벽 필수 |

재고 이벤트는 건당 가볍고(variant 수량 1개 갱신) 상품 이벤트는 무겁다(상품 전체 재구성). **건수보다 "얼마나 오래 끊이지 않고 들어오느냐"가 결정적이다** — 짧게 끝나면 회복할 틈이 있다.

## 구조적 한계 — 근본 대책

Medusa 는 **valkey 사이드카 때문에 태스크 1개**로 묶여 있다. 한 인스턴스가 무너지면 대안이 없고, 스케일아웃으로 못 푼다. valkey 를 분리해 다중 태스크로 가는 게 근본 대책이다.

CPU 포화 구간은 **결제 콜백 타임아웃 전력**이 있다 (주문 생성 실패 → `recoverBankTransferOrder` 컨슈머가 복구). 재고 반영이 늦는 건 참을 수 있어도 결제 실패는 고객이 즉시 체감하므로, 포화를 방치하지 말 것.
