# 카탈로그 읽기 경로의 개인화 입력은 방문자 세그먼트 하나다 — 문서는 세그먼트의 키, 개인은 조각

## Status
Accepted (2026-09-13). #854 의 결정. 구현은 #857(`_medusa_cache_id` 제거) → #858(헤더 배지·프로필
클라이언트 이관) → #617(HTML 캐시) → #859(정밀 무효화). #626 의 「판정을 하나로 합치는 건 답이
아니다」와의 관계는 Decision 마지막 항.

## Context
스토어프론트(`web/almondyoung-storefront`)는 멤버십 회원에게 다른 가격을 보여준다. 그래서 「이
방문자가 누구인가」를 알아야 하는데, 지금은 그 판정을 **페이지 조립 맨 안쪽에서, 데이터 fetch 마다,
쿠키와 고객 조회로** 한다. 코드로 확인된 결과가 넷이다.

- **`_medusa_cache_id` 는 이 배포에서 순비용이다.** Medusa 스타터가 방문자별 캐시 태그용으로 심는
  쿠키인데, (a) Next 의 fetch 캐시 **키**에는 태그가 들어가지 않아 격리 효과가 없고, (b) 방문자별
  태그는 백엔드가 지목할 수 없어 `/api/revalidate` 가 전역 태그(`PRODUCT_LIST_TAG`)와 전 카테고리
  경로를 매번 지우게 됐고(그 라우트 주석이 이 사정을 적는다), (c) `getCacheTag` 의 `cookies()`
  읽기가 모든 라우트를 dynamic 으로 굳히며, (d) 첫 방문 응답의 Set-Cookie 가 CDN 캐시를 막는다.
  2026-09-09~11 CloudFront 로그 3일 전수에서 HTML 적중률은 1.3% 였다(#614 코멘트).
- **로그인 사용자는 카탈로그 캐시 버킷이 사람 수만큼 갈린다.** `lib/api/medusa/products.ts` 가
  목록·상세 fetch 에 개인 JWT 를 `authorization` 헤더로 싣고, fetch 캐시 키는 헤더를 포함한다.
- **루트 레이아웃이 모든 페이지에서 프로필과 카트를 조회한다**(`app/layout.tsx` 의 `getMyProfile`
  · `retrieveCart(no-store)`). 헤더 배지 하나가 사이트 전체를 개인화 페이지로 만든다.
- **판정이 인라인으로 재구현돼 있고 필드 누락이 fail-open 된다**(#626·#627). 크롤러 CDN 분기는
  setter 없이 reader 만 남았다(#834).

한편 가격이 실제로 갈리는 축은 하나다 — 고객 그룹 룰이 걸린 price list 는 멤버십 하나이고
수량할인에는 그룹 룰이 없다(PR #616 본문의 확인, #854 에서 재확인 예정). 즉 카탈로그 응답은
(region, 멤버십 여부)의 함수이고 **개인별 변형이 없다.**

장래 계획으로 **회원 개인별로 완전히 개인화된 페이지**(추천·최근 본 상품·개인 쿠폰가)가 있다.
이 결정은 그 계획을 막지 않아야 한다.

## Decision
- **방문자 세그먼트는 셋이다 — `anon` / `reg` / `mem`.** 로그인 시점과 멤버십 가입·해지 시점에
  한 번 정해 **서명된 쿠키**로 준다. 카탈로그 GET 응답에는 Set-Cookie 를 싣지 않는다.
- **세그먼트는 서버가 내보내는 문서(HTML)의 키다.** 카탈로그 라우트(홈·카테고리·상품 상세·검색·
  베스트·신상품·shop-trade·cs)는 미들웨어가 세그먼트를 내부 경로로 rewrite 하고, 페이지는
  `cookies()`/`headers()` 대신 params 로 세그먼트를 받아 ISR 로 굳는다. 문서는 세그먼트 수만큼만
  존재한다.
- **사람마다 다른 것은 문서에 넣지 않고, 문서가 뜬 뒤 조각으로 붙인다.** 헤더의 카트 배지·프로필이
  첫 조각이다. 장래의 추천·최근 본 상품·개인 쿠폰가도 같은 자리다. 조각은 클라이언트 fetch 로
  시작하고, Next 의 PPR 이 안정되면 서버 스트리밍으로 바꿀 수 있다 — 경계는 같다.
  「홈에 내 최근 본 상품을 넣자」의 답은 **「문서에 넣지 말고 조각으로」** 다.
- **CDN 캐시 키에는 세그먼트 쿠키 하나만 넣는다.** OpenNext 서버 캐시 정책 transform 에서
  `x-crawler` 헤더 항목을 제거하고 `seg` 쿠키를 화이트리스트한다. 쿠키 없는 크롤러는 자동으로
  `anon` 이다 — 별도 크롤러 분기(#834)는 삭제한다.
- **`_medusa_cache_id` 와 방문자별 캐시 태그를 제거한다.** 태그는 전역·정밀해진다 —
  `product-{handle}`, `category-{id}`, 세그먼트별 목록 태그. 카트·배송 태그는 `cart-{cartId}` /
  `fulfillment-{cartId}` 로(카트 id 는 이미 `_medusa_cart_id` 쿠키에 있다).
- **Medusa 측 판정은 서버 간 키 + 세그먼트 헤더다.** PR #616 의 「서버끼리만 아는 키가 맞을 때
  세그먼트 헤더로 고객 그룹만 갈아끼운다」를 재료로 가져온다. 키가 없거나 틀리면 토큰 기반 판정으로
  떨어지고 그 응답은 캐시하지 않는다. 고객 조회에 실패해 세그먼트를 모르면 비회원으로 단정하지 않고
  토큰을 실어 Medusa 가 정하게 한다.
- **카트·체크아웃·마이페이지는 이 ADR 의 대상이 아니다.** 개인 토큰 경로로 남고, 직렬 왕복 축소는
  #835 가 소유한다.
- **#626 과의 경계.** #626 은 「실패 방향이 호출부마다 달라야 하므로 판정을 하나로 합치는 건 답이
  아니다」라 했다. 이 ADR 은 그 논리를 **카탈로그 문서에는 적용하지 않는다** — 거기서는 세그먼트
  하나가 정답이고 틀리면 「비회원 가격이 보인다」 한 방향으로만 틀린다. 카트·결제·구매 버튼에는
  #626 의 논리를 그대로 둔다. 즉 「실패 방향이 다르다」는 경계를 **문서와 개인 경로 사이에** 긋는다.

## Consequences
- **비로그인 문서는 어떤 개인화를 더해도 항상 전량 캐시된다.** anon 에는 붙일 조각이 없다. 이것이
  이 설계가 보장하는 최소치다.
- **회원 문서도 껍데기는 캐시된다.** 개인화가 늘수록 조각이 늘 뿐 문서의 적중률은 변하지 않는다.
  「목록의 순서 자체가 사람마다 다르다」(개인 추천 정렬)는 요구가 오면 그 목록 블록 전체가 조각이
  된다 — 그래도 anon 은 영향이 없다.
- **효과의 크기는 비로그인 비율이 정한다.** CloudFront 액세스 로그는 `includeCookies: false` 라
  지금은 못 센다. `seg` 쿠키가 캐시 키에 들어간 뒤부터 세그먼트별 적중률을 로그에서 읽을 수 있다.
  구현 전 표본은 storefront Lambda 로그의 `_medusa_jwt` 유무로 한 번 낸다(#854).
- **멤버십 가입·해지 직후 짧은 지연.** 쿠키를 바꿔 주는 지점이 가입·해지 처리 경로에 있어야 한다.
  그 경로가 스토어프론트 밖(멤버십 서비스의 결제 웹훅 등)에서 끝나는 경우가 있으면 짧은 max-age +
  만료 시 1회 재판정 폴백이 필요하다. 구현 전 실측 항목(#854).
- **세그먼트가 넷 이상이 되면** 캐시 벌 수가 그만큼 늘 뿐 구조는 같다. 그러나 **가격이 사람마다
  달라지는 기능**(개인 쿠폰가를 목록에 표시 등)은 이 경계를 넘으므로, 문서가 아니라 조각으로
  보여주거나 장바구니에서 보여준다. 그 반대를 원하면 이 ADR 을 개정한다.
- 헤더 배지가 한 박자 늦게 뜬다(문서 먼저, 숫자는 조각). 깜빡임 완화는 #858 의 선택 항목.
- `/api/revalidate` 가 정밀해진다(#859) — 호출 측이 건드린 상품·카테고리를 싣고, 일괄 세션은
  종료 시 1회. #852 의 지배 원인은 아니지만 HTML 캐시가 일괄 작업을 살아남는 전제다.
- 회원전용 카테고리 필터(#627)는 세그먼트별 렌더 한 곳으로 모인다. 필드 누락이 fail-open 되는
  구조는 그 한 곳에서 막는다.
- PR #616 은 이 ADR 의 재료로만 쓰고 되살리지 않는다.
- 검증: PR #616 본문의 4행 표(헤더 없음 / 세그먼트+올바른 키 / 세그먼트+틀린 키 / 세그먼트만)를
  그대로 재실행하고, 카탈로그 GET 응답에 Set-Cookie 가 없음을 로컬 프로덕션 빌드로 확인한다.
  엣지 캐시 키 분리는 배포 후에만 확인된다.
