# 관리자 권한은 «권한 키»로 판정하고, 역할↔권한 매핑의 원본은 user-service 다

## Status
Accepted (2026-10-12). 적용은 단계별로 한다 — 이 ADR 시점에는 목록·원본·배포 경로만 있고 판정은 기존 가드가 한다.

## Context
관리자 업무가 나뉘면(CS·MD·물류·인턴 …) 역할마다 볼 수 있는 화면과 할 수 있는 일이 달라야 한다. 지금 판정은 역할 이름 비교
(`admin`·`master`), 서비스별 스코프, 서비스 고유 가드가 섞여 있고, 스코프 매핑은 서비스마다 부팅 때 코드로 다시 쓰여서
화면에서 바꿀 수 없다.

## Decision
1. **권한 키.** 관리자 권한은 `영역.대상.행동` 키 하나로 표현한다(예: `order.order.read`, `payment.refund.execute`).
   영역은 서비스가 아니라 업무 단위다. 목록의 원본은 `@app/authorization` 의 `PERMISSION_CATALOG` 이고, 키는 `Permission`
   리터럴 유니온 타입이라 목록에 없는 키는 컴파일되지 않는다. 와일드카드는 쓰지 않는다.
2. **매핑의 원본은 user-service DB 다** (`iam_permissions`·`iam_role_permissions`). 코드는 매핑을 덮어쓰지 않는다.
   부팅 동기화는 새 키만 넣고, 그 키가 «처음» 들어갈 때만 `grantOnFirstRegistration` 역할에 한 번 부여한다.
   목록에서 사라진 키는 지우지 않고 `deprecated_at` 만 찍는다.
3. **토큰에는 역할만 싣는다.** 다른 서비스는 user-service 내부 경로(`GET /internal/iam/role-permissions`, 버전 ETag)에서
   역할별 권한을 받아 메모리에 두고 판정한다. 버전은 스냅샷 «내용»에서 계산한다 — 역할을 바꾸는 경로(관리 API, 시드,
   직접 SQL)가 버전을 올리는 걸 잊어도 캐시가 낡지 않는다.
   화면은 `GET /me/permissions` 를 쓴다 — 역할 입력은 토큰이라 화면과 API 가 같은 입력으로 판정한다.
4. **코드는 역할 이름이 아니라 권한만 본다.** 예외는 user-service 의 시스템 역할 규칙 한 곳(`api/iam/iam.constants.ts`)이다:
   master 는 활성 권한 전체를 계산해서 받는다.
5. **초기 부여는 «지금 그 역할이 실제로 할 수 있는 것»을 옮긴다.** 권한 확대는 배포가 아니라 관리 화면에서 한다.

### 라우트 분류와 판정
6. **모든 HTTP 라우트는 넷 중 정확히 하나로 분류한다:** 공개(`@Public`·`@InternalOnly`·`@OptionalAuth`) · 고객(`@StoreRoute`) ·
   키(`@KeyAuthRoute` — 그 앱의 가드가 머천트 API 키 같은 키를 검사하는 경로) · 권한(`@RequirePermission` /
   `@RequireAnyPermission`). `scripts/security/route-classification.spec.ts` 가 강제한다.
7. **조회 동사(GET·HEAD)는 조회 권한을, 쓰기 동사는 조회 아닌 권한을 요구한다.** 예외는 같은 스펙에 이유와 함께 둔다.
8. **각 서비스는 역할별 권한을 메모리에 둔다(`PermissionModule`).** 요청마다 네트워크를 타지 않고, 버전 확인은 배경에서
   주기적으로 한다. 한 번도 받지 못한 상태는 «권한 없음»이 아니라 «판정 불가»로 따로 다룬다.
9. **권한 분류 라우트는 언제나 새 판정(`PermissionGuard`)이 결정한다.** 처음에는 «그림자 → 강제» 순서로 켰다(그림자 단계는
   기존 가드가 결과를 정하고 새 판정은 비교 기록으로만 남겼다). 모든 서비스를 강제로 옮긴 뒤 스위치·기존 가드·비교 기록을
   걷어 냈다(2026-10 개정). 판정은 판정한 자리에서 기록한다 — `AuthzDecisionLog` 가 서비스별 허용·거부·판정 불가를
   `authz_decisions_total` 지표와 창별 요약 로그로 남기고, 거부·판정 불가는 창마다 첫 1건을 자세히 남긴다.
   권한 사본의 나이는 `authz_permission_snapshot_age_seconds` 로 따로 본다 — 갱신이 실패하면 마지막 사본으로 판정을 이어 가므로
   나이가 늘어나는 것이 원본 장애의 신호다(사본을 한 번도 받지 못한 프로세스만 판정 불가다).
10. **가드 순서:** 인증 → 권한 가드(맨 뒤). 권한 분류 라우트에 기존 인가 층은 없다(2026-10 개정).
    `scripts/security/permission-wiring.spec.ts` 가 지킨다.

### 판정 지점
11. **라우트 가드 안쪽의 판정도 권한으로 표현한다** — 남이 잡은 작업 넘기기, 서비스 안 재확인, 본문 조건, 리소스 소유
    예외 같은 곳이다. 지점마다 이름(`영역.이름`, 지표 라벨)을 붙이고 `PermissionCheckpoints.check`(주체)·`checkRoute`(요청)로
    권한만 보고 판정한다. 판정 불가(권한 사본 없음)는 거부다. 지점별 판정은 라우트 판정과 같은 판정 기록에 지점 이름으로 남는다.
    (처음에는 옛 판정과 나란히 비교하며 옛 판정이 결과를 정했지만, 옛 식은 걷어 냈다 — 2026-10 개정.)
12. **같은 서비스 메서드를 권한이 다른 라우트 둘이 부르는 곳은 역할을 다시 따지지 않는다.** 라우트의 `PermissionGuard` 가
    «이 요청이 이 라우트에서 받은 권한»을 요청에 남기고(`getPermissionDecision`), 소비하는 쪽은 그 표식을 본다.
    표식은 가드가 발급한 객체만 인정한다.
13. **사람이 아닌 내부 호출자는 시스템 주체(`systemPrincipal`)로 판정한다.** 사람 역할 이름을 빌리지 않고, 권한 사본이
    없어도 판정할 수 있다.
14. **역할 이름을 판정에 쓰는 코드는 `scripts/security/role-name-checks.spec.ts` 의 목록에만 남는다.** 새 코드는 목록에
    더하지 않는다. 옛 판정을 걷어 낼 때 목록을 비운다. 권한 분류 라우트의 옛 가드와 판정 지점의 옛 식은 비웠고, 남은 것은
    시스템 역할 규칙·역할↔권한 매핑·시스템 행위자 표기와 데이터 값이다(종류는 `role-name-checks.baseline.ts` 가 적는다).
    스캐너는 쉼표로 합친 문자열(`'admin,master'`)의 조각과, 역할 이름 자리에 놓인 고객 역할 이름(`'user'`·`'membership'`)도 센다.
    옛 스코프 가드·`AuthorizationService`·부팅 매핑은 걷어 냈고, 옛 표(`auth` 스키마)도 마이그레이션으로 지웠다.
15. **관리자 화면의 진입 권한은 경로 권한표(`apps/admin-web/src/lib/auth/screen-access.ts`) 한 곳에 둔다.** 페이지는
    `RouteGuard screen="<자기 경로>"` 로 선언하고, 메뉴·검색·모바일 메뉴는 같은 표로 보이기를 정한다. 상세 화면은 가장
    가까운 상위 경로를 물려받는다. 메뉴는 환경마다 달라질 수 있어 판정의 원본이 될 수 없다.
16. **화면의 진입 권한은 그 화면의 주 데이터를 부르는 API 의 권한이다.** 버튼은 `<Can anyOf>`·`useCan` 으로 판정한다.
    권한을 아직 받지 못한 상태는 «권한 없음»으로 보이지 않는다(서버는 «판정 불가» 화면, 버튼은 감춤).
17. **화면의 권한 출처는 user-service `/me/permissions` 다.** 서버는 역할 조합별로 짧게 캐시하고, 조회에 실패하면 마지막
    사본을 쓴다. 화면 판정은 안내이고 강제는 각 API 가 한다.
18. **Medusa 프록시는 `(메서드, 경로) → 권한` 표로 판정하고 표에 없는 경로는 거부한다.** admin-web 이 부르는 Medusa 경로가
    전부 표에 있고, 표의 규칙이 실제로 부르는 조합만 여는지 게이트가 확인한다.
19. **권한 거부(403)는 필요한 권한 키를 `requiredPermissions` 로 알려 준다.** 화면은 그 키를 권한 이름으로 바꿔 안내한다.
20. **쓰기 동작의 권한은 뮤테이션 훅이 선언한다.** `useX.permission = [...] as const satisfies PermissionRequirement`.
    여러 API 를 차례로 부르는 동작은 `{ allOf: [...] }` 로 전부를 요구하고, 컴포넌트 안에서 만든 뮤테이션은
    `meta.permission` 으로 선언한다. 본인 계정 동작(로그인·비밀번호·내 정보)은 `'self'`.
21. **화면은 훅을 가리켜 판정한다** — `<Can run={useX}>`·`usePermissionCheck().canRun(useX)`·`blockedReason(useX)`·
    `<PermissionReadOnly run={useX}>`. 버튼에 권한 키를 다시 적지 않는다. 다른 화면으로 가는 쓰기 진입점은
    `<CanOpen screen="…">`(진입 권한표).
22. **권한이 없는 단독 트리거는 숨기고, 현재 값을 보여 주는 컨트롤은 값을 보이되 막고(`aria-disabled` + 이유),
    편집 폼은 읽기 전용(텍스트 입력은 `readOnly`)으로 둔다.** 권한을 확인하기 전·조회에 실패한 동안에도 트리거는
    보이지 않고, 조회 실패는 화면 위 안내로 알린다. 화면 진입 권한과 다른 조회는 권한이 없으면 요청하지 않고 «가림»으로 보인다.
23. **게이트가 지킨다** — 모든 뮤테이션이 권한을 선언했는지, admin 이 master 전용 말고 전부 실행할 수 있는지,
    뮤테이션을 부르는 화면 파일(또는 그 파일을 그리는 상위 파일)에 그 권한 판정이 있는지(`mutation-guard.gate.spec.ts`).

### 역할·권한 관리

24. **역할·권한·부여를 바꾸는 요청은 user-service `iam` 의 Manager 한 곳을 지난다.** 규칙은 넷이다.
    ① 역할을 만들거나 권한을 바꾸려면 바뀐 뒤 권한(활성 권한) 전체를 요청자가 가져야 하고, 역할을 주거나 회수하려면
    그 역할의 권한 전체를 요청자가 가져야 한다(내가 가진 권한만 남에게 준다).
    ② 시스템 역할은 바꾸거나 지우지 않는다. ③ 자기 역할은 다른 관리자가 바꾼다.
    ④ 로그인할 수 있는 플랫폼 운영자가 한 명 이상 남는다(운영자 행을 잠근 뒤 센다). 운영자는 역할이 아니라 계정의 성질이다
    (`users.is_platform_operator`). (처음에는 «기간 없이 시스템 역할을 가진 사람»을 셌다 — 시스템 역할은 이제 테넌트 안의
    전권 역할이라 잠김 방지를 운영자로 옮겼다.)
    ①은 권한 상승이라 403, ②~④와 버전 충돌·소속 인원이 있는 역할의 삭제는 409 이며, 응답 `code` 로 사유를 구분한다.
    ①의 «요청자의 권한»은 토큰의 역할 중 지금도 유효한 부여만으로 계산한다(토큰 발급 뒤 기간이 끝났거나 회수된 역할은 빼고,
    토큰에 없는 역할을 더하지도 않는다). 관리자 계정을 만들며 첫 역할을 주는 것도 같은 Manager 를 지나 ①~④를 따르고,
    화면은 계정 관리와 역할 부여 권한을 모두 가진 사람에게만 그 버튼을 보인다.
25. **역할의 권한은 «전체 집합 + 버전»으로 저장한다.** 버전이 다르면 409(`ROLE_VERSION_STALE`). 역할 ID(`name`)는 만들 때만
    정하고, 화면에는 표시 이름을 쓴다(토큰이 역할 ID 를 싣기 때문이다).
26. **권한 의존은 권한 목록이 선언한다** — 쓰기·특수 동작은 같은 대상의 조회를, 같은 대상 조회가 없으면 `requires` 를,
    기대는 조회가 없으면 `standalone` 을 적는다(`permission-dependencies.spec.ts`). 역할 편집 화면은 켤 때 의존을 함께 켜고
    끌 때 기대는 것을 함께 끄며, 서버는 이번 저장이 새로 연 누락을 거부한다(보충하지 않는다).
27. **변경 이력은 변경과 같은 트랜잭션에 쓴다** — 이력을 못 쓰면 변경도 없다. 대상과 요청자의 이름은 그 시점 값으로 남기고,
    이력을 고치거나 지우는 경로는 두지 않는다.
28. **역할에 로그인 첫 화면을 지정할 수 있다.** 여러 역할을 가진 사람은 첫 화면이 지정된 역할 중 먼저 만들어진 역할의 값을 쓴다
    (사람마다 다른 값이 아니라 역할 조합만의 값이어야 화면 서버가 권한을 역할 조합으로 캐시할 수 있다). 로그인 직후 기본
    목적지로 갈 때만, 그 화면을 열 수 있을 때만 적용한다.

### 개인정보 표시 제한·접속기록

29. **개인정보를 응답하는 관리자 라우트는 `@PiiResponse` 로 «어느 응답 경로가 어떤 종류의 개인정보인지»와 «대상 식별자 경로»를 선언한다.**
    응답 DTO 는 인스턴스로 만들어지지 않으므로 필드 데코레이터가 아니라 라우트 단위로 적는다. 앱 루트의 `PiiMaskingInterceptor` 가
    그 선언만 본다 — 선언 없는 라우트는 그대로 지난다. 선언 라우트 목록은 `scripts/security/pii-routes.ts` 가 정본이고
    `pii-routes.spec.ts` 가 목록과 선언을 양쪽으로 맞춘다(`@Res()` 금지 — 인터셉터를 건너뛴다).
30. **원문은 권한으로 연다.** 기본 `customer.pii.read`. 출고 화면의 받는 분·주문자 정보는 `fulfillment.recipient.read` 로도 연다.
    권한이 없거나 권한 사본을 아직 받지 못했으면 가린 값을 보낸다 — 판정 불가를 «권한 있음»으로 보지 않는다.
31. **가림 형식은 `libs/shared/src/pii` 한 곳이 정한다**(이름 가운데·전화 가운데 4자리·이메일 앞 2자·주소 시·군·구까지·계좌 끝 4자리,
    비밀값·자유서술은 `[가림]`, 모양이 정해지지 않은 객체는 null). 화면마다 다르게 가리면 여러 화면을 맞춰 원문이 복원되기 때문이다.
    admin-web 은 같은 폴더를 `@pii-masking` 별칭으로 가져간다.
32. **가렸다는 사실은 응답 헤더로 알린다** — `X-Pii-Masked`·`X-Pii-Mask-Reason`·`X-Pii-Redacted`·`X-Pii-Revealable`. 본문 모양은 바꾸지 않는다.
    화면은 셸 배너로 «가려져 있다»와 그 이유를 보인다(가린 값이 «없음»으로 읽히지 않게).
33. **원문이 나간 직원 응답마다 접속기록 1행을 «응답 전에» 남기고, 남기지 못하면 원문 대신 가린 값을 보낸다.** 기록에는 원문 값을 넣지
    않는다 — 행위자·시각(ms)·직원 단말 주소(프록시가 넘긴 값과 연결 주소를 따로)·서비스·라우트 패턴·수행업무(열람·보기·내려받기)·
    대상 식별자(상한 1,000 + 실제 건수)·항목 종류·쿼리 키(값 없음). 아웃박스가 있는 앱은 `PiiAccessed`(`IAM_STREAM`) 이벤트로,
    아웃박스가 없는 앱은 user-service 내부 기록 API 로, admin-web 의 Medusa 프록시는 직원 본인 토큰으로 기록한다.
34. **권한자도 기본 가림으로 바꾸는 스위치가 있다**(`PII_REVEAL_REQUIRED`, 기본 꺼짐). 켜면 `customer.pii.read` 보유자도 가린 값을 받고,
    단건 상세에서 [보기](`X-Pii-Reveal: 1`)로 원문을 연다. 수령인 권한으로 여는 출고 정보는 스위치와 무관하다.
35. **개인정보가 든 내보내기는 사유를 받는다** — `@PiiExport` 라우트는 원문이 나갈 때 `X-Pii-Export-Reason`(5~200자, URI 인코딩)이 없으면
    400 이고, 사유는 접속기록에 남는다. 예외는 `PII_EXPORT_EXCEPTIONS` 에 이유와 함께 적는다.
36. **접속기록은 쓰고 읽기만 한다.** 고치는 경로가 없고, 보관 기간(`PII_ACCESS_LOG_RETENTION_DAYS`, 기본 2년)이 지난 행만 정리 크론이
    지운다. 접속기록을 보는 것도 변경 이력에 남긴다. 점검 기록은 기간·점검자·메모를 남긴다(주기는 내부 관리계획이 정한다).
37. **판정 주체를 고르는 스위치는 없다.** 권한 분류 라우트(`@RequirePermission`)는 `PermissionGuard` 만 결정하고, 기존 인가 가드는
    그 라우트에 걸지 않는다. 공개·고객·키·내부 라우트는 각자의 가드가 판정한다. 되돌리기는 스위치가 아니라 직전 배포 태그
    (`deploy/<stage>/<KST 시각>`) 커밋의 재배포다 — 코드와 배포 설정을 함께 되돌려야 옛 코드가 강제 모드로 뜬다(이미지만 돌리면
    옛 가드가 판정한다). 데이터는 바뀌지 않는다. (처음에는 서비스별 스위치와 옛 가드의 물러남을 답하는 한 곳을 두었으나 2026-10 개정으로 걷어 냈다.)
38. **판정 지점은 권한으로만 판정한다** — `PermissionCheckpoints.check`·`checkRoute`(판정 불가는 거부). (처음에는 같은 스위치를
    따라 옛 판정과 비교하는 `compare`·`compareDecision` 이었다.)
39. **라우트 판정 낙인은 `PermissionGuard` 만 발급한다.** 낙인을 소비하는 곳은 그 판정 함수 하나를 거친다. (처음에는 모드에 따라
    옛 스코프 가드의 낙인도 읽었다.)
40. **개인정보 원문을 본문으로 받는 쓰기는 `@PiiWrite` 로 그 필드를 선언한다.** 본문에 그 필드 값이 있으면 그 원문을 볼 수 있는 권한이 있어야
    한다(필드를 고치려면 그 필드를 볼 수 있어야 한다). 목록은 `scripts/security/pii-routes.ts` 의 `PII_WRITE_ROUTES`.
41. **고객 역할(회원 등급)을 주거나 회수하려면 `customer.profile.write` 도 있어야 한다** — 고객 역할을 바꾸는 것은 고객 정보를 고치는 일이다.
42. **플랫폼 운영자는 휴면 전환 대상이 아니고, 로그인할 수 있는 마지막 운영자는 탈퇴하거나 강등될 수 없다** — 플랫폼을 관리할 사람이 남아야 한다.
43. **업무 기능이 «누가 그 업무 대상인가»를 고를 때도 역할 이름이 아니라 권한을 가진 역할의 보유자로 고른다** — 근태 직원은 `attendance.own.write`, 근태 요청 알림 대상은 `attendance.request.review` 를 가진 역할의 보유자다. 권한 사본을 아직 받지 못했으면 «아무도 없음»이 아니라 판정 불가(503·그 회차 건너뜀)로 다룬다.
44. **급여(`attendance.wage.*`)는 첫 부여가 없다(master 만)** — 조회·설정·내려받기를 나눠 두고, 연장·부재 판정은 근태 판단 권한(`attendance.request.review`)으로 한다. 본인 급여는 `attendance.own.write` 로 열되 대상은 토큰의 사용자로만 고른다(경로·쿼리에 사람을 고르는 값이 없다). 시급·급여액은 개인정보 가림 대상이 아니라 권한으로만 막고, 내려받기는 변경 이력에 한 줄 남긴다.
45. **고객 셀프서비스 라우트는 `@StoreRoute` 와 토큰의 사용자로만 판정한다** — 로그인한 계정이면 누구나 자기 데이터만 다룬다(대상 식별자는 토큰에서 얻는다). 직원 계정은 셀프 탈퇴할 수 없다: 살아 있는 고객 아닌 역할이 있으면 409(`IAM_STAFF_CANNOT_LEAVE`)이고, 판단은 토큰이 아니라 DB 의 역할 부여로 한다. 역할을 회수하거나 기간이 지나면 탈퇴할 수 있다.
46. **직원 후보를 고르는 목록은 `GET /admin/users?audience=staff&holding=<권한>` 로 받는다** — `holding` 은 목록을 거르지 않고 행마다 `holdsPermission` 을 더한다. 후보 선택 화면은 그것으로 권한 보유자를 표시한다. `audience=staff` 없이 `holding` 만 보내면 400 이다.
47. **역할 부여는 언제나 «어느 테넌트에서의» 부여다** — 부여 행에 테넌트가 있고, Manager 는 요청자가 일하는 테넌트 안의 부여만 계산한다(다른 테넌트의 부여는 보지도 지우지도 않는다). 그 테넌트의 소속(`tenant_memberships`)이 없는 계정에는 직원 역할을 주거나 늘릴 수 없다(409 `IAM_NOT_TENANT_MEMBER`). 고객 역할은 소속 없이 받는다. 관리자 계정 생성은 요청자 테넌트의 소속을 먼저 만든다. 변경 이력·개인정보 접속기록은 테넌트를 남긴다.

## Consequences
- 역할 구성을 배포 없이 바꿀 수 있다. 변경은 각 서비스의 버전 확인 주기 안에 반영된다.
- 사람↔역할 변경은 access 토큰 수명 안에 반영된다(토큰 발급 경로가 매번 DB 에서 역할을 읽는다).
- 새 권한을 추가하는 PR 은 목록에 한 줄을 더하고 `grantOnFirstRegistration` 을 정한다. 비워 두면 배포 직후 master 외에는
  그 기능을 못 쓴다.

## Not adopted
- 토큰에 권한 목록 싣기 — 권한이 세분될수록 토큰이 커지고, 회수가 토큰 수명만큼 늦어진다.
- 서비스별 매핑 사본 유지 — 화면에서 여러 서비스에 나눠 써야 하고 일부만 반영되면 서비스마다 권한이 갈린다.
- 정책 엔진(관계 기반·정책 언어) — 데이터 단위 권한(«담당 창고만»)이 생기면 판정부만 그쪽으로 옮긴다. 인터페이스는 권한 키로 유지한다.
