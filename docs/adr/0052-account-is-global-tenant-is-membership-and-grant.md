# 계정은 전역, 테넌트는 소속과 부여로 — 운영자는 계정의 성질

## Status
Accepted (2026-10-29, 교정 10-30). 라이브(2026-11-02). [[0048-admin-permission-model]] 의 역할·권한 사슬 위에 테넌트를 얹는다.
멀티테넌트 전체 그림은 `docs/multi-tenancy.md`. 🔸 열린 질문: «테넌트마다 계정을 따로 둔다»로 이 결정을 다시 열 수 있다(아래 Consequences 끝).

## Context
user-service 는 계정·역할·토큰을 한 DB 에 들고 있고, [[0048-admin-permission-model]] 의 권한 사슬은 역할 «이름»을 키로 토큰·스냅샷·캐시를 잇는다.
테넌트가 둘 이상이 되면서 «누가 어느 테넌트에서 무엇을 할 수 있나»를 어디에 둘지 정해야 했다. user-service 를 테넌트로 쪼개는 길([[0051-core-tenant-per-database]] 처럼)은
login_id·email·소셜·사업자번호 unique 와 로그인 흐름 전체를 건드린다.

## Decision
1. **계정(사람의 신원)은 전역에 하나.** 테넌트와의 관계는 **소속**(직원 관계)과 **테넌트별 역할 부여**로만 표현한다. 역할 정의는 전역이다.
2. **토큰에는 토큰 테넌트(`tenant` 클레임)가 실리고, 역할은 그 테넌트에서 받은 부여만 싣는다.** 이 한 줄이 빠지면 테넌트 2 관리자가 테넌트 1 쇼핑몰 토큰으로
   테넌트 1 관리자가 된다. 소속이 없는 테넌트에서는 역할을 받을 수 없다.
3. **토큰 테넌트를 정하는 곳**: 고정 테넌트 앱(쇼핑몰)은 앱이, 웹 직원 앱(admin-web)은 **들어온 주소(테넌트 도메인)**가 정한다([[0055-tenant-shell-on-tenant-domain]]).
   user-service 는 OAuth 리디렉트를 «등록된 리디렉트 호스트 → 테넌트 도메인 → 테넌트»로 풀어 토큰 테넌트를 정한다(쿼리 파라미터·Host 헤더가 아니다).
   주소가 없는 앱(warehouse-app)만 소속에서 고른다.
4. **user-service 안의 테넌트 1 데이터**(고객·근태 등)는 **토큰 테넌트가 1 일 때만** 답한다. 역할이 전역이라 권한 키만으로는 막을 수 없다.
5. **플랫폼 운영자는 테넌트 역할이 아니라 계정에 붙는 성질이다.** 역할·부여·소속·테넌트 관리는 운영자가 한다. `master` 는 테넌트 안의 전권 역할로 내려오고,
   잠김 방지는 «마지막 플랫폼 운영자» 규칙으로 옮긴다. 운영자 API 는 운영자 성질과 토큰 테넌트의 `master` 둘 다를 본다.
6. **역할·부여·소속·운영자를 바꾸는 코드는 user-service `iam` Manager 를 거친다.** 권한 상승 방지·시스템 역할·자기 자신·마지막 운영자·소속 없는 테넌트 부여 거절과
   변경 이력(`iam_audit_logs`, 테넌트 포함)이 같은 트랜잭션에 묶인다.
7. **내부 세션 토큰도 `tenant` 를 싣는다.** 테넌트 없는 옛 내부 토큰은 core 가 거절한다.

## Considered Options
- **테넌트마다 계정 행** — 개인정보 경계가 구조로 서고 계약 종료 삭제가 한 번에 끝나지만, 전역 unique 들을 넓히고 로그인 화면이 아이디 전에 테넌트를 알아야 한다. 이번엔 반려.
- **역할을 테넌트 소유로** — 테넌트별 역할 편집이 되지만 [[0048-admin-permission-model]] 의 역할 이름 키 사슬을 다시 써야 한다. 보류(부여에 테넌트가 이미 있어 나중 길은 열려 있다).
- **`master` = 플랫폼 운영자** — `master` 가 모든 테넌트 토큰에 실려 전 테넌트를 본다. 반려.
- **운영자에게 모든 테넌트 소속** — 교차 접근에 기간·사유가 남지 않는다. 반려.

## Consequences
- 계정 삭제는 «다른 소속도, 고객 역할도 없는 계정만». 개인정보 경계는 구조가 아니라 위 규칙들이 지킨다.
- 새 테넌트의 직원 계정·역할 부여·비밀번호 초기화는 운영자가 대행한다(테넌트 도메인엔 가입·아이디/비밀번호 찾기가 없다 — [[0055-tenant-shell-on-tenant-domain]]).
  대행으로 만든 직원 계정은 `UserCreated`(고객 가입 이벤트)를 내지 않는다. 첫 로그인에 비밀번호 변경을 강제한다.
- 기존 데이터 백필: 비고객 부여가 있는 계정 → 테넌트 1 소속, 기존 부여 → 테넌트 1, 기간 없는 `master` 보유자 → 운영자 성질(전환 순간 운영자 0명 방지).
- 운영자도 다른 테넌트 데이터를 직접 보지 않는다(지원 접근은 아직 없다). 돕는 건 화면 공유로 한다.
- 계정 이벤트(`users.events.v1` 의 계정 수명주기)는 테넌트가 없는 «계정 이벤트»로 계약에 선언된다([[0053-event-tenant-stamped-by-library-gated-before-handler]]).
- 🔸 사용자 모델로는 «테넌트마다 별개 계정»이 더 자연스럽다는 의견이 있어, 이 결정을 뒤집는 방향을 나중에 다시 연다. 그때 함께 볼 것: 계정 이벤트의 테넌트,
  내부 세션 토큰의 `tenant`, 다른 테넌트 직원이 테넌트 1 주소로 로그인하는 경우(지금은 로그인되지만 역할 0개다).
