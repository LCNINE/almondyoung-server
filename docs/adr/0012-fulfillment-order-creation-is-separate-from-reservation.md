# 출고주문 생성은 재고예약과 분리한다

> **Update (2026-07-18, outbound V2):** 이 결정의 **목표**(재고 부족이 출고주문 생성을 실패시키지 않는다, 매칭 부재는 fail-closed)는 유지되나 **메커니즘은 대체되었다.** 현행 코드는 FO 생성과 같은 트랜잭션에서 상자(draft shipment)·상자 라인을 만들고 라인별 `reservePartial` 로 **부분예약**한다 — 예약 대상은 FO 가 아니라 상자 라인(`stock_reservations.shipmentLineId`)이며, 재고 부족은 실패 상태가 아니라 미달 수량으로 남아 재시도 워커(10초 크론)가 채운다. FO 의 `partially_reserved`/`ready` 는 라인 예약량에서 파생되는 projection 이다. 아래 "생성과 예약을 한 트랜잭션 성공 조건으로 묶는 API 는 폐기한다"는 항목은 "한 트랜잭션에서 실행하되, 예약 충족을 생성의 성공 조건으로 삼지 않는다"로 재해석된 상태다.

Core 의 출고주문 생성은 판매주문 라인을 SKU 구성으로 번역하는 단계이며, 판매상품↔재고상품 매칭이 없으면 생성 자체가 불가능하다. 반면 매칭이 있고 실제 재고가 부족한 경우에는 출고주문과 출고주문 아이템을 생성한 뒤 reservation 단계에서 실패/대기 상태로 남긴다. 재고 부족을 출고주문 생성 실패로 처리하면 결제 수락된 판매주문이 왜 출고되지 못하는지 운영자가 추적할 객체가 사라진다.

## Consequences

- Canonical 출고주문 생성 경로는 매칭 검증을 fail-closed 로 수행해야 한다.
- Reservation 은 출고주문 생성 후 상태 전이이며, 재고 부족은 출고 불가/대기 상태와 실패 사유로 표현한다.
- 생성과 예약을 한 트랜잭션 성공 조건으로 묶는 API 는 폐기하거나 리팩터링한다.
- 빈 출고주문 또는 매칭 누락 라인을 조용히 제외한 출고주문은 만들지 않는다.
