# 관리자 권한은 «권한 키»로 판정하고, 역할↔권한 매핑의 원본은 user-service 다

## Status
Accepted (2026-10-12). 적용은 단계별로 한다 — 이 ADR 시점에는 목록·원본·배포 경로만 있고 판정은 기존 가드가 한다.

## Context
관리자 업무가 나뉘면(CS·MD·물류·인턴 …) 역할마다 볼 수 있는 화면과 할 수 있는 일이 달라야 한다. 지금 판정은 역할 이름 비교
(`admin`·`master`), 서비스별 스코프, 서비스 고유 가드가 섞여 있고, 스코프 매핑은 서비스마다 부팅 때 코드로 다시 쓰여서
화면에서 바꿀 수 없다.

## Decision
1. **권한 키.** 관리자 권한은 `영역.대상.행동` 키 하나로 표현한다(예: `order.order.read`, `payment.refund.execute`).
   영역은 서비스가 아니라 업무 단위다. 목록의 원본은 `@app/authorization` 의 `PERMISSION_CATALOG` 이고, 키는 `Permission`
   리터럴 유니온 타입이라 목록에 없는 키는 컴파일되지 않는다. 와일드카드는 쓰지 않는다.
2. **매핑의 원본은 user-service DB 다** (`iam_permissions`·`iam_role_permissions`). 코드는 매핑을 덮어쓰지 않는다.
   부팅 동기화는 새 키만 넣고, 그 키가 «처음» 들어갈 때만 `grantOnFirstRegistration` 역할에 한 번 부여한다.
   목록에서 사라진 키는 지우지 않고 `deprecated_at` 만 찍는다.
3. **토큰에는 역할만 싣는다.** 다른 서비스는 user-service 내부 경로(`GET /internal/iam/role-permissions`, 버전 ETag)에서
   역할별 권한을 받아 메모리에 두고 판정한다. 버전은 스냅샷 «내용»에서 계산한다 — 역할을 바꾸는 경로(관리 API, 시드,
   직접 SQL)가 버전을 올리는 걸 잊어도 캐시가 낡지 않는다.
   화면은 `GET /me/permissions` 를 쓴다 — 역할 입력은 토큰이라 화면과 API 가 같은 입력으로 판정한다.
4. **코드는 역할 이름이 아니라 권한만 본다.** 예외는 user-service 의 시스템 역할 규칙 한 곳(`api/iam/iam.constants.ts`)이다:
   master 는 활성 권한 전체를 계산해서 받는다.
5. **초기 부여는 «지금 그 역할이 실제로 할 수 있는 것»을 옮긴다.** 권한 확대는 배포가 아니라 관리 화면에서 한다.

## Consequences
- 역할 구성을 배포 없이 바꿀 수 있다. 변경은 각 서비스의 버전 확인 주기 안에 반영된다.
- 사람↔역할 변경은 access 토큰 수명 안에 반영된다(토큰 발급 경로가 매번 DB 에서 역할을 읽는다).
- 새 권한을 추가하는 PR 은 목록에 한 줄을 더하고 `grantOnFirstRegistration` 을 정한다. 비워 두면 배포 직후 master 외에는
  그 기능을 못 쓴다.

## Not adopted
- 토큰에 권한 목록 싣기 — 권한이 세분될수록 토큰이 커지고, 회수가 토큰 수명만큼 늦어진다.
- 서비스별 매핑 사본 유지 — 화면에서 여러 서비스에 나눠 써야 하고 일부만 반영되면 서비스마다 권한이 갈린다.
- 정책 엔진(관계 기반·정책 언어) — 데이터 단위 권한(«담당 창고만»)이 생기면 판정부만 그쪽으로 옮긴다. 인터페이스는 권한 키로 유지한다.
