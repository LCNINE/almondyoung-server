# 관리자 권한은 «권한 키»로 판정하고, 역할↔권한 매핑의 원본은 user-service 다

## Status
Accepted (2026-10-12). 적용은 단계별로 한다 — 이 ADR 시점에는 목록·원본·배포 경로만 있고 판정은 기존 가드가 한다.

## Context
관리자 업무가 나뉘면(CS·MD·물류·인턴 …) 역할마다 볼 수 있는 화면과 할 수 있는 일이 달라야 한다. 지금 판정은 역할 이름 비교
(`admin`·`master`), 서비스별 스코프, 서비스 고유 가드가 섞여 있고, 스코프 매핑은 서비스마다 부팅 때 코드로 다시 쓰여서
화면에서 바꿀 수 없다.

## Decision
1. **권한 키.** 관리자 권한은 `영역.대상.행동` 키 하나로 표현한다(예: `order.order.read`, `payment.refund.execute`).
   영역은 서비스가 아니라 업무 단위다. 목록의 원본은 `@app/authorization` 의 `PERMISSION_CATALOG` 이고, 키는 `Permission`
   리터럴 유니온 타입이라 목록에 없는 키는 컴파일되지 않는다. 와일드카드는 쓰지 않는다.
2. **매핑의 원본은 user-service DB 다** (`iam_permissions`·`iam_role_permissions`). 코드는 매핑을 덮어쓰지 않는다.
   부팅 동기화는 새 키만 넣고, 그 키가 «처음» 들어갈 때만 `grantOnFirstRegistration` 역할에 한 번 부여한다.
   목록에서 사라진 키는 지우지 않고 `deprecated_at` 만 찍는다.
3. **토큰에는 역할만 싣는다.** 다른 서비스는 user-service 내부 경로(`GET /internal/iam/role-permissions`, 버전 ETag)에서
   역할별 권한을 받아 메모리에 두고 판정한다. 버전은 스냅샷 «내용»에서 계산한다 — 역할을 바꾸는 경로(관리 API, 시드,
   직접 SQL)가 버전을 올리는 걸 잊어도 캐시가 낡지 않는다.
   화면은 `GET /me/permissions` 를 쓴다 — 역할 입력은 토큰이라 화면과 API 가 같은 입력으로 판정한다.
4. **코드는 역할 이름이 아니라 권한만 본다.** 예외는 user-service 의 시스템 역할 규칙 한 곳(`api/iam/iam.constants.ts`)이다:
   master 는 활성 권한 전체를 계산해서 받는다.
5. **초기 부여는 «지금 그 역할이 실제로 할 수 있는 것»을 옮긴다.** 권한 확대는 배포가 아니라 관리 화면에서 한다.

### 라우트 분류와 판정
6. **모든 HTTP 라우트는 넷 중 정확히 하나로 분류한다:** 공개(`@Public`·`@InternalOnly`·`@OptionalAuth`) · 고객(`@StoreRoute`) ·
   키(`@KeyAuthRoute` — 그 앱의 가드가 머천트 API 키 같은 키를 검사하는 경로) · 권한(`@RequirePermission` /
   `@RequireAnyPermission`). `scripts/security/route-classification.spec.ts` 가 강제한다.
7. **조회 동사(GET·HEAD)는 조회 권한을, 쓰기 동사는 조회 아닌 권한을 요구한다.** 예외는 같은 스펙에 이유와 함께 둔다.
8. **각 서비스는 역할별 권한을 메모리에 둔다(`PermissionModule`).** 요청마다 네트워크를 타지 않고, 버전 확인은 배경에서
   주기적으로 한다. 한 번도 받지 못한 상태는 «권한 없음»이 아니라 «판정 불가»로 따로 다룬다.
9. **판정은 «그림자 → 강제» 순서로 켠다.** 그림자 단계에서는 기존 가드가 결과를 정하고 새 판정은 계산해
   `authz_shadow_evaluations_total` 지표와 로그로만 남긴다. 강제는 서비스별 `AUTHZ_ENFORCE=true`.
10. **가드 순서:** 관찰 가드(맨 앞) → 인증 → 기존 인가 → 권한 강제 가드(맨 뒤). 관찰 가드가 맨 앞이어야 뒤 가드가
    거부한 요청까지 비교할 수 있다. `scripts/security/permission-wiring.spec.ts` 가 지킨다.

### 판정 지점
11. **라우트 가드 안쪽의 판정도 권한으로 표현한다** — 남이 잡은 작업 넘기기, 서비스 안 재확인, 본문 조건, 리소스 소유
    예외 같은 곳이다. 지점마다 이름(`영역.이름`, 지표 라벨)을 붙이고 `PermissionCheckpoints` 로 옛 판정과 나란히 비교한다.
    비교하는 동안 결과는 언제나 옛 판정이 정한다. 옛 판정이 조회 실패로 끝나면 비교하지 않는다 — 인가 판정이 아니라서다.
12. **같은 서비스 메서드를 권한이 다른 라우트 둘이 부르는 곳은 역할을 다시 따지지 않는다.** 라우트의 `PermissionGuard` 가
    «이 요청이 이 라우트에서 받은 권한»을 요청에 남기고(`getPermissionDecision`), 소비하는 쪽은 그 표식을 본다.
    표식은 가드가 발급한 객체만 인정한다.
13. **사람이 아닌 내부 호출자는 시스템 주체(`systemPrincipal`)로 판정한다.** 사람 역할 이름을 빌리지 않고, 권한 사본이
    없어도 판정할 수 있다.
14. **역할 이름을 판정에 쓰는 코드는 `scripts/security/role-name-checks.spec.ts` 의 목록에만 남는다.** 새 코드는 목록에
    더하지 않는다. 옛 판정을 걷어 낼 때 목록을 비운다.
15. **관리자 화면의 진입 권한은 경로 권한표(`apps/admin-web/src/lib/auth/screen-access.ts`) 한 곳에 둔다.** 페이지는
    `RouteGuard screen="<자기 경로>"` 로 선언하고, 메뉴·검색·모바일 메뉴는 같은 표로 보이기를 정한다. 상세 화면은 가장
    가까운 상위 경로를 물려받는다. 메뉴는 환경마다 달라질 수 있어 판정의 원본이 될 수 없다.
16. **화면의 진입 권한은 그 화면의 주 데이터를 부르는 API 의 권한이다.** 버튼은 `<Can anyOf>`·`useCan` 으로 판정한다.
    권한을 아직 받지 못한 상태는 «권한 없음»으로 보이지 않는다(서버는 «판정 불가» 화면, 버튼은 감춤).
17. **화면의 권한 출처는 user-service `/me/permissions` 다.** 서버는 역할 조합별로 짧게 캐시하고, 조회에 실패하면 마지막
    사본을 쓴다. 화면 판정은 안내이고 강제는 각 API 가 한다.
18. **Medusa 프록시는 `(메서드, 경로) → 권한` 표로 판정하고 표에 없는 경로는 거부한다.** admin-web 이 부르는 Medusa 경로가
    전부 표에 있고, 표의 규칙이 실제로 부르는 조합만 여는지 게이트가 확인한다.
19. **권한 거부(403)는 필요한 권한 키를 `requiredPermissions` 로 알려 준다.** 화면은 그 키를 권한 이름으로 바꿔 안내한다.
20. **쓰기 동작의 권한은 뮤테이션 훅이 선언한다.** `useX.permission = [...] as const satisfies PermissionRequirement`.
    여러 API 를 차례로 부르는 동작은 `{ allOf: [...] }` 로 전부를 요구하고, 컴포넌트 안에서 만든 뮤테이션은
    `meta.permission` 으로 선언한다. 본인 계정 동작(로그인·비밀번호·내 정보)은 `'self'`.
21. **화면은 훅을 가리켜 판정한다** — `<Can run={useX}>`·`usePermissionCheck().canRun(useX)`·`blockedReason(useX)`·
    `<PermissionReadOnly run={useX}>`. 버튼에 권한 키를 다시 적지 않는다. 다른 화면으로 가는 쓰기 진입점은
    `<CanOpen screen="…">`(진입 권한표).
22. **권한이 없는 단독 트리거는 숨기고, 현재 값을 보여 주는 컨트롤은 값을 보이되 막고(`aria-disabled` + 이유),
    편집 폼은 읽기 전용(텍스트 입력은 `readOnly`)으로 둔다.** 권한을 확인하기 전·조회에 실패한 동안에도 트리거는
    보이지 않고, 조회 실패는 화면 위 안내로 알린다. 화면 진입 권한과 다른 조회는 권한이 없으면 요청하지 않고 «가림»으로 보인다.
23. **게이트가 지킨다** — 모든 뮤테이션이 권한을 선언했는지, admin 이 master 전용 말고 전부 실행할 수 있는지,
    뮤테이션을 부르는 화면 파일(또는 그 파일을 그리는 상위 파일)에 그 권한 판정이 있는지(`mutation-guard.gate.spec.ts`).

## Consequences
- 역할 구성을 배포 없이 바꿀 수 있다. 변경은 각 서비스의 버전 확인 주기 안에 반영된다.
- 사람↔역할 변경은 access 토큰 수명 안에 반영된다(토큰 발급 경로가 매번 DB 에서 역할을 읽는다).
- 새 권한을 추가하는 PR 은 목록에 한 줄을 더하고 `grantOnFirstRegistration` 을 정한다. 비워 두면 배포 직후 master 외에는
  그 기능을 못 쓴다.

## Not adopted
- 토큰에 권한 목록 싣기 — 권한이 세분될수록 토큰이 커지고, 회수가 토큰 수명만큼 늦어진다.
- 서비스별 매핑 사본 유지 — 화면에서 여러 서비스에 나눠 써야 하고 일부만 반영되면 서비스마다 권한이 갈린다.
- 정책 엔진(관계 기반·정책 언어) — 데이터 단위 권한(«담당 창고만»)이 생기면 판정부만 그쪽으로 옮긴다. 인터페이스는 권한 키로 유지한다.
