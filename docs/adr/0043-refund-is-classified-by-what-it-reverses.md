# 환불은 «무엇을 되돌리는가»로 나누고, 주문 정본 하나가 낸다

## Status
Accepted (2026-10-10). ADR-0042 원칙 1(환불을 시작하는 쪽은 주문마다 하나)을 «취소» 밖의 환불 전부로 넓힌다 — **유지:**
ADR-0042 원칙 넷 그대로. 트래킹 #1016 37번 행. 첫 적용: `docs/superpowers/specs/2026-10-10-external-refund-partial-cancel-design.md`.

## Context
ADR-0042 는 채널 주문의 «취소»를 누가 시작하는지 정했다. 취소가 아닌 환불 — 품절분 일부 환불, 반품 환불, 차액·보상 환불 — 은
아직 wallet 관리자 화면(`POST /v1/admin/payment-intents/:id/refund`)에서 자유 금액·자유 사유로 낸다. 그 환불은 어느 품목의 몫인지
모른 채 Medusa 장부에 «크레딧 라인 + 환불»(금액 조정)로 투영되고, 같은 품목을 나중에 Medusa 에서 부분취소하면 한 번 더 환불된다
(#1016 37번). wallet 의 환불가능액 검사는 «넘치지 않게»만 막을 뿐 «엉뚱한 품목의 두 번째 환불»은 못 막는다.

2026-10-10 라이브 실측(READ ONLY): Medusa 주문 결제에 붙은 wallet 외부 환불은 대부분 사유 칸에 «○○ 품절 부분 취소»,
«○개 부족 부분 취소»처럼 **품목을 적은 자유 문장**이다. 반품·변경 차액·멤버십가 차액·배송 지연도 같은 칸에 섞여 있다.
«이 돈이 무엇을 되돌렸는가»는 사람이 읽는 문장에만 있고 데이터에는 없다.

환불이 CS(고객 불만·반품)에서 시작되는 일도 많은데, core `cs_cases` 에는 주문·환불과의 연결이 없다.

## Decision

환불을 두 축으로 정한다.

**축 1 — 무엇을 되돌리는가(종류).**

| 종류 | 뜻 | 장부에서의 모양 |
|------|----|----------------|
| 품목 취소 | 출고 안 된 수량을 주문에서 뺀다 | 주문 수정 + 차액 환불 |
| 반품 | 출고된 수량이 돌아온다(회수 입고가 조건) | 반품 + 환불 |
| 금액 조정 | 품목은 그대로, 돈만 일부 돌려준다(차액·보상·배송비·지연) | 크레딧 라인 + 환불 |
| 주문 밖 보상 | 주문과 무관한 호의 | 환불이 아니다 — 포인트 등 |

**축 2 — 누가 낸다(주문의 정본, 판단 10).** Medusa 주문은 Medusa 가 almond-payment → wallet 으로, 네이버·쿠팡은 그 채널이
판매자센터에서(우리는 수집으로 받는다), core 직접 주문은 core 가 wallet 으로. 주문 밖 보상은 wallet(포인트)이 정본이다.

책임 배치:

1. **운영자 입구는 core 주문 화면 하나다.** 종류를 고르고 품목·수량 또는 금액을 구조로 넣는다. 요청은 `sales_order_amendments`
   한 행으로 남는다(판단 6). 취소 요청이 이미 이 모양이다(ADR-0042).
2. **core 는 판정하고 명령한다.** 출고·회수 입고 같은 물리 상태를 아는 곳이 core 뿐이다. 금액은 계산하지 않는다.
3. **주문 정본이 금액을 계산하고 장부에 남기고 환불을 시작한다.** 할인 배분·배송비는 커머스 엔진의 일이다(ADR-0040 §1).
4. **wallet 은 돈만 움직인다.** 관리자 환불 화면은 «주문 정본이 없는 결제»(멤버십 구독료·고아 intent)와 비상용이다.
5. **CS 는 연결만 한다.** CS 사건 하나가 여러 요청(취소·반품·조정)을 낳으므로 요청 쪽이 `cs_case_id` 를 든다. CS 가 돈을 직접
   움직이면 시작하는 쪽이 둘이 된다.
6. **사유는 «종류 + 자유 메모»로 나눈다.** 종류는 기계가 읽고, 메모는 사람이 읽는다.

## Why
- 주문마다 시작하는 쪽이 하나면 이중 환불이 구조적으로 생기지 않는다. 금액 검사로는 못 막는다 — 37번이 그 증거다.
- 종류가 데이터로 남아야 나중의 부분취소·반품이 앞선 환불과 겹치는지 기계가 판정할 수 있다.
- 모든 환불이 정본 장부에 남아야 core 판매주문 = Medusa 장부 = wallet 환불 합이 맞는다(ADR-0042 원칙 3).
- 화면이 하나면 운영 습관을 한 곳에서 바꾼다.

기각:
- **외부 환불을 부분취소 환불에서 자동 차감:** 보상·차액 환불까지 품목 값으로 먹어 버린다. 종류를 모르고는 차감할 수 없다.
- **wallet 관리자 환불에 품목 입력을 더해 wallet 이 품목을 안다:** 품목·할인 배분은 커머스 엔진의 일이고, 시작하는 쪽이 둘로 남는다.
- **CS 사건이 환불을 낸다:** 시작하는 쪽이 늘어난다. CS 는 «왜»를 들고, 요청이 «무엇»을 든다.

## Consequences
- 이 모델은 한 번에 오지 않는다. 지금 있는 것: 품목 취소(ADR-0042), Medusa 장부 투영. 없는 것: Medusa 주문의 금액 조정 경로,
  반품의 Medusa 이전(#1016 34번), wallet 관리자 품목 환불 차단, 사유 구조화, CS 연결, 네이버·쿠팡의 임의 금액 부분환불 지원 확인
  — 각각 #1016 의 행이다.
- 그 사이에 옛 습관(관리자 화면의 품목 환불)은 계속 생긴다. 37번 스펙의 안전망이 그 경계를 지킨다: Medusa 부분취소가 미해결
  외부 환불을 만나면 멈추고, 운영자가 «이미 환불한 금액»으로 금액 조정을 품목 취소로 다시 분류한다.
- 지금 core 의 반품 환불은 Medusa 주문도 wallet 으로 직접 낸다(`RETURN_COMPLETED`) — 원칙 1 위반이지만 투영으로 장부는 맞는다.
  34번에서 옮긴다.
- 셀메이트 과도기에는 판매주문이 일괄 `shipped` 로 올라가 core 부분취소가 막히므로 품절분 환불의 출구가 wallet 관리자 환불뿐이다.
  차단은 core 출고 개통(한진) 때 한다 — 그 전에 막으면 품절분을 돌려줄 길이 없다.
