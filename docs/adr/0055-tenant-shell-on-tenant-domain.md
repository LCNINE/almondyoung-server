# 테넌트 직원 화면은 같은 admin-web 의 «테넌트 셸»이고, 테넌트 도메인이 테넌트와 브랜드를 정한다

## Status
Accepted (2026-10-30, 교정 10-30). 라이브(2026-11-02). 멀티테넌트 전체 그림은 `docs/multi-tenancy.md`.
선행: [[0052-account-is-global-tenant-is-membership-and-grant]] · [[0054-shared-services-serve-one-tenant]].

## Context
admin-web 은 테넌트 1 의 운영 화면 수십 개와 운영사 브랜드를 품고 있고, 그 중 다수가 테넌트 1 만 섬기는 업스트림([[0054-shared-services-serve-one-tenant]])을 부른다.
1 이 아닌 테넌트의 직원은 그 일부(창고·로케이션·SKU·상품)만 쓴다. 그리고 그 테넌트의 직원 화면과 로그인에는 **그 테넌트 브랜드만** 보여야 한다(운영사 흔적 0 — 화이트라벨).

## Decision
1. **같은 admin-web 배포 안의 «테넌트 셸».** 셸 = 화면 본문을 감싸는 바깥 틀(사이드바·헤더·메뉴·탭 제목·파비콘·로고). 테넌트 셸은 **허용 목록**의 화면만 열고 목록 밖은 404 다
   (`apps/admin-web/src/lib/tenant-shell/allowlist.ts`, `apps/admin-web/src/middleware.ts`). 화면 본문은 기존 컴포넌트를 그대로 쓴다.
2. **허용 목록은 테넌트마다가 아니라 코드에 하나.** 게이트 스펙이 «목록의 화면은 테넌트 1 만 섬기는 업스트림을 부르지 않고 `screen-access.ts` 에 있다»를 지킨다
   (`tenant-shell.gate.spec.ts`). 본문 안에서 그런 업스트림을 부르는 블록(배송비 그룹 = Medusa, SKU 연결 패널)은 셸이 알려 주는 «이 테넌트가 못 쓰는 업스트림»을 보고 숨는다.
3. **테넌트 셸은 테넌트 도메인에서만 뜬다.** 들어온 주소가 테넌트를 정하고, 토큰 테넌트가 그 주소의 테넌트와 다르면 거절한다. 테넌트 1 주소는 테넌트 1 토큰만 받는다.
   1 이 아닌 테넌트는 테넌트 도메인이 꼭 하나 있다. auth-web 도 같은 배포가 테넌트 도메인을 받아 그 브랜드로 그린다 — 가입·약관·아이디/비밀번호 찾기가 없고,
   세션 쿠키는 그 도메인에만 붙는다(`PARENT_COOKIE_DOMAIN` 을 쓰지 않는다).
4. **테넌트 도메인마다 admin-web 용·auth-web 용 CloudFront 배포를 하나씩 직접 선언한다**(«칸», `deployments/lcnine/tenant-domain-slots.ts`·`tenant-domain-distribution.ts`).
   SST 사이트 배포의 요청 함수·캐시 정책을 참조하므로 빌드는 한 벌이다. Next 는 `x-forwarded-host` 로 테넌트 도메인을 본다.
5. **테넌트 값(도메인·인증서 ARN·Route53 존 ID·표시 이름·로고)은 레포에 적지 않는다.** 도메인·표시 이름·로고는 user-service 테넌트 행, 인프라가 알아야 하는 값은 칸 Secret 이다.
   코드엔 칸의 **개수와 번호(논리 이름)만** 있다. 칸 수를 env 로 넘기지 않는다 — 그 값 없이 배포한 머신이 테넌트 배포를 지운다.
6. **로그인**: 같은 `admin-web` OAuth 클라이언트에 테넌트 도메인 리디렉트를 더하고, user-service 가 리디렉트 호스트로 토큰 테넌트를 정한다
   ([[0052-account-is-global-tenant-is-membership-and-grant]]). admin-web 의 OIDC 리디렉트 주소는 요청 호스트로 고른다. auth-web 리디렉트 허용 목록은 테넌트 행 도메인에서 읽는다.

## Considered Options
- **admin-web 하나를 권한으로 가린다** — 반려. 필요 없는 화면 수십 개가 «깨지나»의 대상으로 남고, 운영사 브랜드가 셸에 박혀 있으며, 키를 다 가진 역할은 권한만으로 가려지지 않는다.
- **새 Next 앱·새 배포** — 반려. 결과(화면 몇 개, 테넌트 로고, 다른 주소)는 같은데 프록시와 그 위의 게이트(화면 권한·뮤테이션 가드·개인정보 가림·Medusa 판정)를 0 에서 다시 만들고 화면이 두 벌로 갈라진다.
- **SST `domain.aliases`** — 반려. 같은 CloudFront 배포·같은 인증서(SAN)에 별칭이 들어가, 테넌트 도메인 인증서와 공개 CT 로그에 테넌트 1 주소가 보인다.
- **테넌트 1 주소로 먼저 열고 나중에 옮긴다** / **플랫폼 공용 중립 도메인 아래** — 반려. 화이트라벨 요구와 부딪히거나, 테넌트가 남과 나눠 쓰는 주소가 된다.
- **테넌트별 허용 목록(테넌트 행)** — 반려. 그 목록이 테넌트 1 전용 화면을 넣었는지 스펙으로 지킬 수 없다. 테넌트 사이 차이는 역할·권한으로 낸다.
- **도메인·로고를 인프라 코드나 레포 설정 파일에** — 반려. 공개 레포에 테넌트 값이 박힌다.

## Consequences
- ⚠️ **셸은 방어선이 아니다.** 서버 쪽 문(DB 라우팅, 공유 서비스 문, 서버 자격증명 라우트 판정)이 그대로 다 필요하다. 셸의 404 는 화면 정리일 뿐 테넌트 쿠키로 프록시를 직접 부르는 길을 막지 않는다.
- 브랜드는 로그인 전에 필요하다 — auth-web·admin-web 이 «주소 → 테넌트 → 브랜드»를 토큰 없이 조회해 캐시한다. 주소로 브랜드가 갈리는 페이지는 언제나 동적이다(OpenNext 캐시 키에 호스트가 없다).
- admin-web·auth-web 은 `protection: none` 이어야 한다(`oac` 면 테넌트 배포가 403).
- 칸 무효화는 서버 함수 코드 해시(`codeSha256`)가 트리거다. SST 가 매 배포 Next 를 다시 빌드해 BUILD_ID 가 바뀌므로, **소스 변경이 없어도 본 사이트와 칸이 함께 무효화된다**(칸이 본 사이트를 1~2초 뒤 따라간다). 결함이 아니다.
- **«흔적 0» 기준선** = 보이는 화면·탭 제목·파비콘·인증서·브라우저 네트워크 호스트·리디렉트 주소. 테넌트 도메인의 auth-web 은 user-service 를 서버 쪽에서 부르므로
  브라우저 네트워크 호스트는 테넌트 도메인과 그 테넌트 버킷뿐이다. JS 번들 안 문자열은 기준 밖(보이면 치울 대상).
- 휴대폰 인증 문자가 테넌트 1 브랜드로 하드코딩돼 있고 notification(테넌트 1 만 섬김)을 거친다. 그래서 테넌트 도메인은 아이디·비밀번호 찾기를 숨기고 운영자가 초기 비밀번호를 재발급한다.
- 새 화면을 허용 목록에 더할 때마다 위 게이트 스펙과 «흔적 0»을 다시 본다(`npm run isolation:check:local` 의 화면 항목).
