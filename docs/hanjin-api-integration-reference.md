# 한진택배 Open API 연동 정본 (2026-09-21 developers.hanjin.com 실측)

이 문서는 **한진 개발자 포털에서 직접 읽은 외부 계약 사실**만 담는다. 우리 코드에서 도출되는 값은
적지 않는다 — 대조 결과는 §7 에 「도출 명령」으로만 남긴다.

- 출처: <https://developers.hanjin.com> (Guides / APIs / FAQs), 2026-09-21 로그인 상태에서 확인
- 일부 사실은 **DEV 인증키로 실제 호출해 확인**했다 (2026-09-21). 그런 항목은 「실측」 으로 표시한다 —
  포털 문서가 안 적거나 애매하게 적은 것을 응답이 확정해 준 경우다
- 문의처: `openapi@hanjin.com`
- 우리 구현: `apps/core/src/modules/fulfillment/waybill/` (모듈 설명은 그 디렉터리의 `README.md`)

> **포털 문서의 URL 은 전부 개발환경이다.** 운영환경 URL 과 운송장 채번규칙 상세는
> 포털 `Guides → API Spec Download` 로 받는 문서에만 있다. 운영 API 는 별도의 운영 인증키가 필요하다.

## 1. 이용 절차 7단계

```
01 회원가입
02 계정생성 안내메일 확인 (회사명·담당자 정보를 openapi@hanjin.com 으로 회신)
03 한진 담당자 가입승인 처리  ← 한진 «영업담당자»의 승인 요청이 접수되지 않은 계정은 승인되지 않는다
04 로그인 및 인증키 확인 (My Apps)
05 API Self TEST 및 개발 진행
06 통합테스트 / 라이브 인증키 발급
07 라이브 적용 및 모니터링
```

단계별로 사람이 반드시 해야 하는 일:

| 단계 | 내용 |
| --- | --- |
| 03 | 회사명 · 고객사 영업담당자 · 고객사 IT담당자 · **담당 한진 영업담당자** 4종을 회신해야 승인이 진행된다 |
| 04 | 인증키는 **client_id + Key(`x-api-key`) + Secret key** 3종. App 은 **DEV / LIVE 환경별로 따로** 만든다 |
| 06 | 양사간 주문정보·배송정보 송수신 테스트. **자체출력인 경우 영업담당자(본사 또는 택배지점)가 운송장 인쇄 상태를 현물 검수**한다 |
| 06 | **라이브 운송장 출력 API 는 방화벽 조치가 필요하므로 고객사의 서버 IP 정보를 회신**해야 한다 |
| 06 | 통합테스트 완료 후에야 라이브 환경 API·인증키가 발급된다 (**LIVE APP 은 개발환경 테스트 이후 발급**) |
| 07 | 라이브 적용일정을 사전 공유하면 모니터링 지원을 받는다 |

## 2. 인증 — HMAC (Guides → HMAC 가이드)

```
message   = timestamp + METHOD + queryString + secretKey
signature = HMAC_SHA256(message, key = secretKey)  →  hex 소문자
timestamp = yyyyMMddHHmmss, Asia/Seoul (한국표준시)
queryString = URL 의 '?' 뒤 원문 그대로 (없으면 빈 문자열)
```

`secretKey` 는 **message 문자열에도 들어가고 HMAC 키로도 쓰인다.** body 는 서명에 포함하지 않는다.

Request header 3종:

| 헤더 | 값 |
| --- | --- |
| `Content-Type` | `application/json` |
| `x-api-key` | 발급된 Key |
| `Authorization` | `client_id={clientId} timestamp={ts} signature={sig}` — **각 값 사이에 공백** |

포털의 `/v1/util/hmacgen` 은 **테스트 지원용이며 운영환경에서 제공하지 않는다.** 서명은 우리가 구현해야 한다.

## 3. 운송장 출력 가이드 (Guides → 운송장 출력 가이드)

고객사가 **직접** 운송장을 출력한다는 전제의 규격이다. 분류정보는 도로명주소 체계 기반으로 제공된다.

### 3.1 인쇄 규격

| 항목 | 값 |
| --- | --- |
| 적용 FONT | 나눔고딕 |
| 운송장번호 바코드 | **Interleaved 2 of 5 (ITF)** |
| 도착지 터미널 바코드 | **CODE128** (가로 25mm × 세로 8mm, 좌우 여백 5mm) |
| 라벨 타입 | **NS / NL / FS 형** — 어느 것을 쓸지는 한진 영업담당자와 협의해 정한다 |
| NS형 규격 | 좌측 100mm + 우측 100mm, 분류영역 22mm + 본문 80mm |

FAQ 보충: 한진 분류 장비는 **ITF 를 가장 잘 인식하고 그 다음으로 CODE39 를 지원**한다.
운송장 번호에 한해 CODE39 폰트도 사용 가능하다.
**라벨지·라벨 프린터 지원 여부도 영업담당자와 별도 협의** 대상이다.

### 3.4 운송장 번호 채번 규칙

**API 가 전달하는 운송장 번호를 쓰는 경우에는 해당 없다.** 영업담당자로부터 고객사 **전용 운송장 대역대**를
받아 우리가 채번하는 경우에만 지켜야 한다.

```
12자리 = 11자리 시퀀스 숫자 + 1자리 체크디지트
체크디지트 = 11자리 숫자 MOD 7
예) 12345678901 / 7 → 나머지 3  ⇒  123456789013
```

**실측 (2026-09-21)** — 이 규칙은 한진이 **발급하는 번호에도, 우리가 보내는 번호에도** 성립한다.

- `print-wbl` 이 발급한 번호가 규칙을 만족한다: `10003568223` MOD 7 = 5 → `100035682235`
- 규칙을 어긴 번호는 **서버가 거절한다** — `tracking-wbl` 에 `999999999999` 를 보내면
  `ERROR-02 Invalid Format - 운송장 번호 오류(CHECK DIGIT)`. 즉 체크디지트는 검증되는 값이고 자리수 채우기가 아니다

| 30 | `comodityList` | 상품리스트(배열) — 포함하지 않으면 상품내역은 공란 처리 | |
| 30-1 | ┗ `comodityCd` | 상품코드 | |
| 30-2 | ┗ `comodityNm` | 상품명 | ● |

> **19번 `rcvrTelNo` 가 필수이고 20번 `rcvrMobileNo` 는 선택이다.** 휴대폰만 받는 커머스 주문에서
> 이 둘을 바꿔 매핑하면 `ERROR-01` 로 전건 거절된다.

> **실측 (2026-09-21) — 배송구분 `S`(자체출력 출고)에서 `payTypCd` 허용 조합.**
>
> | `payTypCd` | 결과 |
> | --- | --- |
> | `PP` 선불 | `OK` |
> | `CD` 받지신용 | `OK` |
> | `CT` 착지신용 | **`ERROR-14`** 배송구분별 지불조건(payTypCd) 검증 오류 |
>
> `CC`(착불)는 미확인. **두 축이 다른 것을 뜻한다** — 선불/착불은 인도 시점에 현장에서 정산하는 형태이고
> (그래서 §3.2 ⑬ 이 라벨에 **운송료 금액 표시**를 요구한다), 신용은 계약 여신으로 달아 **월 단위로 정산**하는
> 형태다(금액 표시 의무 없음). **월 정산 계약이면 `CD` 하나로 확정된다** — `CT` 는 이 배송구분에서 거절되므로.

### 4.3 예약취소 — 자체출력(S)에는 적용되지 않는다

`cancel-order` 문서 원문 요지:

> 배송구분이 **예약(E: 주문예약(한진출력), R: 반품예약)인 경우** 운송장 출력 전 상태라면 취소합니다.
> 가. 고객사의 주문번호(`custOrdNo`)로 예약을 취소합니다.
> 나. **운송장 출력된 상태라면 예약취소가 불가능합니다.**
> 다. 입력항목: `custEdiCd`(필수), `custOrdNo`(필수)

**우리는 `svcCatCd = 'S'`(출고, 자체출력) 이므로 한진 API 로 취소할 수 있는 경로가 존재하지 않는다.**
운송장을 무효화(void)해도 한진 쪽 주문은 남으며, 물건을 넘기지 않으면 `08 미집하`(§4.4)로 귀결된다.
이것은 우리 구현의 결함이 아니라 계약 구조다 — 「취소 연동 추가」 류의 제안이 나오면 이 절을 근거로 기각한다.

예약취소 결과코드: `OK` / `ERROR-01` 필수 누락 / `ERROR-02` 길이 초과(`custOrdNo` 30 Byte) /
`ERROR-03` 미접수된 주문번호 / `ERROR-04` 취소 불가 (예: `상태: 운송장출력`) / `ERROR-90` / `ERROR-99`.

## 5. 호출량 제한 (FAQ)

```
errorCode: -103, message: Too many request
```

**택배 - 배송정보 API** 에 SpikeArrest(트래픽 급증 저지) 정책이 적용되어 있다.
「슬라이딩 창」 비율 제한 알고리즘으로 **1초당 10개의 요청(10 TPS)** 을 허용한다.

> 🔴 **실측 (2026-09-26) — DEV 에서는 재현되지 않는다.** `api-stg.hanjin.com` 의 `tracking-wbl` 에
> 30건을 동시에 보내 약 0.3초 안에 전부 받았는데(≈초당 100건) **전건 HTTP 200 + 백엔드 응답**
> (`ERROR-02`)이었고, `retry-after`·`x-ratelimit-*` 헤더도 없었다. 그래서 `-103` 이 **어떤 HTTP 상태로,
> 어떤 바디 모양으로 오는지는 아무도 모른다**(포털 문서에도 없다). 운영에서만 걸리는지, FAQ 가 설정과
> 다른지도 미상이다.
>
> 우리 클라이언트는 이 미상을 전제로 짰다 — HTTP 상태가 아니라 **바디의 `errorCode` 가 `-103`** 인지로
> 판별하고(200·429 모두), 어느 API 에서 오든 `transient_rejection` 으로 올린다(#916).
> 판별 규칙: `sed -n '/^const RATE_LIMITED_ERROR_CODE/,/^}/p' apps/core/src/modules/fulfillment/waybill/carrier/hanjin/hanjin-api.client.ts`
> **운영에서 처음 `-103` 을 받으면 실제 응답을 여기에 적을 것** — 판별 규칙이 추정 위에 있다.

```
errorCode: -101, message: App not approved.(장기간미사용 승인중지)
```

**3개월 간 미사용 App 은 중지처리된다.** 재개는 `openapi@hanjin.com` 으로 요청.
