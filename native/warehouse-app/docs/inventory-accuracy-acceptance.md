# 재고 정확성 구현 및 합격 검사 기록

검증일: 2026-09-15. 기준 커밋: `015bb0760`. 작업 브랜치: `fix/warehouse-inventory-accuracy`.

## 구현된 동작

- 입고·출고·실사에서 접수한 동일 상품 연속 스캔을 개별 이벤트로 보존하고 순서대로 처리한다. 발주 목록 선택은 잔량을 제안하고, 바코드 첫 스캔은 실제 1개 또는 포장 단위부터 센다.
- 재고 변경 전에 IndexedDB에 원래 본문·작업 키·사용자/API 범위를 저장한다. 응답이 유실되거나 손상되면 같은 작업을 확인하며, 결과를 알기 전에 내용을 바꾸거나 새 키로 다시 처리하지 않는다. 다른 계정으로 자동 전송하지 않는다.
- 앱을 다시 열면 입고 초안·접수 스캔·미확인 작업을 복구한다. 적치 완료 기록을 입고 화면의 누계에 다시 반영하며, 완료 직후 화면 저장 전에 종료되어도 잔여량이 되돌아가지 않는다.
- 서버 v2 계약은 인증된 사용자와 원래 본문을 중복 방지에 포함한다. 동일 키의 다른 요청은 거절하고, 확정 결과는 재생한다. JSONB에서 읽은 날짜도 정상 응답으로 변환한다.
- 실사는 카운트 revision, 최초 카운트 시점의 원장 version, 검토한 전체 세션의 previewToken을 확인한다. 카운트 이후 재고가 변하면 다시 세기를 요구한다. null(미카운트)과 0(명시적 실사 결과)을 구별한다.
- 실사 완료와 재고 증가·감소가 같은 재고 잠금을 사용한다. 검토한 재고 값에 대한 조정만 원자적으로 반영한다.
- 일반 화면에는 필요한 행동 안내만 표시한다. 개발자 모드는 기본 꺼짐이며 서버 `inventory.manage` 권한 확인 후 직접 켜야 한다. 진단 기록은 24시간/1,000건의 제한된 메타데이터만 보관한다.
- admin-web 실사도 v2·카운트 revision·previewToken·영속 재확인을 사용한다. 실제 CustomError 형식을 처리하며, 인식할 수 없는 성공 응답도 미확인 작업으로 보존한다.

## 배포와 중단 순서

1. `20260914183823_stocktaking-count-baseline.sql`을 정상 운영 절차로 적용한다. 기존 카운트의 기준 version은 만들어 넣지 않으며 해당 실사는 다시 센다.
2. v2 서버를 먼저 배포한다. 이때 `WAREHOUSE_REQUIRE_OPERATION_V2`는 비활성으로 두어 기존 클라이언트 호환성을 유지한다. 이 단계만으로 기존 클라이언트의 안전성이 확보되지는 않는다.
3. warehouse-app과 admin-web을 배포하고 계약 v2 확인 및 복구 동작을 검사한다. 기존 미확인 작업을 먼저 대사하며, 과거 키를 계약 버전을 바꿔 재전송하지 않는다.
4. 현장 장비 검사와 시험 운영 후 `WAREHOUSE_REQUIRE_OPERATION_V2=true`로 미보호 v1 재고 변경을 차단한다. 전환 설정은 운영에 아직 적용하지 않았다.
5. 문제가 생기면 새로운 재고 변경을 멈추고 미확인 작업을 보존한다. 이전 불안전 클라이언트로 자동 복귀하거나 저장소를 삭제하지 않는다. 서버 기록·실물을 대사한 뒤 재개한다.

작업 원본은 서버 보존 기간보다 짧은 29일까지만 자동 재확인한다. 오래된 미확인 건은 관리자 대사가 필요하다. 진단 로그 삭제와 업무 기록 삭제는 분리되어 있다.

실제 장비가 필요한 항목은 소프트웨어 검사로 대체하지 않았다. 공통 처리기에서 수량을 누락시키는 아래 결함이 재현되어 이번 우선 수정 대상으로 정했다. 취소·보류 등 별도 기능 확대는 하지 않았다.

### 확인한 결함: B1 — 저장 실패를 빈 스캔 대기열로 취급 (P1)

1. 간편입고에서 같은 상품을 한 번 스캔해 초안 수량 1을 만든다.
2. 두 번째 스캔의 IndexedDB 저장에 `QuotaExceededError`를 주입한다.
3. 수정 전에는 그 입력이 사라지고 대기 수가 0으로 돌아가 **등록 버튼이 활성화**된다. 작업자는 실물 2개를 1개로 입고할 수 있다.
4. 저장 공간이 복구되어도 화면의 “다시 확인”은 이미 사라진 입력을 되살리지 못한다. 별도 A·A·B 검사에서도 복구 후 처리 결과가 빈 배열이었다.

재개 시에도 같은 문제가 있었다. 초안 1개와 별도의 미처리 스캔 1개를 저장한 뒤, 스캔 기록 읽기만 실패시키면 초안 복원이 끝난 후 등록이 활성화됐다. 따라서 저장 실패뿐 아니라 아직 읽지 못한 입력도 확정 차단 조건에 포함해야 한다.

수정 전 실패 증거는 `ReliabilityReview.test.tsx`의 두 등록 차단 검사와 `useWorkScanQueue.test.tsx`의 입력 복구 검사다. 실패 로그는 로컬 `/tmp/warehouse-readiness-storage-red.log`, `/tmp/warehouse-readiness-queue-red.log`, `/tmp/warehouse-readiness-read-failure-red.log`에 보관했다. DB에 잘못된 수량을 일부러 반영한 재현은 아니다.

### 수정 내용

- `useWorkScanQueue`가 저장 전 입력도 별도 대기열에 원래 ID·내용·순서대로 보존한다. 저장이 성공하기 전에는 업무 처리기로 넘기지 않는다. 오류 이후 입력도 앞선 입력을 추월하지 않는다.
- 복구 버튼은 보존한 입력의 저장부터 다시 수행한다. 초기 기록 읽기가 실패했으면 먼저 저장된 입력을 복원하고 이어서 새 입력을 처리한다.
- `blocked()`는 기록 복원이 끝나지 않았거나 어느 대기열이든 남아 있을 때 참이다. 입고 확정, 수량 편집, 출고 강제처리, 실사 위치 전환·정정 및 화면 이동에 이 조건을 사용한다. `size()`는 실제로 알고 있는 입력 수만 반환한다.
- 작업자 안내: “스캔을 저장하지 못했어요. 이 화면을 유지한 채 저장 공간을 확보하고 다시 확인해 주세요. 상품은 다시 찍지 마세요.” 발주 입고의 저장 실패에는 “이 스캔 제외”를 표시하지 않는다.
- 요청·응답·오류 코드 등 기술 진단을 작업자 화면에 추가하지 않았다. 기존 개발자 모드 권한 경계는 유지한다. 서버/API/DB 스키마 변경은 없다.

**보존 한계:** 저장 자체가 실패한 입력은 공간 확보 전까지 메모리에만 있다. 화면 이동은 막지만 OS 강제 종료·전원 차단에도 남는다고 보장하지 않는다. 해당 상태에서는 화면을 유지해야 한다.
