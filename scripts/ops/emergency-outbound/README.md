# 비상 출고 (#1249)

창고 앱 출고 경로가 막힌 날, 그날 물건을 내보내는 절차. 런북(#1251)에 그대로 옮긴다.
이 문서만 보고 따라 할 수 있어야 한다.

스크립트는 앱이 부르는 core 라우트를 운영자 본인 계정으로 그대로 부른다. 그래서 권한·작업자 기록·셀메이트 상자 거절이 화면과 같다.

**지킬 것 하나: 안 나간 상자를 발송 처리하지 않는다. 한 상자를 두 번 꺼내거나 두 번 보내지 않는다.**

## 언제 쓰나

- 단말·앱 쪽이 막혔다(배치 피킹·검수·송장 출력 중 어디든). **core 는 응답한다.**
- 앱이 아예 안 뜨는 날도, 한 단계만 막힌 날도 같은 길이다.

쓰지 않는 날:

- core 라우트가 고장 난 날. 스크립트도 같은 라우트를 부르니 같이 막힌다. 고쳐서 배포한다.
- 한진 API 가 오래 멈춘 날. 이 길도 송장을 한진에서 받으니 같이 막힌다. 기다린다. 멈춘 송장은 #914 / #1241 화면으로 푼다.
  (잠깐 끊기는 정도는 스크립트가 알아서 다시 한다 — 아래 «송장 발급이 잠깐 실패하면».)
- 셀메이트에 넘긴 주문의 상자. **아직 배치에 안 든** 셀메이트 상자는 스크립트가 뺀다(출고 준비 목록에 안 나온다).
  **이미 배치에 든** 셀메이트 상자는 스크립트가 가리지 못한다 — 컷오버 런북(#1251)의 확인 절차로 미리 빼 둔다.

## 사전 준비 (미리, 리허설 때)

1. **송장 프린터를 Windows 공유로 한 번 설정한다.** 공유 이름을 정해 적어 둔다(아래 `<공유 이름>`). 리허설에서 `copy /b` 로 시험 출력까지 해 본다.
2. **운영자 계정에 권한 4개.** `fulfillment.shipment.read`, `fulfillment.warehouse.operate`, `fulfillment.dispatch.force`, `inventory.stock.read`(창고 조회).
3. **창고가 낱개 피킹(discrete)을 지원해야 한다.**
4. AWS 로그인이 되어 있어야 한다(`--stage live`). 로컬은 `--stage local`.
5. **창고 id 를 적어 둔다**(아래 `<창고 id>`). 어드민 «로케이션 관리» 화면(주소 `/inventory/locations`)에서 창고를 고르면
   주소창 끝에 `?warehouseId=…` 가 붙는다. `=` 뒤의 값이 창고 id 다.

2·3 은 `prepare`·`dispatch` 가 시작할 때마다 먼저 확인한다. 모자라면 무엇이 모자란지 출력하고 멈춘다(아무것도 안 바꾼다).

## 아침

모든 명령은 저장소 루트에서 돌린다. `--stage` 는 꼭 적는다(기본값 없음). 아이디·비밀번호는 화면에 안 보이게 묻는다.

### 1. dry-run

```bash
npx tsx scripts/ops/emergency-outbound/index.ts prepare --stage live --warehouse <창고 id>
```

아무것도 바꾸지 않고 대상 표만 보여 준다. 실행 id(`--run`)는 안 적으면 KST `yyyyMMdd-HHmm` 으로 자동 정해진다. 화면에 찍힌 값을 적어 둔다. 저녁에 쓴다.

- 대상: 배치 밖의 `ready` 상자, 시작된 낱개 배치 안 피킹 전 상자, 포장 중 상자.
- 빠지는 상자와 이유도 상자마다 보인다. 합칠 수 있는 상자(mergeable), 일부만 낼 수 있는 상자(partial), 재고 없음, 정보 부족, 시작 전 배치·다른 피킹 방식 배치에 든 상자,
  **앞 실행의 상자**(같은 PC 에서 먼저 돌린 다른 `--run` 이 맡은 상자 — 아래 «알아 둘 것»).
- 빠진 상자는 이 실행에서 안 나간다. 정식 경로로 간다.

### 2. 실행

```bash
npx tsx scripts/ops/emergency-outbound/index.ts prepare --stage live --warehouse <창고 id> --run <실행 id> --apply
```

순서: 계획 확정, 송장 발급, 낱개 피킹 배치 생성, 배치에 넣기, 시작(위치 배정), 라벨 만들기, 출력 확인 기록.

산출물은 `.scratch/emergency-outbound/<실행 id>/` 에 쌓인다.

| 파일 | 용도 |
|---|---|
| `labels.zpl` | 모든 상자의 송장 라벨. 피킹 리스트 순서 |
| `pick-list.html` | A4 피킹 리스트. 출고번호·받는 분(마스킹)·송장번호·SKU·수량·선반 위치 |
| `shipments.csv` | 저녁 dispatch 의 입력. 한 줄이 한 상자 |
| `run.json` | 실행 상태. 손대지 않는다 |

**종료 코드가 2 면 끝에 나온 `사람이 봐야 할 문제` 목록을 한 줄씩 읽는다.** 문제는 세 가지다.

- 송장번호가 없는 상자
- 라벨을 못 받은 상자(라벨 만들기 실패)
- 출력 확인 기록을 못 남긴 상자

**목록에 나온 상자는 확인된 라벨이 없다. 오늘 이 길로는 못 나간다.** 꺼내지도 포장하지도 않는다. 저녁에 `shipments.csv` 에서 그 상자의 줄을 지운다.

#### 송장 발급이 잠깐 실패하면

한진 응답 지연 같은 일시 실패(일시 오류·발급 대기·시간 초과)는 스크립트가 같은 요청으로 2초·5초·10초 뒤 세 번까지 다시 한다. 계획 확정·배치 담기의 일시 실패도 같다.
세 번 다시 해도 안 된 상자는 `N번 다시 시도해도 안 됨` 사유로 빠진다. **빠진 상자는 같은 `--run` 으로 다시 돌려도 안 들어온다.**
나중에(한진이 돌아온 뒤) 새 `--run` 으로 다시 하거나 정식 경로로 보낸다.

#### 시작이 막히면

**시작은 전부 아니면 전무다.** 막힌 상자(위치 재고 부족·송장 문제)가 나오면 그 상자를 배치에서 빼고 다시 시작한다. 뺀 상자는 사유와 함께 보고된다.

#### 수기 송장

수기 송장(`waybills/manual`)을 단 상자는 core 에 라벨이 없다. 피킹 리스트에 «수기 송장 — 라벨은 따로»로 나오고 `labels.zpl` 에는 없다 — 그 라벨은 원래 있던 것을 붙인다. 문제가 아니라 종료 코드에도 안 든다(저녁 출고도 된다).

### 3. 라벨 출력 (스테이션 PC)

`labels.zpl` 을 스테이션 PC 로 옮겨 찍는다.

```bat
copy /b labels.zpl \\localhost\<공유 이름>
```

**반드시 찍는다.** 스크립트는 출력 확인을 찍기 전에 이미 기록해 둔다. 안 찍어도 시스템은 찍힌 줄 안다. 박스에 붙은 송장이 없는 채로 저녁에 나가면 안 된다.

### 4. 꺼내기·포장·인계

`pick-list.html` 을 A4 로 뽑는다. 리스트의 선반 위치대로 꺼내 포장하고, 박스에 라벨을 붙여 한진 기사에게 넘긴다.
`사람이 봐야 할 문제` 에 나온 상자는 꺼내지 않는다.

## 저녁

### 1. 못 나간 줄 지우기

`.scratch/emergency-outbound/<실행 id>/shipments.csv` 에서 **오늘 못 나간 상자의 줄을 지운다.**

- 아침 `사람이 봐야 할 문제` 에 나온 상자도 지운다.
- 일부만 담긴 상자도 지운다. 강제 발송은 상자 전체를 보낸 것으로 기록되기 때문이다.
- 지운 상자의 송장은 남은 채 두고, 다음 날 정식 경로(앱)에서 그 송장으로 이어 간다.
- 낮에 주문이 취소된 걸 안 상자는 박스를 물리적으로 도로 빼 두고 줄을 지운다.

**지우지 않은 줄 = 실제로 나간 박스다.** 그래서 dispatch 가 그 줄을 거절하면 박스는 이미 나갔는데 기록이 안 된 것이다(아래 «거절·불일치가 나오면»).

### 2. dry-run

```bash
npx tsx scripts/ops/emergency-outbound/index.ts dispatch --stage live --run <실행 id>
```

상자마다 발송 방법·거절 사유를 보여 준다. 끝에 `목록에서 빠진 상자` 가 나온다. 그게 방금 지운 줄과 맞는지 본다.

dispatch 는 **인쇄한 송장번호, CSV, core 가 가진 송장번호** 셋을 대조한다. 하나라도 다르면 그 상자는 거절하고 보내지 않는다.

### 3. 실행

```bash
npx tsx scripts/ops/emergency-outbound/index.ts dispatch --stage live --run <실행 id> --apply
```

끝 요약: 발송 · 이미 발송 · 거절 · 불일치 · 빠진 상자. 거절·불일치가 있으면 종료 코드 2.

거절·불일치 없이 끝나면 마지막 줄에 **`실행 <실행 id> 을 끝냈다`** 가 나온다. 이 줄이 나와야 그날 일이 끝난다(아래 «알아 둘 것» — 실행 끝남).
종료 2 면 이 줄이 안 나온다 — 아래 «거절·불일치가 나오면» 대로 하고, 개발자가 닫은 뒤 같은 명령을 다시 돌려 이 줄을 본다.

CSV 는 `--csv <경로>` 로 다른 파일을 줄 수도 있다. 기본은 실행 폴더의 `shipments.csv`.

### 거절·불일치가 나오면 — 그날 바로 개발자에게

거절·불일치 줄은 **지우지 않은 줄**이다. 박스는 이미 나갔다. **그날 안에 닫아야 한다** — 두면 출고 기록·송장 추적이 없고, 앱이 그 상자를 다시 꺼내라고 한다.
스크립트로는 못 고친다. **실행 id 와 상자 id 를 적어 개발자에게 바로 알린다.** «다음 날 정식 경로로» 미루지 않는다.

| 화면에 나온 사유 | 뜻 | 할 일 |
|---|---|---|
| `LABEL_REPRINT_REQUIRED` | 라벨 출력 기록이 없거나, 찍은 뒤 라벨이 바뀌었다 | 개발자에게 바로 |
| `SIMPLE_OUTBOUND_CLAIMED_BY_OTHER` | 누군가 앱에서 그 상자를 작업 중이다 | 개발자에게 바로 |
| `상태 canceled` | 낮에 주문이 취소됐다. 박스는 나갔다 | **택배 회수** 요청 + 개발자에게 바로 |
| 불일치(`mismatch`) | 인쇄한 송장·CSV·core 의 송장번호가 다르다 | 개발자에게 바로 |
| `이번 실행의 상자가 아니다` | CSV 에 이 실행이 만들지 않은 상자 줄이 있다 | 개발자에게 바로 |
| 그 밖의 사유 | — | 개발자에게 바로 |

## 알아 둘 것

- **같은 `--run` 으로 다시 돌리면 이어진다.** 배치를 두 번 만들지 않는다. 단 **처음 돌린 사람 본인만** 된다. 다른 사람이면 새 `--run` 으로 시작한다.
- **다시 돌려도 `shipments.csv` 는 덮어쓰지 않는다.** 이미 있고 새 목록과 다르면 원래 파일은 그대로 두고 새 목록을 `shipments.<KST 시각>.csv` 로 옆에 쓴다. 화면에 두 파일 이름이 나온다.
  저녁 dispatch 는 기본으로 `shipments.csv` 를 읽는다. 새 목록을 쓰려면 `--csv` 로 그 파일을 주고, 지울 줄을 거기서 다시 지운다.
  `labels.zpl`·`pick-list.html` 은 매번 새로 쓴다.
- **새 `--run` 은 아직 안 끝난 앞 실행의 상자를 안 집는다.** 같은 PC 의 `.scratch/emergency-outbound/` 아래 다른 실행 폴더를 읽어, 그 실행이 맡은 상자는
  «앞 실행 <실행 id> 의 상자 — 그 실행의 dispatch 로» 로 뺀다. 상자가 배치에서 빠져 출고 준비 목록에 돌아와 있어도 같다(라벨은 앞 실행이 이미 찍었다).
  그 상자는 앞 실행의 저녁 dispatch 로 보낸다.
- **저녁 dispatch `--apply` 가 거절·불일치 없이(종료 0) 끝나면 그 실행은 끝난다.** 화면에 `실행 <실행 id> 을 끝냈다` 가 나온다.
  끝난 실행의 상자는 더 가리지 않는다 — 지운 줄의 상자(못 나간 상자)는 다음 날 정식 경로나 새 `--run` 이 집는다. 끝난 실행은 같은 `--run` 으로 prepare 를 다시 못 한다.
  거절·불일치로 끝나면(종료 2) 실행은 안 끝난다 — 개발자가 닫은 뒤 dispatch 를 다시 돌려 0 으로 끝낸다.
- **실행 폴더는 지우지도 옮기지도 않는다**(같은 PC 에서 돌린다). 끝난 실행도 그대로 둔다 — 그날 무엇을 찍고 보냈는지의 기록이다.
  다른 실행 폴더의 `run.json` 이 깨져 있으면 가릴 수 없어 멈춘다. 손으로 고쳤다면 되돌리고, 못 되돌리면 개발자에게.
- 실행에서 빠진 상자(송장 실패·시작 막힘)는 그 실행에 다시 안 들어온다. 새 `--run` 으로 다시 하거나 정식 경로로 간다.
- 그 실행의 배치가 이미 시작됐으면, 나중에 대상이 된 상자는 새 `--run` 이어야 들어간다.
- `--apply` 없이는 아무것도 안 바뀐다(dry-run 이 기본).
- 토큰·비밀번호는 화면·파일에 남기지 않는다.

| 증상 | 할 일 |

| 중간에 죽음(네트워크·창 닫힘) | **같은 명령을 그대로 다시 돌린다.** 같은 `--run`, 같은 사람. 이어진다 |
| 사전 점검 실패(권한·낱개 피킹) | 안내대로 권한을 부여하거나 창고 설정을 고친다. 아직 아무것도 안 바뀐 상태다 |

| 한진 API 가 오래 멈춤 | 이 길도 막힌다. 기다린다 |
| 시작이 막혀 빠진 상자 | 그날 안 나간다. 다음 날 정식 경로로 |

| dispatch 종료 코드 2 | 위 «거절·불일치가 나오면» — 그날 바로 개발자에게 |
| `run.json 이 없다` | `--run` 이 틀렸거나 prepare 를 돌린 PC 가 아니다. `.scratch/emergency-outbound/` 폴더를 확인한다 |
| `다른 실행 폴더 … 의 run.json 을 못 읽었다` | 손으로 고쳤다면 되돌린다. 못 되돌리면 폴더는 그대로 두고 개발자에게 |
| `저녁 dispatch 로 끝났다` | 그 실행은 끝났다. 새 `--run` 으로 |

## 로컬 확인 (개발자)

비상 경로가 정식(앱) 경로와 같은 기록을 남기는지 로컬 스택에서 본다. 2026-11-18 에 이 순서로 통과했다(PR #1434 본문).

```bash
npm run bootstrap:e2e:local          # 컨테이너·마이그·시드
npm run start:all:local              # 가짜 한진(scripts/local/hanjin-stub.ts, :4599)도 띄우고 core 의 한진 주소를 거기로 덮는다
npm run seed:order-path:local        # 주문 가능한 상품(멱등)
npm run order:place:local -- --count 3   # 자사몰 주문 3건 → 부천 상자 3개. 끝 줄 «상자: id,…»
```

1. 상자 하나는 **정식 경로**로 낸다 — 어드민 «출고 › 출고 준비»에서 그 상자만 골라 «출고 준비», 창고 앱(스테이션)에서
   F2 «작업 시작» → «송장 인쇄» → F1 송장·상품 스캔으로 «출고 완료». 비상 prepare 는 부천의 준비된 상자를 모두 집으므로 **이걸 먼저** 한다.
2. 나머지는 비상 경로로: `prepare --stage local --warehouse <부천 id> --run <id> --apply` → `shipments.csv` 에서 한 줄 지우기 →
   `dispatch --stage local --run <id> --apply` 를 두 번(두 번째는 «이미»·«이미 끝났다»).
3. 대조 — 같은 날, 플래그 없이:

```bash
npx tsx scripts/ops/emergency-outbound/local/compare.ts --normal <정식 상자> --emergency <비상 상자,…>
```

종료 0 이면 통과. Medusa 반영은 `order.metadata.coreShipmentAttempts[].invoice.trackingNo` 가 상자 송장과 같은지로 본다(`attemptTracking`).
최상위 `coreTrackingNumber` 는 로컬에서 정식 경로도 비어 있다 — 비교만 하고 판정에 쓰지 않는다.

함정: 워크트리엔 `.env` 가 없다(메인 체크아웃 것을 링크) · 워크트리 docker 는 `COMPOSE_PROJECT_NAME=almondyoung-server` ·
로그인 프롬프트를 파이프로 넣을 땐 입력 사이에 간격(`(sleep 6; echo admin; sleep 3; echo <비번>) | …`).
