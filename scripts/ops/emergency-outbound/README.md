# 비상 출고 (#1249)

창고 앱 출고 경로가 막힌 날, 그날 물건을 내보내는 절차. 런북(#1251)에 그대로 옮긴다.
이 문서만 보고 따라 할 수 있어야 한다.

스크립트는 앱이 부르는 core 라우트를 운영자 본인 계정으로 그대로 부른다. 그래서 권한·작업자 기록·셀메이트 상자 거절이 화면과 같다.

## 언제 쓰나

- 단말·앱 쪽이 막혔다(배치 피킹·검수·송장 출력 중 어디든). **core 는 응답한다.**
- 앱이 아예 안 뜨는 날도, 한 단계만 막힌 날도 같은 길이다.

쓰지 않는 날:

- core 라우트가 고장 난 날. 스크립트도 같은 라우트를 부르니 같이 막힌다. 고쳐서 배포한다.
- 한진 API 장애. 기다린다. 멈춘 송장은 #914 / #1241 화면으로 푼다.
- 셀메이트에 넘긴 주문의 상자. 스크립트가 알아서 뺀다.

## 사전 준비 (미리, 리허설 때)

1. **송장 프린터를 Windows 공유로 한 번 설정한다.** 공유 이름을 정해 적어 둔다(아래 `<공유 이름>`). 리허설에서 `copy /b` 로 시험 출력까지 해 본다.
2. **운영자 계정에 권한 3개.** `fulfillment.shipment.read`, `fulfillment.warehouse.operate`, `fulfillment.dispatch.force`.
3. **창고가 낱개 피킹(discrete)을 지원해야 한다.**
4. AWS 로그인이 되어 있어야 한다(`--stage live`). 로컬은 `--stage local`.

2·3 은 `prepare` dry-run 이 첫 줄에서 확인한다. 모자라면 출력하고 멈춘다(아무것도 안 바꾼다).

## 아침

모든 명령은 저장소 루트에서 돌린다. `--stage` 는 꼭 적는다(기본값 없음). 아이디·비밀번호는 화면에 안 보이게 묻는다.

### 1. dry-run

```bash
npx tsx scripts/ops/emergency-outbound/index.ts prepare --stage live --warehouse <창고 id>
```

아무것도 바꾸지 않고 대상 표만 보여 준다. 실행 id(`--run`)는 안 적으면 KST `yyyyMMdd-HHmm` 으로 자동 정해진다. 화면에 찍힌 값을 적어 둔다. 저녁에 쓴다.

- 대상: 배치 밖의 `ready` 상자, 시작된 낱개 배치 안 피킹 전 상자, 포장 중 상자.
- 빠지는 상자와 이유도 보인다. 합칠 수 있는 상자(mergeable), 일부만 낼 수 있는 상자(partial), 재고 없음, 정보 부족, 다른 피킹 방식 배치에 든 상자.
- 빠진 상자는 오늘 안 나간다. 정식 경로로 간다.

### 2. 실행

```bash
npx tsx scripts/ops/emergency-outbound/index.ts prepare --stage live --warehouse <창고 id> --run <실행 id> --apply
```

순서: 계획 확정, 송장 발급, 낱개 피킹 배치 생성, 배치에 넣기, 시작(위치 배정), 라벨 만들기, 출력 확인 기록.

산출물은 `.scratch/emergency-outbound/<실행 id>/` 에 쌓인다.

| 파일 | 용도 |
|---|---|
| `labels.zpl` | 모든 상자의 송장 라벨. 피킹 리스트 순서 |
| `pick-list.html` | A4 피킹 리스트. 출고번호·받는 분(마스킹)·송장번호·SKU·수량·선반 위치 |
| `shipments.csv` | 저녁 dispatch 의 입력. 한 줄이 한 상자 |
| `run.json` | 실행 상태. 손대지 않는다 |

끝에 `사람이 봐야 할 문제` 가 나오고 종료 코드가 2 면, 송장 번호가 없는 상자가 있다는 뜻이다. 그대로 두면 저녁에 그 상자가 거절된다. 먼저 푼다.

**시작은 전부 아니면 전무다.** 막힌 상자(위치 재고 부족·송장 문제)가 나오면 그 상자를 배치에서 빼고 다시 시작한다. 뺀 상자는 사유와 함께 보고된다.

### 3. 라벨 출력 (스테이션 PC)

`labels.zpl` 을 스테이션 PC 로 옮겨 찍는다.

```bat
copy /b labels.zpl \\localhost\<공유 이름>
```

**반드시 찍는다.** 스크립트는 출력 확인을 찍기 전에 이미 기록해 둔다. 안 찍어도 시스템은 찍힌 줄 안다. 박스에 붙은 송장이 없는 채로 저녁에 나가면 안 된다.

### 4. 꺼내기·포장·인계

`pick-list.html` 을 A4 로 뽑는다. 리스트의 선반 위치대로 꺼내 포장하고, 박스에 라벨을 붙여 한진 기사에게 넘긴다.

## 저녁

### 1. 못 나간 줄 지우기

`.scratch/emergency-outbound/<실행 id>/shipments.csv` 에서 **오늘 못 나간 상자의 줄을 지운다.**

- 일부만 담긴 상자도 지운다. 강제 발송은 상자 전체를 보낸 것으로 기록되기 때문이다.
- 지운 상자의 송장은 남은 채 두고, 다음 날 정식 경로(앱)에서 그 송장으로 이어 간다.
- 낮에 주문이 취소된 상자는 dispatch 에서 `상태 canceled` 로 거절된다. 그 박스는 물리적으로 도로 빼 둔다.

### 2. dry-run

```bash
npx tsx scripts/ops/emergency-outbound/index.ts dispatch --stage live --run <실행 id>
```

상자마다 발송 방법·거절 사유를 보여 준다. 끝에 `목록에서 빠진 상자` 가 나온다. 그게 방금 지운 줄과 맞는지 본다.

dispatch 는 **인쇄한 송장번호, CSV, core 가 가진 송장번호** 셋을 대조한다. 하나라도 다르면 그 상자는 거절하고 보내지 않는다.

### 3. 실행

```bash
npx tsx scripts/ops/emergency-outbound/index.ts dispatch --stage live --run <실행 id> --apply
```

끝 요약: 발송 · 이미 발송 · 거절 · 불일치 · 빠진 상자. 거절·불일치가 있으면 종료 코드 2. 사유별로 풀거나 다음 날 정식 경로로 보낸다.

CSV 는 `--csv <경로>` 로 다른 파일을 줄 수도 있다. 기본은 실행 폴더의 `shipments.csv`.

## 알아 둘 것

- **같은 `--run` 으로 다시 돌리면 이어진다.** 배치를 두 번 만들지 않는다. 단 **처음 돌린 사람 본인만** 된다. 다른 사람이면 새 `--run` 으로 시작한다.
- 실행에서 빠진 상자(송장 실패·시작 막힘)는 그 실행에 다시 안 들어온다. 새 `--run` 으로 다음 날 다시 하거나 정식 경로로 간다.
- 그 실행의 배치가 이미 시작됐으면, 나중에 대상이 된 상자는 새 `--run` 이어야 들어간다.
- `--apply` 없이는 아무것도 안 바뀐다(dry-run 이 기본).
- 토큰·비밀번호는 화면·파일에 남기지 않는다.

## 실패했을 때

| 증상 | 할 일 |
|---|---|
| 중간에 죽음(네트워크·창 닫힘) | **같은 명령을 그대로 다시 돌린다.** 같은 `--run`, 같은 사람. 이어진다 |
| 사전 점검 실패(권한·낱개 피킹) | 안내대로 권한을 부여하거나 창고 설정을 고친다. 아직 아무것도 안 바뀐 상태다 |
| 송장 발급이 멈춤 | #914 / #1241 화면에서 푼다 |
| 한진 API 장애 | 기다린다. 재시도하면 이어진다 |
| 시작이 막혀 빠진 상자 | 그날 안 나간다. 다음 날 정식 경로로 |
| `run.json 이 없다` | `--run` 이 틀렸거나 prepare 를 돌린 PC 가 아니다. `.scratch/emergency-outbound/` 폴더를 확인한다 |
| 다른 사람이 시작한 실행 | 새 `--run` 으로 |
